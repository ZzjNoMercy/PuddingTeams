# PuddingTeams 可选 TUI 入口评估与延期待办

> 日期：2026-08-24  
> 状态：候选能力，暂缓评估，不排期  
> 决策：TUI 仅作为 Web 之外的可选客户端，不替代 Web，不创建第二套产品模型、配置源或 Runtime。

## 0. 结论

PuddingTeams 可以增加 `puddingteams tui`，为偏好终端工作流的用户提供房间、会话、聊天、任务状态与审批入口。但当前 Web 已覆盖完整产品能力，TUI 的新增收益主要是终端内连续操作与远程环境可用性，尚不足以进入发行主线。

本项保留为延期 backlog。重新评估前不新增 TUI 包、不引入终端 UI 依赖、不改现有 Web/API 契约。

## 1. 产品定位

PuddingTeams 是同一产品、多个可选入口：

```text
Web ───────┐
           ├── PuddingTeams Server ── Runtime / Driver / Extension
TUI ───────┘
```

- **Web**：完整产品界面与配置控制台，继续作为默认入口。
- **TUI**：面向偏好终端的用户，承载高频对话和任务操作。
- **CLI**：保留 `init`、`doctor`、进程管理、Extension 管理等命令式运维能力。
- **Server**：房间、Session、消息、工作状态与配置的唯一事实源。

TUI 不是“精简版新产品”，也不要求所有 Web 功能在终端中一比一重做。用户可以自由选择 Web、TUI，或在两者之间继续同一个房间和会话。

## 2. 适合与不适合放入 TUI 的能力

### 2.1 适合 TUI 的高频操作

- 浏览和切换房间、Session；
- 发送消息、查看流式回答；
- 查看工具调用、Manager/Worker 委派和工作状态；
- 回答审批或业务 DecisionRequest；
- 停止当前生成或任务；
- 快速切换当前 Session 模型；
- 新建简单会话；
- 查看 server、provider、worker 与连接状态；
- 从终端跳转到 Web 的对应配置页。

### 2.2 继续由 Web 承担的复杂配置

- Provider、API Key 与自定义模型；
- Agent、Connector、Capability 与资源配置；
- Workspace、信任和权限说明；
- 群聊成员、责任边界和协作提示词；
- Extension 安装、更新、来源与风险提示；
- 产品设置、诊断详情和其他多字段表单。

TUI 可以展示这些配置的只读摘要和状态，但不以多层终端表单复制完整 Web 设置页。需要修改时提供明确链接，例如 `/settings`、`/agents` 或 `/extensions` 命令打开/复制 Web 地址。

## 3. 候选交互范围

若未来启动，第一版只做可验证的窄 MVP：

```text
┌ 房间 / Session ─┬ 当前对话与任务流 ───────────────────┐
│                  │                                    │
│                  │                                    │
├──────────────────┴────────────────────────────────────┤
│ 输入框                                  状态 / 模型    │
└───────────────────────────────────────────────────────┘
```

建议快捷入口：

```text
/room        切换房间
/session     切换 Session
/new         新建 Session
/model       切换当前模型
/status      查看连接与 Agent 状态
/settings    打开或复制 Web 设置页
/agents      打开或复制 Web Agent 管理页
/extensions  打开或复制 Web Extension 管理页
```

窗口较窄时隐藏左栏，通过 Overlay 切换房间和 Session；不强制三栏常驻。

## 4. 技术边界

### 4.1 客户端边界

- TUI 仅调用 PuddingTeams 的 REST/WebSocket 接口；
- TUI 不直接读取或写入 `~/.puddingteams` 业务数据；
- TUI 不直接创建 Driver、加载 Extension 或调用 pi `ExtensionAPI`；
- Runtime/Driver/Extension 的职责边界不因增加 TUI 改变；
- Web 与 TUI 必须消费相同的房间、Session、消息和工作状态语义。

如现有 Web 内部 API 不足，优先增加可同时服务 Web/TUI 的通用端点或共享事件投影；不为 TUI 复制一套领域状态机。

### 4.2 发行边界

- 用户入口候选为 `puddingteams tui [--port N]`；
- CLI 的零依赖 launcher 只负责定位并启动 runtime 内的 TUI bundle；
- TUI 应作为独立 workspace 包构建并随 `build:runtime` 打包；
- server 不运行时，TUI 只提示或按明确规则启动，不私自创建第二个 server；
- 非 TTY 环境应给出清晰提示，不进入 raw mode。

## 5. 开源实现参考

本地源码可以用于评估和借鉴，但不直接整包搬运：

| 本地项目 | 用法 | 原因 |
| --- | --- | --- |
| `源码合集/pi/packages/tui` | 首选底层候选 | TypeScript/Node、MIT、差分渲染、Editor、Markdown、ScrollView、Overlay、IME；与现有 pi SDK 同源 |
| `源码合集/opencode/packages/tui` | 参考完整 TUI 产品交互 | 房间/Session、命令面板、权限与状态组织成熟；但依赖 Bun、Solid、OpenTUI 和其 workspace |
| `源码合集/hermes-agent/ui-tui` | 参考前后端分离与测试 | TUI 通过协议驱动后端，流式、排队、审批、IME 和滚动测试丰富；但使用定制 Ink |
| `源码合集/codex/codex-rs/tui` | 参考 Agent UX | 审批、多 Agent 状态、历史、Diff 和快照测试成熟；Rust/Ratatui 不直接接入 Node runtime |
| `源码合集/grok-build` | 参考 Markdown/输入/Pager | Rust/Ratatui 组件质量高，但技术栈不同 |

若启动实现，优先显式依赖与项目 pi SDK 版本一致的 `@earendil-works/pi-tui`，本地较新源码只用于阅读；不通过软链接把不同版本源码接进发行构建。复制第三方实质代码时必须保留对应 MIT 或 Apache-2.0 许可声明。

## 6. 收益与成本

### 6.1 可能收益

- 用户无需离开终端即可继续房间对话和任务审批；
- SSH、远程开发机和低带宽环境更方便；
- 对偏好键盘和命令面板的用户更高效；
- 为未来 Headless Gateway 提供一个官方交互客户端样本。

### 6.2 主要成本

- 消息流、工具卡、自定义 `pudding:*` 卡和审批需要第二套渲染组件；
- 中文 IME、粘贴、滚动、终端尺寸、颜色和 Windows 兼容需要专项测试；
- Web 新增产品能力时，需要判断 TUI 是支持、摘要展示还是跳转 Web；
- 会增加发行 bundle、依赖许可和终端兼容验收矩阵；
- 当前 Web 已能完成核心流程，因此短期增量收益有限。

## 7. 重新启动的触发条件

满足下列任一条件时再重新评估：

1. 有明确用户反馈或使用数据表明终端入口会提高核心任务完成率；
2. Headless Gateway 已稳定，TUI 可以作为其薄客户端而无需扩展内部 Web API；
3. SSH/远程开发成为主要使用场景，浏览器入口显著不便；
4. 发行主线完成后，有独立维护容量承担跨平台终端测试；
5. 能把 MVP 限制在房间、聊天、任务状态、审批和 Web 设置跳转，不复制完整配置控制台。

## 9. 当前明确不做

- 不用 TUI 替换或弱化 Web；
- 不在 TUI 中复刻全部设置页；
- 不增加 TUI 专属配置文件或业务数据库；
- 不让 TUI 直接依赖 Driver SPI 或 Extension 宿主；
- 不因本待办冻结当前 Web/API 或发行计划；
- 不在缺少收益证据时提前引入实现依赖。
