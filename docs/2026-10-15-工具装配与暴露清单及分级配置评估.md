# 工具装配与暴露方式清单（Manager / Workers）

> 2026-10-15 基于当前代码盘点的事实清单，附「工具分级 UI 化」评估结论（结论：可行、方向已拍板，实现暂缓——见 §6）。

## 1. 暴露方式枚举（pi SDK 1.2.0，`@earendil-works/pi-coding-agent`）

`ToolDefinition.exposure` 完整枚举（`dist/core/extensions/types.d.ts:395`）：

| 值 | 语义 |
| --- | --- |
| `direct`（默认） | 激活即声明给模型、可调用 |
| `model-only` | 模型可见声明、可直接调用；但不能被其他工具经 `ctx.executeTool()` 链式调用（编排/交互类；`tool_search` 本体即此类） |
| `codemode` | 注册后可被 codemode 脚本/`ctx.executeTool` 调用，不声明给模型 |
| `deferred` | 同 codemode 但 codemode 不列出，只能被 `tool_search` 搜索并激活 |
| `hidden` | 注册但完全不可达（用于撤权，工具不可注销） |

平台实际使用：`deferred` 被业务代码显式设置于 Manager 的知识工具（`runtime-service.ts:287`）、日历工具与联网工具（`session-store.ts:577-578`，仅 Manager 原生会话；Worker 委派执行的日历与 Worker 联网仍为 direct）；`tool_search` 只进 Manager 会话（`session-store.ts:652`）；**codemode 机制未使用**（pi-mcp-adapter 以 `directTools: true` + `scriptMode: false` 运行，MCP 工具注册为一等 direct 工具，`mcp-runtime.ts:11-13`）。

## 6. 评估结论：工具装配/分级 UI 化（暂缓实现）

**可行，与现有机制同构，不需要新机制。**

- 先例：`builtinTools`、`codeSearch`（off|builtin|fff）、`mcpServerIds` 白名单、skills/prompts/联网开关，全部落在 `agents.json` + Web 配置页，`before_agent_start` 每轮重装配、保存即下轮生效（`session-store.ts:584-725`、`teams.ts:1295-1308`）。工具分级只是同一机制上的新字段。
- 建议数据模型：按**工具组**而非逐工具，如 `toolExposure?: { knowledge?: "direct" | "deferred" | "off" }`；逐工具开关会让 UI 与校验爆炸。
- 装配落点：`runtime-service.ts:287` managerExtension 注册处（现硬编码 deferred）读配置决定 exposure；worker 侧 `pi-session-factory.ts` 同理。
- 必须守住的边界：
  1. **UI 只控可见性与声明时机，不控权限**——授权边界在宿主 `assertCurrent` / provider stream fence；关工具 ≠ 撤授权，UI 文案必须说清。
  2. fingerprint 已覆盖工具面身份，配置变化自然触发旧会话重建，无驻留复用风险。
  3. 组合校验：`deferred` 必须配 `tool_search` 否则不可发现；`off` 掉 prepare/submit 等于关闭整理能力，需保护性提示；`knowledge_curation_status` 等回执通道建议不可关。
- UI 位置：Agent 配置页新增「工具」分区（或并入「插件」）。
- **方向已拍板（2026-10-15）**：灵活给 Worker 装配工具组、并选择每组的暴露方式（direct/deferred/off），是必要能力——不止 Manager 受益，Worker 同样需要收窄/分级自己的工具面（如知识检索、日历的条件装配）。**实现暂缓**：先把只读预览跑稳，待分级策略稳定后从本节落地。本段即决策记录。

**2026-10-15 进展**：其中的只读工具预览部分已落地为 Agent 配置页「工具」分区（`GET /api/agents/:name/tool-preview`，构建器 `pi-bridge/tool-preview.ts`，前端 `tool-preview-section.tsx`）——按本文 §2–§5 的角色分组成静态装配清单，附 memory 配置与联网授权两处 live 状态，不创建会话、不含分级开关；**分级 UI 化决策本身仍暂缓**，本节其余评估继续有效。

## 7. codemode 是否进设置界面（2026-10-15 评估：暂缓，不单独开配置项）

SDK 的 `createCodemodeExtension()` 注册一个 `codemode` 工具：模型写 JS 脚本，经 `ctx.executeTool()` 链式调用 active `direct` 工具与全部 `codemode`/`deferred` 工具，多步合并为一次工具调用，中间结果不进模型上下文。已核实的边界事实：

- **权限门不破**：嵌套调用走与直接调用完全相同的 tool pipeline（校验、`tool_call`/`tool_result` hook、权限检查），我们的 `assertCurrent`/stream fence 包装继续生效。
- **与 deferred 兼容**：`deferred` 工具 codemode 不列出（只走 `tool_search`），知识工具面语义不冲突；脚本反而可以调用已注册的知识工具。
- **落盘契约要变**：嵌套调用**不产生独立 toolResult 条目**，只在父 codemode 工具的 result 上留有界 `nestedCalls` 记录（`tool_execution_*` 事件带 `parentToolCallId`）。这与 `2026-08-14` 文档「标准工具调用/结果条目」的契约冲突，前端对 `nestedCalls` 也没有渲染——审计可见性下降是最大代价。
- **与 MCP adapter 重复**：pi-mcp-adapter 自带 `scriptMode`（MCP-only JS 脚本工具，默认 true，我们在 `mcp-runtime.ts:13` 显式关闭）+ `directTools`。开 SDK codemode 前要先把这两个通道的关系定清，不能两个脚本入口并存。
- 配置语义上 codemode 是 per-会话/角色的装配策略（Manager 受益最大），不是全局 harness 开关——放进设置 → harness 会让 Manager/Worker/wiki_curator 一刀切，与既有 per-agent 装配粒度不符。

结论：不开独立配置项；codemode 属于「工具装配策略」设计的一部分，与 §6 的分级配置一起做。若要先试验，最小切片是仅 Manager 会话挂 `createCodemodeExtension()` 并把 MCP 工具标 `codemode`——但前提是先解决 `nestedCalls` 的落盘与前端展示，并同步 `2026-08-14` 文档。
