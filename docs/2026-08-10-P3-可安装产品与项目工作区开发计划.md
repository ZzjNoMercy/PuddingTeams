P3-G“Goal 与责任连续性”和 P3-R“Pi Agent 资源配置”现已完成 MVP。通用 HITL 仍不在 P3 关键路径上；等待第二个真实协议样本后再重估，避免为单一 PuddingClaw 协议过拟合。

## 1. 第一性原理

### 1.1 产品的最小承诺

P3 的完成标准不是“能生成安装包”，而是用户在一台新机器上可以完成这一条黄金路径：

```text
安装并启动 → 选择项目 → 添加 Agent → 建立单聊/群聊
→ manager 派活 → worker 在正确项目中执行 → 进度可见
→ 产物返回 → 重启后窗口、项目与 Session 关系仍正确
```

任何不服务这条路径的工作，不应阻塞首个可安装版本。

### 1.2 必须保持的边界

1. **Workspace 是项目上下文，不是通用文件权限沙箱。**
   PuddingTeams 能保证路由、cwd、启动参数、env/secrets 注入、取消与产物归属；Codex sandbox、Claude permission mode 等执行权限由各 Agent 自己实施。真正一致的强制边界需要 OS sandbox 或容器。
2. **项目属于 Window，Agent 配置不携带 cwd。**
   同一个 Agent 可在多个项目中工作；项目不能成为 Connector config 的隐式全局状态。
3. **一次 Delegation 必须使用不可变的 cwd 快照。**
   Window 后续切换项目，不能改变等待审批、恢复执行或重放中的旧 Run。
4. **Session 不能跨项目复用。**
   Session 身份至少由 `Agent + Workspace + Agent 配置修订` 决定；项目变化必须产生新 Session。
5. **项目与 Agent 资源解耦。**
   Workspace/AGENTS.md 属于项目；system prompt、skills、prompt templates 属于 Agent Resource Profile；协作提示词属于 Window。
6. **分发态只有一个入口和一个事实源。**
   npm CLI、Electron 复用同一个生产 server 和同一份静态 Web，不维护两套产品逻辑。
7. **未经隔离，不执行任意第三方代码。**
   在 Extension Host 完成前，正常模式只加载随发行物签入、审核和打包的第一方 Extension。
8. **先规定一条 Session 对应一个主要 Goal，不新建 Topic/WorkItem 子系统。**
   Window 是长期协作空间，Session 是一次主要协作事项，Delegation 是其中一个 Agent Task，Run 是 Agent 的一次实际执行。只有出现 Goal 跨 Session/房间等真实需求时，才重新评估独立 WorkItem。
9. **局部完成不等于协作完成。**
   worker Run 的 `completed` 只说明局部执行结束；默认由 manager 作为唯一负责人，核对 completion boundary 后才能把 Session Goal 标记为 `resolved`。
10. **能力、责任、资源与授权分层。**
    Connector 回答“怎样运行”；Capability 回答“技术上能做什么”；Agent Responsibility Profile 回答“长期负责什么、何时停止”；Resource Profile 回答“加载哪些提示词/skills”；Runtime 权限回答“本次实际允许什么”。
11. **业务决策不冒充底层 HITL。**
    Driver `Interaction` 恢复仍在暂停的原 Run；业务 `DecisionRequest` 恢复一项工作，可能启动新 Run。回答问题不自动扩大授权范围。

## 4. P3-1：项目 Workspace / Session 正确性收口

这是 npm 分发前唯一必须补齐的产品功能阶段。

### 4.1 数据模型

新增平台管理的 Workspace 实体，Window 只引用它：

```ts
interface WorkspaceRecord {
  id: string;
  name: string;
  rootPath: string;
  canonicalPath: string;
  gitRoot?: string;
  createdAt: string;
  lastOpenedAt: string;
}

interface WindowConfig {
  workspaceId?: string; // 缺省 = 原有默认 cwd 聊天模式
  cwdSnapshot: string;   // 无项目模式也冻结，跨重启不漂移
}

interface DelegationRecord {
  workspaceId?: string;
  cwdSnapshot: string;
}
```

项目未上线，不做旧数据兼容：直接替换 `WindowConfig.workspace?: string`，清理开发数据，不保留双字段适配层。

### 4.2 Workspace Store 与 API

- [x] 增加 WorkspaceStore：创建、列出最近项目、按 canonical path 去重、路径失效标记。
- [x] 绑定路径时执行 `realpath`、必须为目录、可读检查；需要写入时再检查可写。
- [x] 识别 Git root；用户选择子目录时保留选择并返回仓库根信息。
- [x] 提供最近项目、手工绝对路径、仅返回目录的 server-side 浏览 API。
- [x] Web 文案明确为“服务端绝对目录”，不使用浏览器目录选择能力冒充后端 cwd。
- [x] 临时项目创建于 `<dataDir>/workspaces/<workspaceId>/`；未选项目不创建伪 Workspace。

### 4.3 Window 与 Session 规则

- [x] 创建单聊/群聊时项目可选；不选时保持原有默认 cwd 行为，选择时可用最近项目、服务端目录或临时项目。
- [x] 单聊去重键改为 `(worker, workspaceId ?? cwdSnapshot)`。

- [x] Delegation 创建时持久化 `workspaceId? + cwdSnapshot`；无项目也冻结默认 cwd，run/continue/respond/cancel/artifact 全部读取快照，不重读 Window 当前值。
- [x] direct 切换项目默认按上下文创建或打开单聊；group 默认新建成员相同、项目不同的群聊；solo 固定单例，只能原地切换。
- [x] 显式项目可切回“不绑定项目”，按当前平台默认 cwd 建立独立上下文。
- [x] 显式原地切换先停止活跃任务，清空 workerBindings，创建新 manager Session；禁止复用旧 Agent Session。

### 4.4 Web 产品面

- [x] 新建窗口对话框加入可选项目区：不选项目、最近项目、服务端目录、临时项目；默认不选以保持原行为，无项目窗口仍显示其冻结 cwd。
- [x] Chat header 使用“默认目录 / 项目 · 名称”的用户语言展示当前上下文；打开项目弹窗以文件夹选择器为主入口、最近项目为快捷选择，并把“新建对话 / 替换当前”收敛为底部动作，不用复选框堆叠内部 Session 细节。
- [x] 本地 server 模式提供跨平台系统目录选择：macOS 调 Finder 原生选择器、Windows 调 FolderBrowserDialog，选择结果自动回填；内嵌服务端目录浏览继续作为通用入口。Electron 阶段改由主进程原生 API 承接同一 UI 协议。
- [x] 项目路径失效时不阻断服务启动；窗口头部明确标记不可用、阻断派活并提供切换/重新绑定，不静默回退 server cwd。可用性要求路径仍解析为同一可读目录。

### 4.5 Artifact 与权限语义

- [x] artifact register/download/observe 统一以 Delegation `cwdSnapshot` 为根做 realpath containment 校验。
- [x] symlink 指向项目外时在登记阶段拒绝，下载阶段再次复核。
- [x] UI 与文档把 workspace 描述为“项目上下文/默认操作范围”，不承诺所有 Agent 都被它强制限制。
- [x] Codex 默认保留 `workspace-write`；Claude `bypassPermissions` 必须明确显示高风险，不能用“cwd 即安全边界”解释。

### 4.6 验收场景

1. 同一个 Codex 分别绑定项目 A、B，得到两个 direct Window 与两个独立 Session；
2. A 中继续对话仍有 A 的记忆，B 中看不到 A 的 Session 历史；
3. 委托在 A 等待/暂停时把 Window 切到 B，恢复后仍在 A 的 `cwdSnapshot` 执行；
4. manager 与 worker 同时读取 A 的项目上下文；
5. 原地切换项目前活跃任务被停止，workerBindings 与 manager Session 被重建；
6. canonical path 和 symlink 别名不会制造重复项目；
7. 项目外 artifact 与越界 symlink 被拒绝。

## 5. P3-G：Goal 与责任连续性（可并行，公开 Beta 前置）

> 实现状态（2026-08-10）：MVP 已落地。权威状态持久化在 `work-states.json`；普通会话通过 `/goal` 创建，manager 通过受控工具维护状态与业务决策，Chat 仅在 Goal 存在时展示“当前工作”、复核结果与委托链。`notification` 不建模为 Delegation：Delegation 是有执行与返回义务的 Run，单向通知继续使用事件/消息通道，避免制造虚假等待。

目标：在不引入 Topic/WorkItem 新实体的前提下，让“一项跨多个 Agent 的工作”有唯一负责人、唯一当前版本和明确完成边界。

### 5.1 对象映射

```text
Window = 长期协作空间
└── Session = 一个主要 Goal / 协作事项
    ├── SessionWorkState = 当前责任与结论
    ├── Delegations[] = Goal 下的 Agent Tasks
    ├── DecisionRequests[] = 业务级 Human 决策
    └── Artifacts[] = 可验证交付证据
```

暂不创建独立 WorkItem。只有以下需求至少真实出现一项时再评估：一个 Goal 横跨多个 Session、一个 Session 并行多个独立 Goal、Goal 跨房间、聊天归档后仍需独立追踪。

### 5.2 Agent Responsibility Profile

责任 Profile 属于 Agent 实例，不属于 Connector manifest，也不等于 skills Resource Profile：

```ts
interface AgentResponsibilityProfile {
  identity?: string;
  domain: string;
  owns: string[];
  excludes: string[];
  escalateWhen?: string[];
}
```

- [x] Agent 管理页增加领域、拥有范围、排除范围和升级条件；
- [x] manager 的 roster/tool description 从 Responsibility Profile 投影；
- [x] Profile 只用于路由与责任提示，不作为能力证明或权限授予；
- [x] 同一 Connector 可创建不同责任的 Agent 实例，禁止把 domain/scope 固化进 Connector 包。

### 5.3 SessionWorkState

```ts
interface SessionWorkState {
  goal: string;
  responsibleAgentId: string; // v1 固定/默认 manager
  participantAgentIds: string[];
  currentBrief: string;
  waitingOn?: string;
  nextAction?: string;
  completionBoundary: string;
  goalRevision: number;
  reviewMode: "manager" | "independent";
  reviewerModel?: string;
  completionReviews: CompletionReview[]; // append-only，保留跨 Goal revision 的复核轨迹
  status: "active" | "waiting_human" | "resolved" | "cancelled";
  artifactIds: string[];
  revision: number;
}
```

- [x] Session 可通过 `/goal` 设置 Goal 与自然语言完成条件；未填写时保持普通聊天，不强制所有 Session 项目化。目标/完成条件变化单独递增 `goalRevision`，复核不能复用旧契约判定。
- [x] 为 manager 提供受控的 `update_session_work_state` 工具，结构化更新 brief/waiting/next/artifacts；使用 revision 防止旧回合覆盖新状态。
- [x] worker Delegation `completed` 只更新局部结果；只有 responsible manager 可将 Goal `resolved`。
- [x] `resolved` 前校验完成条件与最终 brief 非空；普通 REST 更新不能提交 resolved，必须由 responsible manager 走完成申请。
- [x] 独立复核启动全新的只读 Pi SDK in-memory Session；不继承 manager 历史、不装载工具/资源，只接收冻结契约与证据投影。结构化 verdict 与逐项 evidence refs 以 append-only 轨迹持久化，reviewer 必须逐行、原序覆盖完成条件；虚构 evidence id 被拒绝，复核期间 revision 漂移则判定失效。
- [x] 独立 reviewer verdict 为 `not_satisfied` 时 Goal 保持 active 并把 gaps 作为下一步；`needs_human` 要求 manager 创建业务 DecisionRequest；只有 `satisfied` 且无活动委托/待回答决策才 resolved。
- [x] Chat 中只保留轻量“当前工作”摘要和运行详情入口；右侧 Runtime 抽屉承接当前进度、完整验收条件、历次复核与 evidence refs、DecisionRequest、Delegation 链和 Artifact。普通会话不常驻 Goal 横条。

`CompletionReview` 是控制面复核记录，不是 Delegation，也不是房间成员：

```ts
interface CompletionReview {
  goalRevision: number;
  verdict: "satisfied" | "not_satisfied" | "needs_human";
  criteria: Array<{
    criterion: string;
    status: "satisfied" | "unsatisfied" | "uncertain";
    evidenceRefs: string[];
    explanation: string;
  }>;
  gaps: string[];
  reviewerModel: string;
  reviewerSessionId: string;
}
```

### 5.4 有因果的 Delegation

在现有 DelegationRecord 上增加最小交接语义：

```ts
interface DelegationHandoff {
  parentDelegationId?: string;
  handoffKind: "request" | "followup";
  intent: string;
  expectedOutcome?: string;
  evidenceRequirements?: string[];
  completionBoundary?: string;
}
```

- [x] Worker A 的结果触发 Worker B 时，由 manager 写入 `parentDelegationId`；
- [x] request 明确返回义务，followup 沿原任务继续；notification 使用消息/事件通道，不伪装成 Delegation；
- [x] 继续保持 `Worker A → Manager → Worker B`，不开放 worker-to-worker 绕过 manager 的直连；
- [x] API/UI 能从一次 Delegation 追溯触发它的上游结果与所属 Session Goal。

### 5.5 DecisionRequest 与 Interaction 分层

```ts
interface DecisionRequest {
  id: string;
  sessionId: string;
  requestedBy: string;
  question: string;
  context: string;
  options?: Array<{ id: string; label: string }>;
  blockedAction: string;
  resumeHint: string;
  authorizationScope?: string;
  status: "pending" | "answered" | "cancelled";
}
```

- `Interaction`：Driver/Runtime 对象，必须恢复同一个暂停 Run；
- `DecisionRequest`：Window/Session 编排对象，回答后可以由 manager 启动新 Delegation；
- 答复与授权分别记录，例如“继续起草”不能推导成“允许公开发布”；
- 该子项可以晚于 SessionWorkState MVP，但不能通过扩展 Driver HITL 来替代。

实现状态：`request_human_decision` 创建业务级 DecisionRequest 并把 Goal 置为 `waiting_human`；Human 回答后独立记录答案/授权范围、恢复为 active，并通过同一 manager Session 的 follow-up 继续。整个过程不调用 `Driver.respond`。

### 5.6 Artifact 稳定版本

在现有 ArtifactRecord 增加：

```ts
contentHash: string;       // sha256
sourceRevision?: string;  // git base/commit
snapshotPath?: string;    // 正式导出物的冻结副本
```

- `.pudding/handoff/` 的报告/导出物登记时计算 hash，并冻结为不可漂移版本；
- workspace 就地代码修改记录 base revision + diff/patch/hash，不复制整个仓库；
- SessionWorkState 引用 artifact id + hash，而不是只引用可变化路径；
- Artifact 的 cwdSnapshot containment 与 P3-1 共用一套校验。

实现状态：普通文件 Artifact 已在登记时冻结到平台目录并计算 SHA-256，下载只读冻结副本且返回 hash header；workspace 源文件之后修改或删除不影响历史版本。整仓代码 revision/diff 不伪装成普通文件 Artifact，待独立 Patch Artifact 类型出现真实需求时再实现。

### 5.7 验收场景

1. 一个 Session Goal 依次委托分析、实现、测试，三次 Delegation 可沿 parent 链追溯；
2. 实现 worker 完成后 Goal 仍为 active，manager 提交完成申请；独立 reviewer 在隔离 Pi 上下文中逐项核对完成条件与证据，通过后才 resolved；
3. Session 当前卡片能在不重读完整聊天的情况下回答：负责人、当前结论、等待谁、下一步、完成边界；
4. 业务 DecisionRequest 的答复不会调用 Driver.respond，也不会扩大 authorizationScope；
5. Artifact 原文件被修改后，旧 Goal 仍能验证当时引用的 hash/快照；
6. 同一 Agent 的责任 Profile 全局稳定，但 Session、记忆、Goal 与 artifacts 按 workspace 隔离。
7. 普通会话输入 `/goal` 打开创建流程，页面顶部不常驻“设为 Goal”；`/goal 完成登录页` 会预填目标。
8. Reviewer 引用不存在的证据、复核期间 Goal revision 改变、仍有 active/waiting Delegation 或 pending DecisionRequest 时，都不能完成 Goal。

## 6. P3-R：Agent Resource Profile（可并行）

> 实现状态（2026-08-10）：MVP 已落地。`manager.prompt` 与 Pi Connector `config.systemPrompt` 已直接删除，manager/Pi worker 共用 `AgentConfig.piResources`；服务端与实际运行共用资源装配函数，前端可按 Workspace 预览来源、数量、诊断与估算长度。修改后按 `affectedSessions` 明示重开边界。
>
> 二次落地（2026-08-10 资源库 + 独立配置页）：资源管理 UI 已上线，与本文两处设计有意的偏差如下——
> - **资源库 = pi 全局目录**：技能/模板的新建/导入/编辑/删除直接读写 `<agentDir>/skills` 与 `<agentDir>/prompts`（`~/.pi/agent/`），与 pi CLI 共享同一份资源，不另设平台私有库目录。存储层 `apps/server/src/pi-bridge/resource-library.ts`，HTTP 面 `GET/POST/PUT/DELETE /api/resources/skills|templates` + `POST .../import`（`apps/server/src/routes/resources.ts`）。
> - **白名单选用取代 loadGlobal 开关**：`loadGlobalSkills`/`loadGlobalPrompts` 已删除，`PiResourceConfig` 新增 `enabledSkills`/`enabledPrompts`（按 name，缺省 = 不启用任何库资源）；装配经 `skillsOverride`/`promptsOverride` 按 filePath 前缀过滤全局目录条目（`pi-resources.ts`），Workspace 与额外挂载路径资源不受白名单管。`~/.agents/skills` 等跨 agent 标准目录同理不受管（preview 标 `source: "extra"`，始终启用）。
> - **统一配置接口与独立配置页**：`PUT /api/agents/:name/config` 一条接口合并更新 description/responsibility/manager 或 connector/piResources（pinned 分发 `updateManager`，非 pi worker 传 manager/piResources 字段 400）；前端新路由 `/agents/[name]` 五分区（概览/模型与运行/提示词/技能/模板）一个保存按钮，支持「从其他 Agent 复制配置」与导出/导入 JSON。旧管理接口（`PATCH /manager`、`PUT /connector`、`PUT /pi-resources`）保留，非 pi 管理抽屉仍在用。

该工作在 P3-1 数据模型稳定后即可开始，但不阻塞 P3-2。

资源归属：

| 资源 | 归属 |
| --- | --- |
| cwd、AGENTS.md/CLAUDE.md | Workspace |
| system prompt、skills、prompt templates | Agent Resource Profile |
| 协作提示词、成员关系 | Window |
| 历史与 provider session | Agent + Workspace Session |

### 6.1 数据模型与边界

首版直接在 `AgentConfig` 上加入 Pi 资源配置，不提前抽象可复用 Profile 实体。pinned manager 与 Pi worker 共用同一份资源语义：

```ts
interface PiResourceConfig {
  systemPrompt?: string;
  skillPaths?: string[];
  promptTemplatePaths?: string[];
  enabledSkills?: string[];   // 库（pi 全局目录）技能选用名单，缺省 = 不启用
  enabledPrompts?: string[];  // 库模板选用名单，同上
  loadWorkspaceSkills?: boolean;
  loadWorkspacePrompts?: boolean;
  loadWorkspaceContext?: boolean;
}

interface AgentConfig {
  // 仅 type=pi 的 pinned manager 或 connectorId=pi 的 worker 使用。
  piResources?: PiResourceConfig;
}
```

- `PiResourceConfig.systemPrompt` 是 Agent 长期人格、职责与行为规则；不承载某个窗口的成员关系、relay 规则或某个项目的开发约定。
- P3-R 落地时直接用 `piResources.systemPrompt` 替换当前临时的 `manager.prompt` 与 Pi Connector `config.systemPrompt`，不保留双写或兼容读取。项目尚未上线，结构变化直接替换。
- Pi Connector config 回到 Connector 边界，只保留“怎样运行”相关配置，例如 model、thinking level、sessionDir；Agent Resource Profile 回答“给该 Agent 加载什么”。
- `additionalSkillPaths` 是追加语义；需要隔离时必须使用 `skillsOverride`，不能误当独占列表。
- 不通过更换 `agentDir` 隔离资源，因为它会同时耦合 auth/models。
- Capability Extension 与 pi-native skill 保持两个概念，不合并安装入口。
- prompt 组合顺序固定为：Pi base → Agent Resource Profile → Window collaboration prompt → Workspace context。

Window collaboration prompt 只参与 manager 会话；worker 接收的是 manager 包装后的任务文本，不把窗口提示词再次追加到 worker system prompt，避免规则重复和职责串层。Workspace context 则由 manager/worker 各自基于同一个 Delegation `cwdSnapshot` 加载。

### 6.2 前端：统一“提示词与资源”入口

在现有“智能体管理”页继续把 pinned manager 和 worker 当作同一类可管理 Agent。点击 manager 或 Pi worker 后，都提供独立的 **“提示词与资源”** 分区；不新建一个脱离 Agent 的全局“Prompt 管理”页面。

该分区首版包含：

1. **系统提示词**：多行编辑器，编辑 `piResources.systemPrompt`；留空表示只使用 Pi base 及后续 Window/Workspace 层，不用含糊文案称为“默认 relay guidance”。
2. **Skills**：额外 skill paths，以及加载全局/Workspace skills 的开关；展示最终发现数量和诊断信息。
3. **Prompt templates**：额外 template paths，以及加载全局/Workspace templates 的开关；明确它们是用户主动展开的模板，不是常驻 system prompt。
4. **Workspace context**：是否加载 `AGENTS.md` / `CLAUDE.md`；只展示当前项目命中的文件路径与顺序，不在 Agent 表单里编辑项目文件正文。
5. **有效提示词预览**：只读展示各段来源、组合顺序和估算长度；默认折叠 Pi base，避免把 SDK 内置文本误存为用户配置。预览必须基于选定 Workspace 计算，没有项目时明确显示“无 Workspace context”。
6. **恢复为空**：只清除该 Agent Resource Profile 的显式值，不删除 Workspace 文件，不改 Window prompt。

manager 仍保留单独的“运行配置”分区（默认模型、内置工具、thinking level、资源总开关）；Pi worker 的 model、thinking level、sessionDir 仍留在“基础接入/Connector”。也就是说，前端按语义拆分为：

```text
Pi manager
  ├─ 基础信息
  ├─ 运行配置（model / tools / thinking）
  └─ 提示词与资源（system prompt / skills / templates / context）

Pi worker
  ├─ 基础信息
  ├─ 基础接入（Pi Connector：model / thinking / sessionDir）
  ├─ 提示词与资源（system prompt / skills / templates / context）
  ├─ Capability Extensions
  └─ 运行状态
```

非 Pi worker 不显示 Pi Resource Profile；它们若支持提示词，应通过各自 Connector 明确声明的能力或后续通用 Resource SPI 提供，不能假设所有 CLI Agent 都理解 pi 的 `DefaultResourceLoader`。

### 6.3 生效与反馈

- system prompt、skills、templates、context 加载策略修改后，对新建或重开的 Agent Session 生效；不得在旧 Session 中静默替换 system prompt。
- 保存成功后返回受影响 Session 数量，区分“已在当前轮结束后重开”和“用户需手动新建会话”；前端给出明确提示。
- P3-R 必须拆掉当前 `manager.prompt` 同时充当“Agent 人格”和“relay fallback”的重载语义：manager Agent Profile 始终加载；direct/group 的协作段在 `window.prompt` 与内置 relay guidance 之间二选一；solo 不注入 relay。最终装配固定为 `Pi base → Agent Profile → Window collaboration prompt（如有）→ Workspace context`。
- 提供服务端只读 preview API，前端不自行复刻装配算法，确保预览与实际 `DefaultResourceLoader`/Extension 注入结果同源。

完成判据：

1. 用户可从同一个智能体管理入口编辑 Pi manager 与任意 Pi worker 的系统提示词，二者均为多行编辑器；
2. Pi worker 的提示词不再埋在 Connector config，manager 与 worker 使用同一资源模型和表单语义；
3. 同一 Pi Agent 在项目 A/B 中共享显式 Agent 资源，但只加载各自项目上下文，Session 历史不串项目；
4. 有效提示词预览列出的顺序、来源与实际请求一致，Window/Workspace 配置不会被误写回 Agent Profile；
5. 修改资源后，前端准确告知哪些 Session 需要重开，不让用户误以为当前历史会话已经热更新。
