# 真实环境复验与可信验收方案

> 状态：**待审核，未实现**（2026-08-26）。本文是对现有 Session Goal / WorkPlan / Submission / Completion Review 的增量设计，不代表当前产品已具备真实环境复验能力。当前已实现契约仍以 `docs/2026-08-21-Manager-WorkPlan与Delegation-Timeline融合方案.md` 和现有代码为准。
>
> 设计边界：验证编排、Submission 门禁、Goal 最终验收和 UI 只属于 PuddingTeams Harness；Connector 的 pi 入口不获得房间编排能力。Driver SPI 只负责声明和执行它真实支持的环境/权限策略，共享 PWCP 不依赖任一宿主。

## 0. 审阅结论清单

本方案请先审核以下决策，审核通过前不进入实现：

1. **Submission 是执行事实，不由 Manager 决定是否落盘。** 绑定 WorkItem 的执行 Delegation 到达 `completed` 后，平台继续自动生成 Submission；Manager 只决定接受、返修或阻塞。
2. **Verification 是环境事实，Acceptance 是管理决策。** Verifier 不直接把 WorkItem 改为 `accepted`，只产生绑定当前 Submission/契约版本的 `VerificationRecord`。
3. **真实环境复验是可配策略，不是所有对话的默认成本。** 普通聊天和未激活 Goal 的一次性委派不进入正式验收状态机。
4. **Goal 规定验证下限，WorkItem 规定具体策略。** Manager 可以提高 WorkItem 的复验强度，不得低于 Goal 冻结的最低要求。
5. **WorkItem 首次进入 `in_progress` 时冻结验证策略。** 执行后改变验收条件或验证策略必须增加 WorkItem revision、记录原因，并使旧 Submission/Verification 不能用于新版本验收。
6. **Harness 设置配置的是“Verifier Worker + Verification Environment Profile”，不是一个无边界的电脑权限。** 目标 workspace 从 Goal/Window 自动继承，Verifier 只获得完成复验所需的最小权限。
7. **必须复验但无合格 Verifier 时 fail closed。** Submission 保持 `submitted`，Manager 不得 `accepted`；用户可添加 Verifier，或通过一次显式 Goal revision 改变尚未满足的契约/策略，但 Manager 不能为当前版本临时豁免，平台也不静默降级。
8. **WorkItem 复验不取代 Goal Completion Review。** 中间 Submission 通过后只能解锁 DAG 依赖；Goal `resolved` 仍需按 `finalGoalMode` 对冻结 `completionBoundary` 执行最终复核，其中 `environment_verified` 必须重新观测当前整合环境。

## 1. 问题与当前缺口

PuddingTeams 已经有结构化的 Goal 契约、WorkPlan DAG、Submission、Manager 验收、独立 Completion Reviewer、Goal revision/epoch、幂等 operation ledger 和可恢复 outbox。当前信任链为：

```text
Worker 执行
  → Delegation.result
  → WorkItemSubmission
  → Manager accept / revision / blocked
  → Completion Reviewer 阅读 Delegation result、Artifact 元数据、ToolResult 和 Decision
  → Goal resolved / active / needs_human
```

现有独立 Completion Reviewer 是无工具、无项目上下文、不继承 Manager 消息历史的隔离 Session；它可以防止自由改写冻结条件、检查 evidenceRef 是否存在，但无法通用地：

- 重新读取当前 workspace 中的真实文件；
- 重新运行 test/typecheck/build；
- 打开当前网页、文档、设计稿或桌面应用检查真实状态；
- 确认服务、配置或外部系统此刻仍处于声称状态；
- 判断 Artifact 的实际内容是否满足语义验收条件。

因此，当前的“独立”主要是上下文隔离与证据复核，还不是平台级的真实环境独立观测。

## 2. 一个不可混淆的五层信任链

```text
Delegation
  一次 Worker 执行运行事实
      ↓ completed
Submission
  某次尝试已结束并形成的候选交付
      ↓ verify when required
VerificationRecord
  独立 Verifier 在指定真实环境中观测到的事实
      ↓ manager decision
Acceptance
  Manager 对中间交付的管理决策
      ↓ all non-cancelled WorkItems accepted
Completion Review
  冻结 Goal 条件对当前整合结果的最终门禁
```

责任固定如下：

| 概念 | 表达的事实 | 责任主体 | 不能代表 |
|---|---|---|---|
| `Delegation.completed` | 这次 Run 已结束并返回结果 | Runtime / Driver | WorkItem 合格 |
| `Submission` | 形成了可审计的候选交付 | PuddingTeams Goal 控制面 | Manager 认可 |
| `VerificationRecord` | 指定环境和条件下的独立观测结果 | Verifier + Harness 门禁 | 业务接受决策 |
| `accepted` | Manager 接受某个 Submission | Manager | Goal 整体完成 |
| `resolved` | 当前 Goal 契约经最终复核满足 | PuddingTeams Completion Gate | 永久不变的外部状态 |

## 3. 触发语义：不是每个 Run 都验证

### 3.1 有 Goal + WorkPlan

绑定 WorkItem 的执行 Delegation 到达 `completed` 后自动生成 Submission，不由 Manager 决定是否 Submit：

```text
Execution Delegation D1 completed
  → Submission S1 created atomically
  → WorkItem remains submitted
```

Manager 对 Submission 的下一步有四种：

```text
submitted
  ├─ 明显不合格：revision（不浪费 Verifier 成本）
  ├─ 无法继续：blocked
  ├─ 需要复验：request_work_item_verification
  └─ 策略允许：accepted
```

当有效策略为 `environment_verified` 时，Manager 可以决定何时启动 Verifier，但 Store 必须拒绝没有有效 `passed` VerificationRecord 的 `accepted`。这样既保留 Manager 对明显不合格交付直接返修的权力，又不允许跳过必须复验。

可选 `auto_on_submission` 模式可在 Submission 形成后立即由 outbox 调度 Verifier，适合快速 CI 任务；默认建议 `manager_request`，减少明显失败结果的无效复验成本。

### 3.2 有 Goal，无 WorkPlan

direct Session 可以有 Goal 但没有 Manager WorkPlan；solo/group 的简单 Goal 也可以不拆 WorkItem。这时不伪造 WorkItem，在申请 `resolved` 时直接按 `finalGoalMode` 对冻结 `completionBoundary` 生成 Goal 级 VerificationRecord，然后继续现有 Completion Review；只有 `environment_verified` 才声称重新观测了当前整合环境。

### 3.3 无 Goal

普通聊天、一次性问答和未绑定 WorkItem 的 Delegation 不进入正式验收状态机：

```text
Agent Run completed = Agent 本次运行已结束
不等于 PuddingTeams 已验证用户目标完成
```

可以后续提供“验证此结果”的显式用户动作，对某次 Delegation 生成 ad-hoc Verification；它不自动创建隐藏 Goal，也不宣称完成一个未冻结契约。该能力不纳入首期实现。

## 4. 验证策略与冻结时机

### 4.1 不与 CompletionReviewMode 混用

当前 `CompletionReviewMode = "manager" | "independent"` 表示**谁有权对 Goal 执行最终完成复核**。新增 Verification mode 表示**验收前需要什么等级的环境事实**。两者正交，不复用同一字段。

```ts
type VerificationMode =
  | "manager_review"
  | "independent_evidence_review"
  | "environment_verified";

type VerificationTrigger =
  | "manager_request"
  | "auto_on_submission";

interface VerificationPolicy {
  mode: VerificationMode;
  trigger: VerificationTrigger;
  source: "user" | "goal_default" | "manager_derived";
  reason: string;
}
```

强度顺序固定为：

```text
manager_review
  < independent_evidence_review
  < environment_verified
```

`independent_evidence_review` 可复用当前无工具隔离 Reviewer 的证据判定思路，但中间 WorkItem 级记录不直接复用 Goal `CompletionReview` 类型。

### 4.2 Goal 创建时确定下限

Goal 新增验证策略下限和最终整合复验策略：

```ts
interface GoalVerificationPolicy {
  minimumWorkItemMode: VerificationMode;
  finalGoalMode: VerificationMode;
  trigger: VerificationTrigger;
  source: "user" | "harness_default" | "manager_derived";
  reason: string;
}
```

来源规则：

- 用户明确要求“必须实际运行测试/打开页面确认/由另一 Agent 验收”时，以 `source:"user"` 冻结相应下限；
- 用户没有明示时，Manager 可根据已明确的任务性质设置默认值，必须给出 `reason`；
- Manager 不得借验证策略添加用户未要求的新产品标准；验证只是改变已冻结条件的求证方式；
- 用户后续修改 Goal 验证下限时增加 `goalRevision`，WorkPlan 进入 `needsReconcile`。

### 4.3 WorkItem 创建时具体化，开始时冻结

`update_work_plan` 的 upsert item 增加 `verificationPolicy`：

```ts
interface WorkItemVerificationPolicy extends VerificationPolicy {
  frozenAtRevision?: number;
}
```

有效模式取 Goal 下限和 WorkItem 设定中的更严格者：

```text
effectiveMode = max(goal.minimumWorkItemMode, workItem.verificationPolicy.mode)
```

冻结规则：

- `planned/ready`：Manager 可以按 Goal 契约调整策略；
- 首次进入 `in_progress`：写入 `frozenAtRevision`；
- `in_progress/submitted/accepted`：禁止原地降低模式或改写理由；
- 执行后确需改变：增加 WorkItem revision，记录 `lastChange.reason`，清除 `acceptedSubmissionId`，旧 Submission/Verification 仅保留审计价值；
- 新策略低于 Goal 下限时 Store 直接拒绝。

## 5. Verifier Worker 与验收环境

### 5.1 必要条件

本节的 Verifier Worker 专指 `environment_verified` 所需的真实环境执行主体。`independent_evidence_review` 可由现有 pi SDK 隔离 Reviewer Session 完成，不必须创建 Worker Delegation，也不声称已观测 workspace/GUI。

对真实环境复验而言，“Worker 有能力访问电脑”是必要条件，但不是充分条件。一次可信复验还必须由 PuddingTeams 保证：

- 启动全新 Session，禁止 `continue` Executor 会话；
- 精确绑定 `goalId/workPlanId/workItemId/submissionId/goalRevision/workItemRevision/epoch`；
- 自动继承目标 `workspaceId/cwdSnapshot`，不由 Manager 在 prompt 里自由填写路径；
- 只投影冻结验收条件、Submission 声明、必要 Artifact/上游证据引用，不注入 Manager 推理历史；
- 按 Verification Environment Profile 限制工具、写目录、网络和 GUI 权限；
- 输出经平台解析和一致性校验的结构化结果；
- 复验运行本身不能生成新 WorkItemSubmission。

可以使用与 Executor 相同的 Agent 配置/模型，但必须是新 Session；对高风险任务可以配置“必须不同 Worker”。

### 5.2 环境不是自由填写的路径

验收目标环境从原任务继承：

```text
Submission
  → WorkItem
  → Goal / Manager Session
  → Window.workspaceId + cwdSnapshot
```

默认两种 Profile：

```ts
type VerificationEnvironmentMode =
  | "none"
  | "same_target_guarded"
  | "isolated_copy";

interface VerificationEnvironmentProfile {
  id: string;
  modality: "cli" | "gui";
  mode: VerificationEnvironmentMode;
  /** 由平台解析，配置中不接受任意绝对路径。 */
  sourceBinding: "goal_workspace" | "goal_window";
  controlledScopes: string[];
  writableScopes: string[];
  networkPolicy: "deny" | "read_only" | "allowlist";
  mutationPolicy: "block_on_change" | "isolated_changes_only";
}
```

- `none`：仅执行 Manager review 或隔离 evidence review，不将某个 workspace/GUI 观测声称为验证事实。
- `same_target_guarded`：在原 workspace/当前桌面环境直接观测；执行前后记录 fingerprint，越权修改使验证失效并进入 `blocked`。
- `isolated_copy`：将当前 workspace 的可验证快照复制到临时隔离目录，在副本中运行可能产生构建缓存或临时文件的 test/build；它验证的快照必须与 Submission 记录的输入 fingerprint 一致。

Mode 只说明隔离语义，Profile 才是可执行策略。Profile 不能保存由 Manager 临时填写的目标路径；Harness 在调度时把 `sourceBinding` 解析为该 Goal 已绑定的 workspace/window，再将受控范围和权限交给 Driver 强制执行。

CLI/代码复验优先使用 `isolated_copy`；GUI/桌面复验通常只能使用 `same_target_guarded`。涉及外部写操作、发布、购买、删除或业务授权的条件不能由 Verifier 自动执行，仍转 HITL Decision。

### 5.3 权限是平台策略，不是 prompt 声明

当前 `DriverCapabilities` 只描述 operation、interaction、progress 和 transport，不足以证明某 Connector 可以强制执行只读/隔离复验。目标 SPI 需增加可选验证能力声明，类似：

```ts
interface DriverVerificationCapabilities {
  modalities: Array<"cli" | "gui">;
  freshSession: boolean;
  workspaceIsolation: Array<"none" | "mutation_guard" | "isolated_copy">;
  commandExecution: boolean;
  guiObservation: boolean;
  networkObservation: boolean;
}
```

Harness 根据 WorkItem 的验证需求筛选 Verifier，Driver 负责将平台 Profile 映射为该 Agent 的真实启动参数、sandbox、tool allow/deny 或远程环境策略。不支持的 Connector 必须诚实声明，UI 不得将它配置为强制验收 Worker。

验证仍使用 PWCP `run`，不新增“verify” AgentOperation；`verify` 是 PuddingTeams Harness 对一次 Run 的用途和门禁，不是任意 Agent 都必须实现的私有会话协议。

## 6. 配置归属

### 6.1 全局 Harness 设置

在“设置 → Harness → 验收与真实环境复验”增加默认路由与运行策略，落盘到 `config/product.json`：

```json
{
  "harness": {
    "verification": {
      "enabled": true,
      "defaultWorkItemMode": "manager_review",
      "defaultFinalGoalMode": "independent_evidence_review",
      "trigger": "manager_request",
      "reviewers": {
        "evidenceModel": "provider/model"
      },
      "environmentProfiles": {
        "cli-isolated": {
          "modality": "cli",
          "mode": "isolated_copy",
          "sourceBinding": "goal_workspace",
          "controlledScopes": ["**"],
          "writableScopes": ["<isolated-copy>/**"],
          "networkPolicy": "deny",
          "mutationPolicy": "isolated_changes_only"
        },
        "gui-guarded": {
          "modality": "gui",
          "mode": "same_target_guarded",
          "sourceBinding": "goal_window",
          "controlledScopes": ["<bound-app-state>"],
          "writableScopes": [],
          "networkPolicy": "read_only",
          "mutationPolicy": "block_on_change"
        }
      },
      "routes": {
        "cli": {
          "agentId": "codex-verifier",
          "environmentProfileId": "cli-isolated"
        },
        "gui": {
          "agentId": "claude-gui-verifier",
          "environmentProfileId": "gui-guarded"
        }
      },
      "isolation": {
        "requireFreshSession": true,
        "forbidExecutorContinuation": true,
        "requireDifferentAgent": false
      },
      "limits": {
        "timeoutMs": 600000,
        "maxVerificationAttemptsPerSubmission": 2
      },
      "unavailableAction": "block"
    }
  }
}
```

约束：

- Harness 设置只提供默认值和路由，不改写已冻结 Goal/WorkItem 契约；
- Environment Profile 只声明相对受控范围与权限；真实 workspace/window 在运行时从 Goal 绑定解析，不能在设置或 prompt 中替换；
- 修改全局默认值只影响后续创建或尚未开始的 WorkItem；
- `unavailableAction` 首期固定只允许 `block`，不提供静默 fallback；
- CLI/GUI 路由中的 Agent 不必须是当前 Room 的可见成员，但必须是 PuddingTeams 已启用、可使用且被 workspace 信任门允许的 Agent。环境 Verifier 始终是平台发起的可审计 Delegation，不是隐藏模型调用；`evidenceModel` 只用于无工具隔离 Reviewer。

### 6.2 Agent 配置页

Agent 配置页不保存 WorkItem 策略，只展示 Connector/Driver 真实能力和缺口，例如：

```text
✓ Workspace 读取
✓ CLI 命令执行
✓ Browser / Computer Use
△ 只读隔离：仅 mutation guard
✗ isolated copy
```

不得通过前端标签猜能力；展示值必须来自 Driver `capabilities()/probe()`。

### 6.3 Goal / WorkItem 级配置

- Goal 创建表单和 `create_session_goal` 增加最低验证策略；
- `update_work_plan` 为每个 WorkItem 指定具体策略和原因；
- UI 必须显示“来自用户 / Goal 默认 / Manager 派生”和是否已冻结；
- Manager 可以选择符合能力的 Verifier，但不能选择不满足有效策略的 Agent，也不能降低用户冻结的下限。

## 7. 领域模型

### 7.1 WorkItem / Submission 增量字段

```ts
interface WorkItem {
  // 现有字段保持
  verificationPolicy: WorkItemVerificationPolicy;
}

interface WorkItemSubmission {
  // 现有字段保持
  goalRevision: number;
  workItemRevision: number;
  /** 验收契约、执行输入引用与 Artifact hash 的稳定指纹。 */
  inputFingerprint: string;
  verifications: VerificationRecord[];
}

interface SessionWorkState {
  // 现有字段保持
  /** 无 WorkPlan Goal 或 Goal 最终整合复验；不归属某个 Submission。 */
  goalVerifications: VerificationRecord[];
}
```

WorkItem 级 VerificationRecord 作为 Submission 的有界元数据内聚到 `SessionWorkState.plan`；Goal 级复验放入 `SessionWorkState.goalVerifications`。两者均与 Goal revision、operation ledger 和 outbox 在同一次原子改写中提交，不新增独立 `verification-records.json`。详细轨迹、截图、命令输出和大文本仍通过 `verifierDelegationId` 进入现有 Delegation result/timeline/Artifact，不把全文复制进 Goal 聚合。

### 7.2 VerificationRecord

```ts
type VerificationStatus =
  | "pending"
  | "running"
  | "waiting_input"
  | "passed"
  | "failed"
  | "blocked"
  | "stale";

interface VerificationCriterionResult {
  criterion: string;
  status: "satisfied" | "unsatisfied" | "uncertain";
  evidenceRefs: string[];
  explanation: string;
}

interface VerificationRecord {
  id: string;
  goalId: string;
  workPlanId?: string;
  workItemId?: string;
  submissionId?: string;
  goalRevision: number;
  workItemRevision?: number;
  goalEpoch: number;
  mode: VerificationMode;
  status: VerificationStatus;
  verifierAgentId?: string;
  verifierDelegationId?: string;
  reviewerModel?: string;
  reviewerSessionId?: string;
  environmentProfileId?: string;
  environmentMode: VerificationEnvironmentMode;
  inputFingerprint: string;
  outputFingerprint?: string;
  criteria: VerificationCriterionResult[];
  evidenceRefs: string[];
  integrity: "unknown" | "clean" | "suspect" | "violation";
  failureReason?: string;
  createdAt: string;
  updatedAt: string;
  completedAt?: string;
}
```

完整性规则：

- WorkItem 级 `criteria` 必须按原序、原文覆盖该 revision 的全部 `acceptanceCriteria`；
- Goal 级 `criteria` 必须按原序、原文覆盖当前 `completionBoundary` 的每个非空行；
- `passed` 要求全部 criterion `satisfied`、`integrity="clean"`、指纹与当前目标匹配，且无未解决的授权/主观条件；
- 结构解析失败、Verifier 运行时失败、越权写入、证据不可定位或契约不完整时不得推断 `passed`。

### 7.3 Verification Delegation

Verifier 仍通过 Runtime/Driver 运行，Delegation 增加 Harness 用途标记：

```ts
interface DelegationRecord {
  // 现有字段保持
  purpose: "execution" | "verification";
  /** 运行创建时的契约快照，用于隔离晚到结果。 */
  contractGoalRevision: number;
  workItemRevision?: number;
  verificationId?: string;
  verifiesSubmissionId?: string;
}
```

边界结算必须分流：

```text
purpose=execution + completed
  → 生成 WorkItemSubmission

purpose=verification + completed/failed/cancelled/input_required
  → 更新 VerificationRecord
  → 不生成 Submission
```

若 execution Delegation 返回终态时，其 `contractGoalRevision`、`workItemRevision` 或 `goalEpoch` 已过期，系统仍保留 Delegation 结果，并以原始版本快照生成历史 Submission；但该 Submission 不得成为当前待验收 Submission，也不得覆盖新版 WorkItem 状态。这样既保留审计轨迹，又阻止旧 Worker 的晚到结果穿透新契约。

`purpose` 是 PuddingTeams Harness/Runtime 元数据，Driver 不根据该字段自由改变业务状态。Driver 只接收已解析的 InvocationContext 和验证运行 Profile。

## 8. 状态机与强制门禁

WorkItem 主状态继续使用现有 `submitted`，验证进度从最新 Submission 的 VerificationRecord 投影，不为 `verifying` 额外扩张 WorkItemStatus：

```text
in_progress
  → execution completed
submitted + no verification
  → Manager revision/blocked
  → request verification
  → Manager accepted（仅 effectiveMode=manager_review）
submitted + verification running
  → waiting_input / passed / failed / blocked
submitted + verification waiting_input
  → respond/approve → running
submitted + passed
  → Manager accepted
submitted + failed
  → Manager revision
submitted + blocked
  → Manager request Decision / change verifier / retry
```

`review_work_item(verdict:"accepted")` 增加权威 Store 门禁：

```text
1. WorkItem.status == submitted
2. 找到最新未验收 Submission
3. Submission 和 WorkItem/Goal revision 仍匹配
4. effectiveMode == manager_review
   或存在匹配当前 Submission 的有效复核记录
5. environment_verified 必须是 passed + clean + fingerprint current
6. acceptedSubmissionId 只指向通过上述门禁的 Submission
```

Manager 不能通过在 `summary/evidenceRefs` 里声称“已验证”绕过门禁。

### 8.1 时效与失效

这里的 `inputFingerprint` 不是无差别计算整个 workspace 的 hash。它至少覆盖 Goal/WorkPlan/WorkItem/Submission 标识与 revision、`goalEpoch`、冻结的验收标准与验证策略、执行 Delegation 结果身份、Artifact content hash，以及 Environment Profile 声明的受控文件、服务或应用状态范围。构建缓存、日志、临时文件等预期变化必须在 Profile 中声明，不允许靠 Verifier 提示词临时排除。

VerificationRecord 在以下情况直接变为 `stale`：

- `goalRevision/workItemRevision/goalEpoch` 任一不再匹配；
- WorkItem 产生了更新 Submission；
- 对应 Artifact 的 content hash 已变化；
- 在 Manager `accepted` 前，复验声明的受控文件/应用状态 fingerprint 已改变；
- Verifier 运行期间发生不允许的 workspace 写入且未被可证明地隔离。

WorkItem 被 `accepted` 后，它的 VerificationRecord 保留为当时的审计事实，不因后续下游 WorkItem 的合法修改而倒退历史验收。为防止“单项曾经通过，整合后已失效”，`finalGoalMode=environment_verified` 时必须在 Goal `resolved` 前对当前整合环境再执行一次 Goal 级复验。

## 9. Manager Core Tools

新增或扩展的工具都是 PuddingTeams core tools，不属于 Connector Extension：

### 9.1 `create_session_goal` 扩展

```ts
create_session_goal({
  // 现有字段
  verificationPolicy?: {
    minimumWorkItemMode,
    finalGoalMode,
    trigger,
    source,
    reason
  }
})
```

Manager 只能根据明确用户意图派生策略；请求不清晰时仍先询问，不得为了触发复验而滥建 Goal。

### 9.2 `update_work_plan` 扩展

```ts
upsertItems: [{
  // 现有字段
  verificationPolicy: {
    mode,
    trigger,
    source,
    reason
  }
}]
```

Store 校验不得低于 Goal 下限，并按 WorkItem revision 冻结。

### 9.3 `request_work_item_verification`

```ts
request_work_item_verification({
  goalId,
  workItemId,
  submissionId,
  expectedRevision,
  verifierAgentId?
})
```

执行时：

1. 确认 Submission 是当前待验收候选；
2. 解析 effective policy 和所需 modality；
3. 解析 Environment Profile，并校验指定 Agent 或 Harness 默认路由的 Driver capabilities；
4. 幂等创建 `VerificationRecord{status:"pending"}` 和 outbox 事件；
5. dispatcher 启动 `purpose:"verification"` 的新 Delegation；
6. 终态原子回写 VerificationRecord，并唤醒同一 Manager Session。

core tool 在平台内部使用 pi `toolCallId` 作为 `operationId`，不让模型自由填写幂等键；重放相同 tool call 不创建第二个 Verifier Run。

### 9.4 `review_work_item` 扩展

不要求 Manager 复制 Verification 正文；Store 自动查找与当前 Submission 绑定的有效记录。`evidenceRefs` 可引用 `verificationId/verifierDelegationId/artifactId`，但引用文本不代替强制门禁。

### 9.5 Goal 完成入口

当 `finalGoalMode=environment_verified` 时，Manager 提交 `status:"resolved"` 不立即完成 Goal，而是幂等开始 Goal 级 Verification：

```text
Manager 完成申请
  → Goal execution.status = reviewing
  → Goal VerificationRecord pending/running
  → passed
  → 现有 manager/independent Completion Review
  → resolved / active / needs_human
```

复验失败时 Goal 保持 `active`，`nextAction` 写入结构化缺口；不通过自然语言“重试一下”直接重放旧外部副作用。

## 10. 调度、恢复与幂等

Verification 继续使用当前 Goal 聚合的 operation ledger/outbox/epoch 机制：

- 创建复验请求、保留 VerificationRecord 和 outbox 在同一次原子写中完成；
- dispatcher 以 `verificationId` 作为稳定调度身份，以 `operationId/idempotencyKey` 向 Driver 尽可能透传；
- PuddingTeams 重启时，旧运行 Verifier Delegation 按现有原则诚实判死，记录转 `blocked` 或 `stale`，再由同一 Goal 恢复世代决定是否新建复验尝试；
- 旧 `goalId/epoch/revision/submissionId` 的迟到回调只保留审计，不得改写当前状态；
- 上游不支持幂等时，有外部副作用的复验不承诺 exactly-once；结果不明时转 `blocked/needs_human`；
- 同一 Submission 最多运行配置的验证尝试数，超过后不自动循环，由 Manager/人类决策。

## 11. 结构化 Verifier 输入输出

### 11.1 输入边界

Verifier 只接收：

- 原始 Goal 和当前冻结条件；
- 当前 WorkItem 的冻结 acceptanceCriteria；
- Submission 的结构化摘要、Delegation result 引用和 Artifact 引用；
- 已验收上游 WorkItem 的有界状态与必要证据引用；
- 受控 workspace/应用目标和 Verification Environment Profile；
- 人类已授权的有界范围。

不接收：

- Manager 的隐藏推理；
- Executor 的完整 prompt 和未筛选 trajectory；
- 其他 Room/Goal 的上下文；
- Harness 运行目录作为任务交付证据。

### 11.2 输出契约

Verifier Worker 可以返回自然语言作为诊断正文，但 Harness 不从自由文本猜完成状态。首期应为 Verifier 注入受控结构化输出契约，并由隔离 parser/reviewer 校验：

```json
{
  "verdict": "passed | failed | blocked",
  "integrity": "clean | suspect | violation",
  "criteria": [
    {
      "criterion": "原文验收条件",
      "status": "satisfied | unsatisfied | uncertain",
      "evidenceRefs": ["artifact-or-observation-id"],
      "explanation": "观测事实"
    }
  ],
  "observations": [
    {
      "kind": "command | file | gui | service | external_read",
      "target": "受控目标",
      "result": "有界摘要",
      "evidenceRefs": ["..."]
    }
  ],
  "gaps": ["..."]
}
```

对不能原生返回结构化数据的 Connector，可以用一次无工具 format-repair 将已有 Verifier 文本转为该结构；format-repair 不得重新运行工具、补充新观测或改变环境。无法从已有内容得出时保守转 `blocked`。

## 12. 验证类型与默认路由

| 工作类型 | 建议 mode | 默认环境 | 典型观测 |
|---|---|---|---|
| 方案讨论、任务拆解 | `manager_review` | 无 | 契约覆盖、下游可用性 |
| 调研、引用、数据核对 | `independent_evidence_review` | 隔离无工具或只读网络 | 来源存在性、数值/引用一致性 |
| 代码、修复、测试、构建 | `environment_verified` | `isolated_copy` | 文件、test/typecheck/build |
| 网页、交互、视觉稿 | `environment_verified` | `same_target_guarded` | 页面打开、交互、视觉截图 |
| 文档、演示、表格 | `environment_verified` | 优先隔离渲染 | 可打开性、布局、公式/格式 |
| 服务、配置、健康检查 | `environment_verified` | `same_target_guarded` | 进程、日志、健康接口 |
| 发布、购买、删除、授权 | `environment_verified` + HITL | 原环境 | 默认只读复查，不代替人类授权 |
| 主观满意度 | `needs_human` | 不由 Verifier 代替 | 请求用户决策 |

这张表是 Manager 路由和默认配置材料，不应用隐藏关键词分类器直接改写用户契约。

## 13. UI 与可观测性

### 13.1 设置页

新增页面区域：

```text
Harness
  └─ 验收与真实环境复验
      ├─ 默认 WorkItem 验收等级
      ├─ Goal 最终复验等级
      ├─ Evidence Reviewer 模型
      ├─ CLI / GUI Verifier Worker 路由
      ├─ 环境 Profile
      ├─ 隔离要求
      ├─ 超时和尝试上限
      └─ 无可用 Verifier 时的处理
```

### 13.2 目标与执行抽屉

每个 WorkItem 展示：

- 有效 verification mode、来源、理由和冻结 revision；
- 最新 Submission 及其 Verification 状态；
- Verifier Worker、环境 Profile、开始/完成时间；
- 逐项验收条件、观测结果和 evidenceRef；
- 失败/阻塞/过期原因；
- 进入现有 verifier Delegation timeline 的详情入口。

`pudding:verification_update` 如果新增，只是 `display:false` UI 刷新投影，不是权威事实源；Harness 必须回读 `state/work-states.json`。若实现该 customType，必须同步 `docs/2026-08-14-会话记录格式与Harness消费.md` 和前后端渲染契约。

### 13.3 语义标签

前端必须区分：

- `Run completed`：Agent 运行结束；
- `Submitted`：候选交付已落盘；
- `Verified`：当前 Submission 已经指定方式复验；
- `Accepted`：Manager 已接受该 Submission；
- `Goal completed`：当前 Goal 契约经最终门禁完成。

不得把 `Delegation.completed` 显示成“已验收”。

## 14. 安全与副作用

### 14.1 Verifier 默认只观测

- 原 workspace 的源文件和用户交付不允许修改；
- 可写范围限于独立临时目录、明确的构建目录或隔离副本；
- test/build 可能产生缓存，Profile 必须明确允许路径或使用隔离副本；
- GUI 导航也可能改变应用状态，只有契约明确要求且无不可逆副作用的交互才可自动执行；
- 外部写入、账号权限、购买、发布、删除、发送等动作不会因“验收”角色而绕过 Interaction/HITL。

### 14.2 运行记录不是自动证据

Delegation timeline、prompt、reasoning、Dashboard 截图和角色输出是可观测记录，不自动成为验收证据。只有 Verifier 按契约明确登记、平台确认存在且属于当前 Goal/Submission 的 observation/Artifact 才可进入 `evidenceRefs`。

## 15. 不做什么

- 不把所有普通聊天自动升级为 Goal；
- 不为无 WorkPlan 的 Goal 伪造 WorkItem；
- 不把 Verifier 做成绕过 Manager 的第二个完成权威；
- 不把 `verify` 增加为所有 Agent 必须实现的 PWCP operation；
- 不把 WorkPlan/验证编排下放到 Connector 的 pi Extension 门面；
- 不仅靠 prompt 宣称 Verifier 只读；
- 不默认给 Verifier 完整电脑控制权；
- 不对含数据库、服务和外部系统副作用的 workspace 执行粗暴全局回滚；
- 不用旧 WorkItem/Goal revision 的复验记录满足当前契约；
- 不让过期或无法定位的 evidenceRef 只因 ID 存在就通过门禁。

## 17. 验收标准

### 17.1 领域状态

- 绑定 WorkItem 的 Execution Delegation `completed` 必然生成一个可审计 Submission，Manager 无法隐藏该事实；
- Verification Delegation 不会生成 Submission；
- `environment_verified` WorkItem 无当前 `passed + clean` VerificationRecord 时无法 `accepted`；
- 旧 revision/epoch/submission 的 VerificationRecord 不能通过当前门禁；
- WorkItem accepted 仍不直接使 Goal resolved；
- 无 Goal 的普通 Run 不伪造 WorkItem/Submission/Verification。

### 17.2 环境与权限

- Verifier 每次使用新 Session，不能继续 Executor Session；
- 复验 workspace/cwd 由平台绑定，不接受 Manager 通过 prompt 替换目标路径；
- Environment Profile 的 source binding、受控范围、可写范围和网络策略可审计，并由 Driver 实际强制；
- Driver 没有声明所需隔离/观测能力时不能被选为强制 Verifier；
- Verifier 越权改写受保护 workspace 时验证不通过，不从它创建的文件推导交付完成；
- 无可用 Verifier 时保持阻塞，不静默降级。

### 17.3 恢复与幂等

- 同一 `request_work_item_verification` tool call 被重放时，不创建多个 Run；
- server 重启后不把旧 Verifier Run 伪装为仍在运行；
- 旧 Goal/epoch 迟到终态不能覆盖当前记录；
- Manager 收到复验终态后能在同一 Session 继续 accept/revision/Decision；
- 超过验证尝试上限后转人类/管理决策，不无界循环。
