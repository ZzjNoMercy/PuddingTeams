# 可证明的多 Agent 协作协议与可信验收方案

> 状态：**首期实现完成，待代码与产品审核**（2026-08-30，分支 `codex/provable-collaboration-protocol`）。本文合并“LongHorizon 真实环境复验”与“多 Agent 可证明协作协议”两轮分析结论；D1–D15 已按 §19 的建议值冻结并实现。首期范围按 D8 只覆盖 CLI/代码环境，GUI / Computer Use 复验仍是明确的后续范围，不得从当前能力投影为已支持。
>
> 设计边界：完整的任务树、证据账本、Workspace 协调、验证编排、Submission 门禁、Goal 最终验收和 UI 只属于 PuddingTeams Harness；Connector 的 pi 入口不获得房间编排能力。Driver SPI 只负责忠实映射上游协议并执行它真实支持的环境、权限、取消与对账策略；共享 PWCP 只定义宿主无关的运行、回执和能力契约，不依赖 PuddingTeams 或 pi 宿主。

## 0. 审阅结论清单

以下十二条协议原则已经进入实现，审核时应同时核对代码门禁与 §21 的验证证据：

1. **执行结束、事实成立与管理验收是三个正交维度。** UI 和状态投影必须分别表达 Execution、Verification、Settlement，禁止继续用一个绿色 `completed` 同时代表三件事。
2. **Driver 终态只是上游报告，不是可信证明。** Runtime 必须把每个 Run 的终态、契约哈希、上游句柄、证据/产物收集结果封装成不可变 `ExecutionReceipt`；Driver 和 Worker 都不能写入 `verified=true`。
3. **Submission 是执行事实，不由 Manager 决定是否落盘。** 绑定 WorkItem 的执行 Delegation 产生 `reported_completed` Receipt 后，平台自动生成 Submission；Manager 只决定接受、返修或阻塞。
4. **Verification 是环境事实，Acceptance 是管理决策。** Verifier 不直接把 WorkItem 改为 `accepted`，只产生绑定当前 Submission、契约版本和环境指纹的 `VerificationRecord`。
5. **真实环境复验是可配策略，不是所有对话的默认成本。** 普通聊天和未激活 Goal 的一次性委派不进入正式验收状态机。
6. **Goal 规定验证下限，WorkItem 规定具体策略。** Manager 可以提高 WorkItem 的复验强度，不得低于 Goal 冻结的最低要求。
7. **WorkItem 首次进入 `in_progress` 时冻结验证策略。** 执行后改变验收条件或验证策略必须增加 WorkItem revision、记录原因，并使旧 Submission/Verification 不能用于新版本验收。
8. **Workspace 必须有执行级访问策略。** 只读任务可以共享并发；写任务优先使用隔离 worktree，无法隔离时获取独占写 Lease；每次 Run 记录 baseline、write-set 和 change-set 指纹，不能仅凭共同 `cwd` 推断改动归属。
9. **控制面失联不等于执行面失败，取消请求不等于已取消。** Driver 必须声明对账与取消确认能力；无法确认远端状态时进入 `observation_lost/effect_unknown`，在副作用对账前禁止自动重试写操作。
10. **Harness 设置配置的是“Verifier Worker + Verification Environment Profile”，不是一个无边界的电脑权限。** 目标 workspace 从 Goal/Window 自动继承，Verifier 只获得完成复验所需的最小权限。
11. **必须复验但无合格 Verifier 时 fail closed。** Submission 保持 `submitted`，Manager 不得 `accepted`；用户可添加 Verifier，或通过一次显式 Goal revision 改变尚未满足的契约/策略，但 Manager 不能为当前版本临时豁免，平台也不静默降级。
12. **WorkItem 复验不取代 Goal Completion Review。** 中间 Submission 通过后只能解锁 DAG 依赖；Goal `resolved` 仍需按 `finalGoalMode` 对冻结 `completionBoundary` 执行最终复核，其中 `environment_verified` 必须重新观测当前整合环境。

## 1. 问题与当前缺口

PuddingTeams 已经有结构化的 Goal 契约、WorkPlan DAG、Submission、Manager 验收、独立 Completion Reviewer、Goal revision/epoch、幂等 operation ledger 和可恢复 outbox。当前信任链仍主要从 Worker/Driver 报告直接跳到 Manager 验收：

```text
Worker 执行
  → Delegation.result
  → WorkItemSubmission
  → Manager accept / revision / blocked
  → Completion Reviewer 阅读 Delegation result、Artifact 元数据、ToolResult 和 Decision
  → Goal resolved / active / needs_human
```

现有独立 Completion Reviewer 是无工具、无项目上下文、不继承 Manager 消息历史的隔离 Session；它可以防止自由改写冻结条件、检查 evidenceRef 是否存在，但当前协议仍有四类独立缺口：

1. **没有不可变的执行回执。** `Delegation.status="completed"` 只表示 Runtime 收到了 Driver 的 completed boundary；Artifact 登记失败当前不会改变终态，`evidenceRequirements` 也没有逐项结算。
2. **没有通用真实环境复验。** Reviewer 无法重新进入实际 workspace、应用或服务求证。
3. **没有 Workspace 写入所有权。** 多个 Worker 共享同一 `cwdSnapshot` 时，git diff、Artifact 和最终文件可能混入其他并发 Run 的改动。
4. **没有远端 Run 未知态。** 重启时当前实现统一把遗留 Run 收割为 `server_restart` failure，取消时先落 `cancelled` 再 best-effort 通知 Driver；这对生命周期绑定的本地子进程可成立，对 HTTP/RPC/ACP 远端执行面不一定成立。

其中真实环境复验缺口具体包括 Reviewer 无法：

- 重新读取当前 workspace 中的真实文件；
- 重新运行 test/typecheck/build；
- 打开当前网页、文档、设计稿或桌面应用检查真实状态；
- 确认服务、配置或外部系统此刻仍处于声称状态；
- 判断 Artifact 的实际内容是否满足语义验收条件。

因此，当前的“独立”主要是上下文隔离与证据复核，还不是平台级的真实环境独立观测；当前 Workspace 也只是路径与信任边界，还不是并发写协调协议。

## 2. 一个不可混淆的七层协作信任链

```text
Task Contract
  Goal / WorkItem 冻结的任务、验收条件与证据要求
      ↓ execute
Delegation Run
  一次 Worker 执行及其上游会话/运行身份
      ↓ reported boundary
ExecutionReceipt
  Runtime 对上游报告、机械观测和证据收集完整性的不可变封装
      ↓ reported_completed
Submission
  某次尝试已结束并形成的候选交付
      ↓ verify when required
VerificationRecord
  独立 Verifier 在指定真实环境中观测到的事实
      ↓ manager decision
Acceptance
  Manager 对中间交付的管理决策
      ↓ all non-cancelled WorkItems accepted
Completion Review
  冻结 Goal 条件对当前整合结果的最终门禁
```

责任固定如下：

| 概念 | 表达的事实 | 责任主体 | 不能代表 |
|---|---|---|---|
| Task Contract | 本次执行必须完成什么、需要什么证据 | User / Manager / Goal Store | 已经执行 |
| Delegation Run | 一次具体执行的身份、句柄和生命周期 | Runtime / Driver | 已经可靠结束 |
| `ExecutionReceipt` | 上游报告了什么、Runtime 实际收集到了什么 | Runtime 封装，Driver 提供观察 | 声明真实、条件满足 |
| `Submission` | 形成了可审计的候选交付 | PuddingTeams Goal 控制面 | Manager 认可 |
| `VerificationRecord` | 指定环境和条件下的独立观测结果 | Verifier + Harness 门禁 | 业务接受决策 |
| `accepted` | Manager 接受某个 Submission | Manager | Goal 整体完成 |
| `resolved` | 当前 Goal 契约经最终复核满足 | PuddingTeams Completion Gate | 永久不变的外部状态 |

本文把这些记录组成的只读查询投影称为 **Evidence Ledger**。它不是一个让 Agent 自由追加任意文字的新数据库：权威事实仍分别存放在 Delegation/Receipt、Artifact Store、Submission、VerificationRecord、Decision 和 CompletionReview 中，Ledger 只按稳定 ID、revision、epoch 和 hash 连接它们。

## 3. 触发语义：不是每个 Run 都验证

### 3.1 有 Goal + WorkPlan

绑定 WorkItem 的执行 Delegation 形成 sealed `reported_completed` Receipt 后自动生成 Submission，不由 Manager 决定是否 Submit：

```text
Execution Delegation D1 reported_completed
  → ExecutionReceipt R1 sealed
  → Submission S1 created idempotently
  → WorkItem remains submitted
```

Manager 对 Submission 的下一步有四种：

```text
submitted
  ├─ 明显不合格：revision（不浪费 Verifier 成本）
  ├─ 无法继续：blocked
  ├─ 需要复验：request_work_item_verification
  └─ 策略允许：accepted
```

当有效策略为 `environment_verified` 时，Manager 可以决定何时启动 Verifier，但 Store 必须拒绝没有有效 `passed` VerificationRecord 的 `accepted`。这样既保留 Manager 对明显不合格交付直接返修的权力，又不允许跳过必须复验。

可选 `auto_on_submission` 模式可在 Submission 形成后立即由 outbox 调度 Verifier，适合快速 CI 任务；默认建议 `manager_request`，减少明显失败结果的无效复验成本。

### 3.2 有 Goal，无 WorkPlan

direct Session 可以有 Goal 但没有 Manager WorkPlan；solo/group 的简单 Goal 也可以不拆 WorkItem。这时不伪造 WorkItem，在申请 `resolved` 时直接按 `finalGoalMode` 对冻结 `completionBoundary` 生成 Goal 级 VerificationRecord，然后继续现有 Completion Review；只有 `environment_verified` 才声称重新观测了当前整合环境。

### 3.3 无 Goal

普通聊天、一次性问答和未绑定 WorkItem 的 Delegation 不进入正式验收状态机：

```text
Agent Run reported completed = Agent 本次运行已结束
不等于 PuddingTeams 已验证用户目标完成
```

可以后续提供“验证此结果”的显式用户动作，对某次 Delegation 生成 ad-hoc Verification；它不自动创建隐藏 Goal，也不宣称完成一个未冻结契约。该能力不纳入首期实现。

## 4. 验证策略与冻结时机

### 4.1 不与 CompletionReviewMode 混用

当前 `CompletionReviewMode = "manager" | "independent"` 表示**谁有权对 Goal 执行最终完成复核**。新增 Verification mode 表示**验收前需要什么等级的环境事实**。两者正交，不复用同一字段。

```ts
type VerificationMode =
  | "manager_review"
  | "independent_evidence_review"
  | "environment_verified";

type VerificationTrigger =
  | "manager_request"
  | "auto_on_submission";

interface VerificationPolicy {
  mode: VerificationMode;
  trigger: VerificationTrigger;
  source: "user" | "goal_default" | "manager_derived";
  reason: string;
}
```

强度顺序固定为：

```text
manager_review
  < independent_evidence_review
  < environment_verified
```

`independent_evidence_review` 可复用当前无工具隔离 Reviewer 的证据判定思路，但中间 WorkItem 级记录不直接复用 Goal `CompletionReview` 类型。

### 4.2 Goal 创建时确定下限

Goal 新增验证策略下限和最终整合复验策略：

```ts
interface GoalVerificationPolicy {
  minimumWorkItemMode: VerificationMode;
  finalGoalMode: VerificationMode;
  trigger: VerificationTrigger;
  source: "user" | "harness_default" | "manager_derived";
  reason: string;
}
```

来源规则：

- 用户明确要求“必须实际运行测试/打开页面确认/由另一 Agent 验收”时，以 `source:"user"` 冻结相应下限；
- 用户没有明示时，Manager 可根据已明确的任务性质设置默认值，必须给出 `reason`；
- Manager 不得借验证策略添加用户未要求的新产品标准；验证只是改变已冻结条件的求证方式；
- 用户后续修改 Goal 验证下限时增加 `goalRevision`，WorkPlan 进入 `needsReconcile`。

### 4.3 WorkItem 创建时具体化，开始时冻结

`update_work_plan` 的 upsert item 增加 `verificationPolicy`：

```ts
interface WorkItemVerificationPolicy extends VerificationPolicy {
  frozenAtRevision?: number;
}
```

有效模式取 Goal 下限和 WorkItem 设定中的更严格者：

```text
effectiveMode = max(goal.minimumWorkItemMode, workItem.verificationPolicy.mode)
```

冻结规则：

- `planned/ready`：Manager 可以按 Goal 契约调整策略；
- 首次进入 `in_progress`：写入 `frozenAtRevision`；
- `in_progress/submitted/accepted`：禁止原地降低模式或改写理由；
- 执行后确需改变：增加 WorkItem revision，记录 `lastChange.reason`，清除 `acceptedSubmissionId`，旧 Submission/Verification 仅保留审计价值；
- 新策略低于 Goal 下限时 Store 直接拒绝。

## 5. Workspace 执行所有权与变更结算

`cwdSnapshot` 只能回答“在哪个目录运行”，不能回答“谁拥有这次写入”。所有执行 Delegation 必须在创建时冻结访问策略：

```ts
type WorkspaceAccessMode =
  | "read_only_shared"
  | "exclusive_write"
  | "isolated_worktree";

interface WorkspaceExecutionPolicy {
  mode: WorkspaceAccessMode;
  source: "harness_default" | "manager_derived" | "user";
  reason: string;
  baselineStrategy: "git_tree" | "filesystem_manifest" | "external_snapshot";
  promoteOnAcceptance: boolean;
}

interface WorkspaceExecutionScope {
  id: string;
  owner:
    | { kind: "work_item"; goalId: string; workItemId: string }
    | { kind: "delegation"; delegationId: string };
  delegationIds: string[];
  policy: WorkspaceExecutionPolicy;
  targetWorkspaceId?: string;
  executionCwd: string;
  baselineFingerprint: string;
  state: "active" | "fenced" | "promoted" | "released";
}

interface WorkspaceChangeSet {
  id: string;
  executionScopeId: string;
  delegationIds: string[];
  workspaceId?: string;
  mode: WorkspaceAccessMode;
  baselineFingerprint: string;
  outputFingerprint: string;
  changedPaths: string[];
  diffArtifactId?: string;
  diffHash?: string;
  promotionState: "not_required" | "pending" | "applied" | "conflict" | "failed";
  createdAt: string;
  promotedAt?: string;
}
```

### 5.1 三种访问模式

| mode | 适用 | 并发规则 | 结果结算 |
|---|---|---|---|
| `read_only_shared` | 调研、分析、检查 | 同一 Workspace 可并发 | 发现受控范围写入则 Receipt 标记 integrity violation |
| `isolated_worktree` | Git Workspace 中的代码/文档修改 | 每个写 WorkItem 独立 execution scope/worktree | 验收后按精确 change-set 提升到目标 Workspace |
| `exclusive_write` | 非 Git 项目、无法隔离的 GUI/外部状态修改 | 按 canonical Workspace/目标资源获取独占 Lease | 改动已发生在目标环境，Receipt 必须记录 baseline/write-set |

默认路由固定为：只读任务使用 `read_only_shared`；可建立 Git worktree 的写任务使用 `isolated_worktree`；其余写任务使用 `exclusive_write`。Manager 可以提高隔离等级，但不能把已判定为写任务的 WorkItem 降为只读共享来绕过调度。

`read_only_shared` admission 要求 Driver `readOnlyEnforcement != "none"`。只有事后 mutation observation、不能强制只读的 Connector，不得直接运行在用户目标 Workspace：Git 项目改用隔离 worktree，非 Git 项目首期阻塞并提示更换 Connector/Profile。mutation guard 是完整性检测，不是权限边界。

`isolated_worktree` 的 baseline 必须等价于用户当前可见工作树，不得默认从 `HEAD` 丢掉未提交改动：clean Workspace 可直接从当前 commit 建立；dirty Workspace 需把 tracked diff、staged diff 和非 ignored untracked 文件机械物化到隔离 worktree 并记录 manifest/hash。无法完整物化（例如不受支持的 submodule、嵌套仓库或路径冲突）时必须阻塞或显式回退 `exclusive_write`，不能静默使用旧 commit。ignored 文件只有被任务/Profile 明确声明为输入时才进入 baseline。

### 5.2 baseline、write-set 与 Artifact 归属

Runtime 在 Driver 启动前生成 baseline，在终态后机械收集 write-set/change-set：

```text
admit Delegation
  → freeze workspace policy
  → create/reuse WorkItem execution scope
  → acquire lease or create worktree and freeze execution cwd
  → capture baseline fingerprint
  → run / continue / respond on the same execution binding
  → collect touched files + git/fs diff + artifact snapshots
  → seal WorkspaceChangeSet and ExecutionReceipt
```

事件流触碰文件集是优先事实源，git/fs diff 是机械兜底；模型最终回复只能提供命名和说明。Artifact 登记失败、diff 生成失败或 baseline 身份变化必须进入 Receipt 的 `collectionStatus/issues`，不得继续静默吞掉并显示为“证据完整”。

同一 WorkItem 的首次执行、followup 和 revision attempt 串行复用一个 execution scope，避免 `continue` 到旧 Session 时 cwd 突然切换，也保留返修前改动。每个 Delegation Receipt 记录本 Run 的增量观测，WorkspaceChangeSet 表达该 WorkItem scope 相对初始 baseline 的累计改动。跨 WorkItem 不复用 scope；未绑定 WorkItem 的普通 Delegation 以自身作为 scope owner。

### 5.3 隔离写入的提升门禁

`isolated_worktree` 的修改在 Manager 验收前不进入目标 Workspace：

```text
Submission
  → required Verification passed in execution worktree
  → Manager requests accepted
  → Harness checks base/diff hash and promotes exact change-set
  → promotion applied: WorkItem accepted
  → promotion conflict/failed: WorkItem blocked, no downstream unlock
```

因此 `accepted` 仍表示“候选交付已经成为可供下游消费的正式状态”，不是仅在隔离目录里看起来正确。首期提升只支持可证明的 Git change-set；不自动提交、不自动推送远端。冲突时保留 worktree、diff Artifact 和 Receipt 供人类/Manager 处理，不做隐式覆盖或丢弃。

提升成功且 Receipt/change-set 已持久化后，平台可以回收受控临时 worktree；`revision/blocked/conflict/observation_lost` 的 scope 默认保留并在 UI 标注占用，只有 WorkItem 终止、用户显式放弃或确定性保留期到期后才能清理，清理不删除目标 Workspace 内容。

`exclusive_write` 无法提供延迟提升，也不承诺自动回滚；它通过独占 Lease、前后指纹、write-set 和最终 Goal 整合复验降低串扰。涉及不可逆外部副作用时还必须经过现有 HITL 授权与幂等/对账策略。

首期 `assignedAgentId="manager"` 只允许 `read_only_shared` 的分析、规划和综合 WorkItem，继续通过 `advance_manager_work_item` 形成 `source="manager"` Submission；它没有 Worker ExecutionReceipt，不能声称独立执行证明。需要修改 Workspace、运行有副作用工具或形成可提升 change-set 的 WorkItem 必须走正式 Worker Delegation（可以选择与 Manager 相同的底层 Agent 配置，但必须是独立执行 Session）。这样避免 Manager 长会话绕过 Lease、worktree 和 Receipt 门禁。

### 5.4 Lease 与恢复

- Lease key 使用稳定 `workspaceId`；无显式 Workspace 时使用 canonical `cwdSnapshot`，不能用模型输入路径；
- Lease 记录 `executionScopeId/delegationIds/goalId/epoch/ownerToken/expiresAt`，continue、respond 和取消都验证同一 token；
- 本地 Run 确认终止后释放 Lease；远端 Run 失联时 Lease 进入 fenced 状态，完成对账或人工接管前不允许新的冲突写；
- 旧 epoch 的迟到事件不能续租、提升 change-set 或覆盖新 owner；
- 只读共享 Run 不占写 Lease，但仍受 Workspace trust 和 Connector 自身 sandbox/permission 约束。

## 6. Verifier Worker 与验收环境

### 6.1 必要条件

本节的 Verifier Worker 专指 `environment_verified` 所需的真实环境执行主体。`independent_evidence_review` 可由现有 pi SDK 隔离 Reviewer Session 完成，不必须创建 Worker Delegation，也不声称已观测 workspace/GUI。

对真实环境复验而言，“Worker 有能力访问电脑”是必要条件，但不是充分条件。一次可信复验还必须由 PuddingTeams 保证：

- 启动全新 Session，禁止 `continue` Executor 会话；
- 精确绑定 `goalId/workPlanId/workItemId/submissionId/goalRevision/workItemRevision/epoch`；
- 自动继承目标 `workspaceId/cwdSnapshot`，不由 Manager 在 prompt 里自由填写路径；
- 只投影冻结验收条件、Submission 声明、必要 Artifact/上游证据引用，不注入 Manager 推理历史；
- 按 Verification Environment Profile 绑定执行根、Workspace 边界与 mutation policy；首期网络权限显式记为继承 Connector/账号策略，不虚构平台网络隔离；
- 输出经平台解析和一致性校验的结构化结果；
- 复验运行本身不能生成新 WorkItemSubmission。

可以使用与 Executor 相同的 Agent 配置/模型，但必须是新 Session；对高风险任务可以配置“必须不同 Worker”。

首期 `environment_verified` 只允许 PuddingTeams 能直接绑定并观察签发环境的本地 `spawn/sdk` Driver。HTTP/RPC/ACP 远端 Driver 即使声称接受某个 cwd，也无法证明其实际运行环境就是平台签发副本，因此 Runtime 在创建 Verification Delegation 前 fail closed；后续只有协议提供可校验的环境绑定回执/签名后，才可开放远端 Verifier。远端 Driver 仍可执行普通任务或 `independent_evidence_review` 所需的证据审阅，但不得产出 `environment_verified` 声明。

### 6.2 环境不是自由填写的路径

验收目标环境从原任务继承：

```text
Submission
  → WorkItem
  → Goal / Manager Session
  → Window.workspaceId + cwdSnapshot
```

默认两种 Profile：

```ts
type VerificationEnvironmentMode =
  | "none"
  | "same_target_guarded"
  | "isolated_copy";

interface VerificationEnvironmentProfile {
  profileId: string;
  environmentId: string;
  /** 由平台解析，配置中不接受任意绝对路径。 */
  sourceBinding: "goal_workspace";
  executionRoot: string;
  workspaceBoundary: "platform_isolated_copy" | "platform_mutation_guard";
  networkPolicy: "inherit_connector_policy";
  mutationPolicy: "block_on_change" | "isolated_changes_only";
}
```

- `none`：仅执行 Manager review 或隔离 evidence review，不将某个 workspace/GUI 观测声称为验证事实。
- `same_target_guarded`：在原 workspace/当前桌面环境直接观测；执行前后记录 fingerprint，越权修改使验证失效并进入 `blocked`。
- `isolated_copy`：将当前 workspace 的可验证快照复制到临时隔离目录，在副本中运行可能产生构建缓存或临时文件的 test/build；它验证的快照必须与 Submission 记录的输入 fingerprint 一致。

Mode 只说明隔离语义，Profile 才是可执行策略。Profile 不能保存由 Manager 临时填写的目标路径；Harness 在调度时把 `sourceBinding` 解析为该 Goal 已绑定的 workspace，签发一次性 environmentId，并把 executionRoot、Workspace 边界与 mutation policy 交给 Driver。首期 Codex Driver 对 verification Run 强制 `workspace-write` sandbox；网络仍服从 Connector/账号自身策略，因此 Profile 明确记录 `inherit_connector_policy`，不能把它宣传为断网沙箱。

CLI/代码复验优先使用 `isolated_copy`；GUI/桌面复验通常只能使用 `same_target_guarded`。涉及外部写操作、发布、购买、删除或业务授权的条件不能由 Verifier 自动执行，仍转 HITL Decision。

### 6.3 权限是平台策略，不是 prompt 声明

当前 `DriverCapabilities` 只描述 operation、interaction、progress 和 transport，不足以证明某 Connector 可以强制执行只读/隔离复验。目标 SPI 需增加可选验证能力声明，类似：

```ts
interface DriverVerificationCapabilities {
  modalities: Array<"cli" | "gui">;
  freshSession: boolean;
  workspaceIsolation: Array<"none" | "mutation_guard" | "isolated_copy">;
  commandExecution: boolean;
  guiObservation: boolean;
  networkObservation: boolean;
}

interface DriverWorkspaceCapabilities {
  honorsInvocationCwd: boolean;
  readOnlyEnforcement: "none" | "sandbox" | "remote_policy";
  mutationObservation: Array<"event_stream" | "git_diff" | "filesystem_diff">;
}
```

Harness 根据 WorkItem 的执行/验证需求筛选 Worker，Driver 负责将平台 Profile 映射为该 Agent 的真实启动参数、sandbox、tool allow/deny 或远程环境策略。PuddingTeams 可以自行创建 worktree 和 Lease，但 Connector 必须保证实际 Run 使用 `InvocationContext.cwd`，并诚实声明是否能强制只读及如何机械观察修改。不支持的 Connector 不得被配置为需要相应保证的执行者或 Verifier。

验证仍使用 PWCP `run`，不新增“verify” AgentOperation；`verify` 是 PuddingTeams Harness 对一次 Run 的用途和门禁，不是任意 Agent 都必须实现的私有会话协议。

## 8. 领域模型

### 8.1 ExecutionReceipt：上游报告的不可变封装

共享 `@puddingteams/pwcp` 定义宿主无关的回执 payload；PuddingTeams Runtime 在本地补齐 Delegation、契约和 Workspace 身份并封存。Driver 仍只产生规范化事件，不能自己签发平台 Receipt：

```ts
// @puddingteams/pwcp
interface ExecutionReceiptPayload {
  schemaVersion: 1;
  operationId: string;
  reportedOutcome: "completed" | "failed" | "blocked" | "cancelled";
  upstream: {
    sessionHandle?: string;
    runHandle?: string;
  };
  reportedEvidence: Array<{
    requirement: string;
    evidenceRefs: string[];
  }>;
  reportedArtifacts: ArtifactRef[];
  startedAt: string;
  observedAt: string;
  observer: {
    connectorId: string;
    transport: DriverTransport;
  };
}

interface ResultBase {
  // 现有字段保持
  /** Worker/Driver 按冻结要求报告的引用；Runtime 仍要验证引用存在性与归属。 */
  reportedEvidence?: Array<{
    requirement: string;
    evidenceRefs: string[];
  }>;
}

// PuddingTeams Runtime envelope
interface ExecutionReceipt extends ExecutionReceiptPayload {
  id: string;
  delegationId: string;
  goalId?: string;
  workPlanId?: string;
  workItemId?: string;
  attempt?: number;
  goalRevision?: number;
  workItemRevision?: number;
  goalEpoch?: number;
  /** Harness 冻结的 WorkItem 业务契约；WorkItem 验收只比较此字段。 */
  taskContractHash?: string;
  /** Runtime 执行信封，额外覆盖 Agent、cwd 与执行上下文。 */
  contractHash: string;
  requirementResults: Array<{
    requirement: string;
    status: "provided" | "missing" | "unavailable";
    evidenceRefs: string[];
  }>;
  artifactCapture: Array<{
    reportedPath: string;
    artifactId?: string;
    contentHash?: string;
    status: "captured" | "rejected" | "missing" | "failed";
    issue?: string;
  }>;
  collectionStatus: "complete" | "partial" | "failed";
  workspaceExecutionScopeId?: string;
  workspaceChangeSetId?: string;
  integrity: "clean" | "suspect" | "violation";
  issues: string[];
  sealedAt: string;
}
```

哈希分成两个不可混用的层次：`taskContractHash` 是 Harness 冻结的 WorkItem 业务契约哈希，覆盖 Goal/WorkItem/revision/epoch、验收条件、VerificationPolicy 与 WorkspaceExecutionPolicy，是 Store 接受 Submission 的依据；`contractHash` 是 Runtime 执行信封哈希，在业务契约之外还覆盖任务文本、`expectedOutcome`、`evidenceRequirements`、`completionBoundary`、Workspace/cwd、Agent 配置 revision 等实际执行上下文。Receipt 中的 `reported*` 字段只保留“上游声明”；Runtime 机械捕获的 Artifact、change-set 和完整性结果单独记录，二者不能混写。

每个终态 Worker Delegation Run 都生成 Receipt，包括 failed/cancelled/blocked；只有 `reportedOutcome="completed"` 的 execution Receipt 才生成 WorkItem Submission。Receipt 封存后不可修改；若 boundary 已落盘但收集阶段崩溃，启动对账必须生成带 `collectionStatus="partial"` 的确定性 Receipt，不能凭空补成完整。

冻结的 `evidenceRequirements` 必须逐项得到 disposition。存在 `missing/unavailable` 时仍保留 Submission 作为执行事实，但 Store 不允许该 Submission 通过要求相应证据的验收门。Artifact 捕获失败也不反向伪造 Run failure；它通过 Receipt 明确降低证据完整性。

`ExecutionReceipt` 内聚保存到 `DelegationRecord.receipt`；大文本、命令输出、diff 和文件内容继续存 timeline/Artifact Store，只保存稳定引用与 hash。Evidence Ledger 从这些权威记录生成，不新增可被 Agent 直接写入的 `evidence-ledger.json`。

```ts
interface SessionWorkState {

```

WorkItem 级 VerificationRecord 作为 Submission 的有界元数据内聚到 `SessionWorkState.plan`；Goal 级复验放入 `SessionWorkState.goalVerifications`。两者均与 Goal revision、operation ledger 和 outbox 在同一次原子改写中提交，不新增独立 `verification-records.json`。详细轨迹、截图、命令输出和大文本仍通过 `verifierDelegationId` 进入现有 Delegation result/timeline/Artifact，不把全文复制进 Goal 聚合。

### 8.3 VerificationRecord

```ts
type VerificationStatus =
  | "pending"
  | "running"
  | "waiting_input"
  | "passed"
  | "failed"
  | "blocked"
  | "stale";

interface VerificationCriterionResult {
  criterion: string;
  status: "satisfied" | "unsatisfied" | "uncertain";
  evidenceRefs: string[];
  explanation: string;
}

interface VerificationRecord {
  id: string;
  goalId: string;
  workPlanId?: string;
  workItemId?: string;
  submissionId?: string;
  goalRevision: number;
  workItemRevision?: number;
  goalEpoch: number;
  mode: VerificationMode;
  status: VerificationStatus;
  verifierAgentId?: string;
  verifierDelegationId?: string;
  reviewerModel?: string;
  reviewerSessionId?: string;
  environmentProfileId?: string;
  environmentMode: VerificationEnvironmentMode;
  inputFingerprint: string;
  outputFingerprint?: string;
  criteria: VerificationCriterionResult[];
  evidenceRefs: string[];
  integrity: "unknown" | "clean" | "suspect" | "violation";
  failureReason?: string;
  createdAt: string;
  updatedAt: string;
  completedAt?: string;
}
```

完整性规则：

- WorkItem 级 `criteria` 必须按原序、原文覆盖该 revision 的全部 `acceptanceCriteria`；
- Goal 级 `criteria` 必须按原序、原文覆盖当前 `completionBoundary` 的每个非空行；
- `passed` 要求全部 criterion `satisfied`、`integrity="clean"`、指纹与当前目标匹配，且无未解决的授权/主观条件；
- 结构解析失败、Verifier 运行时失败、越权写入、证据不可定位或契约不完整时不得推断 `passed`。

### 8.4 Verification Delegation

Verifier 仍通过 Runtime/Driver 运行，Delegation 增加 Harness 用途标记：

```ts
interface DelegationRecord {
  // 现有字段保持
  purpose: "execution" | "verification";
  executionState: ExecutionState;
  receipt?: ExecutionReceipt;
  /** execution purpose 使用；verification purpose 使用 environmentProfileId。 */
  workspaceExecutionPolicy?: WorkspaceExecutionPolicy;
  workspaceExecutionScopeId?: string;
  workspaceChangeSetId?: string;
  /** 运行创建时的契约快照，用于隔离晚到结果。 */
  contractGoalRevision?: number;
  workItemRevision?: number;
  verificationId?: string;
  verifiesSubmissionId?: string;
}
```

边界结算必须分流：

```text
purpose=execution + reported_completed
  → 封存 ExecutionReceipt
  → 生成 WorkItemSubmission

purpose=verification + reported_completed/reported_failed/cancelled/input_required
  → 更新 VerificationRecord
  → 不生成 Submission
```

若 execution Delegation 返回终态时，其 `contractGoalRevision`、`workItemRevision` 或 `goalEpoch` 已过期，系统仍保留 Delegation 结果，并以原始版本快照生成历史 Submission；但该 Submission 不得成为当前待验收 Submission，也不得覆盖新版 WorkItem 状态。这样既保留审计轨迹，又阻止旧 Worker 的晚到结果穿透新契约。

`purpose` 是 PuddingTeams Harness/Runtime 元数据，Driver 不根据该字段自由改变业务状态。Driver 只接收已解析的 InvocationContext 和验证运行 Profile。

## 9. 状态机与强制门禁

### 9.1 Execution / Verification / Settlement 三轴

三个轴分别由自己的权威聚合持有，不再扩张一个跨层 mega-status：

```ts
type ExecutionState =
  | "admitted"
  | "running"
  | "waiting_input"
  | "reported_completed"
  | "reported_failed"
  | "cancel_requested"
  | "reconciling"
  | "cancelled"
  | "observation_lost";

type VerificationProjection =
  | "not_required"
  | "unverified"
  | "pending"
  | "running"
  | "waiting_input"
  | "passed"
  | "failed"
  | "blocked"
  | "stale";

type SettlementState =
  | "pending"
  | "submitted"
  | "accepted"
  | "revision"
  | "blocked"
  | "cancelled";

interface CollaborationTrustProjection {
  execution: ExecutionState;
  verification: VerificationProjection;
  settlement: SettlementState;
}
```

- Execution 由 `DelegationRecord.executionState + ExecutionReceipt` 决定；
- Verification 由当前 Submission/Goal 的有效 `VerificationRecord` 投影；
- Settlement 由 WorkItem/Submission review 事实决定；
- `WorkItem.status` 继续负责 DAG 工作流（planned/ready/in_progress/submitted/...），不是为了兼容旧数据，而是因为计划调度与 Run 生命周期本来就属于不同聚合；
- 前端和 API 返回显式三轴投影，不让消费者从任意一条自然语言消息猜状态。

Execution 状态机为：

```text
admitted → running ↔ waiting_input
running/waiting_input → reported_completed → sealed Receipt
running/waiting_input → reported_failed → sealed Receipt
running/waiting_input → cancel_requested
cancel_requested → cancelled（上游已确认或本地进程退出可观察）
cancel_requested/running/waiting_input → observation_lost（无法确认真实状态）
observation_lost → reconcile → reconciling（正在重挂同一远端 Run）
reconciling → running/waiting_input/reported_*/cancelled
reconciling → observation_lost（重挂流中断或未产生边界）
```

`reconciling` 是活跃控制面状态，不是失败或新 attempt：它保留原 Delegation、Run handle、并发锁与写 scope，直到原 Run 重新产生可观察状态。`reported_completed` 只能显示为“Worker 已报告完成”，不得直接显示“完成”或“验收通过”。

### 9.2 WorkItem 提交、验证与验收

WorkItem 主状态继续使用现有 `submitted`，验证进度从最新 Submission 的 VerificationRecord 投影，不为 `verifying` 额外扩张 WorkItemStatus：

```text
in_progress
  → execution reported_completed + Receipt sealed
submitted + no verification
  → Manager revision/blocked
  → request verification
  → Manager accepted（仅 effectiveMode=manager_review）
submitted + verification running
  → waiting_input / passed / failed / blocked
submitted + verification waiting_input
  → respond/approve → running
submitted + passed
  → Manager accepted
submitted + failed
  → Manager revision
submitted + blocked
  → Manager request Decision / change verifier / retry
```

`review_work_item(verdict:"accepted")` 增加权威 Store 门禁：

```text
1. WorkItem.status == submitted
2. 找到最新未验收 Submission
3. delegation source Submission 绑定 sealed ExecutionReceipt，且 goal/workItem/epoch/`taskContractHash` 仍匹配；manager source 必须满足 §5.3 的只读限制
4. Receipt.integrity != violation，全部必需 evidenceRequirements 已 provided
5. effectiveMode == manager_review
   或存在匹配当前 Submission 的有效复核记录
6. environment_verified 必须是 passed + clean + fingerprint current
7. isolated_worktree 的精确 change-set 已成功提升；冲突或失败不得解锁下游
8. acceptedSubmissionId 只指向通过上述门禁的 Submission
```

Manager 不能通过在 `summary/evidenceRefs` 里声称“已验证”绕过门禁。

### 9.3 时效与失效

这里的 `inputFingerprint` 不是无差别计算整个 workspace 的 hash。它至少覆盖 Goal/WorkPlan/WorkItem/Submission 标识与 revision、`goalEpoch`、冻结的验收标准与验证策略、执行 Delegation 结果身份、Artifact content hash，以及 Environment Profile 声明的受控文件、服务或应用状态范围。构建缓存、日志、临时文件等预期变化必须在 Profile 中声明，不允许靠 Verifier 提示词临时排除。

VerificationRecord 在以下情况直接变为 `stale`：

- `goalRevision/workItemRevision/goalEpoch` 任一不再匹配；
- WorkItem 产生了更新 Submission；
- 对应 Artifact 的 content hash 已变化；
- 在 Manager `accepted` 前，复验声明的受控文件/应用状态 fingerprint 已改变；
- Verifier 运行期间发生不允许的 workspace 写入且未被可证明地隔离。

WorkItem 被 `accepted` 后，它的 VerificationRecord 保留为当时的审计事实，不因后续下游 WorkItem 的合法修改而倒退历史验收。为防止“单项曾经通过，整合后已失效”，`finalGoalMode=environment_verified` 时必须在 Goal `resolved` 前对当前整合环境再执行一次 Goal 级复验。

## 10. Manager Core Tools

新增或扩展的工具都是 PuddingTeams core tools，不属于 Connector Extension：

### 10.1 `create_session_goal` 扩展

```ts
create_session_goal({
  // 现有字段
  verificationPolicy?: {
    minimumWorkItemMode,
    finalGoalMode,
    trigger,
    source,
    reason
  }
})
```

Manager 只能根据明确用户意图派生策略；请求不清晰时仍先询问，不得为了触发复验而滥建 Goal。

### 10.2 `update_work_plan` 扩展

```ts
upsertItems: [{
  // 现有字段
  verificationPolicy: {
    mode,
    trigger,
    source,
    reason
  },
  workspaceExecutionPolicy: {
    mode,
    source,
    reason,
    baselineStrategy,
    promoteOnAcceptance
  }
}]
```

Store 校验 Verification 不得低于 Goal 下限，Workspace policy 与 Verification policy 都按 WorkItem revision 冻结。Harness 必须基于 Workspace 类型和 Driver 能力验证组合可执行，例如非 Git Workspace 不允许声明 `isolated_worktree`。

### 10.3 `request_work_item_verification`

```ts
request_work_item_verification({
  goalId,
  workItemId,
  submissionId,
  expectedRevision,
  verifierAgentId?
})
```

执行时：

1. 确认 Submission 是当前待验收候选；
2. 解析 effective policy 和所需 modality；
3. 解析 Environment Profile，并校验指定 Agent 或 Harness 默认路由的 Driver capabilities；
4. 幂等创建 `VerificationRecord{status:"pending"}` 和 outbox 事件；
5. dispatcher 启动 `purpose:"verification"` 的新 Delegation；
6. 终态原子回写 VerificationRecord，并唤醒同一 Manager Session。

core tool 在平台内部使用 pi `toolCallId` 作为 `operationId`，不让模型自由填写幂等键；重放相同 tool call 不创建第二个 Verifier Run。

### 10.4 `review_work_item` 扩展

不要求 Manager 复制 Verification 正文；Store 自动查找与当前 Submission 绑定的 Receipt、Verification 和 WorkspaceChangeSet。`evidenceRefs` 可引用 `executionReceiptId/verificationId/verifierDelegationId/artifactId`，但引用文本不代替强制门禁。

当策略为 `isolated_worktree` 时，Manager 的 `accepted` verdict 先形成“允许提升”的审计决策，Harness 再应用冻结 change-set；只有提升成功后 Store 才提交最终 `accepted` 并解锁下游。提升冲突或失败转 `blocked`，不得把 Manager 意图伪装成已结算事实。

### 10.5 Goal 完成入口

当 `finalGoalMode=environment_verified` 时，Manager 提交 `status:"resolved"` 不立即完成 Goal，而是幂等开始 Goal 级 Verification：

```text
Manager 完成申请
  → Goal execution.status = reviewing
  → Goal VerificationRecord pending/running
  → passed
  → 现有 manager/independent Completion Review
  → resolved / active / needs_human
```

复验失败时 Goal 保持 `active`，`nextAction` 写入结构化缺口；不通过自然语言“重试一下”直接重放旧外部副作用。

## 11. 调度、恢复与幂等

### 11.1 Driver 对账与取消能力

`DriverCapabilities` 增加可选、可探测的诚实声明：

```ts
interface DriverCapabilities {
  // 现有字段保持
  reconciliation: "none" | "query_run" | "reattach_stream";
  cancelConfirmation: "none" | "acknowledged" | "observable";
}

type ReconciledRun =
  | { state: "running"; sessionHandle?: string; runHandle: string }
  | { state: "needs_input"; result: NeedsInputResult }
  | { state: "completed"; result: CompletedResult }
  | { state: "failed" | "cancelled"; result: FailedResult }
  | { state: "unknown"; reason: string };

interface AgentDriver {
  // 现有 SPI 保持
  reconcileRun?(
    input: { runHandle: string; lastObservedAt?: string },
    ctx: InvocationContext
  ): Promise<ReconciledRun>;
  reattachRun?(
    input: { runHandle: string; afterCursor?: string },
    ctx: InvocationContext
  ): AsyncIterable<AgentEvent>;
}
```

这两个方法是 Runtime/Driver 控制面能力，不新增 Manager 可调用的 PWCP `AgentOperation`。声明 `query_run/reattach_stream` 却未实现相应方法属于 Connector 契约失败；`probe()` 必须报告不可用。

`cancelConfirmation` 语义固定：

- `none`：只能证明取消请求已发出，不能证明远端停止；
- `acknowledged`：上游明确确认该 Run 已接受终止且不会继续产生效果；
- `observable`：Runtime 能通过退出状态、查询或重挂流观察到终态 `cancelled`。

### 11.2 重启对账

启动恢复按 Driver 能力和执行面归属分流：

```text
persisted running/waiting_input/cancel_requested
  ├─ 本地生命周期绑定且进程已确认消失
  │    → reported_failed(server_restart) + sealed Receipt
  ├─ reconciliation=query_run
  │    → query real state → update / seal Receipt / keep running
  ├─ reconciliation=reattach_stream
  │    → reattach from cursor → continue observing same Run
  └─ cannot reconcile
       → observation_lost
       → write/external side effect present: Goal effect_unknown + fenced Lease
```

`observation_lost` 不是失败别名：它表示平台失去观察能力，真实执行结果未知。此时不能生成 completed Submission，不能释放可能仍在生效的写 Lease，也不能自动新建一个会重复副作用的 attempt。用户或 Manager 必须先查询外部状态、恢复 Connector、确认终止，或通过 HITL 接受风险。

### 11.3 取消结算

取消流程先写 `cancel_requested` 和 operation ledger，再调用 Driver：

```text
cancel requested
  → abort local observation / call driver.cancel
  → confirmed by acknowledged/observable capability: cancelled Receipt
  → not confirmed before timeout: observation_lost, not cancelled
```

迟到 completed 若属于同一 goal/epoch/revision 且取消从未得到确认，应作为真实回执进入审计，由 Manager 决定 Submission 去向；如果取消已确认或 epoch 已推进，迟到事件只保留诊断，不得复活 Run、提升 change-set 或覆盖当前 WorkItem。

### 11.4 Operation ledger、Outbox 与重试

Execution、Verification、Workspace promotion 继续使用当前 Goal 聚合的 operation ledger/outbox/epoch 机制：

- 创建 Delegation/复验/提升意图、权威记录与 outbox 采用可重放的稳定 operation identity；
- dispatcher 以 `delegationId/verificationId/changeSetId` 作为稳定调度身份，以 `operationId/idempotencyKey` 向 Driver 尽可能透传；
- boundary 已落盘但 Receipt 未封存时，恢复流程只能从已有 boundary、Artifact 和 change-set 事实补封存，不重新运行 Worker；
- 旧 `goalId/epoch/revision/submissionId` 的迟到回调只保留审计，不得改写当前状态；
- 只有 `read_only_shared` 且无外部副作用的确定性检查允许在未知终态后自动新建 attempt；写入、发布、发送、购买、删除等操作必须先对账；
- 上游不支持幂等时不承诺 exactly-once，Evidence Ledger 必须显示该限制；
- 同一 Submission 最多运行配置的验证尝试数，超过后不自动循环，由 Manager/人类决策。

## 12. 结构化 Verifier 输入输出

### 12.1 输入边界

Verifier 只接收：

- 原始 Goal 和当前冻结条件；
- 当前 WorkItem 的冻结 acceptanceCriteria；
- Submission 的结构化摘要、Delegation result 引用和 Artifact 引用；
- 已验收上游 WorkItem 的有界状态与必要证据引用；
- 受控 workspace/应用目标和 Verification Environment Profile；
- 人类已授权的有界范围。

不接收：

- Manager 的隐藏推理；
- Executor 的完整 prompt 和未筛选 trajectory；
- 其他 Room/Goal 的上下文；
- Harness 运行目录作为任务交付证据。

### 12.2 输出契约

Verifier Worker 可以返回自然语言作为诊断正文，但 Harness 不从自由文本猜完成状态。首期应为 Verifier 注入受控结构化输出契约，并由隔离 parser/reviewer 校验：

```json
{
  "verdict": "passed | failed | blocked",
  "integrity": "clean | suspect | violation",
  "criteria": [
    {
      "criterion": "原文验收条件",
      "status": "satisfied | unsatisfied | uncertain",
      "evidenceRefs": ["artifact-or-observation-id"],
      "explanation": "观测事实"
    }
  ],
  "observations": [
    {
      "kind": "command | file | gui | service | external_read",
      "target": "受控目标",
      "result": "有界摘要",
      "evidenceRefs": ["..."]
    }
  ],
  "gaps": ["..."]
}
```

对不能原生返回结构化数据的 Connector，可以用一次无工具 format-repair 将已有 Verifier 文本转为该结构；format-repair 不得重新运行工具、补充新观测或改变环境。无法从已有内容得出时保守转 `blocked`。

## 13. 工作类型与默认路由

| 工作类型 | 执行 Workspace | 建议 Verification | 默认验收环境 | 典型观测 |
|---|---|---|---|---|
| 方案讨论、任务拆解 | `read_only_shared` | `manager_review` | 无 | 契约覆盖、下游可用性 |
| 调研、引用、数据核对 | `read_only_shared` | `independent_evidence_review` | 隔离无工具或只读网络 | 来源存在性、数值/引用一致性 |
| 代码、修复、测试、构建 | `isolated_worktree` | `environment_verified` | execution worktree / `isolated_copy` | diff、文件、test/typecheck/build |
| 网页代码与交互 | `isolated_worktree` | `environment_verified` | worktree 服务 + 受控浏览器 | 页面打开、交互、视觉截图 |
| GUI/桌面目标修改 | `exclusive_write` | `environment_verified` | `same_target_guarded` | 应用状态、截图、前后指纹 |
| 文档、演示、表格 | 优先 `isolated_worktree`，否则 `exclusive_write` | `environment_verified` | 优先隔离渲染 | 可打开性、布局、公式/格式 |
| 服务、配置、健康检查 | `exclusive_write` | `environment_verified` | `same_target_guarded` | 进程、日志、健康接口 |
| 发布、购买、删除、授权 | `exclusive_write` + HITL | `environment_verified` + HITL | 原环境只读复查 | 外部真实状态，不代替人类授权 |
| 主观满意度 | 依任务决定 | `needs_human` | 不由 Verifier 代替 | 请求用户决策 |

这张表是 Manager 路由和默认配置材料，不应用隐藏关键词分类器直接改写用户契约。

## 14. UI 与可观测性

### 14.1 设置页

新增页面区域：

```text
Harness
  └─ 可证明协作与验收
      ├─ Workspace 只读/隔离写/独占写默认策略
      ├─ Lease、change-set 提升和冲突策略
      ├─ 默认 WorkItem 验收等级
      ├─ Goal 最终复验等级
      ├─ Evidence Reviewer 模型
      ├─ CLI / GUI Verifier Worker 路由
      ├─ 环境 Profile
      ├─ 隔离要求
      ├─ 超时和尝试上限
      └─ 无可用 Verifier 时的处理
```

### 14.2 目标与执行抽屉

每个 WorkItem 展示：

- Execution / Verification / Settlement 三轴状态；
- 当前执行 Receipt 的 contract hash、证据收集完整性和 issues；
- Workspace access mode、Lease/worktree、baseline/write-set/change-set 与提升状态；
- 有效 verification mode、来源、理由和冻结 revision；
- 最新 Submission 及其 Verification 状态；
- Verifier Worker、环境 Profile、开始/完成时间；
- 逐项验收条件、观测结果和 evidenceRef；
- 失败/阻塞/过期原因；
- 进入现有 verifier Delegation timeline 的详情入口。

`observation_lost/effect_unknown` 必须作为高优先级阻塞状态展示，并给出“重新对账 / 确认外部状态 / 人工接管”的明确动作；不能退化成普通红色失败后直接出现“重试”。Leader progress 和房间摘要从 WorkPlan、Receipt、Verification、Settlement 与 Decision 自动投影，Manager 自由文本只作为补充说明。

`pudding:verification_update` 如果新增，只是 `display:false` UI 刷新投影，不是权威事实源；Harness 必须回读 `state/work-states.json`。若实现该 customType，必须同步 `docs/2026-08-14-会话记录格式与Harness消费.md` 和前后端渲染契约。

### 14.3 语义标签

前端必须区分：

- `Worker reported completed`：上游报告 Run 已结束；
- `Receipt sealed`：Runtime 已封装报告与证据收集结果；
- `Submitted`：候选交付已落盘；
- `Verified`：当前 Submission 已经指定方式复验；
- `Accepted`：Manager 已接受该 Submission；
- `Goal completed`：当前 Goal 契约经最终门禁完成。

不得把 `reported_completed` 显示成“已完成”或“已验收”。

## 15. 安全与副作用

### 15.1 Verifier 默认只观测

- 原 workspace 的源文件和用户交付不允许修改；
- 可写范围限于独立临时目录、明确的构建目录或隔离副本；
- test/build 可能产生缓存，Profile 必须明确允许路径或使用隔离副本；
- GUI 导航也可能改变应用状态，只有契约明确要求且无不可逆副作用的交互才可自动执行；
- 外部写入、账号权限、购买、发布、删除、发送等动作不会因“验收”角色而绕过 Interaction/HITL。

### 15.2 运行记录不是自动证据

Delegation timeline、prompt、reasoning、Dashboard 截图和角色输出是可观测记录，不自动成为验收证据。只有 Verifier 按契约明确登记、平台确认存在且属于当前 Goal/Submission 的 observation/Artifact 才可进入 `evidenceRefs`。

ExecutionReceipt 也不是 Verification：它证明平台收到了哪条声明、机械捕获了哪些文件/事件、哪些证据缺失，不证明 Worker 声明为真。任何 `verified/passed/accepted` 字段都只能由对应的 Verification/Settlement 权威入口写入。

### 15.3 Workspace 与外部副作用

- `read_only_shared` 必须由 Driver 强制只读；只有 mutation guard 时不能进入用户目标 Workspace，guard 只用于发现 Connector/沙箱契约被突破并标记 violation；
- worktree、隔离副本和临时构建目录必须位于平台受控目录，路径与原 Workspace 的映射进入 Receipt；
- 独占 Lease 只解决 PuddingTeams 内部并发，不等于 OS 级文件锁，也不能阻止用户或外部进程修改；因此仍需 fingerprint 新鲜度判断；
- Artifact/content hash、diff hash、workspace fingerprint 都是完整性材料，不等于语义正确；
- 外部系统副作用结果未知时保持 `effect_unknown`，禁止以“再执行一次”代替对账。

## 16. 不做什么

- 不把所有普通聊天自动升级为 Goal；
- 不为无 WorkPlan 的 Goal 伪造 WorkItem；
- 不把 Verifier 做成绕过 Manager 的第二个完成权威；
- 不把 `verify` 增加为所有 Agent 必须实现的 PWCP operation；
- 不把 WorkPlan/验证编排下放到 Connector 的 pi Extension 门面；
- 不允许 Driver、Worker 或 Connector 自行把 Receipt 标记为 verified/accepted；
- 不把 Evidence Ledger 做成模型可自由写入的第二事实源；
- 不仅靠 prompt 宣称 Verifier 只读；
- 不默认给 Verifier 完整电脑控制权；
- 不对含数据库、服务和外部系统副作用的 workspace 执行粗暴全局回滚；
- 不用旧 WorkItem/Goal revision 的复验记录满足当前契约；
- 不让过期或无法定位的 evidenceRef 只因 ID 存在就通过门禁。
- 不让两个写任务在同一 Workspace 无 Lease 并发执行；
- 不在 `observation_lost/effect_unknown` 未对账时自动重试可能产生副作用的 Run；
- 不在 change-set 提升冲突时自动覆盖用户或其他 Worker 的修改；
- 不为实现新协议保留旧 `completed=可信完成` 的兼容映射；项目未上线，字段与投影直接切换。

## 18. 验收标准

### 18.1 领域状态

- 每个终态 Delegation 都生成 sealed ExecutionReceipt；failed/cancelled Receipt 不生成 Submission；
- 绑定 WorkItem 的 execution Delegation `reported_completed` 必然通过 Receipt 幂等生成一个可审计 Submission，Manager 无法隐藏该事实；
- Receipt 中 Worker 声明、Runtime 机械捕获、缺失 evidence requirement 和 Artifact capture issue 可区分；
- Receipt 为 `partial/failed` 时 UI 不显示“证据完整”，必需证据缺失时 Store 拒绝 accepted；
- Verification Delegation 不会生成 Submission；
- `environment_verified` WorkItem 无当前 `passed + clean` VerificationRecord 时无法 `accepted`；
- 旧 revision/epoch/submission 的 VerificationRecord 不能通过当前门禁；
- API/UI 对同一 WorkItem 同时返回 Execution / Verification / Settlement 三轴，不从单个 status 推测跨层结论；
- WorkItem accepted 仍不直接使 Goal resolved；
- 无 Goal 的普通 Run 不伪造 WorkItem/Submission/Verification。

### 18.2 环境与权限

- 只读共享 Run 的受控写入被 Driver 强制阻止；不具备强制能力的 Connector 被路由到隔离环境或在 admission 阶段阻塞；
- 两个写任务不能在同一目标 Workspace 无 Lease 并发运行；
- Git 写任务的 worktree、baseline、write-set、diff hash 和 change-set 都绑定唯一 execution scope；每个 Delegation Receipt 保留本 Run 增量；
- `isolated_worktree` 的 Submission 在 change-set 成功提升前不能 accepted，提升冲突不能解锁下游；
- 非 Git `exclusive_write` Run 记录前后 fingerprint，不把其他并发/外部修改归到自身 Receipt；
- Verifier 每次使用新 Session，不能继续 Executor Session；
- 复验 workspace/cwd 由平台绑定，不接受 Manager 通过 prompt 替换目标路径；
- Environment Profile 的 source binding、execution root、Workspace 边界、mutation policy 和实际网络口径可审计；首期只承诺 Workspace 隔离/变更守卫，不承诺平台级网络隔离；
- Driver 没有声明所需隔离/观测能力时不能被选为强制 Verifier；
- Verifier 越权改写受保护 workspace 时验证不通过，不从它创建的文件推导交付完成；
- 无可用 Verifier 时保持阻塞，不静默降级。

### 18.3 恢复与幂等

- boundary 已持久化但 Artifact/Receipt 收集崩溃时，恢复只补封存 partial Receipt，不重复运行 Worker；
- 同一 `request_work_item_verification` tool call 被重放时，不创建多个 Run；
- 本地生命周期绑定 Run 重启后按可观察事实失败；可对账远端 Run 查询/重挂原 Run；不可对账远端 Run 进入 observation_lost；
- cancel 未得到上游确认时保持 cancel_requested/observation_lost，不伪装为 cancelled；
- effect_unknown 的写任务在对账前不能自动重试，也不能释放冲突写 Lease；
- 旧 Goal/epoch 迟到终态不能覆盖当前记录；
- 旧 epoch 的 change-set 不能提升到当前 Workspace；
- Manager 收到复验终态后能在同一 Session 继续 accept/revision/Decision；
- 超过验证尝试上限后转人类/管理决策，不无界循环。

### 18.4 必测故障矩阵

- Worker 已产生外部副作用，但 completed boundary 丢失；
- 两个 Worker 同时请求修改同一文件；
- dirty Git Workspace 建立 worktree 时，staged/unstaged/untracked baseline 不得丢失或误归为 Worker 改动；
- 同一 WorkItem 的 followup/revision 继续旧 Worker Session 时，execution cwd 与 scope 不得漂移；
- Worker 声称测试通过，但 Receipt 没有对应命令/Artifact evidence；
- Worker 声明 Artifact，实际登记时文件缺失、越界或 hash 失败；
- server 在 boundary 落盘与 Receipt 封存之间退出；
- cancel 请求已发出，但远端继续运行并迟到 completed；
- verification passed 后、Manager accepted 前受控文件变化；
- worktree 验证通过，但提升时目标分支产生冲突；
- 旧 epoch 的迟到 completed/verification/promotion 试图污染新 attempt；
- Verifier 越权修改受保护 Workspace 后仍输出 passed。

### 21.2 已完成能力

1. `ExecutionState` 取代模糊 status；`reconciling` 显式表示正在重挂同一远端 Run，仍属于活跃执行并保留锁/scope。终态必须与 immutable sealed ExecutionReceipt 同次 Delegation 改写提交。跨 Store 收集前先落 `pendingTerminal` journal，重启只恢复同一边界的 Receipt/Artifact/change-set 收集，不重跑 Worker。
2. Receipt 区分 Worker 报告、Runtime requirement disposition、Artifact capture 与 Workspace integrity，并分别保存 Harness 业务契约 `taskContractHash` 和 Runtime 执行信封 `contractHash`；WorkItem 验收只比较前者。Artifact 缺失/越界/失败形成 `partial/failed` 和 issue，必需证据门禁 fail closed。
3. WorkItem/Goal 使用独立 VerificationPolicy/VerificationRecord；同一 verification tool call 重放直接返回已有记录，不创建重复 Verifier Run。Goal minimum mode 与 trigger 会冻结进新 WorkItem。
4. `environment_verified` 必须使用平台签发并绑定 verificationId 的环境，Driver 收到 `VerificationInvocationProfile`；fresh Session、source binding、mutation policy、可写范围和平台隔离方式可审计。首期只接受平台能直接绑定 cwd 的本地 spawn/sdk Driver，HTTP/RPC/ACP 在没有可校验环境回执前于创建 Delegation 之前 fail closed。
5. 每条 satisfied criterion 必须绑定本次 Verifier 时间线产生的不可伪造 tool/file/search observation ref；只引用 Submission/Receipt/Delegation ID 或空运行输出 passed 会被改判 failed。
6. Git 写任务使用包含 staged/unstaged/untracked 脏基线的独立 worktree；非 Git 写任务使用持久 exclusive Lease；只读共享要求 Driver 强制只读，否则隔离或阻塞。
7. change-set 提升使用目标 Workspace promotion lock、逐路径基线复核、原文件原子移出和排他创建；检查窗口内发生外部修改时转 conflict、fence scope、保留执行环境，不自动 commit/push。
8. 启动恢复按执行所有权区分本地/远端：本地确认消失封存 server_restart Receipt；远端 query/reattach 原 Run；重挂期间的 running/needs_input/terminal 与无边界流均回写 WorkState，不可确认转 observation_lost/effect_unknown，并恢复持久并发锁、Interaction 与 revision。
9. cancel 只有收到 acknowledged 或观察到本地进程真实退出才结算 cancelled；远端 observable 未见终态时进入 observation_lost，不伪造成功取消。
10. Web 提供真实“重新对账原 Run”和“确认上游已终止后人工接管”动作。后者要求显式 confirmation 与至少 8 字依据，才封存 cancelled Receipt、释放 fenced Lease；不会把人工接管伪装成 Worker 自报完成。
11. Harness 设置页承载 D1–D15：可变策略可编辑；安全固定项显示为禁用字段，服务端也强制固定，不能只靠前端。Git 默认、Verifier、trigger 和 lease 改动会影响之后创建的 Goal/WorkItem，不追改已冻结记录。
12. 执行动态、Goal 抽屉和 Worker 过程统一展示 Execution / Verification / Settlement 三轴；WorkItem 审核详情展示 Receipt、requirement/artifact 数量与 issue、冻结策略、Workspace mode/change-set/promotion、Verifier/Profile、平台 observation 和逐项结论。
