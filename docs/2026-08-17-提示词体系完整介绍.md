# PuddingTeams 提示词体系完整介绍

## 2026-10-15 P4：普通会话与只读执行记录

普通聊天只使用 `windows.json` v3 的 `sessions[]`、`activeSession` 与 `sessionRefs`。不再投影执行会话列表，不保留执行面查看指针；同版本文件若仍含已移除的执行面指针，校验明确拒绝，不转换或静默删除。历史 v1/v2 也不自动迁移。

Goal 创建同步收口（2026-10-15）：`manager_explicit` 模式删除，Goal 只能由用户通过 `/goal` 或界面显式创建（`user_explicit`），或整体 `disabled`；Manager 工具面不再包含 `create_session_goal` / `supersede_session_goal`，`goalActivation.confirmWhenAmbiguous` 一并移除。

委派只通过 `delegation` 工具发起一次 fresh 调用；`delegationId` 标识执行，`managerToolCallId` 关联真实 Pi toolCall。Driver 的 active registry、Interaction、Receipt、ChangeSet 与追加式 timeline 保留。Pi 执行回放位于 `worker-process-session.ts`，仅供 `/api/delegations/:id/process/*` 使用。普通会话端点不能向执行 handle 发送消息、切换、重命名或删除。

执行索引以台账的来源 `managerSessionId` 为准，拒绝从其他聊天的镜像卡推导归属；全局 `/api/delegation-records` 可按 `sourceSessionId/workerId/workspaceId/goalId` 过滤。全局搜索把原生会话与执行记录分开，执行结果打开只读详情，保留精确单次 cancel。

Manager 和 Pi Worker 使用同一原生会话机制，模型/思考设置作用于当前 Session 的 owner；忙碌输入仅以服务端 capability 开放。Pi 单聊写真实 user/assistant/toolResult JSONL，不写容器直派卡。非 Pi Connector 继续使用 Driver 单聊适配，其 `pudding:user_message/task_assign/task_result` 和内部续接绑定仍有实际用途；它们不把 Manager delegation 变成连续聊天，也不开放原生 followUp/steer/Fork。Pi 原生 provider 连续性已由 `sessionRefs[sessionId].provider` 承载。

平台 Worker 输入队列模块、启动装配、GET/DELETE 队列端点和灰态排队气泡已删除。`GET /api/diagnostics/legacy-data` 只返回旧队列文件的路径、大小与时间，不解析输入、不补投、不删除；用户数据清理是独立明确操作。Fork、SDK followUp/steer 及其未知消费回执沿用 P3 契约。


## 2026-10-15：Manager 即知识整理负责人（去委派化）

Manager 在自己会话直接承担知识查询、查重、整理与修订，不再委派 Wiki 管家（内置 Wiki Worker 保留，仅服务 Wiki 单聊、后台整理与稍后读晋升）。KnowledgeRuntime 为 Manager 注册完整知识工具面：`knowledge_curation_status` 与 `knowledge_update_interaction_status` 保持直接可用；其余 `knowledge_*`（context/search/glob/read/links、候选准备/提交、稍后读）以 `exposure:"deferred"` 注册，不进默认工具声明，由 pi SDK 原生 `createToolSearchExtension()` 提供 `tool_search`，Manager 按任务关键词搜索后声明，声明在会话分支上持久（重启/空闲重建时由平台从 transcript system 消息的 `toolsAdded`/`toolsRemoved` 增量回放恢复，见接入方案 §3.3 激活态回放）。日历（calendar_*）与联网（web_search/fetch_url）工具在 Manager 原生会话同样以 deferred 注册、经 tool_search 声明；Worker 委派执行的日历与 Worker 联网保持 direct。Manager prompt 追加获准库的名称/用途/bindingId、tool_search 引导、直接整理与回执纪律（`managerCuratorGuidance`）。候选准备沿当前 Manager 会话的 intake/userEntry 解析来源，不再走 Delegation 的 `managerSessionId`/`managerToolCallId`。知识 profile fingerprint 为 `manager-curator-v1`（取代 `manager-delegation-v1`），旧会话重建当前运行面并保留历史。权限边界不变：provider stream fence、轮中撤权即抛错、submit 校验与人审 Publisher 均由宿主执行，deferred 只控制声明时机、不放宽授权。

## 2026-10-14 P3：原生 Worker 对话与快照

Manager 继续使用 Pi 1.2.0 SDK，增加 delegation/Goal；Pi Worker 单聊也使用原生 SDK，但按持久负责人装配自己的指令、模型、工具、MCP 白名单、Capability 和知识授权。单聊只有一份可发送的 Session，不创建委派来承载每条输入，不获得 Manager delegation/Goal/日历控制。内置 Wiki 保持受限知识工具面，使用既有 prepare/submit 候选管线，提交即停并等待审核；任意原生写工具、扩展、MCP 与 Workspace 指令不进入它。普通 Worker 保持知识读取、默认 memory 待审核请求和已授权能力。全新会话在 Window 负责人落盘后注册知识工具；真实用户 JSONL 与素材绑定在 provider 发送前完成，SDK Skill/模板展开只改变执行文本，不改原始素材。其他 Connector 本阶段仍用既有直派通道，不宣称支持原生忙碌输入或快照。

`windows.json` v3 在同一次原子写中保存 `windows` 和 `sessionRefs[sessionId]={sessionId,ownerAgentId,createdAt,sourceSnapshotId?,provider?}`；`sessions[]` 保留成员 ID 索引。provider 对 Pi 原生会话记录 `driverId:"pi-native"`、负责人配置修订和 SDK sessionId。打开时按 ownerAgentId 装配；成员数量不改变负责人。一个 Worker/Workspace 保持一个 direct Window，里面可以有多段原生对话。旧 v1/v2 开发状态显式拒绝，不迁移、不删除；缺负责人记录拒绝，已删除或停用负责人保留只读历史。

Pi Manager/Worker 运行中缺省 followUp、显式 steer；空闲时正常启动，返回真实 delivery。HITL 等待独立于 running，追加走 followUp 入队、不启动 run、不提交卡片。返回 disposition=started/queued/handled 与 persistence=durable/pending/not_applicable；queued 202 只承诺 SDK 受理，不等于模型已消费。原操作键重试不再次入队；正文/附件/delivery 改变冲突。SDK 不携带输入 operationId；同文案多次、展开改写等无法唯一关联时保持未知，不能伪造精确消费身份。回执不保存自动重放正文，不新增平台 FIFO。待消费 SDK 队列或未终结回执阻止淘汰、重建、模型/思考切换、项目切换和 fork；Stop 清队列并标记 cancelled_unconfirmed，附件保留。确定的 compaction 拒绝返回 session_compacting，允许原键原消息再受理；不确定错误不自动重发。

Fork 冻结当前已提交分支，由 `ConversationSnapshots` 保存不可变 manifest 与独立资产；hash 使用递归排序键的 JSON，覆盖版本、创建时间、来源、分支、cwd、transcript 和资产清单，读时核验文件 bytes/hash。保留配对完整的历史工具消息、compaction 和展示卡；排除 Manager 指令、roster、配置、审批权限与运行控制，Goal 仅保留历史文字投影。委派内部 trace 不混入。平台外置结果改为快照中的文件引用，目标用 read 读取；不继承 read_delegation_result 权限。

目标必须在当前有效范围，且会话提供方明确支持格式1。本阶段只有 native Pi provider 声明导入能力，委派 Driver 不声明；不以 Connector 名字推测其他 Driver 能力。目标 SDK 重新编写 entryId、消息传输 ID 和 compaction 引用，使用自己的模型/思考设置；不调用会复制控制记录的 SDK forkFrom，不触发 prompt、不复制活动 Goal、不重放工具。预算为 UTF-8 serialized entries 的保守上界：min(2MB, 已配置模型 contextWindow/2)，模型未配置时64KB；预算超限显式拒绝，不静默摘要。单资产64MB、总资产128MB。

一个 `fork-operations.json` v1 账本预约 snapshotId/sessionId，依次 reserved→snapshot_saved→session_saved→attached。快照 hash、导入标记和窗口唯一性负责冷恢复；同键相同意图返回同一目标，改来源/Worker/leaf 冲突。快照完成后源删除可继续；目标删除成为 gone，不重建。冻结前需当前 leaf、不忙碌、不等待、不含待确认输入且执行证据已封存；恢复也校验这些事实。UI 仅在原生对话菜单提供 Fork，显示来源快照；未确认时保留原键，仅服务器确认尚无操作后允许用户重新选择。

本节描述已实现的 Pi 原生会话与快照契约；P4 的入口清理见上文。


> 核心委派使用统一 `delegation({workerId, task, contextRefs?, parentDelegationId?, ...Goal字段})`。每次 fresh，因果不导入历史，审批与结果只回 owner；operationId/requestHash 保证同键同意图去重。

## 1. 全景：一个 Agent 的提示词由哪些层构成

以普通 pi 系 Agent（Manager / pi Worker）的一次模型请求为例，system prompt 按以下顺序装配；内置 Wiki 管理员的受限例外见 §5.4：

| 顺序 | 层 | 内容来源 | 谁会有 | 编辑入口 |
| --- | --- | --- | --- | --- |
| 1 | pi base | pi 内嵌默认系统提示词，或 SYSTEM.md 覆盖 | 所有 pi 会话 | 文件（见 §2） |
| 2 | pi 原生追加 | APPEND_SYSTEM.md | 所有 pi 会话 | 文件（见 §2） |
| 3 | Agent 运行指令 | `piResources.systemPrompt`（agents.json） | pi 系 Agent 各自独立 | Web 配置页 → 提示词 |
| 4 | Window 协作提示词 | 窗口 collaboration（内置或 window.prompt 覆盖） | 仅 Manager 会话 | 聊天信息（群聊） |
| 5 | Manager roster | worker 描述 / 责任边界 / 工具清单，每轮现拼 | 仅 Manager 会话 | Web 概览页 |
| 6 | Goal 工作上下文 | WorkStateStore 当前状态，context hook 注入 | 仅 Manager 的 Goal 会话 | 仅用户 `/goal`/UI 显式创建（2026-10-15 起 Manager 无创建工具） |
| 7 | Goal 执行计划 | 未完成 WorkItem、dependsOn、提交/验收状态和活动 Delegation 引用 | 有活动 WorkPlan 的 solo/group Goal Manager 会话 | Manager core tools；用户从 Goal 会话顶部“目标与执行”查看 |
| — | 上下文文件 | AGENTS.md / CLAUDE.md（global + 目录层级） | 所有 pi 会话 | 文件 + 开关（见 §2、§4） |

Skills 和 Prompt Templates **不在 system prompt 正文里**：skills 渐进式披露（匹配任务后读取），也可由用户通过 `/skill:<name> [任务参数]` 显式调用；`disable-model-invocation: true` 的 Skill 不暴露给模型，只保留这一手动入口。templates 由 / 命令调起。Web 输入框的 `/` 菜单从当前 Session/Direct worker 的真实启用范围读取 Skill 命令，不展示未启用资源。它们是"资源"，不是提示词层。

MCP 同样不是提示词层。平台默认装配 `pi-mcp-adapter`，但 `mcp` 代理工具背后的 Server 集合只来自当前 Pi Agent 的 `mcpServerIds` 白名单；Server 全集在“扩展 → MCP”维护，Agent 在自身独立“MCP”分区勾选。外部 Pi 全局配置中发现的 `pi-mcp-adapter` 会被过滤，不能把未选择的 Server 带入会话。

## 2. pi 原生文件约定（SDK 0.83，DefaultResourceLoader）

普通 pi 会话使用以下四类文件的原生发现逻辑；受限 Wiki 会话关闭发现，由宿主显式读取操作契约（§5.4）：

| 文件 | 查找顺序 | 作用 |
| --- | --- | --- |
| `SYSTEM.md` | 项目 `<cwd>/.pi/SYSTEM.md`（项目被 pi 信任时）→ 全局 `~/.pi/agent/SYSTEM.md` | **整体替换** pi 内嵌默认提示词。二选一，不叠加 |
| `APPEND_SYSTEM.md` | 项目 `<cwd>/.pi/APPEND_SYSTEM.md`（信任时）→ 全局 `~/.pi/agent/APPEND_SYSTEM.md` | **追加**在 base 之后。二选一，不叠加 |
| `AGENTS.md` / `CLAUDE.md`（大小写不敏感） | 全局 `~/.pi/agent/` 一份 + 从 cwd 向根逐级目录各取一份（祖先在前） | 上下文文件，作为 context 注入，不进正文拼接 |
| skills / prompts 目录 | `~/.pi/agent/skills`、`~/.pi/agent/prompts` + `<cwd>/.pi/skills`、`<cwd>/.pi/prompts` | 资源库 |

注意：

- **pi 没有 `APPEND_AGENTS.md` 这个约定**（0.83 源码确认不存在），不要引用它。
- 项目级 SYSTEM.md / APPEND_SYSTEM.md 需要 pi 自己的 project trust 才生效；PuddingTeams 的 Workspace 信任门是另一道（§4），两道独立。
- 编辑入口就是直接编辑这些文件；改动在下一个新装配上生效。
- Web 的 Skills / Prompt templates 资源库读取失败时，列表状态是未知，不等于库为空；配置页应保留错误和重试入口，恢复前不展示旧列表供选用。额外来源预览失败也不能解释为“没有始终启用的资源”。新建、导入、编辑或删除后的回读只接受最新请求，避免迟到的旧列表覆盖当前状态。

## 3. PuddingTeams 的注入方式：append-only

代码：`apps/server/src/pi-bridge/pi-resources.ts`（`appendPiPrompts` / `piResourceLoaderOptions`）。

核心原则：**不走 `systemPromptOverride`**——override 返回非空会形成 customPrompt，让 pi 跳过内嵌默认提示词。我们用 `appendSystemPromptOverride` 在 pi 原生 append 列表（含 APPEND_SYSTEM.md）之后继续追加：

```
pi base → pi 原生 APPEND_SYSTEM.md → Agent 运行指令 → Window collaboration
```

- **Agent 运行指令**（层 3）：`piResources.systemPrompt`，每个 pi 系 Agent 独立，追加到该 Agent 自己的 system prompt。编辑入口：Web 配置页 → 提示词分区「运行指令」。Connector worker 没有这一栏（见 §5）。
- **Window collaboration**（层 4）：仅 Manager 会话。solo 窗口用内置固定文案；group 窗口可用 window.prompt 覆盖（在聊天信息里管理）。

生效时机：Manager 会话的 `before_agent_start` hook 每次 run 开始前重读 agents.json 重新装配（`agent-extensions.ts`），**保存即下轮生效，不用重启**。roster 同理。Goal 工作上下文（层 6）与 WorkPlan（层 7）走 `context` hook，每个模型请求前注入、`display: false` 不落盘——因为 sendCustomMessage 触发的续接轮不发 before_agent_start，只有 context hook 能覆盖所有轮次。WorkPlan 位于 Goal WorkState 之后，只投影未完成项和稳定引用，不复制 Timeline 或超长 worker 结果。

`create_session_goal` 与 `supersede_session_goal` 已于 2026-10-15 删除：Goal 只能由用户通过 `/goal` 或界面显式创建（`user_explicit`），或按 Harness `goalActivation` 整体 `disabled`，Manager 工具面没有任何 Goal 创建/更换入口。`update_session_work_state`、Decision、WorkPlan、`abandon_session_goal` 仍常驻暴露——Provider 会在一次模型请求开始时冻结可调用工具 schema，常驻是可靠性的前提，执行时仍校验当前 durable Goal。用户创建成功后，下一请求的 context hook 即注入完整层 6/7。无 Goal 注入只告知 Manager 当前没有进行中的 Goal：认为任务需要持续追踪时用自然语言建议用户创建，不调用任何 Goal 工具，也不主动提及 Goal 机制；`disabled` 时界面创建同样被服务端拒绝。

已有 active Goal 时，每轮仍先按用户意图路由：相关追问、补充或约束变更继续当前 Goal；无关的一次性问答作为普通会话回答，不得改写 Goal；用户明确“不干了”时调用 `abandon_session_goal`；用户提出的新持续任务明确取代旧目标时，Manager 说明新 Goal 需用户通过 `/goal`/UI 创建（2026-10-15 起 Manager 不再有 `supersede_session_goal`），不能把新任务绑定进旧 WorkPlan。同一 Session 仍同时最多一个 active Goal。待人工反馈门禁不阻止 abandon 这个收敛工具，否则 pending 卡本身会重新制造死端。

Manager 遇到 Teams 准入、Worker 原生 HITL 或业务决策卡时，roster 与委托结果明确要求沿原卡片等待；`context` hook 额外投影当前持久化等待项（沿用临时 `pudding:work_state_context`，不新增落盘类型）。这些提示不承担执行门禁：宿主在工具批次落盘后停止 Manager 本轮，工具 hook 与核心写入口拒绝等待期间继续推进。Runtime 的 `waiting_admission` / `waiting_input` 和原 Run 保留，卡片回答后沿既有闭环恢复。

## 4. 上下文文件开关与信任门

「加载项目上下文（AGENTS.md / CLAUDE.md）」开关（`piResources.loadWorkspaceContext`）：

- 关闭时用 `agentsFilesOverride` 只剔除显式 Workspace 及目录层级的文件，**保留** `~/.pi/agent/AGENTS.md`（pi global 上下文不受开关影响）；
- 生效需要两道都开：Agent 自己的开关 **且** Workspace 信任门放行（`workspaceAccess.context`，未信任/被拒绝的项目不注入）；
- skills / prompts 同理（`loadWorkspaceSkills` / `loadWorkspacePrompts` 与信任门取与）。

编辑入口：Web 配置页 → 提示词分区的开关；项目信任在聊天窗口的 Workspace 绑定处管理。

## 5. 责任边界与路由材料（给 Manager 看的，不是 Worker 的提示词）

Worker 的「描述」「责任边界」**不进 Worker 自己的 prompt**，是 Manager 的路由输入。注入方式：Manager 每次 run 开始前由 `before_agent_start` hook 拼 roster 段追加（`agent-extensions.ts:243` `rosterPromptSection`）。

字段去向：

| 概览页字段 | 注入位置 |
| --- | --- |
| 描述 | roster 行首 + delegate 工具 description |
| 责任领域 / 负责范围 / 明确不负责 / 升级条件 | roster 行尾（空的不显示）+ delegate 工具 description（领域/负责/不负责） |
| 身份定位 | roster 行首括号注（`- 名（身份）：描述…`）+ delegate 工具 description 行首 |
| capabilities 标签 | roster 的「｜能力：」段；种子已清空，前端暂无编辑入口 |

边界规则（2026-08-28 更新，方案文档 §9.1）：Connector 包不预置 Manager 路由材料。首装 `DEFAULT_TEAMS` 仅为用户指定的 Designer、Claude Code、Codex 种子保留基线名称/描述，不携带开发机的 model、provider、skills、密钥或登录态；首装后 `agents.json` 仍是唯一事实源，用户可在前台继续修改。

编辑入口：Web 配置页 → 概览分区。Manager 自身没有责任边界（那是写给 Manager 看的，Manager 用不到），Manager 概览页不渲染该卡片。

### 5.1 delegation 工具输入与因果

Manager 只注册统一 `delegation` 工具，workerId 参数由当前 eligibleWorkers 校验。task 是实际发送的材料；contextRefs 是显式引用；parentDelegationId/handoffKind 仅记录同一来源会话内因果。每次 fresh，不提供 session/new/continue 业务参数。审批通过原调用的 respond 恢复。

工具结果包含 delegationId 和本轮结果；超长正文统一外置，Manager 可按受权分页回读。下游材料由 Manager 明确传入，不自动共享 Worker A 的私有历史。需要持续聊天时用原生单聊或 Fork。


### 5.2 Manager WorkPlan 不是 Worker Todo（已实现）

完整设计见 `2026-08-21-Manager-WorkPlan与Delegation-Timeline融合方案.md`。solo/group Goal 中，Manager 通过 PuddingTeams core tools 显式维护 Goal 内的 WorkPlan/WorkItem；平台在每次模型请求前投影未完成项、`dependsOn`、最近 Submission/验收状态和 `activeDelegationId`。direct Goal 无 Manager WorkPlan context，只注入现有 Goal context。约束如下：

- Worker 私有 Todo 不进入 Manager WorkPlan；Connector 若把 todo 公开为 `WorkerActivity`，也只在某次 Delegation 的只读 Timeline 中展示；
- WorkItem 验收条件由 Manager 从冻结 Goal 契约与该步骤预期产物派生，不得暗中扩张 Goal；
- Goal context 以 `{index, criterion}` 数组展示冻结条件；`update_work_plan` 只接收从 1 开始的 `sourceGoalCriterionIndexes`，内部稳定 ID 由 core tool 映射，模型不得手抄 `goal:*` 引用；
- `Delegation.executionState=reported_completed` 只表示 Worker 已报告完成；Runtime 封存 ExecutionReceipt 后才可形成 Submission，Manager 仍必须根据 WorkItem 验收条件和复验门禁明确 accept/revision/blocked；人类不默认逐项验收 WorkItem；
- Goal 状态写工具必须严格串行，每次拿到新的 revision 后才能发起下一次写入，禁止并行提交多个携带同一 revision 的变更；revision 只能取自当前权威 context 或上一写工具的成功结果，遇到 stale 冲突禁止推算、递增猜测或复用委托开始前的 revision；
- `review_work_item` 必须原样回传 context 中的 `expectedEpoch + expectedWorkItemRevision + expectedSubmissionId`。Store 只在这组验收目标及冻结契约完全未变时容忍无关的 Goal 全局 revision 推进并安全 rebase；Submission、WorkItem 契约、Goal contract 或 epoch 变化时必须重新阅读后验收，不能自动沿用旧 verdict；
- `assignedAgentId=manager` 的工作项必须调用 `advance_manager_work_item` 记录开始与正式提交，再走 `review_work_item`；工作项一旦开始或产生 Submission 就不能物理删除，只能取消并保留审计历史；
- manager 自审完成 Goal 时必须逐条原样回填冻结完成条件、证据与结论；429/过载由 Runtime 保持同一 Delegation/Session 冷却续跑，Manager 不应立即重建委托；
- Goal 独立 Reviewer 只输出冻结条件的逐项判定、解释和证据映射，criterion 必须逐行原样覆盖 `completionBoundary`，不能生成、改写或增加验收标准；证据无法判断的主观/授权条件转 `needs_human` Decision；
- WorkPlan context 使用有界摘要和引用，详细证据按 Delegation result/Artifact 回读；
- `isolated_worktree` 的 cwd 所有权说明由 Runtime 在委托边界 append-only 注入：当前 cwd 已是平台创建的独立 checkout，Worker 必须直接使用现有可写 `.git`，不得再次 clone/worktree add 或写目标 checkout；该规则不是 Manager 可省略、改写或由用户提示伪造的路由材料；
- Goal context 同时注入稳定 `goalId`、当前 `execution.epoch/status`、中断原因、可复用上游与需对账副作用；Manager 的每个写工具调用都必须回传该 `goalId`，并且只能在当前 epoch 继续，不得重放已 accepted 项或尚未对账的外部写操作；
- `pudding:work_plan_update(display:false)` 只供 UI 刷新恢复，不代替 context hook，也不是模型事实源。

### 5.3 Harness 复验路由材料与 Verifier 输入边界

- Harness 设置中的默认 WorkItem/Goal verification mode、trigger、Verifier 选择、CLI environment mode 和三类 Workspace 默认策略在创建 Goal/WorkItem 时解析；WorkItem 首次执行或提交后冻结，后续设置变化不追改历史契约。
- Manager 只决定业务上的 mode、触发时机和可选 Verifier，不得把任意 cwd 伪装成复验环境。Runtime 根据 Workspace scope 签发一次性的 `verificationEnvironmentId` 和可执行 `VerificationInvocationProfile`，Driver 只消费该 profile 与 Driver SPI。
- `purpose=verification` 必须新建 Worker Session，即使选择同一 Agent 也不能续接 Executor Session。Verifier prompt 只包含冻结 Goal/WorkItem/Submission/Receipt/change-set 引用、逐项 criterion 和结构化输出格式，不继承 Manager/Executor 私有聊天历史。
- `environment_verified` 的 `satisfied` criterion 必须引用本次 Verifier Delegation 时间线中由平台生成的 tool/file/search observation；Submission、Receipt 或 Delegation 身份 ID 只能作为上下文引用，不能单独证明条件已满足。
- Verifier 输出不能直接改写 WorkState。平台先校验 criterion 原文/顺序、evidence ref、环境 fingerprint、integrity 和 revision/epoch，再写 VerificationRecord；不可用环境或能力不足时写 `blocked`，不降级成普通文本自审。
- 这些约束属于 Harness/Runtime，不注入 Connector worker 的系统提示词，也不把完整房间能力下沉到 pi Extension 门面。

### 5.4 Wiki 管理员：操作契约是有界材料，权限由宿主签发

`builtinId="wiki"` 的启用 `pi/sdk` Worker 可编辑名称、描述、模型与 `piResources.systemPrompt`，也与其他本地 Pi Worker 一样可配置联网搜索/网页阅读。运行指令仍是宿主追加材料，不能使 Worker 自行批准、直接发布、挂载其他库或获取 bash/MCP。宿主按该内置身份签发 `executionProfile="wiki_curator"`，不是按提示词文本识别角色。`LocalPiDriver` 的受限交互路径关闭原生 extension/skill/template/context 装配与本地设置，只保留宿主知识工具及经 `webResearchToolsFor` 显式授权的联网工具白名单；附加运行规则将网页内容视为来源材料，不作为用户指令。聊天整理由当前 Worker 在同一执行中准备并提交候选，不再另开 Curator 生成会话。独立 `WikiCuratorService.generate` 仅用于后台 Job，使用任务 cache cwd，关闭同类资源发现及原生工具，追加已冻结任务、素材、schema 与操作契约后生成完整待审候选，不从交互授权自动增加联网工具。pi 内嵌默认提示词保留，不用自定义文本取代默认 base。

库根 `AGENTS.md` 在这里是**知识库操作契约**，不是从 cwd/祖先目录自动发现的项目上下文。`knowledge/operation-contract.ts` 显式从获准 binding 的 canonical root 打开它：`O_NOFOLLOW`、普通文件、单硬链接、最多 64 KiB，前后 stat 与严格 UTF-8 校验。不存在可返回 null；读取失败/变化不能解释为“空契约”。Job 将契约字节保存到对象库并冻结 hash，任务与候选边界再次核对当前 hash。普通 `loadWorkspaceContext` 开关不控制这次显式读取，编辑 Worker prompt 也不扩大它的读取范围。

契约可写知识命名、结构、来源与整理规则，仍然没有授予磁盘写入或人类批准的效力。宿主当前对候选路径、schema、sources、基线、字节预算作校验；只支持正文及 index/log 候选，禁止修改 AGENTS/CLAUDE。契约明确要求 index/log 只追加时，宿主检查候选以前一固定正文为前缀；这只是已实现的特定校验，不是任意自然语言契约的通用执行器。index/log 也须逐文件已阅并随整批批准，Publisher 回执才允许称知识已更新。

知识上下文 prompt 只包含本轮授权库元数据与工具用法，不复制全库，也不通过软链接把库塞入 cwd。`knowledge_search` 从私有索引返回已采纳 index.md 导航命中，并对排除控制文档的事实集合做有界全库字面检索（导航未命中仍检索全库），`knowledge_glob` 每页最多 50 条已采纳路径，`knowledge_read` 从冻结已采纳对象读取默认 80、最多 200 行且单片段最多 32 KiB，返回 noteRef/hash/行号；`knowledge_links` 分页返回关联而不读全文。本轮工具返回预算为 64 次、256 KiB。目录/检索摘要不等于事实全文，引用已采纳来源前必须实际读取；本轮 read evidence 留在宿主 context 和候选 validationReceipt。没有完成索引导航优先性的浏览器/模型验收，也没有向量检索或全库全文注入。

工作台 Manager 在自己会话直接执行知识查询与整理（工具面与渐进式声明见本文 2026-10-15 修订段），不再委派 Wiki Worker；Wiki 单聊由当前 Wiki Worker 执行。纯查询不创建 Job；需要修改时，当前 Worker 调用 `knowledge_prepare_candidate(bindingId,task)`，获得宿主冻结的素材、当前基线、schema/pathRules/fieldFormats 与操作契约，再在本次执行中检索查重并调用 `knowledge_submit_candidate(bindingId,pages)`。准备登记 `executionMode="worker"` 的持久 Job，供任务查询与状态投影，但不启动后台 generate。工具成功回执只表示候选已固定；自然语言不能代替提交、批准或发布。生命周期收尾负责将准备后未提交的任务记录为失败，不能默默改成后台继续生成。

用户原话和已验证附件字节在 HTTP 入站冻结为独立来源；宿主按准确的已落盘 user 条目/direct operation 将 sourceIds 私下传给候选准备，不把 Manager/Worker 的委派文字当作原话，也不从模型 prompt 中解析附件路径。模型 `task` 单独作为整理指令，不能扩大当前事实来源清单。委派按其前置 user 关联素材，因此晚到的委派不获得之后收到的附件，预拒绝消息的预备素材也不会交给当前回合。文字/Markdown 为 ready 来源；图片原件单独冻结为 needs_attention，由配置的 Wiki 视觉模型提取后创建独立 ready 衍生来源，PDF 仍只保留原件并提示解析/OCR 尚未接入。知识库选择/信任变化令工具失效。宿主在 pi Worker、后台整理执行器及 Manager 的 provider `streamFunction` wrapper 中核对当次授权/Job/profile；Manager 同时核对本轮 user 正文/图片与素材关联并确保 JSONL 同步，失败不进入 provider。SDK 的 context/before-provider 类 hook 可能吞异常，不能承担阻止外发的权限门。pi Worker 续接以 `pudding:knowledge-profile` 判断运行面重建，但继续原 JSONL 历史；Manager 每轮刷新 profile 与路由，同聊天无需新建。本轮中途授权变化仍拒绝执行。该 marker 是宿主私有 `custom` 条目，不进入系统提示词。来源正文、聊天内容和可编辑 prompt 均不能替代宿主权限、审核 manifest 或 Publisher 回执。

Manager 的技能和 prompt template 保持原生展开。真实 `before_agent_start` 提供 SDK 已展开的 prompt/images，只用于宿主核对本轮执行 user；来源库保存的用户原话不被替换，也不把技能/模板指令升级为事实。合法 SDK 首 token 命令不触发附件路径探测，但命令参数中的真实绝对文件路径仍要按普通入站路径规则验证和冻结。

图片提取使用独立 `pi-vision-v1` 协议：固定转录提示词、私有 cache cwd、无原生工具/扩展/技能/项目上下文，只向支持 image input 的配置模型发送原图。原图 hash、提取 artifact hash、modelRef、协议版本、归一化近似区域及辨认告警分别固定；片段为空、JSON/区域不合法、超限或中断都不生成候选。提取返回及衍生来源提交前复核任务和权限，完成的取消/撤销由同步提交栅栏拦截。告警和模型描述是待核对资料，不能成为已确认事实。

图片入 Wiki 使用普通 Markdown 相对路径。整理模型得到宿主签发的来源 ID 与库内图片目标映射；宿主只为页面实际采纳的图片来源生成或归一引用，原图从固定来源读取。Markdown 不得把 uploads 绝对路径、对象库路径、API 地址或 data URL 作为正式原图引用。图片与页面共同冻结、共同审核，发布器把原图写入 Wiki 内容根下的 `assets/images/`；模型的“已发布”文字或对磁盘路径的描述不能代替原图 manifest、权限检查和发布回执。技能 / 模板提示词不会被复制成用户原始事实来源。

用户在 Obsidian 等外部编辑器直接修改已绑定知识库时，平台仅自动观察当前文件、同步检索与来源快照，不要求采纳或审批，不回写用户文件。提示词不能让 Agent 要求用户审批这些已由外部编辑器保存的修改，也不能把自动同步当成 Agent 的发布授权。Agent 自己提出的变更仍必须生成候选并经过平台审核；发布中断残留由宿主隔离，不作为外部修改自动供给模型。

“退回修订”是持久新任务指令：原批次保持固定字节和 returned 状态，新的任务保存原件、独立反馈文字来源、原候选文件以及通过旧 receipt 实际读取的采纳快照；后者在新模型轮次仍需实际读取。新候选、新 manifest 与已阅/批准状态重新建立，旧批准不继承。修订失败可重试，原审核页沿受验证的 retry 链查到后续任务；聊天通知只投影状态。

## 7. 调试工具：有效提示词预览

### 长期记忆的运行时规则（2026-09-30）

当前用户所有已接入且可用的知识库（含 memory）默认加入新旧会话，显式取消项按上下文持久化并随新会话继承；新接入库自动加入，离线库恢复后可用。提示词仅注入库 ID、名称与最多 200 字的用途说明，正文按需检索读取。普通 Pi Worker 的知识库 surface 始终只读；当宿主默认 memory 实际已挂载时，额外提供仅含 task 参数的 `memory_request_update` 并附加 `knowledge/memory-runtime-policy.ts` 的简短规则：按需检索；在普通任务中识别明确记住/纠正/忘记，以及有来源的长期偏好、决策与方法；查重后提交后台整理请求。用户无需专门找管理员，Worker 无需经 Manager 中转，也不获得跨 Worker 任意调用权。Manager 只在需要综合时汇总；任务回执与来源约束仍由宿主检查。Manager 的知识业务在其自身会话直接执行（2026-10-15 起）：知识检索与候选准备/提交工具以 `exposure:"deferred"` 注册，经 `tool_search` 渐进式声明，详见本文 2026-10-15 修订段；内置 Wiki Worker 在当前执行中使用候选准备与提交工具；普通 Worker 不提供这些通用工具，仍以 `memory_request_update` 请求 `executionMode="background"` 的任务。默认 memory 的身份及授权在工具与 provider 边界复核，模型不能通过额外参数改目标。Pi 以外 Connector 不在本次范围内。

运行时规则与库根 AGENTS.md 分工：前者给业务 Agent 判断触发时机，后者给后台 Wiki worker 执行整理。编译执行器只拿显式目标库，不携带主动请求规则，避免整理递归触发。工具请求不等于批准或发布，提示词不替代权限门；一次调用可以不产生记忆变更。该段依赖会话实际挂载状态，属于运行时装配，不作为静态 Agent 配置预览中的固定规则。

Web 配置页 → 提示词分区 →「有效提示词预览」按真实装配顺序分段展示（`pi-resources.ts:160` `previewPiResources`）：pi-base → pi-native-append → agent-instructions → window-collaboration → global-context → workspace-context，附 skills/templates 启用清单与字符估算。预览展示的是**已保存配置**的结果；信任门被拒绝的来源不进预览候选集。

Workspace 列表处于加载或读取失败时，配置页不能把它显示为“没有显式 Workspace”；失败须留在页面并提供重试，预览范围选择和预览请求等列表恢复后才开放。预览结果只对应发起请求时的 Agent 与 Workspace；切换范围或预览失败后，不继续展示上一范围的结果。预览失败保留明确错误，避免把旧结果当作本次真实装配。

与提示词预览并列，配置页另有「工具」分区（`GET /api/agents/:name/tool-preview`）：提示词预览按真实装配分段展示提示词内容，工具预览按分组列出该角色实际装配的工具名、暴露方式（直接 / 渐进声明 / 仅模型）与启用条件，两者都只读、互不替代。

## 2026-09-30：大管家知识职责收敛（2026-10-15 起被取代）

本节及以下两段记录的「Manager 经 `delegation({workerId:"wiki",task})` 委派知识管家」模式，自 2026-10-15 起不再描述当前行为；当前契约见文首「2026-10-15：Manager 即知识整理负责人（去委派化）」。聊天入口仍由宿主冻结用户原话与附件，在 provider stream fence 核对并关联持久 user entry——这一事实不随整理执行者变化。后台任务返回 `queued` 仅表示请求已受理、准备启动（当前无同库 FIFO 调度）；候选、人审、Publisher 回执分别代表生成、确认和实际生效。历史 `manager-delegation-v1` fingerprint 会话按 `manager-curator-v1` 重建当前工具与提示词，保留已发生的历史上下文；历史读取不授予当前工具权限。

## 2026-10-01：知识整理阶段用语

执行整理的 Manager/Wiki Worker 必须按宿主工具回执说明状态并提供任务链接：queued/running/submitting 尚无可审核候选，pending_review 且返回 batch 才表示候选已生成。禁止把素材原件冻结说成“原话已落库”，禁止把候选准备说成“已经进入审核”，禁止凭模型自述说正式知识库更新。失败或超时报告宿主给出的真实原因，用户可在知识库“整理任务”中查看；worker 模式普通失败返回来源聊天继续，background 生成失败才可后台重试。固定候选登记失败使用同 Job 的重新登记，不重新生成。不能把旧回执作为实时执行状态。聊天 Worker 与后台生成会话都必须实际调用 knowledge_submit_candidate，确无变更也提交 pages=[]，自然语言不能取代宿主固定提交。纯查询不先准备候选，也不为了查状态创建 Job。

聊天候选由当前 Wiki Worker 的有效会话模型执行，受该 Worker 的会话运行参数控制；后台候选生成会话尊重管理员显式 model/thinkingLevel 配置，与 Manager 对话的模型选择分别管理。提示词或 origin.sessionId 不授予把 Manager 会话模型当成 Wiki 有效配置的权限。执行诊断应区分配置、实际使用模型、工具结果与超时；不能因为模型文本出现工具名就宣称提交成功。

### 2026-10-01：后台整理状态与结构规则交付

Manager 和 Wiki 已有 jobId 时使用 `knowledge_curation_status`，不得搜索 Wiki 正文查任务，也不得以重发整理请求代替查询。queued/running/submitting 表示生成或提交尚未完成，不能据此判任务失败或要求重交；executionMode 指明由当前 Worker 执行还是独立后台执行，不能把 worker 的 running 解释为后台接手。生成阶段完成与 ReviewStore 当前审核/发布阶段分别读取。只读状态结果有长度和枚举边界，不含用户素材或模型正文。

独立整理 Worker 首条宿主 JSON 除 schema/operationContract 外还提供 pathRules（内容前缀、实体完整目录、首页/日志路径）及 fieldFormats（date、datetime、当前 ISO 时间）。已提供的契约无需循环搜索，datetime 不能只写 YYYY-MM-DD；可选字段缺少依据时可省略。错误回执指出期望目录及字段类型，允许在执行预算内修正再提交。正文结构仍以获准用户要求和正式 schema 为依据，不由宿主静默改写。

### 2026-10-01：当前 Wiki Worker 直接生成候选

当前聊天规则以 §5.4 为准：Manager 在自己会话直接执行（2026-10-15 起，见文首修订段）；Wiki 单聊由当前 Wiki Worker 本人执行。需要修改时先 prepare，再使用宿主提供的固定来源/基线/结构材料检索查重并 submit；不再提示 Wiki 调 `knowledge_request_curation` 让第二个 Curator 重复整理。查询不 prepare、不创建 Job。prepare 不是生成或审核成功，最终自然语言不是提交证明；宿主 submit 回执才可报告候选已生成，并提供 Job/review 链接，随后停止在候选边界。

worker Job 的未提交收尾与 provider 权限门由宿主负责，提示词不能绕过。撤权或来源/基线/契约变化时失败关闭；不能把无效准备任务交给后台重跑来掩盖失败。后台 `executionMode="background"` 仍服务主页、普通 Worker 默认 Memory、稍后读及后台生成故障的明确重试/退回修订，并使用独立生成提示词；两种生成方式共用提交校验和审批发布规则。聊天使用当前 Worker 的实际模型，后台使用 Wiki Connector 配置，均不隐式继承 Manager 模型。

所有整理工具回执由 `curatorJobFeedback` 携带 executionMode，状态卡 `pudding:knowledge_job.details` 使用同一字段；状态查询只以有界白名单投影它。running 的用户文案与 nextAction 区分“当前对话正在整理”和“后台任务继续执行”，不能把 worker 的执行过程误称队列后台。普通 worker 失败/取消不能通过后台 retry 续跑，用户应沿真实 room/session 深链返回来源聊天。

`candidate_registration_failed` 表示宿主已有 frozenCandidate，但审核登记异常；必须说明“候选已固定、登记失败”，不能说没有候选字节，也不能让模型重新整理。重新登记在同 Job、同 manifest 与固定字节上补交 ReviewStore，不调用模型；该宿主恢复步骤不依赖提示词授予权限，也不能变成人工批准。

当前默认预算为 15 分钟。超时/取消的同步执行栅栏阻止候选 CAS 和图片衍生来源 INSERT，终态持久化不等待 SDK abort 结束；模型及工具即使迟到返回，也不能绕过栅栏继续提交。已固定 submitting 的宿主登记恢复不重新启动生成模型。纯查询不创建整理 Job，因而不挂整理任务的 deadline。

2026-10-03 单聊重编译可通过 knowledge_context.sourceMessages 与 prepare.sourceMessageIds 明确引用同聊天的已准入原消息，沿用原来源和日期；该参数是素材引用，不是 prompt few-shot 路由。

### 2026-10-03 人脉共同往来

人脉 schema guidance 明确 involves 只链接实际/计划往来的明确参与人，普通提及不能当作参与人。共同往来图谱由宿主从正式 Wiki 的已接纳记录确定性投影；不要求模型写两两关系，不重复复制事件，不通过 few-shot 推断关系亲密度。现有 interaction 本人参与约定仍保留，计划与已发生分别统计。

### 2026-10-04 日历工具装配

平台日历能力通过 CalendarService 原生工具定义装配到 Pi Manager 与普通 Pi Worker，共用页面 HTTP 业务服务；不新增个人助理身份，不增加意图路由 few-shot。Manager 原生会话中日历工具以 `deferred` 注册、经 `tool_search` 渐进声明（2026-10-15 起，联网工具同）；Worker 委派执行路径保持 direct。工具自身提供参数、作用域与真实回执语义，参与人使用当前已挂载人脉库稳定引用，往来候选必须审核后由 Publisher 发布。内置 Wiki 管理员仍运行受限 wiki_curator 表面，不加入日历编排工具；日历产生往来候选不需要再委托其调用模型。
