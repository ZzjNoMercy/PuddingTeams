# 房间即群聊：solo / 单聊 / 群聊产品模型方案

> 创建：2026-08-05。定位：阶段二产品模型的正式方案，作为开发核对基准（用户开发完成后对照本文档核对、优化）。
> 关联：`docs/puddingteams-platform-design.md`（§3 Web 界面两个面）。本文档落地后，§3 的房间描述以本文为准。
> 现状基线：本文基于 2026-08-05 工作区实际代码（阶段二未提交状态）盘点撰写，下文"现状"均指代码事实而非设计意图。

## 1. 产品模型

**聊天窗口（window）是侧栏的一级实体**，分三种，语义 = 成员数：

| 类型 | 成员 | 说明 |
|---|---|---|
| **solo** | 仅 pi manager | 默认态，**置顶单例**（有且仅有一个，不可删除）。与 manager 自由对话，可触发派活（§4） |
| **单聊** | 1 个 worker（+ manager 隐含在场） | 有 worker 头像，点开即与该 worker 的持续对话 |
| **群聊** | 2+ 个 worker（+ manager 恒定在场） | 成员消息流：worker 以独立身份出现在时间线 |

核心规则：

- **pi manager 恒定在场**：单聊/群聊中用户的消息都由 manager 接收，经 `team_task` 中转给 worker（现状代码已如此，保持）；三种窗口共享同一套 manager 运行时，差异只是 `team_task` 白名单与渲染形态。
- **session 归属窗口，不再是一级入口**：每个窗口拥有自己的 session 列表 + active session；侧栏只出现窗口，session 在窗口内部管理（§5）。
- **worker 是一等消息作者**：单聊/群聊时间线里，worker 的任务执行与回复渲染为带其头像/名字的消息条目（成员消息流），而不是裹在 manager 气泡里的工具卡。solo 里保留 TeamTaskCard 形态（派活是 solo 时间线的过程记录）。

## 2. 领域模型与数据落地

现状：`RoomConfig.sessionId` 即房间主键（房间挂在某个 pi session 上），`GET /api/rooms` 遍历所有 pi session 拼房间。目标：**窗口成为独立实体**，session 只是窗口内的资源。

```
windows.json（由 rooms.json 演进）
Window {
  id: string                    // 窗口自己的 id（不再是 sessionId）
  type: "solo" | "direct" | "group"   // solo 全局单例
  members: string[]             // worker 名；solo=[]，direct=[w]，group=[w1,w2,...]
  sessions: SessionRef[]        // [{sessionId, title, createdAt, modifiedAt}]
  activeSession: string
  workerSessions: Record<worker, session_id>   // worker 侧多轮续接（现状已有）
  createdAt / pinned
}
```

- **solo 窗口**：服务端启动时保证存在（没有则建），`pinned: true`，拒绝删除。
- **direct 窗口按 worker 去重**：同一 worker 只有一个单聊窗口（重复"发起单聊"= 打开已有窗口）；群聊不去重。
- **窗口级联删除**：删窗口 → 删其全部 pi session（JSONL）+ workerSessions 记录；删窗口内 session → 仅删该 pi session，窗口保留（至少保留一个 session，删到最后一个则自动新建空 session）。现状 `TeamsStore.removeRoom()` 是死代码、删 session 不清理 rooms.json，本次一并补上。
- **直接兼容演进**：rooms.json 加 `id`/`type` 字段迁移为 windows.json，旧 `sessionId` 主键映射为首个 session。

## 3. 侧栏与导航

- 侧栏结构：**solo 置顶**（ManagerAvatar，"pi manager"）→ 单聊区 → 群聊区（MemberStack 头像堆叠）。现状 `session-list.tsx` 的渲染逻辑已按成员数区分，改为按 `type` 分区 + solo 固定钉顶。
- 「+ 新对话」入口改为**发起**：选 worker 单聊（若已有该 worker 的单聊则直接打开）/ 勾选 2+ 建群聊。solo 不在创建选项里（单例）。现状 `create-room-dialog.tsx` 勾选逻辑复用，补去重逻辑。
- 智能体管理页、设置和更多菜单不变。

## 4. solo 派活路由（本方案核心新机制）

**场景**：用户在 solo 里对话，manager 判断要派活，调 `team_task(worker=X, task)`。平台动作：

1. **定位窗口**：找到 worker X 的 direct 窗口（没有则自动创建，无需用户介入）。
2. **session 决策（solo 决定）**：`team_task` 工具描述中注入该 direct 窗口的现有 session 摘要（title + 最近活跃时间），manager 据此判断本次 query 与哪个 session 相关——相关则透传其 worker session 续接，不相关则开新 session（工具参数加 `session?: "new" | "continue"`，默认 `continue`；描述中写明"若现有会话与任务无关则传 new"）。
3. **执行**：用 direct 窗口的 `workerSessions[X]`（或新建）spawn worker，与窗口内派活走同一条 `runAgent` 路径。
4. **可见性（"自动找到对应的单聊，发个信息"）——已调研，pi 原生路径成立（2026-08-05 查证 pi 源码）**：用 `AgentSession.sendCustomMessage(msg, {triggerTurn: false})` 向 direct 窗口的 active session 写两条 `custom_message` entry：
   - `pudding:task_assign`（content=任务文本，details={taskId, worker}）
   - `pudding:task_result`（content=结果，details={taskId, worker, status}）

   该 API 一次满足三个要求：**落盘 JSONL**（重开 session 回放可见）+ **向订阅者 emit `message_start`/`message_end`**（WS 桥原样透传，前端实时收到）+ **不触发 LLM turn**（纯记录写入）。源码佐证：`agent-session.ts:1451-1461`（无 trigger 分支：push 内存 + `appendCustomMessageEntry` 落盘 + emit，无双写）、`session-manager.ts:396-400`（custom_message 回放进 context）。三个注意点：
   - `custom_message` **会进 LLM context**（convertToLlm 转成 user 消息）——worker 上下文可见派活记录，视为特性而非缺陷；
   - 调用前 `session.isIdle` 把守：streaming 中调用会退化为 steer/followUp 注入（语义变了），目标 session 忙碌时平台侧排队等 idle；
   - 前端 `message.tsx` 需认识 `role:"custom"` 消息并按 `customType` 渲染——worker 头像消息条目正好落在这里，与 §7 成员消息流共用同一渲染。
   - SDK 升级回归点：`sendCustomMessage` 无 trigger 分支行为（agent-session.ts:1451-1461）。

   **废弃**原"window-activity.jsonl 投影"备选（pi 原生路径成立，不引入第二存储）；**禁止**直接 append JSONL 文件（运行中 SessionManager 无文件变更感知、外部写入的 entry 会脱离 leaf 链导致回放丢失、新 session 首次落盘用 `openSync(wx)` 遇外部预写文件直接 EEXIST——session-manager.ts:1029-1038）。
5. **solo 时间线**：保留 TeamTaskCard（含"已同步到与 X 的单聊"链接式元信息，点击跳到对应窗口）。

群聊/单聊窗口内的派活不走路由（本窗口即归属窗口），仅按 §1 以成员消息流渲染。

## 5. 窗口内 session 管理与"命令"展示

- **session 列表**：窗口头部「会话」下拉（现状已有列表/切换/新建），**补删除**——`DELETE /api/rooms/:id/sessions/:sid`（级联清理 pi session 文件与 workerSessions 中指向它的记录；禁止删最后一个）。前端在会话下拉里给每项删除入口（与窗口删除同款确认）。
- **命令展示**：窗口头部「成员」弹层中，每个成员条目显示其 `invoke.command + runArgs`（等宽、可复制）与启用状态；群聊里同时显示 `workerSessions` 续接状态（续接中/新会话）。这让"这个窗口在跑什么命令、接着哪个 worker session"对用户透明。

## 6. 后端端点变化（在现状 rooms 路由上演进）

| 端点 | 变化 |
|---|---|
| `GET /api/rooms` | 返回窗口模型（id/type/members/sessions/activeSession/pinned），solo 恒在首位 |
| `POST /api/rooms` | 接受 `{type, members}`；direct 去重命中则 200 返回已有窗口 |
| `DELETE /api/rooms/:id` | **新增**：级联删除（solo 拒绝，405/400） |
| `POST /api/rooms/:id/sessions` | 不变（窗口内新建 session） |
| `DELETE /api/rooms/:id/sessions/:sid` | **新增**：窗口内删 session（最后一个拒绝） |
| `POST /api/rooms/:id/sessions/:sid/activate` | 不变 |
| `team_task` 工具 | solo 上下文时注入目标窗口 session 摘要 + `session` 参数；执行后写 direct 窗口消息流（§4.4） |

agents CRUD / probe 端点不变。

## 7. 前端渲染变化

- **成员消息流**（单聊/群聊）：`team_task` 事件折叠出的块不再渲染为 manager 气泡内的 TeamTaskCard，而是独立条目：WorkerAvatar + worker 名 + task（作为"用户侧"内容）+ 结果 markdown + 状态徽章；manager 的转述文本仍是 manager 条目。solo 派活同步进单聊的 `custom_message`（`pudding:task_assign` / `pudding:task_result`，§4.4）复用同一渲染。事件层 `lib/events.ts` 已有 `teamTaskWorker()`，改造点在 `message.tsx` 的分发逻辑。solo 窗口维持 TeamTaskCard。
- **窗口头部**：房间名（可改）+ 成员副标题 + 「会话」下拉（增删）+「成员」弹层（含命令）+ 连接状态（现状基础上增量）。
- 空态：选中窗口无 session 时不出现（§2 保证至少一个）。

## 9. 明确不做

- 不做绕过 manager 的 worker 直连通道（违背"manager 恒定在场"，审计性也变差）；
- 不做 `team_broadcast` 并行派活（阶段四）；
- 不做 MCP invoke；没有可执行协议就不保留“看似支持”的死类型，未来出现真实 MCP Connector 时按 Driver SPI 接入；
- 不做窗口级未读数/通知（本地自用）。

## 11. agents 页趣味化与头像（追加，2026-08-05）

背景：agents 管理页现为纯表格，工具感过重；配合群聊模型，worker 应有"角色感"（参照 Marvis 角色矩阵的趣味方向，但保持全站扁平风）。

- **页面形态**：列表 → 角色卡片网格。每卡：大头像 + 名字 + 描述（一行截断）+ capabilities 标签 + 启用/健康状态灯；点击进入编辑抽屉（现有表单字段不变），卡片上保留探测按钮。头像体系全站复用：agents 卡片、侧栏单聊/群聊项、窗口成员弹层、§7 成员消息流条目，同一 `WorkerAvatar` 组件一处升级处处生效。

- **端点**：

**已落地**：§1–§7 全部（§10 清单已逐项勾销）；§11 头像开发中。关键实现决策：

- **solo 路由**（`pi-bridge/team-task.ts` 重写）：solo 白名单 = 全部 enabled worker；`session?: "new"|"continue"` 参数；工具 description 用 getter 动态注入（pi 每轮重读，摘要缓存每次 execute 后刷新）；`TeamsStore.ensureDirectWindow` 自动建单聊；执行后 `syncToWindow` 向 direct 窗口 active session 写 `pudding:task_assign` / `pudding:task_result`（details 含 taskId/worker/windowId）。

- **渲染**：`message.tsx` 抽出共享 `WorkerTaskEntry`（头像+名字+徽章+任务+结果 markdown），custom_message 与 direct/group 的 team_task 独立条目复用；solo 维持 TeamTaskCard + "已同步到单聊 →"跳转链接（details 需带 windowId/synced，历史回放路径已补 details 折叠）。

**用户开发中自加的设计（回写确认，均为有意决策）**：

- **Relay 硬约束**：direct/group 窗口的 manager session 被 `noTools: "builtin"` 剥光内置工具、只留 team_task，systemPrompt 追加"必须转发、不许自己动手"（`session-store.ts:74-95`）。solo 保留全工具。这比方案"manager 中转"更强：单聊/群聊里 manager 是纯粹的转发器，动手能力差，行为可控。

## 13. 可选 Workspace 语义（2026-08-10 收口）

- Workspace 不是发起聊天的必填项。solo、direct、group 都允许不选择项目；创建时把平台默认 cwd 冻结到 Window，manager Session 与 worker Driver 始终共享该快照，保持原有入口且避免跨重启漂移。
- 选择 Workspace 后，Window 保存 `workspaceId + cwdSnapshot`，manager 与 worker 共享该项目的 canonical cwd；路径失效只把对应窗口标记为不可用并阻断执行，不阻断服务启动，也不回退默认 cwd。
- 项目上下文可双向切换：显式 Workspace 可以切回“不绑定项目”。direct 默认按 `(worker, workspaceId ?? cwdSnapshot)` 创建或打开单聊，group 默认新建一个成员相同、项目不同的群聊；solo 是固定单例，只能原地切换。原地模式会停止旧任务、清空续接并重建 manager Session。
- direct 的身份为 `(worker, workspaceId ?? cwdSnapshot)`：同一 worker 可以同时拥有不同默认 cwd 的无项目单聊以及多个不同项目单聊，彼此不复用 manager/worker Session。
- 每次 Delegation 无论是否选择项目都冻结 `cwdSnapshot`；worker binding 同时记录 `workspaceId? + cwdSnapshot + agentRevision`，从而让无项目模式保留原行为、有项目模式保持跨项目隔离。

## 14. Session Goal 与当前工作（2026-08-10 收口）

- Window 仍是长期协作空间；Session 可以是普通聊天，也可以显式设置为一个 Goal，不新增 WorkItem/Topic 实体。
- Goal 的权威当前版本是 `SessionWorkState`：manager 固定为责任主体，通过 revision 乐观锁维护当前摘要、等待项、下一步、完成边界与稳定 Artifact 引用；worker Run 的 completed 不直接把 Goal 判为 resolved。
- 业务取舍使用 `DecisionRequest`，与恢复同一暂停 Run 的 Driver `Interaction` 分层。回答 DecisionRequest 后在同一 manager Session 中继续，不调用 `Driver.respond`，也不从普通答案推导额外授权。
- Delegation 保持 `Worker A → manager → Worker B`，记录 `parentDelegationId + handoffKind + intent + expectedOutcome + evidenceRequirements + completionBoundary`；单向通知走 custom message/event，不制造假的 Delegation 等待。
- Chat 顶部展示轻量“当前工作”卡片和最近委托链；普通 Session 可原地设为 Goal，未设置时不强迫用户进入项目管理流程。
- 用户附件冻结到平台受控目录，图片作为模型 image input 传入，所有附件路径明确注入当前消息，manager 接力派活时必须原样传递所需路径。
