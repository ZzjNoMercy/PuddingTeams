# 房间即群聊：solo / 单聊 / 群聊产品模型方案

## 2026-10-15 P4：普通会话与只读执行记录

普通聊天只使用 `windows.json` v3 的 `sessions[]`、`activeSession` 与 `sessionRefs`。不再投影执行会话列表，不保留执行面查看指针；同版本文件若仍含已移除的执行面指针，校验明确拒绝，不转换或静默删除。历史 v1/v2 也不自动迁移。

委派只通过 `delegation` 工具发起一次 fresh 调用；`delegationId` 标识执行，`managerToolCallId` 关联真实 Pi toolCall。Driver 的 active registry、Interaction、Receipt、ChangeSet 与追加式 timeline 保留。Pi 执行回放位于 `worker-process-session.ts`，仅供 `/api/delegations/:id/process/*` 使用。普通会话端点不能向执行 handle 发送消息、切换、重命名或删除。

执行索引以台账的来源 `managerSessionId` 为准，拒绝从其他聊天的镜像卡推导归属；全局 `/api/delegation-records` 可按 `sourceSessionId/workerId/workspaceId/goalId` 过滤。全局搜索把原生会话与执行记录分开，执行结果打开只读详情，保留精确单次 cancel。

Manager 和 Pi Worker 使用同一原生会话机制，模型/思考设置作用于当前 Session 的 owner；忙碌输入仅以服务端 capability 开放。Pi 单聊写真实 user/assistant/toolResult JSONL，不写容器直派卡。非 Pi Connector 继续使用 Driver 单聊适配，其 `pudding:user_message/task_assign/task_result` 和内部续接绑定仍有实际用途；它们不把 Manager delegation 变成连续聊天，也不开放原生 followUp/steer/Fork。Pi 原生 provider 连续性已由 `sessionRefs[sessionId].provider` 承载。

平台 Worker 输入队列模块、启动装配、GET/DELETE 队列端点和灰态排队气泡已删除。`GET /api/diagnostics/legacy-data` 只返回旧队列文件的路径、大小与时间，不解析输入、不补投、不删除；用户数据清理是独立明确操作。Fork、SDK followUp/steer 及其未知消费回执沿用 P3 契约。


## 2026-10-14 P3：原生 Worker 对话与快照

Manager 继续使用 Pi 1.2.0 SDK，增加 delegation/Goal；Pi Worker 单聊也使用原生 SDK，但按持久负责人装配自己的指令、模型、工具、MCP 白名单、Capability 和知识授权。单聊只有一份可发送的 Session，不创建委派来承载每条输入，不获得 Manager delegation/Goal/日历控制。内置 Wiki 保持受限知识工具面，使用既有 prepare/submit 候选管线，提交即停并等待审核；任意原生写工具、扩展、MCP 与 Workspace 指令不进入它。普通 Worker 保持知识读取、默认 memory 待审核请求和已授权能力。全新会话在 Window 负责人落盘后注册知识工具；真实用户 JSONL 与素材绑定在 provider 发送前完成，SDK Skill/模板展开只改变执行文本，不改原始素材。其他 Connector 本阶段仍用既有直派通道，不宣称支持原生忙碌输入或快照。

`windows.json` v3 在同一次原子写中保存 `windows` 和 `sessionRefs[sessionId]={sessionId,ownerAgentId,createdAt,sourceSnapshotId?,provider?}`；`sessions[]` 保留成员 ID 索引。provider 对 Pi 原生会话记录 `driverId:"pi-native"`、负责人配置修订和 SDK sessionId。打开时按 ownerAgentId 装配；成员数量不改变负责人。一个 Worker/Workspace 保持一个 direct Window，里面可以有多段原生对话。旧 v1/v2 开发状态显式拒绝，不迁移、不删除；缺负责人记录拒绝，已删除或停用负责人保留只读历史。

Pi Manager/Worker 运行中缺省 followUp、显式 steer；空闲时正常启动，返回真实 delivery。HITL 等待独立于 running，追加走 followUp 入队、不启动 run、不提交卡片。返回 disposition=started/queued/handled 与 persistence=durable/pending/not_applicable；queued 202 只承诺 SDK 受理，不等于模型已消费。原操作键重试不再次入队；正文/附件/delivery 改变冲突。SDK 不携带输入 operationId；同文案多次、展开改写等无法唯一关联时保持未知，不能伪造精确消费身份。回执不保存自动重放正文，不新增平台 FIFO。待消费 SDK 队列或未终结回执阻止淘汰、重建、模型/思考切换、项目切换和 fork；Stop 清队列并标记 cancelled_unconfirmed，附件保留。确定的 compaction 拒绝返回 session_compacting，允许原键原消息再受理；不确定错误不自动重发。

Fork 冻结当前已提交分支，由 `ConversationSnapshots` 保存不可变 manifest 与独立资产；hash 使用递归排序键的 JSON，覆盖版本、创建时间、来源、分支、cwd、transcript 和资产清单，读时核验文件 bytes/hash。保留配对完整的历史工具消息、compaction 和展示卡；排除 Manager 指令、roster、配置、审批权限与运行控制，Goal 仅保留历史文字投影。委派内部 trace 不混入。平台外置结果改为快照中的文件引用，目标用 read 读取；不继承 read_delegation_result 权限。

目标必须在当前有效范围，且会话提供方明确支持格式1。本阶段只有 native Pi provider 声明导入能力，委派 Driver 不声明；不以 Connector 名字推测其他 Driver 能力。目标 SDK 重新编写 entryId、消息传输 ID 和 compaction 引用，使用自己的模型/思考设置；不调用会复制控制记录的 SDK forkFrom，不触发 prompt、不复制活动 Goal、不重放工具。预算为 UTF-8 serialized entries 的保守上界：min(2MB, 已配置模型 contextWindow/2)，模型未配置时64KB；预算超限显式拒绝，不静默摘要。单资产64MB、总资产128MB。

一个 `fork-operations.json` v1 账本预约 snapshotId/sessionId，依次 reserved→snapshot_saved→session_saved→attached。快照 hash、导入标记和窗口唯一性负责冷恢复；同键相同意图返回同一目标，改来源/Worker/leaf 冲突。快照完成后源删除可继续；目标删除成为 gone，不重建。冻结前需当前 leaf、不忙碌、不等待、不含待确认输入且执行证据已封存；恢复也校验这些事实。UI 仅在原生对话菜单提供 Fork，显示来源快照；未确认时保留原键，仅服务器确认尚无操作后允许用户重新选择。

本节描述已实现的 Pi 原生会话与快照契约；P4 的入口清理见上文。


> 核心委派使用统一 `delegation({workerId, task, contextRefs?, parentDelegationId?, ...Goal字段})`。每次 fresh，因果不导入历史，审批与结果只回 owner；operationId/requestHash 保证同键同意图去重。

## 1. 产品模型

**聊天窗口（Window）是侧栏一级实体，类型由负责人和委派范围明确确定，不按成员数量推导。**

| 类型 | 负责人 / 可委派范围 | 说明 |
| --- | --- | --- |
| solo | 原生 Pi Manager / 全部启用的可委派 Worker | 置顶单例；Manager 可直接执行，也可委派 |
| direct | 一个 Worker | Pi 使用原生会话；其他 Connector 使用 Driver 单聊适配 |
| group | 原生 Pi Manager / 已选成员与启用 Worker 的交集 | 创建与成员更新去重后至少两位有效 Worker；仍是 Manager 对话 |

群聊是用户给 Manager 缩小 Worker 选择范围的配置。Manager 的原生工具、模型和自身 MCP 授权独立于该范围；多人不代表多个共享上下文的发言者。配置只给 Manager 的群聊提示词仍可追加。Manager 保留 Pi SDK 的模型请求、Agent Loop、原生工具、上下文压缩及 JSONL；平台增加 Goal/委派能力与执行协调，不重写 Pi。

默认 Manager solo/group 提供 `read/ls/grep/find/edit/write/bash`；显式 `builtinTools=false` 移除工具，`codeSearch=off` 关闭搜索，受限知识执行 profile 不因此放开。Goal 自执行先开始自己的 WorkItem，原生工具记录 NativeExecution 和 ChangeSet，按同样的冻结策略提交/验收。普通写工具按执行单元取得并释放租约，隔离工作项保留私有 checkout；Manager 不跨等待 Worker 占有目标目录写租约。

`eligibleWorkers` 是 roster、搜索/Capability 装配和 Invoker 接单的共同范围规则。配置收缩阻止新调用，已接单调用及其原审批保持冻结生命周期；取消是独立动作。群聊创建与成员编辑至少两位 Worker；成员停用导致可用范围收缩时不转 direct，全部成员失效时 Manager 仍可直接工作。

仅用户明确要求才创建群或扩大范围。AI 建群/邀请工具要求真实 `sourceMessageId` 并保守核对当前用户消息中的明确操作意图；不识别的表达由用户通过 UI 配置，工具不自动放行。`task` 可省略；仅明确要求建群后立即执行才下达首条任务。创建 UI 明确选择“Worker 单聊”或“Manager 群聊”。

> 2026-10-14 P1 实现边界：Delegation 的单次化、结果只投 owner、旧委派会话视图移除属于 P2；Worker 原生单聊、快照 fork、followUp/steer 属于 P3。本文后续历史说明中的双边展示/续接只描述尚未替换的实现，不代表新目标模型。

## 2. 领域模型与数据落地

Window 是独立实体，包含 type、members、cwdSnapshot、workspaceId、sessions 和唯一 activeSession。solo 离开的项目连同会话停放在 parkedContexts；direct/group 项目身份不可原地更换。

Session 的持久负责人和快照来源在 windows.json v3 的 sessionRefs 中；Pi provider 连续性不依赖 Worker delegation 台账。非 Pi 单聊保留内部 Driver 连续性绑定，Manager 单次工具调用不续接。项目以 Workspace/cwd 为准，Goal 仍属于会话。


## 3. 侧栏与导航

- 2026-10-15 按确认原型更新聊天导航：`/chats` 侧栏改为同一会话索引的「Agent / 项目」两种分组，默认 Agent，浏览器记住选择。一级是展示分组，二级是普通 Session；Window 继续承担会话归属、负责人及委派范围，不因展示分组改变。Manager 仍有独立 `/` 工作台；Agent 视图中的 Manager 分组优先，其余分组按最近会话时间排序。项目按 workspaceId 分组，无项目按冻结 cwd 区分，不能把同名文件夹合并。群聊 Session 按真实负责人 Manager 分组，不复制到所有成员名下。
- 切换视图只重排列表，保留当前 Room/Session、消息及输入。每组先展示五条，可展开、折叠；搜索覆盖会话名、首条消息、Agent、项目和文件夹路径，搜索时展开匹配分组。Agent 视图持续显示项目名；项目视图持续显示 Agent，完整目录通过悬停提示提供。未读仍来自现有 Room 活动与已读水位投影，不从 token 或本地改名推导。
- 分组悬停/键盘聚焦显示更多与新建聊天，行内显示置顶、归档、更多。触屏直接显示操作，置顶可从更多菜单访问。两视图共享置顶与归档；置顶在组内优先，归档从常规列表移到已归档入口，可恢复。归档不删除、不停止任务、不触发项目切换；删除仍明确为删除整个对话窗口并二次确认，solo 不可删除。重命名沿用原会话接口及 60 字限制；停放项目须先打开该项目会话再重命名，不能绕过原活动上下文守卫。
- 新建聊天沿用现有卡片、工作空间选择和群聊幂等操作。Agent 分组快捷入口直接打开该 Agent 的新会话，项目分组预选项目；Agent 单聊可选 Manager。同一 Agent、同一项目已有空白普通 Session 时优先复用当前空白 Session，其次打开该上下文中的其他空白 Session；已在其中时提示“已在新会话中”，不继续新增。空白由服务端真实会话条目判断，不依赖 `firstMessage` 的展示占位符或标题；带消息、工具/自定义消息、压缩历史、快照来源或 Goal 的 Session，以及已归档或运行中的 Session 均不复用。没有可用空白 Session 才创建；已有重复空白会话不自动删除。Manager 进入目标项目仍走原地切换协议，只在目标项目查找，不复用停放项目的空白会话；群聊仍由 Manager 负责并至少选择两名 Worker。
- 侧栏、聊天区及新建弹窗共用 `POST /api/rooms/:id/sessions` 的 `reuseEmpty` 分支，返回 `reused` 供提示。前端阻止未完成的重复操作，服务端按 Window 串行检查与创建，并与消息提交和项目切换共用生命周期门禁；请求携带预期 Workspace/cwd 时不匹配返回 409。显式 Goal 与首发幂等预约继续沿用原协议，不进入空白聊天复用分支。
- `GET /api/chat-navigation` 只索引持久 Window 拥有的普通 Session，覆盖当前/停放项目；负责人以 SessionRef 为准，不猜测成员。列表本身不激活上下文。选择停放的 Manager 会话先定位并按现有项目切换协议恢复，再串行激活普通 Session；迟到选择不能覆盖较新的选择。置顶/归档元数据独立存于 `<PUDDINGTEAMS_HOME>/state/chat-navigation.json`，不写会话 JSONL、不改变运行状态；PATCH 核验 Room/Session 归属，只接受 pinned/archived 布尔值，原子保存递增修订，前端拒绝倒退的回读。房间清单仍决定房间增删，保留原活动修订与已读水位的收敛规则。
- Session 历史 HTTP 快照与 WebSocket 帧重对齐时，较早的 `message_update` 可能在较新的完整快照后才被折叠。assistant 同一轮的正文、thinking 与已出现的工具卡不得因该旧帧缩短或消失；`message_end` 仍负责封存终态。Room 活动的落盘修订与已读水位继续以服务端 JSONL 投影为准，不能从流式 token 推导。
- direct/group 列表每行持续显示所属 Workspace（无项目时为“默认工作目录”），使同一 Worker 在不同项目的房间于点击前可辨；项目名不依赖消息摘要、搜索词或悬停才出现，选择按钮的可访问名称也包含项目。
- 从工作台 Manager 会话打开 Worker 窗口时，`/chats` 地址携带 `returnSession` 作为返回来源，并在后续切换 direct/group 窗口时保留；“返回 Manager 原工作”跳到 `/?session=<id>`。Session ID 只是定位线索，工作台仍须调用服务端归属/Workspace 定位并激活原 Session；对话文本草稿按用户、Workspace、Room、Session 隔离保存，切换范围时重建输入状态，不把 Worker 房间并入 Manager 模型上下文。本地存储被拒绝时，同一标签内用同样的隔离键暂存文本，跨刷新恢复只在存储成功时成立；身份读取失败时保留当前输入并显示重试，不能把未确定身份的草稿存入其他用户范围。发送确认后立即清除本次正文的持久草稿；等待期间的新编辑仍保留，失败时保留原草稿。未发送附件在同一标签内按相同隔离键暂存 File 对象，切回时重新生成预览 URL；页面刷新后不恢复附件。同一浏览器标签的对话阅读位置按 Room/Session 暂存，完整历史显露后才恢复，处于底部时继续自动跟随；精确滚动与审批上下文仍须在 M1/A05 浏览器旅程中独立验证。
- 从 `/?session=A` 深链由本页主动把 Solo Manager 原地切换到另一 Workspace 后，地址与本地定位必须立即指向服务端返回的目标 active Session；不能让旧 `?session=A` 的定位守卫把用户自己的切换误判为“其他窗口改变”。浏览器后退或再次选择 A 时仍按归属路由重新定位；运行中或待审批委托按项目切换协议终止/过期，不假称仍可审批。
- 静态导出的工作台和 `/chats` 在服务端 HTML 与浏览器首帧使用相同的空定位状态；挂载后才恢复 URL 中的 Session、Room 及 `returnSession` 并执行归属定位。`/chats` 的路由观察器首次通知必须处理（包括空查询），不能用浏览器当前查询初始化“已处理查询”而跳过恢复；归档返回链接和“返回 Manager 原工作”入口均随恢复后的定位更新。直接打开深链不得因首帧条件分支不同产生 hydration 错误，定位失败仍给出显式恢复入口。
- 普通会话发送须在同一标签内串行占用提交操作；HTTP 请求未决时显示提交状态、阻止连续提交，运行中的 Session 拒绝新的发送而保留输入。拒绝/失败不能被输入组件误当作成功并清空草稿；服务端已确认接收后才清空本次正文。
- 普通会话发送使用同标签页稳定 `Idempotency-Key`；服务端在附件冻结、写 user 或派发 Worker 前，将操作键与 Session、窗口/Workspace 身份、正文及有序附件摘要持久预约。缺键返回 428，同键异上下文/内容返回 409；pi 路径在本次 user 条目写入 JSONL 后标记接受，direct 路径严格核对用户卡和 task_assign 的可见 JSONL 条目及文件同步，并等待 Delegation 持久接单后才标记接受。direct 的两张入场卡带 `operationId`，`taskId` 由操作键稳定派生，Worker 请求也沿用同一操作身份。响应丢失后的同键重试或冷启动重试可回放已接受结果，不再新增 user/用户卡或启动第二次 Worker；成功回放后客户端须同时清除恢复自同标签存储的操作键，使之后再次发送相同正文成为新意图；预约已落盘但结果不可判定时返回 `message_delivery_unconfirmed`，页面保留草稿与原键并提示核对历史，不能自动重放。当前实现是阻止重复副作用的保守协议，不声称所有进程中断都能自动恢复完成；direct 卡片与 Delegation 的崩溃中间态尚未统一为可恢复事务，浏览器与真实 Worker 故障旅程仍属 T13 出口。
- direct 卡片写入期间持有窗口生命周期锁并在锁内重核窗口/Worker 身份；等待 Delegation 接单必须在释放该锁之后进行，因为委托创建也要取得同一锁。安装态断连夹具已证明服务端已接受后代理吞响应、同键与冷启动回放不重复 user 卡或 Worker 派发。`reserved` 同键重试只有在当前窗口/Worker、两张唯一可见 JSONL 入场卡和同操作键的 Delegation 身份均匹配时，才可把账本恢复为 `accepted`；缺任一事实仍保持未确认。合成账本断点已验证完整事实前缀，部分前缀和真实进程退出点仍待 T13 验证。
- 普通消息结果未确认时，界面先刷新并展示会话历史，供用户核对旧消息是否已出现。用户核对后可明确选择把保留的草稿作为新消息；界面须提示旧请求稍后完成可能产生重复消息。确认只废弃本标签旧操作键并保留草稿，仍由用户再次点击发送；默认重试继续使用旧键。旧结果未确认时即使用户修改正文或附件，发送入口也不能自动换键提交，而应要求先核对历史并明确选择新消息；刷新后从同标签存储恢复的旧键同样受此门禁。刷新历史本身不生成新键。Session 不存在、项目上下文已失效等确定性错误不提供该入口。此人工恢复路径不能被视为服务端 `reserved` 事务已解决。
- 普通 pi 路径在本次 user JSONL 条目已确认后追加隐藏的 `pudding:message_admission` 接收凭据，写入并同步同一 Session 文件，再标记操作账本 `accepted`。凭据绑定操作键、请求与上下文摘要、本次 user 条目 ID；冷启动同键重试只有凭据唯一且对应 user 条目唯一时才恢复 `accepted`。user 已落盘但凭据尚未写入的中断点仍保持未确认，不凭相同正文推断本次操作已接收。
- 普通 pi 消息已接受、模型请求进行中但服务进程中断后，历史可能只有已落盘 user 而无 assistant。历史接口在当前未运行、最后一条对话消息仍是 user 且该条目确实存在于 Session JSONL 时返回 `unansweredUserMessage=true`；只有内存 user 不足以声称已保存。若已有落盘的 `stopReason=toolUse` assistant、但没有后续最终回复且当前不运行，返回 `unfinishedAssistantTurn=true`，提示先核对工具及审批状态。两类提示只陈述已有历史和运行态，不自动恢复模型执行；同键回放仍只确认接收，不自动重派。
- 普通消息的绝对路径可访问性、Workspace 外目录授权、附件形状与内部冻结身份在冻结/发送前检查。能够证明尚未开始附件冻结的确定性失败，以 `message_operation_rejected` 持久记录原请求和原因；同键重试回放相同 400，同键改内容仍为冲突。页面保留草稿但清除已拒绝的操作键，下一次主动发送生成新键，以便用户修复文件或权限后用相同正文重试。附件冻结开始后的异常以及 pi/direct 发送中断仍保持 `message_delivery_unconfirmed`，不能被预检拒绝逻辑降格为安全重发。
- 打开行内 Pi Worker 历史时，主会话与 Worker 历史索引共享首次就绪边界；索引请求失败后主会话可局部降级为任务卡片，但必须展示“Worker 执行记录暂不可用”和重试入口，不能把失败当成无记录。索引恢复后清除提示，后续自动轮询仍可追上进展。失败或重试不应重新遮蔽已经呈现的主会话。运行中任务的“终止任务”入口放在该任务行内记录顶部右侧，不能随长正文落到记录末尾；终止仍只作用于该 Worker 委托。
- Worker 索引成功后，单条执行历史读取失败也必须在对应任务处显式显示错误和单条重试；已有任务摘要可保留作为局部信息，不能覆盖错误提示。重试只重新读取这一条 Worker 历史；主会话和其他 Worker 记录维持当前呈现状态。
- Worker 执行过程的实时 WS 中途断开时，已显示的过程正文仍留在抽屉并标明可能不是最新；手动重新读取期间不退回空白加载态。非归属类快照读取失败继续保留正文与局部重试，归属拒绝则隐藏旧正文。重连后只接受当前 WS 的事件；终态快照确认后撤销旧连接，迟到事件不得改写终态记录。
- 普通 pi 消息入口的 HTTP `accepted` 必须等待 pi 的模型/扩展准入回调；准入失败返回错误，不能先答应发送再异步失败，导致前端清空未被接收的草稿。工作台首次发送另须等待对应 user JSONL 条目落盘；direct Worker 消息走独立委托路径，不能把 pi 的流式运行门禁套到并行委托上。direct 房间的 Session 模型不控制 Worker 委托：执行模型来自目标 Agent 的 Connector 配置；输入区展示该 Worker 的**配置模型**并链接到 Agent 配置，不提供会误导用户的 Session 模型切换入口。配置变更只对新建或重开的 Worker Session 生效，续接中的 Session 可能继续使用旧模型，因此页面不能把配置模型称为当前 Run 的实测模型。
- `/chats?room=` 的目标接受仍存在的 solo/direct/group 窗口。已删除的房间不得让旧 `session` 参数挂到回退后的其他房间。初次列表回读或已加载页面的路由变化发现失效目标时，选择现存窗口、清除失效的 `session` 并修正 URL；原 `returnSession` 参数继续保留。房间仍存在但目标 Session 已删除时，以房间详情的权威回读为准清除 URL 的旧 `session`，旧请求回调不得覆盖后来的导航；目标 Session 仍存在但激活或回读失败时保留深链并显示重试，不把当前会话当作已定位目标。浏览器历史返回无 `room` 参数的 `/chats` 时，已加载页面立即恢复当前有效窗口，不等下一轮列表轮询。用户正在发起的本地导航尚未落到地址栏时，列表轮询不得用旧 URL 覆盖新选择。
- 全局搜索从 Manager 当前有效 Session 进入 Worker 对话时带上来源；在 `/chats` 内搜索切换其他 Worker Room/Session 时沿用已有 `returnSession`。搜索结果中的 Manager 工作与智能体配置链接不附带该参数。参数本身不授予权限，返回时仍由服务端核验目标 Session 归属。搜索会话时，默认的“新对话”或 `(no messages)` 名称不能遮蔽已落盘的首条消息；对话侧栏筛选也同时检索名称与首条消息。Manager 工作索引覆盖当前和停放项目中由 solo Window 拥有、已落盘首条消息的 Session；用项目名辨识，不收孤立 Session、手动命名的空容器或重复的活动项目结果。已改名工作和历史会话仍按首条消息摘要可检索；精确标题优先于宽泛摘要命中，避免 20 条截断隐藏精确对象。点击后走原有 Session location/Workspace 激活流程，搜索索引本身不改变活动上下文。direct/group 的房间和现有会话搜索范围不受此限制。Manager 工作、对话与智能体独立加载，先完成的来源即可点击，其他来源仍显示加载状态；全部来源结束前 Enter 不按不完整排序跳转。关闭、重开或重试使此前的请求结果失效；任一来源失败时保留可用来源并显示局部错误。三个来源全部失败时明确显示搜索不可用；部分失败且无命中时，空态仅说明已加载来源的结果，不声称全局无匹配。
- direct/group 的历史 Session 切换按本页面点击顺序提交激活，防止较早请求迟到后覆盖较新的选择；切换期间忽略旧房间轮询结果，本地会话列表以最新状态为基础更新。历史预加载只作性能优化，不延迟激活请求的完成。
- Manager 的顶部会话菜单与聊天信息中的会话菜单均提供「新建会话」（2026-09-30）。新建或选择历史会话后，前端回读房间当前会话并同步页面目标及查询参数，刷新保持该会话；旧会话保留。知识库结构、授权或工具配置变化触发旧会话上下文守卫时，错误卡明确引导新建会话、选择知识库并重新提交原始资料。
- Teams 2.0 的「发起新工作」先保留按 `Idempotency-Key` 绑定的 solo Session，再提交首条消息；操作键、房间、Workspace context 和正文哈希固定绑定，重试复用同一 Session，冲突返回 409。工作台按用户与 context 在当前标签页的 `sessionStorage` 保存文本草稿及操作键；首次请求尚未发出前编辑正文可生成新操作。请求一旦尝试发出且结果未确认，编辑正文、模型或附件只更新可见草稿，保留原操作身份；相同输入可原键重试，变化后的输入须先刷新并核对工作记录，再由用户明确选择作为新工作发送。不同标签页分别持有未发送意图，不能用一个共享键互相删除。提交处理器在发出请求前同步锁住本次正文，阻止 React 状态更新前连续点击生成两个操作键；成功后、清空草稿的渲染完成前，同一正文也不能再次提交。浏览器存储不可用时，同一标签内按用户与 context 的内存草稿仍保留正文和操作键，支持切换项目后返回继续编辑或原键重试；跨刷新恢复仅在存储成功时成立。存储清理失败不得把已成功的发送报告为失败，也不得在同一标签内重新显示已提交草稿。身份接口加载失败时发送入口保持禁用并提供重试，不能永久停在无动作的错误态。接口 `POST /api/rooms/:id/new-work` 只用于 solo，请求必须携带发起时的 `workspaceId` 和 `cwdSnapshot`；服务端在预约前与 Session 创建后核对当前/实际 context，项目已切换时返回 409，不把旧项目草稿发送到新项目。提交前检查所选模型是否已配置凭证；内部首发消息入口在 pi 准入后还须确认本次正文对应的新增 user 条目已进入 Session JSONL，才向工作台返回 Session ID。若预约 Session 的首条新增 user 内容不是本次正文，即使它已经落盘，也不能冒充本次首发成功；原键重试按正文冲突拒绝。准入成功但没有 user 条目时返回可用原键重试的错误，不能假报成功；确认 user 落盘后无需等待 assistant 完成。模型运行过程中的异步失败仍由原聊天流呈现。
- 工作台首发可显式选择模型引用与最多五个附件；模型选择、附件 File 对象按用户与 Workspace context 保存到新工作草稿。预约摘要覆盖规范化正文、所选模型、附件顺序、规范化文件名、媒体类型、大小与字节 SHA-256；同键改模型、改附件或去掉附件返回 409。没有首条 user 消息时先将明确模型应用到预约 Session，再检查凭证并通过普通消息入口冻结附件、提交首发；响应丢失后同键恢复要核对首条 user 所列冻结路径对应的文件字节，不能只按正文或文件名假报成功。用户在首发请求尝试前改选模型/附件可清除尚未使用的操作键；请求尝试后的改选保留待核对身份并阻止直接换键发送，迟到确认只清理本次提交匹配的草稿与 File 对象。附件字节不进入浏览器存储，同一标签项目往返可恢复 File；刷新后丢失的附件会阻止发送，保留旧操作身份，要求重新选择并核对原工作，或明确清除后作为新工作发起。
- 消息入口若明确收到模型准入拒绝、执行已结束且没有新增 user 条目，回收本次冻结的文件；若已有新增 user，即使准入回调报错也保留可能被引用的文件。首发冻结文件带有本操作正文/附件身份派生的批次标记。超时或落盘结果不确定时不立即删除；同键重试仅在原预约 Session 已空闲、SessionManager 分支仍无任何消息时回收该批次，再执行下一次冻结。仍在运行时要求稍后重试；已有消息时先按首条 user 核对或保守冲突，不清理可能被引用的文件。同 Session 其他操作及普通消息的附件不在本次回收范围。
- 新工作正文引用 Workspace 外绝对文件时，消息入口把原路径替换为 Session 所属冻结路径并将文件列入首条 user 的附件清单。响应丢失后的同键重试按同一条路径解析规则重建正文，验证清单中的文件在该 Session 下、大小与文件名内的 SHA-256 和实际字节一致；原源文件删掉后仍可确认已经落盘的首发，不重新读取它或制造第二条用户消息。操作键在此绑定的是正文中的路径引用及 Workspace context，实际发送的冻结副本是已接受回合的事实；对源路径状态变化不能误称为“新附件上传”。
- 源路径已失效且文本路径位于 Workspace 内时，它可能原先是指向外部文件的符号链接。恢复时把这类引用当作可选冻结候选，按原消息入口的引用顺序与落盘清单尝试重建正文；所有候选组合都不能匹配时拒绝自动确认，搜索有上限并在歧义过大时保守失败。首发尚未接纳前，绝对路径是“在发送时读取”的引用；要固定提交字节应使用显式上传附件。首条 user 已落盘后只认它指向的冻结副本，原路径变化不改写既有工作。
- 新工作操作账本必须校验顶层映射和每项键、Room、context、Session、正文摘要及状态；格式损坏时拒绝预约且不覆盖原文件。合法操作键即使与普通对象的继承属性同名，也只能按账本自有键判断是否已经预约。
- 操作键预约先以 `0600` 临时文件写入并同步文件，再 rename 和同步目录，全部完成后才允许据此创建 Session。rename 前失败清理临时文件；rename 已发生而目录同步失败时，当前实例无法判定提交是否持久，必须封锁后续预约/附着写入，重启从账本回读并核对原 Session 身份后再继续。
- 预约为 `reserved` 时，重试按固定 Session ID 逐步修复：Session 文件已存在但尚未挂房间则只补房间关系；已挂房间但未标 `attached` 则重复挂载必须去重，再落 `attached`。只有 `attached` 且 Session 与房间均不存在时才报告已删除，不自动新建替代工作。该流程不得因中断点不同产生第二个 Session。
- 首次发送重试若预约 Session 已有用户消息，必须核对首条用户消息的正文与本操作冻结正文一致；其他消息不能当作“原工作已发送”的证明。内容不一致返回 `first_message_conflict` 与原 Session ID，保留草稿和操作键，不再次向有内容的 Session 注入原工作；工作台展示跳转到该 Session 的核对入口。
- Pi 1.x 在 user 之前落盘的 system 配置条目不表示首发已受理。无 user、当前不运行且分支仅有配置/状态条目或空文本、已确认 error、明确零用量且无 nestedCalls 的 assistant 时，同键可重试原预约 Session；错误记录保持原样，不改写 SDK JSONL。已有回复/思考/工具调用或结果、custom message、compaction/branch summary、非零或未知用量、取消状态时仍返回冲突，不把缺失意图当成安全重跑许可。只在真实 user 落盘并匹配原操作及冻结附件后返回 accepted。
- 首发重试核对的首条 user 必须能以同一 SessionManager 条目 ID 在 JSONL 中找到；仅存在于内存的 user 不能返回 `accepted`。运行中的重试保留原操作键和附件、不重复发送；持久状态仍不确定时返回可重试错误，冷启动后再按落盘分支决定确认、回收或冲突。
- 条目 ID 命中本身不足以证明接纳：JSONL 中该行还必须是 `message/user`，且落盘正文与本次冻结发送正文一致。首次提交核对落盘正文，重试也以磁盘正文对照本操作及冻结附件；内存正文与落盘正文不一致时不得返回 `accepted`。
- 进程内只合并尚未完成的同键请求；一次请求已经返回成功后，后续同键重试仍重新核对 JSONL 与冻结文件。若 Session 文件随后丢失 user 或内容变化，旧成功标记不能继续冒充持久事实，也不得自动制造第二条用户意图。
- 已附着的首发操作若其 Session 已从房间和 Session 存储中删除，同键重试返回 409 `session_creation_deleted` 与原 Session ID，不补建替代 Session。工作台保留正文，明确显示“确认作为新工作重新发送”；只有用户点击后才换新操作键提交。切换 Workspace 的明确 Manager 更新同步推进前端当前 context 身份，旧请求即使在 React 下一次 render 前返回也不能导航或覆盖新项目草稿；原请求成功时可清理原项目的已提交草稿。Session 仍在但归属或存储不一致时继续拒绝自动恢复，不能将不确定状态误判为已删除。
- 工作台的 solo 历史菜单只负责切换、重命名和删除已有 Session，不暴露会预创建空 Session 的旧“新建会话”动作；新工作统一从工作台输入并在首次发送时创建/复用 Session。direct/group 的“新建会话”动作仍按原语义保留。
- 工作台首页只保留发起新工作和当前项目的工作记录入口，不嵌入聊天窗口；选取记录或发送新工作后进入同一路由的独立 Manager 对话视图，顶部可返回工作台。工作台输入框以 Enter 发送、Shift+Enter 换行；顶部不再重复提供“全部对话”跳转，统一由左侧主导航进入对话。发起区可按当前 Manager/Workspace context 选择一个或多个已接入知识库，选择结果通过 revision 门禁持久化；项目切换后读取对应 context 的独立选择。历史工作入口只列当前 solo Workspace context 的有内容 Session，选择后用 `/?session=<id>` 定位并由 ChatPane 核验归属；切换 Workspace 后依服务端当前 context 的 Session 列表刷新，不显示停放项目的历史为当前项目工作。列表轮询用请求序号丢弃乱序旧响应；历史 Session 定位与 ChatPane 明确更新当前项目时，使此前发出的轮询失效，定位期间不接受列表响应覆盖目标项目。同一标签快速选择多个历史 Session 时，定位请求按选择顺序执行；旧请求切项目返回后不得继续激活旧 Session，后来选择必须在旧副作用结束后重新按服务端归属定位，不能因原本在本地列表中就跳过。工作台仅在定位、激活和 Room 回读确认目标仍为 active 后挂载带目标 Session 的 ChatPane；该入口由父页面负责激活。轮询或 ChatPane 回读发现目标已被其他窗口切走时，撤销定位并显示重试入口，由用户决定是否重新定位，避免多个标签自动互相抢占 solo context。首页项目按钮直接在工作台上层打开同一项目选择弹窗；打开、取消和关闭时保持工作台背景与页面位置不变，确认切换后刷新当前项目的工作记录。`/chats` 独立入口仍由 ChatPane 自己激活请求的 Session。后端复用初始空容器时同时检查已落盘业务活动和内存消息，避免首条消息尚未投影时把已有对话当空容器。
- 直接打开 `/?session=<id>` 且目标属于已停放的 solo context 时，先通过 `GET /api/rooms/:id/sessions/:sid/location` 校验房间归属并取得原 Workspace，再走现有 `switch-workspace` 的 in_place 停放/恢复流程，最后激活目标 Session。目标不存在、属于其他房间或原 Workspace 不可用时显示错误，不把旧会话接到当前项目；从工作台手动切项目时清除旧 Session 查询参数。
- 已读水位按当前本机用户、Room 和 Session 保存；`PUT /api/rooms/:id/read-watermark` 必须带所属 `sessionId` 与客户端已经呈现的 `activityRevision`，在重建活动投影后检查修订上界，只确认该 Session。`GET /api/rooms` 返回 `readRevision`/`hasUnreadActivity`；其中 `readRevision` 是已确认的最高 Room 快照修订，跨 Session 是否仍未读以 `hasUnreadActivity` 为准。前端在目标 Session 的完整历史显露且页面可见后确认进入时看到的修订；当前打开的 Session 后续出现新修订时，先重新取得并呈现该 Session 的持久消息快照，再确认旧修订；快照或确认失败会重试，隐藏页面延后确认。确认成功后须记录本地已确认修订，即使 Room 状态回读触发页面 effect 重建也不得重复确认同一修订；确认失败才按原策略重试。其他 Session 与尚未呈现的新后台进展仍保留未读，并优先成为列表打开目标。已读不改变 `lastActivityAt` 或列表排序。
- `activityRevision` 比较的是 Room 内去重后可见业务事件集合的稳定摘要，而非只比较最新事件 ID；因此延迟落盘、时间戳早于当前最新消息且需要阅读的新进展仍推进对应 Session 的未读版本，但不把 `lastActivityAt` 倒退。未读 Session 的预览取其最后落盘的可见进展，避免迟到事件到来时仍显示已读的较新时间戳消息；Room 的 `lastActivityAt` 与整体活动排序仍按业务时间戳。相同 Session/条目 ID 的重放只计一次，改名和模型元数据不进入摘要。
- `display:false` 的 `pudding:*` 恢复/审计投影不单独渲染，也不计入 Room 活动或未读。可见的 `pudding:task_assign` 以 Session + `taskId` 作为一次业务指派；后续同任务的 `delegationId`/`sessionHandle` 富化卡只更新既有执行卡，不再次推进活动时间、修订或未读。
- 活动修订和按 Session 的已读水位保存在 Home 状态文件。重启读取该文件时只有文件不存在才从空状态建立；读盘错误或格式/字段损坏必须报错并保留原文件，不能静默重置修订和已读水位后覆盖它。
- 状态文件更新先写权限为 `0600` 的临时文件并同步文件内容，再 rename 与同步目录；rename 失败清理临时文件并保留旧状态。若 rename 已发生而目录同步失败，当前进程不能判断磁盘提交结果，必须拒绝后续投影/已读操作，待重启从状态文件与 Session JSONL 重放。
- 扫描 checkpoint 只在当前进程内缓存文件身份与已解析事件；同一 Room 的 Session 文件身份均未变时，复用上次投影结果，不再合并和散列全部事件。持久化的是 Room 事件集合摘要、修订及已读水位。重启按 JSONL 重新计算事件，避免把另一个可陈旧的消息副本当作事实源。双 Room、多 Session 的重复条目、token、改名与重启反例必须保持各自摘要和修订稳定。可用 `apps/server/scripts/room-activity-benchmark.mjs` 量测大历史重放；若将来引入持久扫描缓存，它只能是可丢弃的优化，源文件身份失配时必须重放 JSONL。
- 房间仍引用某 Session 时，已有历史文件的读取失败或缺失不能解释为“该 Session 的消息已删除”；投影拒绝此次更新并保留已持久化的修订/水位。房间 Session 关系确实移除该 Session 时，才允许缺少该 Session 的文件路径并重建摘要。新建且尚未落盘的 Session 可以没有历史文件。扫描缓存的文件身份同时检查大小、修改时间和状态变更时间，避免同尺寸、恢复旧修改时间的改写长期滞留。
- Session JSONL 中已换行完成的记录若无法解析，活动投影报错并保留旧修订与水位；未换行的最后一行可能正在追加，暂不纳入投影，文件再次变化后重试。不能将完整坏行静默跳过并把不完整的活动当作已确认事实。
- 自己发送的 user 消息及其 `pudding:user_message` 镜像、自己回答决策后的 `pudding:decision_answered` 与处理审批后的 `pudding:interaction_resolved` 可推进房间业务活动与排序，但不单独制造未读；随后 Worker 的 `pudding:task_result`、assistant 回复及其他需阅读的协作事件才推进对应 Session 的未读版本。
- `PiSessionStore.create()` 已在返回前首刷 Session header，首条 user 消息由真实 SessionManager 直接追加，即使 assistant 尚未回复也能按 JSONL 重建活动。assistant 的 `message_start`/`message_update` 是实时过程，不进入 Room 活动；完整 `message_end` 落盘后才推进摘要、排序与未读修订。前端重放历史加载期间到达的实时事件时，优先以同进程 HTTP/WS 的 `puddingMessageId` 对账 user/assistant，避免同一消息出现双份又保留同毫秒、同正文的不同用户意图；pi 的流快照若换对象使 wire ID 变化，只允许按同一 timestamp 合并**仍在流式状态且中间没有新 user** 的 assistant 回合，不能合并已完成或下一轮消息。错过本轮 `message_start` 的 update/end 应补入本轮消息，已终结快照不被迟到事件改写。若界面已看到流式文本而列表尚未置顶，这是持久事实边界，不能用 token 时间冒充已落盘回复。
- 当前房间选择按浏览器本地状态保留：刷新后优先恢复最后打开且仍存在的 solo/direct/group 房间，不得无条件跳回 solo manager；历史房间已删除或数据目录已切换时才回退到 solo。
- `/chats?room=` 的房间首次读取失败时，对话区域持续显示实际错误与重新加载入口；重试成功后才展示该房间及其会话。加载期间显示明确状态，不用空白聊天区域或一次性 toast 代替错误态。
- 删除对话的确认弹窗在服务端确认删除后才关闭；请求期间禁用重复提交和取消，失败保留原确认上下文与重试入口，列表与当前选择只在成功后更新。等待删除响应时若用户已选别的房间，成功返回不能覆盖后来选择；只从最新房间列表移除目标。
- 发起 direct/group 的请求发出后，创建弹窗保持打开并显示提交中，取消、Esc、遮罩关闭及重复提交暂时不可用；服务端确认后再关闭并切到返回的房间。失败则保留 Worker 和 Workspace 选择，允许明确重试。
- 群聊创建请求必须携带本次意图的 `Idempotency-Key`。客户端在同标签页保留未确认操作键；网络响应丢失后，以相同成员与 Workspace 重试复用原键，服务端按成员集合、Workspace、名称和协作提示词核对请求身份。相同键与意图只返回原 Room/Session；同键改意图返回 `409 room_operation_conflict`。删除后保留操作键墓碑，迟到重试返回 `409 room_operation_gone`，用户再次明确发起时换新键。窗口和操作身份原子写入 `windows.json`；提交状态不确定时返回 `409 room_creation_uncertain`，重启回读后再决定后续动作。该保证覆盖携带操作键的 API 请求，不把相同成员的不同意图自动合并。
- 从已有群聊跨项目“新建群聊”同样要求 `Idempotency-Key`；请求身份由源 Room、页面所见的来源配置快照和目标 Workspace 确定，并与新目标 Room 原子落盘。同键回放先查目标操作身份，响应丢失后的冷启动回放仍回到原目标 Room/Session，即使此后源 Room 改动或删除。首次发起 direct/group 时，客户端传来源类型、显示名、成员、提示词、Workspace ID 和冻结目录；服务端先与当前来源核对，在建房写入队列中再次核对来源存在且配置未变，然后才复用目标或创建 Session。来源已删除返回 `404 room_source_unavailable`，配置变化返回 `409 room_source_changed`；页面清除未成立的群聊操作键、刷新房间列表并要求重新打开来源后发起。Direct 的跨项目入口按 Worker 和 Workspace 复用；solo 的原地切换沿用其独立停放/恢复契约。
- 跨项目弹窗从创建或切换请求开始到收到确定结果期间保持打开并锁定选项、取消、Esc、遮罩关闭及再次提交；信任确认后发出的同一请求也受此锁。失败恢复原选择和可重试入口，群聊结果不确定时继续使用该目标的原操作键，成功后再进入目标房间。
- 「+ 新对话」入口改为**发起**：明确选择 Worker 单聊（已有窗口则打开）或 Manager 群聊（至少两位 Worker）。solo 不在创建选项里（单例）。现状 `create-room-dialog.tsx` 勾选逻辑复用，补去重逻辑。
- 发起或跨项目打开 direct/group 前，服务端必须核对所有成员仍存在且处于启用状态；该核对先于 direct 去重命中，停用 Worker 不能借已有房间绕过发起门禁。建房存储队列内再次复核成员，并在复核后创建 Session、写入窗口，避免启停插队造成孤立 Session；`create_group_window` 与自动 direct 建房使用同一门禁。群聊成员更新同样拒绝停用、未知或 pinned Manager；已存在房间的历史仍可读取。停用冲突返回 `409 worker_disabled`，发起弹窗刷新可用成员并移除失效勾选，保留工作空间选择；用户重新启用后可继续打开原单聊。
- 建房横跨 Session JSONL 与 `windows.json`：窗口写入在 rename 前明确失败时清理本次新 Session；rename 后目录同步失败则保留 Session，封锁继续写入并要求重启回读，不把结果当作确定失败重试。若补偿清理自身失败，接口明确报服务端恢复错误。新房间在创建 Session 前先把随机 Session ID 记入 `room-creation-journal.json`；启动时仅处理该预约指向的 Session，有窗口归属则保留、无归属才清理，恢复失败阻止开放路由。专用账本、真实 Pi SDK JSONL、当前发行 bundle 的两侧进程退出回读，以及当前 tgz 的空缓存常规 npm 安装与 CLI 回环已验证；其他目标平台与真实目录同步故障仍是独立验收项。
- Teams 2.0 发起对话时明确选择已有 Workspace 或默认工作目录；从当前对话发起时预选当前 Workspace。目录不可用或原 Workspace 已从列表移除时保留原选择并阻止提交，必须由用户重新选择，不静默落到默认目录；Worker/Workspace 列表加载失败显示错误与重试，不伪装成空列表。若提交期间 Worker 被删除/停用或 Workspace 被移除/路径失效，服务端返回可区分的选择失效错误；该判定覆盖页面预检之后、建房存储复核之前的竞态。发起弹窗就地刷新 Worker 与 Workspace 清单，保留失效 Workspace 的原 ID 并阻止再次提交，直到用户重新选择。跨项目弹窗也回读失效项目列表、显示错误并要求重选；列表读取失败可重试，不能显示成真实空列表。创建成功关闭后清除上次勾选。创建请求携带 `workspaceId`，direct 仅在同 Worker、同 Workspace/cwd 身份下复用，group 在所选项目新建。
- 智能体与扩展是两个一级入口：`/agents` 只管理 Manager/Worker 角色、连接方式与运行状态；`/extensions` 统一承载 Skills、MCP 与插件入口。Agent 配置页不再提供 Skills 编辑入口，避免把“谁在工作”和“系统装了什么能力”混在一起。当前版本的 MCP 页只保留真实能力边界说明，未接入可执行 MCP invoke 前不提供伪配置动作。
- 主导航底部展示当前用户名。身份读取收敛到 `GET /api/identity`，响应从一开始就拆为 `user{id, username, displayName}` 与 `tenant{id, name}`；当前单机版由本机 OS 账户映射为 `mode=local`，未来接认证与多租户时替换 identity provider，不改导航消费契约。用户节点保留稳定的 `data-track="nav.current-user"` 及 user/tenant 维度，供后续行为分析接入，不在当前版本上报遥测。
- 左侧导航抽屉的“知识库”显示全局、当前用户可见的待审核批次数，复用审核中心的 `pendingCount` 与刷新事件，页面可见时每 4 秒回读。无待审、尚未读取或读取失败时不显示数字；超过 99 显示 `99+`，完整数量供辅助阅读与悬停查看。知识库与“稍后读”共用弱化文字计数样式，无实心底色；展开时右对齐，收起与窄屏时在图标角上显示。

## 4. Manager 派活路由

solo 允许全部启用 Worker；group 使用选定成员与有效 Worker 的交集。Manager 使用统一 delegation 工具，每次 fresh；越范围调用拒绝。调用与结果属于来源会话，不自动建单聊或复制可见镜像。已有调用及审批按冻结契约处理。

## 5. 会话管理与聊天信息

菜单只列普通会话，支持切换、新建、重命名、删除和支持时 Fork；聊天信息中的会话数量只计算这些会话。执行记录从工具详情或全局搜索打开，不提供第二个发送入口。模型与思考档位作用于当前会话负责人。


## 6. 后端端点变化（在现状 rooms 路由上演进）

| 端点 | 变化 |
|---|---|
| `GET /api/rooms` | 返回窗口模型（id/type/members/sessions/activeSession/pinned），按业务活动排序；solo 置顶由前端分区实现 |
| `POST /api/rooms` | 接受 `{type, members}`；direct 去重命中则 200 返回已有窗口 |
| `DELETE /api/rooms/:id` | **新增**：级联删除（solo 拒绝，405/400） |
| `POST /api/rooms/:id/sessions` | 不变（窗口内新建 session） |
| `PATCH /api/rooms/:id/sessions/:sid` | **新增**：重命名窗口内 session，手动名称不被自动标题覆盖 |
| `DELETE /api/rooms/:id/sessions/:sid` | **新增**：窗口内删 session（最后一个拒绝） |
| `POST /api/rooms/:id/sessions/:sid/activate` | 不变 |
| `team_task` 工具 | solo 上下文时注入目标窗口 session 摘要 + `session` 参数；执行后写 direct 窗口消息流（§4.4） |

agents CRUD / probe 端点不变。

## 13. 可选 Workspace 语义（2026-08-10 收口）

- Workspace 不是发起聊天的必填项。solo、direct、group 都允许不选择项目；创建时把平台默认 cwd 冻结到 Window，manager Session 与 worker Driver 始终共享该快照，保持原有入口且避免跨重启漂移。
- 选择 Workspace 后，Window 保存 `workspaceId + cwdSnapshot`，manager 与 worker 共享该项目的 canonical cwd；路径失效只把对应窗口标记为不可用并阻断执行，不阻断服务启动，也不回退默认 cwd。
- 项目上下文可双向切换：显式 Workspace 可以切回“不绑定项目”。direct 默认按 `(worker, workspaceId ?? cwdSnapshot)` 创建或打开单聊，group 默认新建一个成员相同、项目不同的群聊；二者的 Workspace 身份不可原地替换。solo 是固定单例，切换时停止旧任务并停放完整 context，切回后恢复原 Session/续接状态，首次进入目标项目才新建 manager Session。
- Worker 的 cwd/Workspace 只是协作上下文，不是 Teams 沙箱。只读任务若目标 Worker 无法证明原生只读，房间先显示 Teams 准入卡：明确 `Worker 尚未启动`，用户可继续、换成服务端确认能补足当前缺口的 Worker，或取消。继续只代表允许 Teams 使用当前 Worker，不修改 Worker 权限；换 Worker 会终结原委托并创建有因果链接的新委托，不复用旧 Worker 会话。改派候选在选择时和 Driver 启动前各校验一次；房间、Workspace、成员、能力或 WorkState 已变化就 fail closed。`waiting_admission` 会阻止 Goal 完成和同 WorkItem 重派，但不计为 live Worker；停止 Session、删除房间、切换 Workspace 或 Goal interrupt 会直接取消该准入请求而不调用 Driver。
- direct 的身份为 `(worker, workspaceId ?? cwdSnapshot)`：同一 worker 可以同时拥有不同默认 cwd 的无项目单聊以及多个不同项目单聊，彼此不复用 manager/worker Session。
- 每次 Delegation 无论是否选择项目都冻结 `cwdSnapshot`；worker binding 同时记录 `workspaceId? + cwdSnapshot + agentRevision`，从而让无项目模式保留原行为、有项目模式保持跨项目隔离。
- manager 的 pi Session 统一保存在共享 `sessionDir`，恢复与枚举必须按该目录全量发现，再由 Window 持久化的 Session ID 和 `cwdSnapshot` 决定归属；不能用当前进程 cwd 过滤共享目录，否则不同 Workspace 的 Session 会在重启后被遗漏。刚创建、尚未首次落盘但仍在内存打开的 Session 同样视为存活，避免连续请求把 solo Session 误判为丢失并替换。

> 实现注记（2026-08-11，用户数据目录迁移与 Workspace 信任门）：上述共享 `sessionDir` 即 `PUDDINGTEAMS_HOME/sessions/`。无项目窗口的默认 cwd 快照固定为 `PUDDINGTEAMS_HOME/workspaces/unscoped`（中性空目录，不再使用 `process.cwd()`），服务端强制关闭 Workspace context/skills/prompts 发现，Preview 返回 `workspace: null, contextFiles: []`。显式 Workspace 增加信任状态：`WorkspaceTrust{state: pending|trusted|denied, decidedAt, policyVersion: 1, canonicalPathAtDecision, approvedResources?}`——managed Workspace 默认 trusted，外部项目初始 pending，`realpath` 漂移自动退回 pending；信任决定经 `PUT /api/workspaces/:id/trust` 保存，撤销后相关活跃 Session 标记 `runtimeDirty`。Workspace context/skills/prompts 进入装配候选的判定收敛为单点（`workspaceId && trusted && approvedResources 含对应 kind`，再与 Agent 自身资源开关相与），Preview、会话装配与 Delegation 统一消费。详见 `docs/2026-08-11-用户数据目录与Workspace上下文迁移方案.md` §6.3/§7。

## 14. Session Goal 与当前工作（2026-08-10 收口）

- Window 仍是长期协作空间；Session 是连贯对话容器，可以没有 Goal，也可以串行包含多个 Goal，但同时最多一个 active Goal。Manager Goal 内已实现 `WorkPlan/WorkItem` Harness 计划层；它不替代 Window、Session、Goal 或 Delegation，详见 `2026-08-21-Manager-WorkPlan与Delegation-Timeline融合方案.md`。
- Goal 的权威当前版本是带稳定 `goalId` 的 `SessionWorkState`：Goal 属于 Session，终态后保留为只读历史；solo/group 由 manager 维护，Pi 原生 Worker 不获得 Manager Goal 控制；Goal 由 Manager 会话维护。worker Run 的 completed 不直接把 Goal 判为 resolved。`goalRevision` 只在同一 Goal 的目标/完成条件变化时递增，使验收契约与普通进度 revision 分离，不能用来区分多个 Goal。
- 普通会话通过 composer 的 `/goal` 命令原地创建 Goal，不再常驻展示“设为 Goal”横条；`/goal <目标>` 可预填目标。当前代码要求用户在创建表单中逐行填写自然语言 `completionBoundary`，每个非空行就是一项冻结验收条件；没有“LLM 先生成标准”的步骤。Reviewer 只生成逐项满足状态、解释和证据引用，其 criterion 文本必须与冻结条件逐行、原序完全一致，不能合并、拆分、改写、降低或追加条件。
- Room、群聊或 Manager 在场都不等于 Goal 已创建。（2026-10-15 修订：`manager_explicit` 已删除）Goal 只能由用户通过 `/goal`/UI 显式创建（solo/group/direct 一致），或按 Harness `goalActivation` 整体禁用；Manager 不再有 `create_session_goal`/`supersede_session_goal` core tool，认为任务需要持续追踪时只能用自然语言建议用户创建，不主动提及 Goal 机制。完整矩阵见 Goal/Timeline 融合方案 §1.1。
- 完成方式由创建 Goal 的用户选择，当前前端默认 `independent`：`manager` 表示执行 Manager 根据冻结条件自审并提交完成，不产生隔离 Reviewer 记录；`independent` 表示 Manager 先提交完成申请，再由 PuddingTeams 启动一个全新的 Pi SDK in-memory Session。该 Session 不继承 manager 历史、不加载 Extension/Skill/项目上下文、无任何工具，只读取冻结目标、完成条件、最终摘要及可追溯 ToolResult/Delegation/Artifact/Decision 证据，返回逐项 `satisfied/unsatisfied/uncertain`。Reviewer 不能直接更新 Goal；只有 PuddingTeams 可在 revision 未漂移、无活动委托和待回答决策且 verdict 为 satisfied 时提交 resolved。若证据无法判断主观满意、业务授权或发布许可，Reviewer 返回 `needs_human`，Goal 保持 active，由 Manager 发起 `DecisionRequest` 请人确认；人类不是默认逐项验收者。
- 业务取舍使用 `DecisionRequest`，与恢复同一暂停 Run 的 Driver `Interaction` 分层。回答 DecisionRequest 后在同一 manager Session 中继续，不调用 `Driver.respond`，也不从普通答案推导额外授权。
- Delegation 保持 `Worker A → manager → Worker B`，记录 `parentDelegationId + handoffKind + intent + expectedOutcome + evidenceRequirements + completionBoundary`；单向通知走 custom message/event，不制造假的 Delegation 等待。
- Chat 顶部使用统一“任务与执行”入口：当前 Session 只要存在 Goal 历史或真实 Delegation 就显示；入口 badge 只展示当前轮次的 Delegation 完成进度，没有本轮 Delegation 时再展示 Goal 待处理/运行状态。轮次以用户消息为边界：从一条 user message 开始，直到下一条 user message 之前创建的 Delegation 都归入同一轮；最新一条 user message 对应“本轮”，更早任务通过执行区顶部的紧凑轮次下拉切换，不在内容末尾重复铺开历史列表。右侧第一层抽屉以“执行动态 / Goal”切换：执行动态的任务事实仍来自当前 Session 的 Delegation 权威列表，消息时间戳只负责划分展示边界；Goal 视图继续承接完整验收条件、当前进度、append-only 复核轨迹、证据引用、DecisionRequest、WorkItem 与 Artifact；没有 Goal 时不显示 Goal Tab，也不强迫普通 Session 进入项目管理流程。
- “任务与执行”抽屉固定在 Chat Header 下方，Header 始终保持全宽；桌面宽度足够时，只压缩中间消息区与 composer 为抽屉让位，抽屉和正文不重叠，窄屏回退为覆盖式全屏。worker 的“执行过程”仍使用 Chat 内右侧 Inspector，不打开居中弹窗；从执行动态或 Goal 深链进入时先关闭第一层抽屉，再按 Delegation 展示 pi Session 回放或 spawn 事件时间线，不能叠两层抽屉。切换 worker 不改变房间/会话，也不合并不同 Delegation 的历史。pi、Codex、PuddingClaw 与后续 Connector 共用该信息架构。
- 用户附件冻结到平台受控目录，图片作为模型 image input 传入，所有附件路径明确注入当前消息，manager 接力派活时必须原样传递所需路径。用户在消息正文粘贴绝对路径时，Workspace 内文件保持原路径；Workspace 外的普通文件由消息入口先通过安全文件描述符读取并冻结为当前 Session 附件，模型只看到冻结后的平台路径，源文件后续变化不影响本轮附件。Workspace 外目录不会因粘贴而被隐式授权，必须先登记为 Workspace，或由未来/显式的临时挂载控制面给出精确范围。
- 消息 Markdown 中的文件/附件链接统一按本地文件处理：相对路径基于 Window 冻结的 `cwdSnapshot` 解析，绝对路径仅允许位于该工作目录或**当前 active Session** 的平台附件子目录；不能把整个 `uploads/` 或同一 Window 的历史 Session 当成共享根。服务端经 `realpath` 校验存在性、文件类型与目录边界后调用系统默认应用打开。仅 HTTP(S) 等真正网络地址保留网页链接行为，折叠消息中不得嵌入会被裁剪的外链确认弹层。

### 14.1 Harness 代码搜索策略（2026-08-28）

- Harness 提供 Worker 全局默认 `codeSearch.defaultProvider: builtin | fff`；每个 Pi Worker 用 `AgentConfig.codeSearch: inherit | builtin | fff` 覆盖。`inherit` 在每次创建/恢复 Worker Session 时解析，Harness 设置变化不会让驻留 Session 永久保留旧工具集。
- Manager 使用独立的 `manager.codeSearch: off | builtin | fff`，默认 `builtin`，在 solo/group Manager 生效；direct 维持现有 Worker 通道。非 Pi Connector 不消费该设置。
- `builtin` 显式激活 pi 原生 `grep/find`；`fff` 以 override 工具名装配受控 `@ff-labs/pi-fff`。服务端过滤 pi 全局目录中用户自行安装的 `pi-fff`，防止绕过 Harness/Worker/Manager 策略；FFF 的 `/fff-mode` 也不暴露，Session 不能把产品策略改回其他模式。
- FFF 仅为显式且已信任的 Workspace 启用。frecency/history 数据位于 `PUDDINGTEAMS_HOME/runtime/fff/workspaces/<sha256(workspaceId,canonicalPath)>/`，Workspace 身份或 canonical path 任一变化都会产生独立状态，禁止跨 Workspace 共用索引、历史或排序信号。SDK Session 创建后必须绑定 Extension 生命周期，且受控 FFF 将 `session_start.cwd` 强制设为登记的 canonical Workspace，不能使用 Server `process.cwd()`。无 Workspace 或未信任 Workspace 选择 FFF 时 fail closed，不回退扫描 Home、文件系统根或平台默认目录。
- Goal/当前工作的动态状态必须在每次模型请求的 context 阶段按最新 revision 注入；仅依赖 `before_agent_start` 会漏掉 custom message 触发的 DecisionRequest 回答与续接，使 manager 读取到旧状态。该上下文消息只参与本次请求，不写回长期聊天历史。
- Goal 中断恢复以“同一 Goal/同一 Session，从最后原子安全点开新执行回合”为语义，不伪造崩溃前的 Manager/Worker Run 还存活。稳定 goalId fence 同一 Session 的旧 Goal 写入，恢复 epoch fence 同一 Goal 的旧执行回调，Goal 级 operation ledger 防重复写，outbox 保证 Decision 回答与 Goal resume 最终唤醒。对外部副作用不明的步骤不自动重放。

### 14.1 Session Goal 执行计划与统一“任务与执行”抽屉（2026-08-27 已落地）

- `SessionWorkState` 继续是 Goal 的高层权威状态；`WorkPlan/WorkItem` 是 solo/group Goal 内部的结构化执行面，不允许脱离 Goal 独立存在。Worker 私有 Todo 仍归 Worker 自管，不提升为房间事实源。
- `Delegation.completed` 只把绑定的 WorkItem 推进到 `submitted`；Manager 明确 `accepted` 后才解锁依赖项。WorkPlan 全部 accepted 后，Goal 仍需现有 completion review 才能 resolved。
- WorkItem `acceptanceCriteria` 由 Manager 从冻结 Goal 条件、步骤预期产物和下游依赖派生，Manager 负责 `accept/revision/blocked`；它不能给 Goal 暗中增加新要求，也不要求人类逐项验收 Worker 交付。Goal 条件仍由用户意图控制，最终按上面的 manager/independent/needs_human 门禁完成。
- solo/group/direct 都可以把普通 Session 原地设为 Goal；有 Goal 或 Delegation 的 Session 在头部展示“任务与执行”按钮。执行动态对三类 Session 都只展示真实 Delegation；Goal Tab 中 solo/group 展示 WorkItem 依赖图，direct 展示 Goal/完成条件与当前 Worker Timeline，不伪造 Manager Todo。
- WorkItem 默认以有向连线的 DAG 表达 `dependsOn`：分叉表示并行，汇合表示多前置条件，阻塞通过节点和入边色彩表达；不再以“依赖 W1”文字作为主表达。
- `SessionActivityDrawer` 与 `SessionRuntimeDrawer` 构成统一入口的两个第一层 Tab：前者使用 `/api/rooms/:id/delegation-processes?managerSessionId=` 获取当前 Session 的并行执行事实，再按 user message 时间边界分组为本轮与历史轮次；后者保留完整 Goal/WorkItem 信息。具体执行过程继续复用 `WorkerProcessDrawer` 内的 pi Session 回放或现有 `delegation-timelines/<delegationId>.jsonl`，不新增第二套 timeline。
- 消息卡“执行过程”、执行动态任务行和 Goal 内执行记录都保留为深链入口；打开 Worker 过程前必须关闭第一层“任务与执行”抽屉并预选对应 Delegation，不能同时叠两层抽屉。

### 14.2 可信协作状态与真实环境复验（2026-08-30 已落地）

- 房间消息流继续是协作入口，但“Worker 已报告完成”“已复验”“已接受”是三个正交事实。执行动态、Goal 抽屉和 Worker 过程统一展示 Execution / Verification / Settlement 三轴，不能用一个绿色 completed 同时代表三者。
- solo/group 的 Manager 负责 WorkPlan 编排和业务验收，但首期禁止 Manager 自执行写任务；写任务必须形成 Worker Delegation、sealed ExecutionReceipt 与 WorkspaceChangeSet。direct 仍是纯 Worker 通道，不因复验协议引入隐藏 Manager。
- WorkItem 的 VerificationPolicy 与 WorkspaceExecutionPolicy 来自 Harness 默认或 Manager 显式提高，并在执行边界冻结。Git 写任务默认进入独立 worktree，非 Git 写任务使用带持久 Lease 的 exclusive write；验收通过只提升精确 change-set，不自动 commit/push，冲突保留执行环境并阻塞。
- 强制 Verifier 可以不是房间可见成员，但必须是可审计的 `purpose=verification` Delegation、新 Session，并满足 Driver 声明且实际执行的复验能力。CLI/代码复验使用平台签发的隔离副本或受控目标；首期不把 GUI/Computer Use 作为强制路由范围。
- `observation_lost/effect_unknown` 是高优先级阻塞，不是普通失败。可能仍有外部副作用或写 Lease 时禁止自动重试；任务与执行 UI 明确提示对账/人工接管，不用新 Run 掩盖未知事实。
- Receipt、逐项 VerificationRecord、平台 observation、Workspace baseline/write-set/promotion 与冻结策略在 WorkItem 详情可审核；房间时间线不复制这些权威对象，只通过稳定引用和 API 投影。

## 15. Manager/Worker 提示词可见性（2026-08-11 收口）

核心事实源见 `docs/2026-08-11-PuddingTeams核心提示词管理方案.md`。房间模型固定以下规则：

- `AgentConfig.description` 保留通用名称：既用于 UI 展示，也给 manager 做 roster 展示、搜索与选择；`responsibility` 补充结构化责任和停止边界。二者都不是 Worker 自己的运行提示词。
- Worker 运行指令只进入该 Worker Session；manager 不读取其正文来做路由。平台在每个 manager 回合开始前按 Window 候选集合把最新 `description`、`responsibility`、能力事实和实际委托工具投影进 manager system prompt：Solo 为全部启用 Worker，Direct 为唯一成员的最小信息，Group 为全部已启用成员；manager 据此选择和委托。
- **Solo**：manager 在全部启用 Worker 的完整路由卡中选择；没有 Window collaboration。
- **Direct**：目标 Worker 已由窗口成员唯一确定，没有二次选择，也没有用户可编辑 Window Prompt。2026-08-12 起 direct 窗口无 manager 回合：用户消息直派该 Worker，Worker 行为由自己的运行指令决定；roster 与 relay 不再注入 direct session。
- **Group**：用户可编辑“群聊协作提示词”，只进入该 Group 的 manager，描述拆分、并行、交接、裁决与汇总；不得传给 Worker。
- pi global `~/.pi/agent/AGENTS.md` 与当前显式 Workspace context 会分别进入 manager/Pi Worker；只想让 manager 看到的规则不能写进 global `AGENTS.md`。
- 输入栏“默认目录”是 Window 的中立 cwd，不是 `~/.pi/agent`；切换项目决定显式 Workspace context，不能改变 pi global context 的归属。

## 16. Manager 建房与拉人（2026-08-12 落地）

只有用户明确要求时，solo Manager 才能创建群聊，群聊 Manager 才能扩大 Worker 范围。两者仍是平台 core 工具，要求当前用户的 sourceMessageId 与明确操作意图；普通多 Worker 工作不授予建群或加人权限。首发任务需要用户明确要求，否则只创建空白会话。

- **`create_group_window`（仅 solo 激活）**：参数 `members`（≥2 个不同的已启用 worker，内部 id 或显示名均可——服务端先按 id 精确命中、再按显示名唯一匹配，统一以 id 落库；roster 行首在显示名与 id 不同时标注 `（id：xxx）` 供模型映射）、`task`（可选，用户明确要求首发执行时填写）、`sourceMessageId`（用户明确操作的消息引用）、可选 `name` 与 `prompt`（群聊协作提示词，只给该房间 manager）。执行链路复用 `rooms.ts` 建房路径：先建 group manager Session 再落窗口记录，仅填写 task 且用户明确要求执行时，fire-and-forget 把 `task` 作为首条消息发给房间 manager（`chat.ts` 首发消息同款，异步生成标题），工具立即返回 `windowId` 而不等待执行结果——房间在自己窗口里干活，用户在群聊窗口看进度。前端把该工具结果渲染为「打开群聊」跳转卡。
- `create_group_window` 在初次解析 roster 后，仍须于存储串行写入区再次校验成员；Session 创建和窗口写入位于该复核之后。自动 direct 建房与旧房间复用也在同一队列内复核启用状态。
- **`invite_to_group`（仅 group 激活）**：参数 `members`（≥1 个已启用 worker）。逐个校验存在、非 pinned manager、已启用、未在群内（已在的跳过并注明），经 `updateWindow` 加入成员——自动走 emitChange → 撤权/空闲重建链，新成员下一轮进入 roster prompt，其委托工具在会话装配空闲重建后可用，与 UI 改成员完全一致。
- 门禁双保险：激活策略按窗口类型分发（solo 只激活建房、group 只激活拉人），工具 execute 内再做第二道上下文校验； pinned manager、禁用或不存在的 worker 一律拒绝入群。
- roster prompt 相应提示两条规则：solo 里任务一旦需要两个及以上 worker（含串行交接：一个 worker 的产出是另一个的输入）就用 `create_group_window` 建群聊下达整体任务，而不是在 solo 里逐个单聊派活、由 manager 搬运中间结果；group 人手不够时用 `invite_to_group` 拉人。
- 不做：manager 删房间、移除成员（涉及在跑 Run 的处理，保留为用户手动操作）；非 solo 窗口建房。

## 17. 长期记忆 Wiki 与首次初始化（2026-09-30）

- 初始化拒绝非空目录，并在确认执行前重新检查；既有 Wiki 通过原接入向导处理。后续内容增删改由 Agent 请求知识库管理 worker，继续走现有候选、diff 审核和发布流程。

- 这是所有 Pi Worker 的运行时标配：`AgentInvoker` 对 Pi Driver 统一提供知识 surface，`LocalPiDriver` 统一装配工具与运行时提示词。已有、新建、复制的普通 Pi Worker 均适用，不要求选择某个模板或逐个配置 memory 提示词。尚未初始化 memory 或用户取消挂载时，不伪造可用记忆。
- 普通 Pi Worker 的普通知识库工具只包含 `knowledge_context/search/glob/read/links`，另有仅默认 memory 可用的 `memory_request_update`，创建后台整理任务。受保护 builtinId 的 Wiki Worker 使用 `knowledge_prepare_candidate` 与 `knowledge_submit_candidate` 在本轮完成候选生成；Manager 沿已有 Wiki 委派入口处理知识业务，不直接获得这些工具。普通 Worker 不获得其他 Wiki 的整理能力。默认库或工具集合变化进入会话 fingerprint，旧缓存会话必须重新装配。

### 17.1 聊天中的知识整理（2026-10-01）

用户在工作台向 Manager 提出知识查询或整理要求时，Manager 在自己会话直接执行（2026-10-15 起不再委派 Wiki Worker）；用户在 Wiki 单聊发起时，由当前 Wiki Worker 直接执行。纯查询不创建整理任务。需要修改时，执行者先通过 `knowledge_prepare_candidate(bindingId,task)` 获得宿主关联的真实原话、附件和冻结基线/结构契约，再由本人检索查重、整理并调用 `knowledge_submit_candidate(bindingId,pages)`；不再转交另一个后台 Wiki 模型重复整理。

聊天整理仍登记持久 Job，`executionMode="worker"` 表示由当前 Worker 执行，不是一个等待后台接手的队列项。准备并不等于候选完成：本轮结束而没有有效提交，任务应显示失败；有效提交后的宿主回执提供固定候选与审核入口，Wiki Worker 停在候选边界。素材冻结、模型“完成”文字和聊天委派完成卡都不能代替候选提交，更不能表示原话已写入正式库。真正的写入只发生在用户审核后，由统一 Publisher 完成。

知识库主页、普通 Worker 的默认 Memory 更新、稍后读晋升以及后台生成故障的明确重试/退回修订仍可创建 `executionMode="background"` 的后台整理 Job。所有 Job 共用知识库“整理任务”入口及状态查询；后台 queued 对用户表示“已受理，准备启动”，不宣称存在同库 FIFO 调度。生成完成、当前审核状态与实际发布结果分别读取，已有 jobId 应查询而不是重复发起整理。

工具回执、任务 API 与聊天 `pudding:knowledge_job` 状态卡都使用宿主 executionMode，running 明确显示当前对话整理中或后台任务。worker 模式普通失败/取消只提供查看任务与返回真实来源 room/session 的入口，不能诱导用户点后台重试创建第二个整理模型。后台生成失败允许明确重试新任务，保留原失败记录。

候选已固定而审核登记失败时显示“候选已固定，登记失败”，失败码为 `candidate_registration_failed`；任务页提供“重新登记”。这一操作复用同 Job 的固定字节与 manifest，只补审核登记，不调用模型、不生成新任务、不改正式 Wiki。成功后进入真实候选审核入口，仍需用户确认发布。

默认整理预算为 15 分钟。超时先同步关闭提交栅栏，并持久化失败，不等待 SDK 中止完成才能显示终态；迟到候选或图片提取结果不能继续提交。已固定的候选登记恢复是宿主事务，不因模型停止而丢弃或重新生成。纯查询不创建整理任务。

同一人物对只显示一条线，按事件稳定身份去重汇总。done 且日期合法、不在未来的计入已发生次数及最近共同往来；planned 单独计数，仅有计划时用虚线。时间过去不自动将计划转为 done。cancelled/unknown 保留在已有连线的详情中，但不独立创建连线。连线只说明有共享活动记录，不宣称参与者直接交谈、认识或关系亲密；介绍人等明确关系在详情中保留方向和来源。

2026-10-04 联系人头像编辑：通讯录详情的头像提供上传、更换、预览和恢复姓名头像。支持 PNG/JPEG/WebP，最大 2 MiB；列表与详情共同读取人物笔记的 `avatar` 元信息（相对于该 Markdown 的图片路径），缺失或图片无法加载回退姓名缩写。手动保存直接编辑当前人物 Markdown，进入手动修改历史，不创建 Worker 候选或审批。图片存同一 Wiki 的 `assets/images/<sha256>.<ext>`（wiki 内容树对应 `wiki/assets/images/`），图片先完整落盘、排他发布，再以笔记 contentHash 做 CAS 保存相对引用。恢复仅移除引用，保留图片供旧版本使用。头像编辑不创建第二套联系人数据库、不修改用户的定制 schema，也不自动识别人脸或生成头像。

2026-10-04 好得内置头像选项：联系人头像弹窗优先显示好得 APP 的 32 款原始头像，保留名称与商务、专业、创意、活力、生活、经典分类，支持筛选、预览和选择；自定义上传仍可用。预览头像下方提供「恢复默认」，恢复姓名缩写；已处于默认状态时禁用。上传按钮使用「上传头像」。不根据姓名、职业或性别自动决定头像。内置选择保存时同样复制 PNG 到对应 Wiki 的哈希图片目录，用标准相对路径引用，离开客户端后人物笔记和图片仍完整。资源随 server assets 打包，不依赖好得 APP 的安装路径或远程服务。

### 2026-10-04 平台日历与人脉往来

日程事实保存在 `state/calendar/events.json`，参与人通过 `bindingId + personId` 引用已接入人脉库的现有联系人。`GET /api/calendar/people?q=&vault=` 复用 ContactsProjection 的有效 schema、采纳快照和权限检查，不按姓名推断身份，也不自动创建人物页。前端创建/编辑日程支持搜索、多选参与人；未选择往来关联时仅保存日程。当前往来关联支持同一人脉库的定时普通日程，全天和专注时段不生成往来。

勾选“同时记录为人脉往来”后，CalendarService 从日程字段确定性生成 `interaction` 候选，复用现有审核与 Publisher；没有第二轮模型调用、后台整理 Job 或 Agent 队列。批次身份为 `calendar:<eventId>:<calendarRevision>`，目标为该库 schema 布局下的 `Interactions/<日程标题>.md`（实体目录以 schema 为准；标题清洗为安全文件名，重名时追加事件短 id 后缀，标题清洗后无可用字符时回退 `calendar-<eventId>.md`，后续版本沿用首次生成的文件名，改标题不移名）。候选冻结日程版本、参与人的身份/路径/内容哈希、来源快照、schema/契约与库权限版本。日程先保存；候选失败明确呈现“日程已保存，往来未同步”并提供重试，审核通过才写 Wiki。日程与往来页互相提供查看入口。计划状态固定为 planned，不随时间自动变成已完成；取消日程生成同一页的 cancelled 候选。

创建/更新/取消通过 `operationId + expectedRevision` 保持持久化幂等与版本冲突检查。重复请求先返回已落盘回执，不因参与人后续删除而重复建日程；后续版本变化时不会从旧回执补生成过时候选。改期与发布共用目标库变更锁；正常发布和中断恢复在未采纳前均复核日程版本与冻结参与人来源，旧候选不能生效。已独立编辑、移动或删除的往来页保留原文，不覆盖或重建；需要用户在知识库处理。已采纳的发布组只补恢复日志，不因之后的改期回滚已生效历史。

平台提供原生工具 `calendar_find_people`、`calendar_list_events`、`calendar_get_event`、`calendar_create_event`、`calendar_update_event`、`calendar_cancel_event`、`calendar_retry_interaction`，与 HTTP 页面使用同一个 CalendarService。Pi Manager 与普通 Pi Worker 挂载工具；受限 Wiki 管理员保留原有整理工具边界。联系人查询/修改只允许本轮挂载库，日程读取隐藏未挂载库的参与人资料与知识链接，工具返回前及写入前复核挂载选择。现有飞书日历仍为只读来源；本轮工具只操作平台日历，没有邀请、外部日历写入、后台提醒或新个人助理 Agent。

### 2026-10-16：独立归档管理页

归档入口打开静态路由 `/chats/archived`，使用平台导航与主题，不复用聊天侧栏筛选状态，不挂载 ChatPane、消息流、模型选择或聊天输入框。页面按真实项目身份分组，提供搜索、Agent / 项目筛选、每条恢复/删除、本组恢复/删除及全部删除。恢复只恢复列表可见性，留在管理页，不自动打开或发送消息；返回聊天保留来源 Room / Session / returnSession，外部与递归返回 URL 被拒绝。

所有删除先确认数量与范围。顶部“全部删除”指全部已归档项，不受当前筛选隐藏项影响；组操作仅针对当前显示的本组归档项。每条操作前回读归档状态，已恢复项跳过删除，部分失败明确列出，不假报全部完成。未归档的兄弟聊天保留。删除仅剩一个 Session 的非 solo 窗口时，DELETE Room 携带 `onlySession`，在生命周期预检和 Store 串行提交中校验窗口仍只含该 Session；发生变化返回 409，不扩张删除范围。停放项目中的 Session 沿用现有删除协议，不激活项目。

普通聊天区也读取同一份归档元数据；当前聊天已归档时替换为“此聊天已归档，恢复后可继续对话”，不挂载聊天输入框。归档不停止服务端已有运行，恢复保留原会话与历史。本次没有修改 Agent 工具面或会话 JSONL。
