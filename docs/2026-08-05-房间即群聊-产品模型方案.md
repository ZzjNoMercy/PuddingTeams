# 房间即群聊：solo / 单聊 / 群聊产品模型方案

> 创建：2026-08-05。定位：阶段二产品模型的正式方案，作为开发核对基准（用户开发完成后对照本文档核对、优化）。
> 关联：`docs/puddingteams-platform-design.md`（§3 Web 界面两个面）。本文档落地后，§3 的房间描述以本文为准。
> 现状基线：本文基于 2026-08-05 工作区实际代码（阶段二未提交状态）盘点撰写，下文"现状"均指代码事实而非设计意图。

## 1. 产品模型

**聊天窗口（window）是侧栏的一级实体**，分三种，语义 = 成员数：

| 类型 | 成员 | 说明 |
|---|---|---|
| **solo** | 仅 pi manager | 默认态，**置顶单例**（有且仅有一个，不可删除）。与 manager 自由对话，可触发派活（§4） |
| **单聊** | 1 个 worker（+ manager 隐含在场） | 有 worker 头像，点开即与该 worker 的持续对话 |
| **群聊** | 2+ 个 worker（+ manager 恒定在场） | 成员消息流：worker 以独立身份出现在时间线 |

核心规则：

- **pi manager 恒定在场**：单聊/群聊中用户的消息都由 manager 接收，经委托工具中转给 worker（现状代码已如此，保持）。Direct 只使用平台固定 relay，不提供用户可编辑 Window Prompt；Group 才允许配置只给 manager 的群聊协作提示词。Worker 自己的运行指令属于 Agent 配置，不属于 Window。
- **session 归属窗口，不再是一级入口**：每个窗口拥有自己的 session 列表 + active session；侧栏只出现窗口，session 在窗口内部管理（§5）。
- **worker 是一等消息作者**：单聊/群聊时间线里，worker 的任务执行与回复渲染为带其头像/名字的消息条目（成员消息流），而不是裹在 manager 气泡里的工具卡。solo 里保留 TeamTaskCard 形态（派活是 solo 时间线的过程记录）。

## 2. 领域模型与数据落地

现状：`RoomConfig.sessionId` 即房间主键（房间挂在某个 pi session 上），`GET /api/rooms` 遍历所有 pi session 拼房间。目标：**窗口成为独立实体**，session 只是窗口内的资源。

```
windows.json（由 rooms.json 演进）
Window {
  id: string                    // 窗口自己的 id（不再是 sessionId）
  type: "solo" | "direct" | "group"   // solo 全局单例
  members: string[]             // worker 名；solo=[]，direct=[w]，group=[w1,w2,...]
  sessions: SessionRef[]        // [{sessionId, title, createdAt, modifiedAt}]
  activeSession: string
  workerSessions: Record<worker, session_id>   // worker 侧多轮续接（现状已有）
  createdAt / pinned
}
```

- **solo 窗口**：服务端启动时保证存在（没有则建），`pinned: true`，拒绝删除。
- **direct 窗口按 worker 去重**：同一 worker 只有一个单聊窗口（重复"发起单聊"= 打开已有窗口）；群聊不去重。
- **窗口级联删除**：删窗口 → 删其全部 pi session（JSONL）+ workerSessions 记录；删窗口内 session → 仅删该 pi session，窗口保留（至少保留一个 session，删到最后一个则自动新建空 session）。现状 `TeamsStore.removeRoom()` 是死代码、删 session 不清理 rooms.json，本次一并补上。
- **直接兼容演进**：rooms.json 加 `id`/`type` 字段迁移为 windows.json，旧 `sessionId` 主键映射为首个 session。

> 实现注记（2026-08-11，用户数据目录迁移）：窗口、Agent 与 Workspace 的平台状态现统一位于 `PUDDINGTEAMS_HOME`（默认 `~/.puddingteams`）——`state/windows.json`、`state/agents.json`（原 teams.json）、`state/workspaces.json`；pi Session JSONL 在 `sessions/`（pi worker Session 在 `sessions/workers/`）；上传头像在 `assets/avatars/`。文中各处 `.teams/` 路径均为历史说明，运行时代码不再读取。

## 3. 侧栏与导航

- 侧栏结构：**solo 置顶**（ManagerAvatar，"pi manager"）→ 单聊区 → 群聊区（MemberStack 头像堆叠）。现状 `session-list.tsx` 的渲染逻辑已按成员数区分，改为按 `type` 分区 + solo 固定钉顶。
- 「+ 新对话」入口改为**发起**：选 worker 单聊（若已有该 worker 的单聊则直接打开）/ 勾选 2+ 建群聊。solo 不在创建选项里（单例）。现状 `create-room-dialog.tsx` 勾选逻辑复用，补去重逻辑。
- 智能体管理页、设置和更多菜单不变。

## 4. solo 派活路由（本方案核心新机制）

**场景**：用户在 solo 里对话，manager 判断要派活，调 `team_task(worker=X, task)`。平台动作：

1. **定位窗口**：找到 worker X 的 direct 窗口（没有则自动创建，无需用户介入）。
2. **session 决策（solo 决定）**：`team_task` 工具描述中注入该 direct 窗口的现有 session 摘要（title + 最近活跃时间），manager 据此判断本次 query 与哪个 session 相关——相关则透传其 worker session 续接，不相关则开新 session（工具参数加 `session?: "new" | "continue"`，默认 `continue`；描述中写明"若现有会话与任务无关则传 new"）。
3. **执行**：用 direct 窗口的 `workerSessions[X]`（或新建）spawn worker，与窗口内派活走同一条 `runAgent` 路径。
4. **可见性（"自动找到对应的单聊，发个信息"）——已调研，pi 原生路径成立（2026-08-05 查证 pi 源码）**：用 `AgentSession.sendCustomMessage(msg, {triggerTurn: false})` 向 direct 窗口的 active session 写两条 `custom_message` entry：
   - `pudding:task_assign`（content=任务文本，details={taskId, worker}）
   - `pudding:task_result`（content=结果，details={taskId, worker, status}）

   该 API 一次满足三个要求：**落盘 JSONL**（重开 session 回放可见）+ **向订阅者 emit `message_start`/`message_end`**（WS 桥原样透传，前端实时收到）+ **不触发 LLM turn**（纯记录写入）。源码佐证：`agent-session.ts:1451-1461`（无 trigger 分支：push 内存 + `appendCustomMessageEntry` 落盘 + emit，无双写）、`session-manager.ts:396-400`（custom_message 回放进 context）。三个注意点：
   - `custom_message` **会进 LLM context**（convertToLlm 转成 user 消息）——worker 上下文可见派活记录，视为特性而非缺陷；
   - 调用前 `session.isIdle` 把守：streaming 中调用会退化为 steer/followUp 注入（语义变了），目标 session 忙碌时平台侧排队等 idle；
   - 前端 `message.tsx` 需认识 `role:"custom"` 消息并按 `customType` 渲染——worker 头像消息条目正好落在这里，与 §7 成员消息流共用同一渲染。
   - SDK 升级回归点：`sendCustomMessage` 无 trigger 分支行为（agent-session.ts:1451-1461）。

   **废弃**原"window-activity.jsonl 投影"备选（pi 原生路径成立，不引入第二存储）；**禁止**直接 append JSONL 文件（运行中 SessionManager 无文件变更感知、外部写入的 entry 会脱离 leaf 链导致回放丢失、新 session 首次落盘用 `openSync(wx)` 遇外部预写文件直接 EEXIST——session-manager.ts:1029-1038）。
5. **solo 时间线**：保留 TeamTaskCard（含"已同步到与 X 的单聊"链接式元信息，点击跳到对应窗口）。

群聊/单聊窗口内的派活不走路由（本窗口即归属窗口），仅按 §1 以成员消息流渲染。

## 5. 窗口内 session 管理与聊天信息

- **session 列表**：窗口头部「会话」下拉支持列表、切换、新建、重命名与删除。重命名走 `PATCH /api/rooms/:id/sessions/:sid`，名称写入 session 自身且优先于自动标题；删除走 `DELETE /api/rooms/:id/sessions/:sid`（级联清理 session 文件与关联工作状态；禁止删最后一个）。
- **聊天信息**：窗口头部提供独立「聊天信息」面板，参考常见聊天产品的信息层级，但只展示 PuddingTeams 已有且对用户有意义的数据。群聊展示群头像、成员宫格、群聊名称与群聊协作提示词；单聊展示对方头像、职责描述与可用状态，**不展示协作提示词编辑入口**；三类窗口统一展示运行项目、当前会话和会话数量，并可从信息行进入适用的重命名、群聊协作提示词和项目切换。「当前会话」直接复用窗口头部的完整会话菜单，支持切换、新建、重命名和删除，不维护第二套交互。
- **技术信息收口**：聊天信息不暴露 Connector 命令、内部 worker session handle 等运行时细节；这些属于管理/诊断域，不是聊天关系信息。

## 6. 后端端点变化（在现状 rooms 路由上演进）

| 端点 | 变化 |
|---|---|
| `GET /api/rooms` | 返回窗口模型（id/type/members/sessions/activeSession/pinned），solo 恒在首位 |
| `POST /api/rooms` | 接受 `{type, members}`；direct 去重命中则 200 返回已有窗口 |
| `DELETE /api/rooms/:id` | **新增**：级联删除（solo 拒绝，405/400） |
| `POST /api/rooms/:id/sessions` | 不变（窗口内新建 session） |
| `PATCH /api/rooms/:id/sessions/:sid` | **新增**：重命名窗口内 session，手动名称不被自动标题覆盖 |
| `DELETE /api/rooms/:id/sessions/:sid` | **新增**：窗口内删 session（最后一个拒绝） |
| `POST /api/rooms/:id/sessions/:sid/activate` | 不变 |
| `team_task` 工具 | solo 上下文时注入目标窗口 session 摘要 + `session` 参数；执行后写 direct 窗口消息流（§4.4） |

agents CRUD / probe 端点不变。

## 7. 前端渲染变化

- **成员消息流**（单聊/群聊）：`team_task` 事件折叠出的块不再渲染为 manager 气泡内的 TeamTaskCard，而是独立条目：WorkerAvatar + worker 名 + task（作为"用户侧"内容）+ 结果 markdown + 状态徽章；manager 的转述文本仍是 manager 条目。solo 派活同步进单聊的 `custom_message`（`pudding:task_assign` / `pudding:task_result`，§4.4）复用同一渲染。事件层 `lib/events.ts` 已有 `teamTaskWorker()`，改造点在 `message.tsx` 的分发逻辑。solo 窗口维持 TeamTaskCard。
- **窗口头部**：房间名 + 成员副标题 + 「会话」下拉（增删改）+「聊天信息」面板 + 连接状态。群聊信息以成员为主，单聊信息以对方职责为主，设置与上下文采用统一信息行。
- **输入栏上下文**：当前运行目录/项目从窗口头部移到输入栏底部工具区，紧邻模型选择器；这里是消息实际执行环境的快捷入口，点击仍进入项目切换。路径失效时就地显示异常状态。聊天信息面板继续保留完整项目名称与路径，承担信息汇总而非快捷操作。
- 空态：选中窗口无 session 时不出现（§2 保证至少一个）。

## 9. 明确不做

- 不做绕过 manager 的 worker 直连通道（违背"manager 恒定在场"，审计性也变差）；
- 不做 `team_broadcast` 并行派活（阶段四）；
- 不做 MCP invoke；没有可执行协议就不保留“看似支持”的死类型，未来出现真实 MCP Connector 时按 Driver SPI 接入；
- 不做窗口级未读数/通知（本地自用）。

## 11. agents 页趣味化与头像（追加，2026-08-05）

背景：agents 管理页现为纯表格，工具感过重；配合群聊模型，worker 应有"角色感"（参照 Marvis 角色矩阵的趣味方向，但保持全站扁平风）。

- **页面形态**：列表 → 角色卡片网格。每卡：大头像 + 名字 + 描述（一行截断）+ capabilities 标签 + 启用/健康状态灯；点击进入编辑抽屉（现有表单字段不变），卡片上保留探测按钮。头像体系全站复用：agents 卡片、侧栏单聊/群聊项、窗口成员弹层、§7 成员消息流条目，同一 `WorkerAvatar` 组件一处升级处处生效。
- **头像数据模型**：`AgentConfig.avatar?: string`（相对文件名）。文件存 `.teams/avatars/<name>.<ext>`（与 teams.json 同目录，一并 gitignore 与否再定——头像属用户数据，建议忽略）。
- **端点**：
  - `POST /api/agents/:name/avatar`：上传（multipart 或 `{data: base64}` JSON，取实现简单的）；限制 2MB，白名单 png/jpg/webp/gif；落盘后回写 teams.json 的 `avatar` 字段；同名覆盖。
  - `DELETE /api/agents/:name/avatar`：删文件 + 清字段，回落默认头像。
  - `GET /api/agents/:name/avatar`：读文件流返回（带 content-type 与缓存头），无头像 404，前端 onError 回落默认。
- **默认头像（不接任何模型）**：程序化生成——名字哈希 → 固定调色板取色 + 几何图案（DiceBear/identicon 风格的自绘 SVG 小组件，纯前端零依赖；现有 `worker-avatar.tsx` 的哈希配色即雏形，升级为"色块 + 图案/emoji"）。**不接多模态/图像生成模型**：那需要额外的图像生成 API 与成本，违背极简原则；若将来想要 AI 生成 mascot，作为独立优化项再议（届时也应走"生成一次、落盘为头像文件"的离线路径，不进运行时链路）。
- **Connector 默认头像（追加，2026-08-09）**：Connector 包可自带品牌头像——manifest 声明 `connector.avatar`（包内相对路径，扩展名白名单 png/jpg/webp/gif/svg，禁止绝对路径与 `..`）。展示回退链：**上传头像 → connector 包内默认 → 程序化 identicon**。`GET /api/agents/:name/avatar` 在未上传时回退读包内资源（builtin 从注册时给的 assetsDir、安装包从 sourcePath）；`GET /api/agents` 用 `hasDefaultAvatar` 标记让前端走 avatar URL。上传白名单不变（svg 只允许包内置资源，不开放上传）。已落地：Codex/Claude Code（lobehub 品牌图标）。

## 12. 实现纪要（2026-08-05，第一轮落地后补记）

**已落地**：§1–§7 全部（§10 清单已逐项勾销）；§11 头像开发中。关键实现决策：

- **solo 路由**（`pi-bridge/team-task.ts` 重写）：solo 白名单 = 全部 enabled worker；`session?: "new"|"continue"` 参数；工具 description 用 getter 动态注入（pi 每轮重读，摘要缓存每次 execute 后刷新）；`TeamsStore.ensureDirectWindow` 自动建单聊；执行后 `syncToWindow` 向 direct 窗口 active session 写 `pudding:task_assign` / `pudding:task_result`（details 含 taskId/worker/windowId）。
- **同步把守**：写 custom_message 前 `isIdle` 检查 + `waitForIdle(15s)`，超时/失败降级 `synced:false` 写入 tool result details——同步是 best-effort，绝不让派活本身失败。
- **force-flush hack（SDK 升级回归点）**：SDK `_persist` 在首个 assistant 消息前不落盘，而同步要求文件存在——同步前手动 `writeFileSync(wx)` 写入 header 并置 `SessionManager.flushed=true`（私有字段，`team-task.ts` 有注释）。连同 §4.4 标注的 `sendCustomMessage` 无 trigger 分支，共两处 SDK 升级回归点。
- **渲染**：`message.tsx` 抽出共享 `WorkerTaskEntry`（头像+名字+徽章+任务+结果 markdown），custom_message 与 direct/group 的 team_task 独立条目复用；solo 维持 TeamTaskCard + "已同步到单聊 →"跳转链接（details 需带 windowId/synced，历史回放路径已补 details 折叠）。

**用户开发中自加的设计（回写确认，均为有意决策）**：

- **Relay 硬约束**：direct/group 窗口的 manager session 被 `noTools: "builtin"` 剥光内置工具、只留 team_task，systemPrompt 追加"必须转发、不许自己动手"（`session-store.ts:74-95`）。solo 保留全工具。这比方案"manager 中转"更强：单聊/群聊里 manager 是纯粹的转发器，动手能力差，行为可控。
- **ensureWindowAlive 自愈 + 修复**：窗口 session 未落盘时重启自动补建；后修复为 `diskIds.has(id) || sessions.isOpen(id)`——SDK `_persist` 延迟落盘曾导致每次 GET /api/rooms 铸新 session（脏 session 来源）。
- **其他**：`POST /api/rooms` 返回 `existed` 标志（前端"打开已有单聊"差异化）；`PATCH /api/rooms/:id` 按类型校验成员数（solo 拒加 / direct 恒 1 / group ≥2）；窗口头部 solo 徽章。

**对方案的偏离（接受）**：

- §2 `sessions: SessionRef[]`（带 title/createdAt）简化为 `string[]`，标题/时间在 API 层从 pi SessionManager 现拼——少一层冗余状态，合理。

**遗留**：

## 13. 可选 Workspace 语义（2026-08-10 收口）

- Workspace 不是发起聊天的必填项。solo、direct、group 都允许不选择项目；创建时把平台默认 cwd 冻结到 Window，manager Session 与 worker Driver 始终共享该快照，保持原有入口且避免跨重启漂移。
- 选择 Workspace 后，Window 保存 `workspaceId + cwdSnapshot`，manager 与 worker 共享该项目的 canonical cwd；路径失效只把对应窗口标记为不可用并阻断执行，不阻断服务启动，也不回退默认 cwd。
- 项目上下文可双向切换：显式 Workspace 可以切回“不绑定项目”。direct 默认按 `(worker, workspaceId ?? cwdSnapshot)` 创建或打开单聊，group 默认新建一个成员相同、项目不同的群聊；solo 是固定单例，只能原地切换。原地模式会停止旧任务、清空续接并重建 manager Session。
- direct 的身份为 `(worker, workspaceId ?? cwdSnapshot)`：同一 worker 可以同时拥有不同默认 cwd 的无项目单聊以及多个不同项目单聊，彼此不复用 manager/worker Session。
- 每次 Delegation 无论是否选择项目都冻结 `cwdSnapshot`；worker binding 同时记录 `workspaceId? + cwdSnapshot + agentRevision`，从而让无项目模式保留原行为、有项目模式保持跨项目隔离。
- manager 的 pi Session 统一保存在共享 `sessionDir`，恢复与枚举必须按该目录全量发现，再由 Window 持久化的 Session ID 和 `cwdSnapshot` 决定归属；不能用当前进程 cwd 过滤共享目录，否则不同 Workspace 的 Session 会在重启后被遗漏。刚创建、尚未首次落盘但仍在内存打开的 Session 同样视为存活，避免连续请求把 solo Session 误判为丢失并替换。

> 实现注记（2026-08-11，用户数据目录迁移与 Workspace 信任门）：上述共享 `sessionDir` 即 `PUDDINGTEAMS_HOME/sessions/`。无项目窗口的默认 cwd 快照固定为 `PUDDINGTEAMS_HOME/workspaces/unscoped`（中性空目录，不再使用 `process.cwd()`），服务端强制关闭 Workspace context/skills/prompts 发现，Preview 返回 `workspace: null, contextFiles: []`。显式 Workspace 增加信任状态：`WorkspaceTrust{state: pending|trusted|denied, decidedAt, policyVersion: 1, canonicalPathAtDecision, approvedResources?}`——managed Workspace 默认 trusted，外部项目初始 pending，`realpath` 漂移自动退回 pending；信任决定经 `PUT /api/workspaces/:id/trust` 保存，撤销后相关活跃 Session 标记 `runtimeDirty`。Workspace context/skills/prompts 进入装配候选的判定收敛为单点（`workspaceId && trusted && approvedResources 含对应 kind`，再与 Agent 自身资源开关相与），Preview、会话装配与 Delegation 统一消费。详见 `docs/2026-08-11-用户数据目录与Workspace上下文迁移方案.md` §6.3/§7。

## 14. Session Goal 与当前工作（2026-08-10 收口）

- Window 仍是长期协作空间；Session 可以是普通聊天，也可以显式设置为一个 Goal，不新增 WorkItem/Topic 实体。
- Goal 的权威当前版本是 `SessionWorkState`：manager 固定为责任主体，通过 revision 乐观锁维护当前摘要、等待项、下一步、完成条件与稳定 Artifact 引用；worker Run 的 completed 不直接把 Goal 判为 resolved。`goalRevision` 只在目标/完成条件变化时递增，使验收契约与普通进度 revision 分离。
- 普通会话通过 composer 的 `/goal` 命令原地创建 Goal，不再常驻展示“设为 Goal”横条；`/goal <目标>` 可预填目标。用户填写的自然语言“完成条件”是冻结验收语义，reviewer 只能解释和核对，不能事后降低或增加条件。
- 完成方式分为 `manager` 自审与 `independent` 独立复核。独立复核由 PuddingTeams 启动一个全新的 Pi SDK in-memory Session：不继承 manager 历史、不加载 Extension/Skill/项目上下文、无任何工具，只读取冻结目标、完成条件、最终摘要及可追溯 ToolResult/Delegation/Artifact/Decision 证据，返回逐项 `satisfied/unsatisfied/uncertain`。Reviewer 不能直接更新 Goal；只有 PuddingTeams 可在 revision 未漂移、无活动委托和待回答决策且 verdict 为 satisfied 时提交 resolved。
- 业务取舍使用 `DecisionRequest`，与恢复同一暂停 Run 的 Driver `Interaction` 分层。回答 DecisionRequest 后在同一 manager Session 中继续，不调用 `Driver.respond`，也不从普通答案推导额外授权。
- Delegation 保持 `Worker A → manager → Worker B`，记录 `parentDelegationId + handoffKind + intent + expectedOutcome + evidenceRequirements + completionBoundary`；单向通知走 custom message/event，不制造假的 Delegation 等待。
- Goal Session 的 Chat 顶部只展示轻量“当前工作”摘要与 Runtime 入口；右侧抽屉按 PuddingClaw Inspector 的白盒化思路承接完整验收条件、当前进度、append-only 复核轨迹、证据引用、DecisionRequest、Delegation 链与 Artifact。普通 Session 顶部不展示 Goal 控件，未设置时不强迫用户进入项目管理流程。
- 用户附件冻结到平台受控目录，图片作为模型 image input 传入，所有附件路径明确注入当前消息，manager 接力派活时必须原样传递所需路径。
- Goal/当前工作的动态状态必须在每次模型请求的 context 阶段按最新 revision 注入；仅依赖 `before_agent_start` 会漏掉 custom message 触发的 DecisionRequest 回答与续接，使 manager 读取到旧状态。该上下文消息只参与本次请求，不写回长期聊天历史。

## 15. Manager/Worker 提示词可见性（2026-08-11 收口）

核心事实源见 `docs/2026-08-11-PuddingTeams核心提示词管理方案.md`。房间模型固定以下规则：

- `AgentConfig.description` 保留通用名称：既用于 UI 展示，也给 manager 做 roster 展示、搜索与选择；`responsibility` 补充结构化责任和停止边界。二者都不是 Worker 自己的运行提示词。
- Worker 运行指令只进入该 Worker Session；manager 不读取其正文来做路由。平台在每个 manager 回合开始前按 Window 候选集合把最新 `description`、`responsibility`、能力事实和实际委托工具投影进 manager system prompt：Solo 为全部启用 Worker，Direct 为唯一成员的最小信息，Group 为全部已启用成员；manager 据此选择和委托。
- **Solo**：manager 在全部启用 Worker 的完整路由卡中选择；没有 Window collaboration。
- **Direct**：目标 Worker 已由窗口成员唯一确定，没有二次选择，也没有用户可编辑 Window Prompt。manager 只接收平台固定 relay（必须委托、不得自己执行、结果转述与续接），Worker 行为由自己的运行指令决定。
- **Group**：用户可编辑“群聊协作提示词”，只进入该 Group 的 manager，描述拆分、并行、交接、裁决与汇总；不得传给 Worker。
- pi global `~/.pi/agent/AGENTS.md` 与当前显式 Workspace context 会分别进入 manager/Pi Worker；只想让 manager 看到的规则不能写进 global `AGENTS.md`。
- 输入栏“默认目录”是 Window 的中立 cwd，不是 `~/.pi/agent`；切换项目决定显式 Workspace context，不能改变 pi global context 的归属。

## 16. Manager 建房与拉人（2026-08-12 落地）

solo 的 manager 可以自行创建群聊房间；群聊的 manager 可以补充人手。两者都是 core 工具（与 `search_agent_tools` 同层，平台生成、非用户 Extension），直接执行、不需要审批（与 solo 自动建单聊的行为一致）。

- **`create_group_window`（仅 solo 激活）**：参数 `members`（≥2 个已启用 worker）、`task`（首条整体任务）、可选 `name` 与 `prompt`（群聊协作提示词，只给该房间 manager）。执行链路复用 `rooms.ts` 建房路径：先建 group manager Session 再落窗口记录，然后 fire-and-forget 把 `task` 作为首条消息发给房间 manager（`chat.ts` 首发消息同款，异步生成标题），工具立即返回 `windowId` 而不等待执行结果——房间在自己窗口里干活，用户在群聊窗口看进度。前端把该工具结果渲染为「打开群聊」跳转卡。
- **`invite_to_group`（仅 group 激活）**：参数 `members`（≥1 个已启用 worker）。逐个校验存在、非 pinned manager、已启用、未在群内（已在的跳过并注明），经 `updateWindow` 加入成员——自动走 emitChange → 撤权/空闲重建链，新成员下一轮进入 roster prompt，其委托工具在会话装配空闲重建后可用，与 UI 改成员完全一致。
- 门禁双保险：激活策略按窗口类型分发（solo 只激活建房、group 只激活拉人），工具 execute 内再做第二道上下文校验； pinned manager、禁用或不存在的 worker 一律拒绝入群。
- roster prompt 相应提示两条规则：solo 需要多 worker 协作时用 `create_group_window` 而不是把多 worker 任务塞进单聊委托；group 人手不够时用 `invite_to_group` 拉人。
- 不做：manager 删房间、移除成员（涉及在跑 Run 的处理，保留为用户手动操作）；非 solo 窗口建房。
