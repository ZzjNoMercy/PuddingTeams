# 速记收件箱与定期整理方案

> 状态：已实现（2026-10-28，M1 + M2）。产品主线通过，按 §10–§13 的审核修正与开发清单实施；实现记录见 §14。
> 范围：Web / 桌面端的随手记录入口、独立存储、以及「整理进知识库」与既有审核发布链路的衔接。
> 不在范围：自动定时整理、语音输入、多用户共享速记、速记正文进入会话默认上下文。

## 1. 问题

当前记录一条观点备忘的成本，是结构性的高，不是交互手感问题：

1. **结构门槛**：Wiki 页面必须匹配 `wiki.schema.json`，证据型 Wiki 的 `sources` 还是必填（[schema-presets.ts](../apps/server/src/knowledge/schema-presets.ts) 的 `wikiCommon`）。一句"我觉得 X 更重要"没有来源可挂。
2. **流程门槛**：写入正式库只有两条路——Agent 走 `prepare_candidate → submit → 人审 → Publisher`，或外部编辑器直接改文件后等平台扫描同步。前者对一句话过重，后者要求用户另开 Obsidian。
3. **入口缺失**：知识库界面没有「新建笔记」。`PUT /api/knowledge/:id/note` 只接受已存在文件 + `expectedHash` 的 CAS 改写（见 [routes/knowledge.ts](../apps/server/src/routes/knowledge.ts) 与 [note-write.ts](../apps/server/src/knowledge/note-write.ts)），没有 create 语义。所以「随手记一句」在产品里**没有落点**。
4. **混放代价**：库内树与笔记计数统计内容根下所有非控制 `.md`（[reader.ts](../apps/server/src/knowledge/reader.ts)）。把草稿塞进 Wiki 目录会直接污染笔记面与结构校验边界。

结论：草稿与成品必须分层，而不是把 Wiki 的闸门调松。

## 2. 结论：记录分两层

| | 速记（原料） | Wiki（成品） |
|---|---|---|
| 定位 | 碎片、观点备忘、未成形想法 | 有结构、有证据、可被引用的知识 |
| 写入 | 一句话回车即存，0 决策 | schema + 候选 + 人审 + 发布 |
| 结构 | 正文 + 标签 + 时间 | 实体类型、字段、来源引用 |
| 生命周期 | 未整理 → 已整理（保留正文） | 版本化、可回滚、有审计 |
| 转换 | 整理时把选中的速记冻结成 `KnowledgeSource` | 走既有 curator → review → publish |

速记**不是**长期记忆：memory 是"要 Agent 长期遵守的事实"，必须审核后生效；速记是"用户自己还没想清楚的东西"，是否升级由用户决定。两者不共用存储，也不互相注入。

## 3. 产品形态

### 3.1 捕获

- 入口：侧栏「速记」+ 任意页面内 `⌘/Ctrl+Shift+Space` 唤起浮层；`Esc` 关闭，未提交草稿写 `sessionStorage`。M1 不做 Electron 全局热键。
- 一个多行输入框：`Enter` 保存，`Shift+Enter` 换行；IME 组词中的 Enter 不保存。不选库、不填标题、不做类型选择。
- 正文内 `#标签` 即时预览，服务端保存时统一解析进 `tags`；正文原样保留，支持中文标签。
- 保存后 toast 提示「已记下」并提供「撤销」。前端可乐观更新，但撤销必须调用本地 server 的软删除接口；不能宣称撤销或持久化不需要 API。
- 单条上限 10,000 字；列表每页 50 条。捕获路径不触发任何模型调用、不重建搜索索引、不写知识库文件。

### 3.2 时间线

- 按天分组（今天 / 昨天 / 日期），倒序；每条显示时间、正文、标签。
- 状态筛选：未整理（默认）/ 整理中 / 已整理 / 全部；标签筛选 + 关键字过滤。原三态筛选不足以表达审核中、发布中和异常锁定，正式实现必须补上「整理中」。
- 「未整理」只包含可编辑、可提交整理的条目；「整理中」条目只读；「已整理」表示已发布或无需变更。侧栏徽标只统计未整理，不把审核中的条目重复算作待处理（刷新模式见 [nav-rail.tsx](../apps/web/src/components/chat/nav-rail.tsx)）。
- 速记正文始终保留。审核/发布状态以只读投影显示，并提供既有回链（`/knowledge/review?batch=...`、`/knowledge?vault=...`）；不得把发布后的 Wiki 正文回写成速记正文。

### 3.3 整理

- 单条「整理这条」或多选「整理 N 条」。只有 `unorganized` 可选择和提交；整理中、审核中、发布中以及异常待处理条目均锁定。
- 弹窗只有两项：目标知识库（从真实可用 bindings 加载，不使用原型硬编码库）+ 整理要求（预填"把这些速记整理成知识库条目，合并重复观点"）。要求必填且去空白后非空，因为 `WikiCuratorService.create` 的 `task` 必填。
- 提交即冻结：先在同步事务中完成整批归属、状态、revision 校验，保存有序正文/tags 快照并锁定 memo；再用确定性 source id 冻结来源，最后调用 `WikiCuratorService.create()`。不能直接用会生成随机 UUID 的 `createText()` 代替崩溃恢复设计。
- 后续完全复用现有链路：`queued → running → submitting → pending_review` → 用户审核 → Publisher 发布。速记侧只投影状态，**不新增审核或发布通路**。
- 同一 `operationId` 重放只对账本次 attempt。审核 `rejected`，或 `failed/cancelled` 且经对账没有必须续接的候选/发布副作用时，才允许用新 `operationId` 重新整理；旧候选和历史仍保留。`returned` 要跟随既有修订链，`partial/conflict/candidate_registration_failed` 不得直接解锁重提。

## 4. 数据与接口

### 4.1 存储

`state/memo/memo.sqlite` 使用与稍后读一致的单文件 sqlite、`BEGIN IMMEDIATE` 和 owner 隔离（参考 [read-later/store.ts](../apps/server/src/read-later/store.ts)）。原来的单条 `promotion?` 与只有 `job_id` 的 operations 表不足以断点恢复，也不能保留多次整理历史；至少拆成下列四类记录：

```sql
CREATE TABLE memos(
  id TEXT PRIMARY KEY, owner_id TEXT NOT NULL, deleted INTEGER NOT NULL,
  created_at TEXT NOT NULL, record_json TEXT NOT NULL
);
CREATE INDEX memos_timeline ON memos(owner_id, deleted, created_at DESC, id DESC);

CREATE TABLE operations(
  owner_id TEXT NOT NULL, id TEXT NOT NULL, kind TEXT NOT NULL,
  request_hash TEXT NOT NULL, result_json TEXT,
  PRIMARY KEY(owner_id, id)
);

CREATE TABLE memo_promotions(
  owner_id TEXT NOT NULL, operation_id TEXT NOT NULL,
  request_hash TEXT NOT NULL, binding_id TEXT NOT NULL, task TEXT NOT NULL,
  phase TEXT NOT NULL, job_id TEXT, last_error TEXT,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
  PRIMARY KEY(owner_id, operation_id)
);

CREATE TABLE memo_promotion_items(
  owner_id TEXT NOT NULL, operation_id TEXT NOT NULL, position INTEGER NOT NULL,
  memo_id TEXT NOT NULL, memo_revision INTEGER NOT NULL,
  text_snapshot TEXT NOT NULL, tags_json TEXT NOT NULL, source_id TEXT,
  PRIMARY KEY(owner_id, operation_id, position),
  UNIQUE(owner_id, operation_id, memo_id)
);
CREATE INDEX memo_promotions_phase ON memo_promotions(owner_id, phase);
CREATE INDEX memo_promotion_items_memo ON memo_promotion_items(owner_id, memo_id, operation_id);
```

- `memos.record_json` 只保存当前事实：`{ id, ownerId, text, tags, lifecycle, createdAt, updatedAt, revision, currentOperationId?, lastError? }`，其中 `lifecycle = unorganized | promoting | organized`。审核/发布显示状态不塞进这个字段。
- `operations` 是所有写操作共用的幂等注册表，kind 纳入 requestHash；同 owner 下同 ID 不同 kind/载荷也返回 409。`memo_promotions` 保存整批 attempt，`memo_promotion_items` 保存有序快照和逐条 source checkpoint。
- 多选整理共享一条 promotion，多条 memo 只用 `currentOperationId` 指向当前 attempt。重新整理创建新 attempt，旧 attempt 及其 sources/job/batch 关联不得覆盖。
- `phase` 至少区分 `freezing / sources_frozen / job_created`，用于崩溃后续跑，不用于展示审核状态。
- 正文快照同时存在于 attempt 与 `KnowledgeSource` 对象库，二者独立：删除速记不影响已固定的候选、审核与发布历史；已发布内容也不回写速记正文。
- owner 一律取 `localViewerIdentity().user.id`，请求体不得传 ownerId/tenantId；DTO 不暴露 ownerId、requestHash 等内部字段。

### 4.2 REST

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/memos` | `{ operationId, text }`；幂等，服务端从正文派生 tags，返回条目 |
| GET | `/api/memos` | `filter=unorganized\|promoting\|organized\|all&tag=&q=&before=&limit=`；默认/最大每页 50 条 |
| PATCH | `/api/memos/:id` | `{ text, expectedRevision }`；仅 `unorganized` 可改，保存后重算 tags、revision + 1 |
| DELETE | `/api/memos/:id` | `{ operationId, expectedRevision }`；软删除，整理中拒绝，已整理可删但历史保留 |
| POST | `/api/memos/:id/restore` | `{ operationId }`；恢复软删除并递增 revision，用于删除撤销 |
| POST | `/api/memos/promote` | `{ operationId, memoIds, bindingId, task }`，1–50 条且 ID 不重复，成功返回 202 |

GET 响应固定为 `{ items, counts, tags, nextBefore }`：`counts = { unorganized, promoting, organized, all }` 是全 owner、未删除、与当前筛选无关的权威计数；`tags` 含数量；`before` 是包含 `(createdAt, id)` 的不透明游标，不能只传时间戳。列表排序固定为 `created_at DESC, id DESC`。

错误沿用现有约定：400 参数错误、404 不存在、409 revision/幂等/状态冲突、422 业务不可执行。promote 同键重放返回当前 attempt、Job 与最新投影，不是第一次响应时的状态快照。

### 4.3 生命周期与显示状态

```
unorganized ──fresh promote──> promoting ──published / no_changes──> organized
      ^                            │
      │                            ├─ rejected / 可重试 failed / cancelled → unorganized
      │                            └─ returned→revision、needs_attention、partial/conflict → promoting（锁定）
```

- 生命周期决定能否编辑、删除和再次整理；`queued/running/pending_review/approved/publishing/published/rejected/returned/...` 是显示投影，两者不得混为一个 `status`。
- `returned` 会创建修订 Job，不是可重新整理的终态；`candidate_registration_failed` 必须沿原 curator Job 恢复固定候选，不能重新生成来源。
- `partial/conflict/needs_attention` 保持锁定并引导到现有审核/发布处理界面，防止新 attempt 放大已有副作用。
- `no_changes` 进入已整理并显示“无需变更”，不伪造发布页面链接。
- 同批 `operationId` 重放只恢复本次 attempt；`requestHash` 不同则 409。curator 原 Job 重试与 fresh promote 是两种不同操作，不得共用“重试”按钮语义。

## 5. 与现有系统的边界

- **不新增 session customType**：整理任务状态继续复用 `pudding:knowledge_job` 投影卡，速记本身不写会话 JSONL。若后续要新增，必须先更新 `docs/2026-08-14-会话记录格式与Harness消费.md`。
- **来源证据**：给 `KnowledgeSourceOrigin` 增加 `memo?: { id, createdAt, tags, revision }`，同时修改 `cleanOrigin()` 与 `knowledgeSourceManifestHash()`（[sources.ts](../apps/server/src/knowledge/sources.ts)）。tags 必须规范化、排序后参与 hash；只改 TypeScript 类型而不改清洗逻辑，字段会在保存前被丢弃。
- **不进入会话上下文**：速记默认不注入 Manager/Worker 的知识工具面，也不进入 `knowledge_context`；避免草稿污染检索与自动整理触发。Agent 若要“帮我记一下”，M3 再评估单独的 `memo_add` 工具。
- **不自动发布**：整理结果仍停在候选，人工审核后由 Publisher 写入正式库。速记侧的任何按钮都不能绕过审核。
- **不镜像到 Wiki 目录**：MVP 不写 `memo/` 目录。双写会引入两边冲突规则，且与“内容根下全是正式笔记”的树/计数语义冲突。数据所有权由 M3 的单向 Markdown 导出解决。
- **不依赖互联网与模型**：捕获、编辑、列表、标签仍依赖本机 PuddingTeams server 和 sqlite，不依赖外网；只有整理会触发现有后台任务。未提交草稿仅在 `sessionStorage`，不能脱离 server 宣称完整离线可用。

## 6. 实施复用点

- 存储/幂等：参考 `read-later/store.ts` 的 sqlite 封装、事务和 operations 模式；memo 必须额外实现 attempt、items 快照和 source checkpoint，不能只复制表名。
- 整理：参考 `read-later/promote.ts` 的同操作串行化、整批预检、先保存 promotion 再 `curator.create()` 的顺序。不能直接换成随机 UUID 的 `createText()`；应新增带确定性 id 与完整性校验的 memo 冻结入口。
- 审核/发布：复用 `WikiCuratorService`、ReviewStore、Publisher、PublishJournal 和 `curatorTaskView()`；memo 不另写审核、发布或修订逻辑。
- 路由：参考 `routes/read-later.ts` 的注册与错误映射，在 `index.ts` 与稍后读路由相邻处装配。
- 前端：参考 `features/read-later/read-later-app.tsx` 的筛选、分页、选择和整理轮询，但不复制文章阅读器；浮层使用现有 `components/ui/dialog`，toast 使用现有 Sonner。
- 导航与快捷键：`nav-rail.tsx` 的计数与 30 秒刷新可复用。`⌘K` 已被全局搜索占用，速记页不得再次接管；M1 只新增 `⌘/Ctrl+Shift+Space` 页面内监听。

## 7. 分期与验收

**M1 捕获与时间线**
- 侧栏入口 + 页面内快捷键浮层，Enter 保存、标签解析、创建/删除撤销。
- 时间线稳定分页、四类状态/标签/关键字筛选、未整理徽标。
- 验收：断开互联网仍可通过本机 server 使用；本机常规操作下捕获到列表可见 < 200ms；重启 server 后数据完整；不产生任何知识库文件变化与后台任务。

**M2 整理进知识库**
- 单条/多选整理，冻结来源 + 后台 curator 任务 + 状态回链 + 失败恢复。
- 验收：同一操作重放不重复 Source/Job；各崩溃点可续跑；审核批次可追溯到具体速记快照；`rejected` 可重新整理，`returned` 跟随修订；发布后回链到知识库，`no_changes` 不伪造页面链接。

**M3 可选**
- 单向导出 `memo/YYYY-MM-DD.md`（不镜像、不反向同步）；Agent `memo_add` 工具；未整理提醒。自动定时整理若要做，需另写调度、时区、暂停与幂等方案，不包含在本期。

## 8. 明确不做

- 不做定时自动整理：自动整理仍必须产候选，MVP 不引入调度器。
- 不做速记全文进入 Agent 上下文、不做速记自动分类/自动打标签。
- 不做多用户共享、协作评论、附件与图片（图片可先用稍后读或知识库通道）。
- 不改动 Wiki 的 schema 校验、审核窗、Publisher 与发布日志。
- 不做 Electron 全局热键，不覆盖既有 `⌘K` 全局搜索，不新增前端 localStorage 数据库。

## 9. 开发默认决策

1. 产品名固定为「速记」，路由固定为 `/memos`，不再因命名阻塞开发。
2. 默认只显示「未整理」；增加「整理中」筛选；已整理正文保留但不占据默认收件箱。
3. M1 只做应用聚焦时的 `⌘/Ctrl+Shift+Space`，Windows/Linux 使用 Ctrl；桌面全局热键另行评审。
4. 文档标题中的「定期」只指用户可周期性手动整理；当前交付不包含自动调度或定时提醒。

## 10. 审核结论

**结论：产品主线通过，可以进入开发；原稿的存储、冻结与状态部分必须按本修订稿执行。** 独立收件箱、速记与 Wiki 分层、整理复用 curator → review → Publisher 都是正确方向，不需要另起一套知识系统。

| 审核项 | 结论 | 开发时必须落实 |
|---|---|---|
| 两层记录模型 | 通过 | 草稿不写 Wiki 内容根，不进默认 Agent 上下文 |
| 捕获与撤销 | 修正 | 可乐观 UI，但创建、删除、恢复都必须经本机 API；离线仅指不依赖外网 |
| 整理历史 | 修正 | attempts 与逐条快照独立持久化，重试不得覆盖旧 promotion |
| 来源冻结 | 修正 | 确定性 source id + 已存在来源完整性校验，不能直接用随机 id 的 `createText()` |
| 状态管理 | 修正 | memo 生命周期与 Job/Review/Publication 显示投影分离 |
| 重试与异常 | 修正 | 区分同操作重放、curator 原 Job 重试、fresh promote；异常不能一律解锁 |
| 原型交互 | 修正 | 整理中条目不可编辑/选择；空整理要求不能提交；计数由服务端返回 |
| 快捷键 | 修正 | 使用根布局单例捕获；速记搜索不注册 `⌘K` |
| 「定期整理」 | 范围澄清 | 本期仅手动整理，自动调度另立方案 |

原型只作为视觉与交互参考，以下演示逻辑不得搬进正式实现：`localStorage` 充当数据库、硬编码 `LIBRARIES`、前端定时器伪造审核发布、手写 Dialog、整理中仍可编辑/选择、空 task 自动兜底、客户端用 `status !== done` 推断权威计数，以及提交时直接 `trim()` 改写正文。

- `apps/server/src/index.ts`：在 KnowledgeSourceStore/WikiCuratorService 之后装配 MemoStore/MemoPromoter/projection，注册路由并调用启动恢复；目录使用 `path.join(paths.state, "memo")`，无需新增 paths 配置。

### 11.2 M1：CRUD、标签与列表

1. `contracts.ts` 统一校验：operationId 非空且长度受限；正文以 `trim()` 判断非空但保存原文；按 Unicode 字符执行 10,000 字上限，不用 UTF-8 字节数冒充字符数。
2. 标签解析前后端使用同一规则：支持 Unicode 中英文、数字、`_`、`-`，空白及中文标点作为边界，正文不改写；tags 做 NFKC 规范化、去重，单标签最多 32 字、单条最多 16 个。预览只是提示，服务端结果才是权威。
3. `POST /api/memos` 在同一事务内完成 operation 注册与 memo 插入；同键同载荷返回已创建条目，同键异载荷 409。
4. `PATCH` 使用 `expectedRevision` CAS，只有 `unorganized` 且未删除可改；保存正文后重算 tags、updatedAt 和 revision。
5. `DELETE` 同时校验 operationId、expectedRevision；整理中返回 409。软删除后默认列表和计数排除，但 attempts、Source、Review 与发布历史不动。
6. 增加 `POST /api/memos/:id/restore`，请求 `{ operationId }`，用于删除 toast 的撤销；恢复后 revision + 1。创建撤销仍调用 DELETE，删除撤销调用 restore，两者不能只改 React state。
7. GET 使用 `(created_at, id)` 双向确定排序和游标；标签、状态、关键字都在服务端过滤。M1 的 `q` 使用转义后的包含匹配即可，不引入 FTS 或重建索引。
8. GET 的 counts/tags 不受当前页、当前筛选影响；整理中计数由 lifecycle 得出，不能使用前端 `status !== organized` 猜测。

### 11.3 M2：来源冻结

1. 在 `KnowledgeSourceStore` 新增可信 `createMemoText()`（名字可调整，但语义不变）：输入 owner、确定性 id、正文、标题和 memo origin。
2. source id 按 `memo:sha256(ownerId:operationId:memoId)` 生成；每个 memo 在一次 attempt 中唯一，崩溃后同操作重放仍得到同一 id。
3. 已存在同 id Source 时，核对 owner、正文 hash 与完整 memo origin；一致才复用，不一致返回完整性错误，不能盲目接受旧记录。
4. `KnowledgeSourceOrigin.memo` 保存 `{ id, createdAt, tags, revision }`，`channel` 使用 `user_input`。`cleanOrigin()` 清洗并限制字段，manifest hash 纳入完整规范化 memo 对象；tags 顺序不得影响 hash。
5. 新增测试分别证明：memo id、createdAt、tags、revision 改变会改变 manifest hash；同操作重放不新增 Source；不同 operationId 不共用来源身份。

### 11.4 M2：promote 事务与恢复顺序

`MemoPromoter.promote(ownerId, input)` 按以下顺序实现，任何一步失败都要能从持久化状态继续：

1. 校验 1–50 个有序、去重 memoIds，task 去空白后非空并沿用 curator 的长度限制，bindingId 必填。
2. 先以 `${ownerId}:${operationId}` 做进程内串行化，再查同 owner/operationId 的旧 attempt；旧 attempt 按已保存的快照、bindingId、task 校验 requestHash，异载荷直接 409，且不重新读取正文覆盖快照。
3. 调用 `KnowledgeBindingRegistry.requireUsable()`，在任何 Source 冻结前确认目标库仍属于该 owner 且可用。
4. 新 attempt 在一个 `BEGIN IMMEDIATE` 事务中完成：整批重新读取并校验 owner、未删除、`unorganized`、revision，生成有序正文/tags 快照；requestHash 绑定 kind、有序 memoIds、每条 revision + 实际锁定的快照、bindingId、task；再写 operation、promotion、items，并将 memos 置为 `promoting + currentOperationId`。任一条件失败，整批无副作用。
5. 旧 attempt 不重新读取可变的 memo 正文来覆盖快照；按 items 顺序逐条冻结 Source，每冻结一条立即保存 `source_id` checkpoint。
6. 全部 sourceIds 就绪后将 phase 置为 `sources_frozen`；已有该 phase 的重放直接复用持久化 sourceIds。
7. 调用 `WikiCuratorService.create({ ownerId, operationId: "memo:" + operationId, bindingId, agentId: "wiki", task, sourceIds, executionMode: "background" })`。
8. Job 创建成功后保存 jobId 和 `job_created`。若 Job 已创建但响应前崩溃，重放通过相同 curator operationId 找回原 Job，再补写 checkpoint。
9. 返回 202 与当前 attempt/Job/投影。同操作重放恢复关联，不重新生成 Source，不把 failed 伪装成 queued。
10. 增加 `MemoPromoter.recover()`：server 启动时扫描 `freezing/sources_frozen` attempts 并按原 operationId 续跑；不能只依赖用户再次点击才能解除卡住状态。无法恢复的 attempt 保持可见错误并锁定到可安全判定的分支。

fresh promote 只用于 `rejected` 或经对账可重新开始的 failed/cancelled；curator 内部重试使用现有 `curator.retry()` 和原 sourceIds。`candidate_registration_failed` 恢复原 frozenCandidate，`returned` 走现有 revision 服务，二者均不得走 fresh promote。

### 11.5 M2：审核/发布投影

`projection.ts` 在每次列表查询及 promote 对账时组合当前 attempt 的 Job、candidateBatchId 对应 ReviewStore、同 owner/binding/batch/manifest 的 PublishJournal；需要时通过 `WikiRevisionService.followup()` 沿修订链读取最新 Job/Batch。可复用 `curatorTaskView()`，但必须再次核对 owner、binding、batch 和 manifest，不能跨库串数据。

| 当前真实状态 | memo 生命周期与 UI |
|---|---|
| queued/running/submitting | `promoting`；显示整理中，只读 |
| pending_review/approved/publishing | `promoting`；显示待审核/发布中，链接既有审核页 |
| published | `organized`；显示已发布，链接知识库结果 |
| no_changes | `organized`；显示无需变更，不生成虚假页面链接 |
| rejected | 回到 `unorganized`；保留原因和旧 attempt，可用新 operationId 再整理 |
| returned | 保持 `promoting`；跟随修订 Job/新 Batch，不解锁 |
| 普通 failed/cancelled | 对账无必须续接的副作用后回 `unorganized`，允许新 attempt |
| candidate_registration_failed | 保持 `promoting`；引导原 curator 恢复，不重新生成 |
| partial/conflict/needs_attention | 保持 `promoting` 且锁定；引导现有异常处理，禁止 fresh promote |

回到 `unorganized` 时清除 memo 的 `currentOperationId` 指针并保留 lastError，旧 attempt 永不删除；`organized` 保留当前指针用于结果回链。`conflictClosure/closed` 只有在既有 Review/Publication 投影给出明确终态后才能解除锁定，否则仍按 conflict 处理。

投影只读审核/发布事实源，不让 Publisher 回调直接改 memo.text。若为了性能改为持久化投影，必须同时提供启动全量对账，不能只靠运行时事件。

### 14.2 实现中的取舍

- 显示状态不持久化：每次列表查询先对 `promoting` 条目做只读对账并回写生命周期；投影失败不阻断列表，只表现为锁定状态与可读错误。
- 释放回未整理时写入可读原因：`上次整理失败，可重新整理` / `审核已拒绝，可修改后重新整理` / `整理已取消`；旧 attempt、Source、Review、发布历史均保留。
- `q` 使用转义 LIKE 匹配，不引入 FTS；标签计数走 `json_each` 聚合，与当前筛选无关。
- `memo:<operationId>` 作为 curator operationId；前缀后超过 200 字符在 promote 入口直接拒绝，避免撞 curator 上限。
- `returned` 沿 `WikiRevisionService.followup()` 追修订链读取最新 Job/批次（最多 5 跳），直到发布或新的审核状态；读取 review 校验 owner + binding，读取发布日志校验 owner + batchId + bindingId + manifestHash。
- 审核侧明确写入 `conflictClosure` 后才解除 conflict 锁定；仅处于 conflict 状态仍锁定。
- Job 创建前的确定性失败走 `failPromotion()` 单一事务：phase=failed + 释放 memos；同 operationId 重放时若已有 `memo:<op>` 的 Job 则 `adoptJob()` 认领并重新锁定，否则 409 要求新 operationId。前端收到 409 后换新 ID 再提交。
- 不同写操作共用同一 operationId（create/promote/delete/restore）一律 409，不再落到 sqlite 唯一键错误。
- 投影终态回写按 `currentOperationId` 做同一事务归属校验，迟到投影不能释放/完成新 attempt；`adoptJob` 整批校验归属、revision 与删除状态，`findJob` 只认领同 binding、同 task 的 `memo:<op>`。
- 前端只对 `queued/running/submitting/approved/publishing` 轮询（2.5s）；`pending_review` 等人工终态不轮询。
- 捕获浮层提交中禁止 Esc 与外部点击关闭；创建成功时只有当前草稿仍等于已提交正文才清理，迟到响应不会清掉后来输入。
- 未新增 session customType；整理状态仍复用 `pudding:knowledge_job` 投影卡。
