# 会话深链交接方案

2026-10-16。动机：Codex 桌面端的「复制深度链接」（`codex://threads/{thread_id}`）证明了一条更轻的交接路径——交接的不是历史副本，而是一个**稳定引用**，接收方按需回读。本文评估这条路径在 PuddingTeams 的落法，与既有快照 Fork 的关系，以及分期实施方案。

## 1. 两个范式，两个语义

| | 快照 Fork（现有） | 深链交接（本方案） |
|---|---|---|
| 交接物 | 冻结在某一刻的历史副本 | 指向活会话的引用 |
| 源会话继续演进 | 接收方看不到 | 接收方读到最新 |
| 大小约束 | 有导入预算（字节数 ≤ 目标上下文一半） | 无——读多少由接收方自己决定 |
| 隔离性 | 强：目标拥有自己的历史，可独立演化 | 弱：依赖源持续存在且可读 |
| 溯源 | `sourceSnapshotId` 不可变 | 引用本身即溯源，但内容可变 |
| 适用 | 「交接出去各干各的」 | 「跟进同一件事」「补充背景」 |

两者互补，不互替。快照 Fork 解决所有权转移；深链解决上下文供给。

## 2. 深链的三层形态

同一份引用，三种载体：

1. **内部标识**：`roomId + sessionId`（数据层的唯一身份，已有）。
2. **Web 链接**：`/chats?room=<id>&session=<id>`——现有路由已支持，缺的只是「复制链接」入口。
3. **应用 URL scheme**：`puddingteams://rooms/<roomId>/sessions/<sessionId>`——Electron 桌面端注册 scheme 后，可从终端、浏览器、文档直接唤起定位。Codex 验证过这个模式（ChatGPT.app 注册 `codex` scheme，LaunchServices 路由）。Electron 已在仓库里，注册 scheme 是小改动，可后置。

## 3. Agent 侧：`session_read` 工具（方案核心）

让「给链接、自己读」成立的关键不是链接本身，而是**接收方有读取工具**。装配走 `agent-extensions.ts` 的既有 InlineExtension 模式（与 `read_delegation_result`、`knowledge_*` 同一条路），native pi Worker 直接可用；命令行 Connector 通过 HTTP API（`GET /api/sessions/:id/messages` 已存在）获得等价能力。

工具形态（建议）：

```
session_read({ session: "<link|sessionId>", mode: "messages" | "full", cursor?, limit? })
```

- `messages`：只回用户/助手文本（默认，省上下文）；`full`：含工具调用与结果。
- 分页游标 + 条数上限，读取量由调用方自控——这是深链范式没有「预算」的原因：上下文管理责任从平台检查转移给读取方，模型自己决定读多少。
- 返回里带 `leafEntryId`，调用方据此判断源是否有新进展（活引用的「新鲜度」语义）。

### 权限边界（必须先定的部分）

深链把「读另一条会话」从平台内部的特例（`read_delegation_result` 只读自己的委派执行）泛化成通用能力，权限模型是主要设计点：

- **同窗口会话**：自由读。同一房间的会话本来就是同一上下文家族的成员。
- **跨窗口、同 Workspace**：Manager 可读（它本来就统筹全局）；Worker 需要该会话被显式引用进它的任务（见 §4），引用即授权。
- **跨 Workspace**：拒绝。Workspace 是数据边界（用户数据目录迁移方案已确立）。
- 一律只读。深链永远不提供写入口。

## 4. 交接载荷：任务里的 `contextRefs`

深链进入工作流的方式不是新交互，而是现有任务载荷的可选字段：

- Manager 委派 / 用户指派任务时，可附 `contextRefs: ["<会话链接>"]`，语义是「背景材料，按需回读」。
- Worker 提示词里得到一句路由材料：这些引用可用 `session_read` 读取，只读。
- 与 Fork 的选择交给场景：要冻结副本走 Fork；要活背景走 contextRefs。UI 上 Fork 对话框可以加一档「仅引用，不复制历史」。

## 5. 与现有能力的关系

- `read_delegation_result`：深链读取的特例（读自己委派的执行记录）。`session_read` 是它的泛化，泛化后两者可共用实现，delegation 特例保留（语义更明确）。
- 快照 Fork：保留。深链不解决「源可能被删/改写而我需要稳定基线」的问题。
- 知识库工具：知识库是「沉淀后」的读；深链是「进行中和刚完成」的读。漏斗两端。

## 6. 分期实施

- **P1（小，已落地）**：聊天菜单加「复制链接」（web 查询参数形态，零后端改动）+ `session_read` 工具（native pi 先行）+ 权限规则（§3）。
  - 实现：`apps/server/src/pi-bridge/session-read.ts`（`SessionReadService`，权限：同窗口自由读 / 同 Workspace Manager 自由读、Worker 引用即授权 / 跨 Workspace 拒绝；只读已落盘条目，分页 cursor + 100k 字符上限，返回 `leafEntryId`）。装配点两处：窗口聊天会话（`PiSessionStore.managerResourceLoader`，manager 与 worker 单聊）与 Worker 委派执行会话（`LocalPiDriver.newSession`，引用扫描覆盖委派任务文本里的 contextRefs）。「复制链接」在 `apps/web` 会话菜单（`session-list.tsx`）。
- **P2（中，已落地）**：委派/指派载荷支持 `contextRefs`（`DelegateParams.contextRefs` 描述含会话深链；委派任务文本追加「可用 session_read 只读回读」提示）；Worker 提示词路由材料（`SESSION_READ_WORKER_HINT` / `SESSION_READ_MANAGER_HINT`）；Fork 对话框加「仅引用」档（`fork-session-dialog.tsx` 的 reference 模式：复制链接 / 复制链接并打开与目标 Worker 的单聊）。
- **P3（后，已落地 Electron 部分）**：Electron 注册 `puddingteams://` scheme——`electron/src/deep-link.ts`（纯解析模块，白名单形态校验）+ `main.ts`（`setAsDefaultProtocolClient`、macOS `open-url`、Windows/Linux `second-instance` 与冷启动 argv、冷启动 pending 消费）+ `electron-builder.yml` 的 `protocols`。命令行 Connector 的 HTTP 读取路径写进 Driver SPI 文档（未做）。

## 7. 风险

- **活引用的不确定性**：Worker 读到的内容可能晚于任务发出时。缓解：返回 `leafEntryId`；需要冻结语义的场景仍走 Fork。
- **上下文失控**：`full` 模式可能一次读入巨量内容。缓解：默认 `messages`、分页上限、单条消息超限也截断（100k 硬上限，实现已覆盖单块超限路径）、工具描述里写明成本。
- **权限蔓延**：引用即授权需要落审计（谁把哪条会话引用给了谁），复用 delegation 的审计落盘。**当前实现未落授权/读取审计，列为后续工作**（P1-P3 验收时确认不阻塞）。
- **威胁模型边界（已确认的已知边界）**：授权扫描只认自己会话里 `role === "user"` 的条目；有 bash 写盘能力的 Worker 理论上可以往自己的会话 JSONL 追加伪造 user 条目实现自我授权。但这类 Worker 本就能直接 `cat` 任意会话文件，`session_read` 的权限矩阵约束的是遵循提示词约束的 Worker，不构成新增攻击面。后续如需收紧，可改为只认平台自己追加的条目（按 entry id 登记）。
- **内容透出**：读到什么取决于目标会话看过什么——目标会话里出现过的敏感内容（如 `cat .env` 的输出）会随授权读出。这是授权模型的固有语义，工具描述已写明成本。
