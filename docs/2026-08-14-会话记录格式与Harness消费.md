# 会话记录（Session JSONL）格式与 Harness 消费

2026-08-14。本文是 PuddingTeams harness 的事实源之一：会话**记录了什么、落在哪里、怎么读**。
内容以代码实现为准：`apps/server/src/pi-bridge/session-store.ts`（PiSessionStore）、
`apps/server/src/agent-runtime/direct-dispatch.ts`（direct 单聊）、
`apps/server/src/agent-runtime/invoker.ts`（委派与审批投影）、
`apps/server/src/pi-bridge/agent-extensions.ts`（窗口镜像）、`apps/server/src/paths.ts`（目录）。

## 1. 定位

每个窗口（solo / direct 单聊 / 群聊）背后是一个 pi 会话，pi SDK 以 **JSONL 事件流**持久化：
每条 JSON 一行，按 `id` / `parentId` 串成链，只追加不改写。它是三样东西的合一：

- **对话历史**：重启后恢复上下文、前端渲染历史消息的事实源；
- **运行账本**：每轮 assistant 的 thinking、工具调用、usage/cost 全量留痕（可审计、可对账）；
- **harness 总线**：平台侧的委派卡、审批卡、镜像卡也作为自定义条目写进同一文件，与 LLM 消息共享时间线。

非 pi worker（puddingclaw / codex / claude-code）的会话在各自 CLI 后端。窗口 Session JSONL 只存窗口绑定关系对应的聊天投影、委派卡与最终结果，不把高频 CLI 事件塞进 manager 上下文；逐事件执行轨迹另存为 delegation 时间线（§2.1）。

## 2. 落点与命名

```
~/.puddingteams/sessions/<创建时间ISO，冒号句号换成连字符>_<sessionId>.jsonl   # manager / solo / direct / 群聊的 pi 会话
~/.puddingteams/sessions/workers/                                            # pi worker 会话
~/.puddingteams/state/windows.json                                           # 窗口及每个房间 Session/worker 的续接绑定
~/.puddingteams/state/work-states.json                                       # Session 的 Goal 历史/Decision 快照；v5 内聚 plan/recovery/operations/outbox
~/.puddingteams/state/delegations.json                                       # Delegation 当前快照 + 因果链
~/.puddingteams/state/interactions.json                                      # 待审批 Interaction 的公开记录
~/.puddingteams/state/delegation-timelines/<delegationId>.jsonl              # 非 pi Driver worker 逐事件时间线
```

目录根由 `PUDDINGTEAMS_HOME` 决定（缺省 `~/.puddingteams`）。pi SDK **惰性落盘**：首个 assistant
消息出现前会话只在内存；平台侧在新会话上写自定义卡时由 `ensureSessionFile` 复制 SDK 首刷逻辑
提前落盘（`wx` 不覆盖），防重启丢失。

### 2.1 非 pi Driver worker delegation 时间线

Codex、PuddingClaw、Claude Code 和声明式 CLI Connector 的执行过程不写成新的 `pudding:*` 卡，而是逐条追加到独立 JSONL。transport 可以是 spawn/http/rpc/acp；PuddingClaw 的 spawn JSONL 与 HTTP NDJSON 共用同一套投影，所以落盘格式与房间展示不因 transport 改变。每行字段为：

```json
{"id":"<delegationId>:12","delegationId":"…","seq":12,"timestamp":"…","source":"codex","sourceEvent":"item.completed","kind":"tool","status":"completed","title":"命令完成","content":"…","itemId":"item_…","sourceSeq":123,"metadata":{}}
```

`seq` 是 PuddingTeams 分配的 delegation-local 单调序号，是 REST/WS 断点续读的唯一游标；`sourceSeq` 仅在上游暴露时保留。文件 append-only，事件之间不做按 `itemId` 覆盖或折叠，所以 started/updated/completed 会作为三条独立记录保留。`metadata` 只能放有界且已脱敏的展示事实，不能落凭证或无界工具输出。

PuddingClaw 的 `token` 是传输增量，不作为平台语义事件逐 token 落盘。Driver 在内存中缓冲连续 token，遇到 `segment_break`、工具、审批、final/result 等非 token 事件或流结束时，只写一条 `sourceEvent:"token.batch"` 的 assistant 活动；`content` 是合并文本，`metadata` 保留 `tokenEventCount` 与可用的 `sourceSeqStart/sourceSeqEnd`。REST/WS 与 JSONL 因此都只承载合并批次，避免一 token 一行的磁盘与 DOM 膨胀；旧版本已经落盘的 raw token 仅由 Web 兼容聚合展示，不改写历史文件。

这份时间线是执行过程视图的事实源，不进入 LLM 会话主链：task 卡继续表达委派的最新状态，timeline 表达委派内部发生过的每一步。这样既能完整回放，又不会让 token/工具增量制造 Session JSONL 与 manager 上下文的高频膨胀。

### 2.2 Delegation 因果链：怎么落盘、怎么读

`state/delegations.json` 与上面两种 JSONL 不同：它是 `DelegationStore` 维护的**当前状态快照**，外层结构固定为：

```json
{
  "version": 1,
  "delegations": {
    "D1": {
      "id": "D1",
      "managerSessionId": "manager-session-1",
      "agentId": "researcher",
      "task": "调研 2026 年 Agent 产品趋势",
      "handoffKind": "request",
      "status": "completed"
    },
    "D2": {
      "id": "D2",
      "managerSessionId": "manager-session-1",
      "agentId": "researcher",
      "task": "继续补充市场规模数据和出处",
      "parentDelegationId": "D1",
      "handoffKind": "followup",
      "status": "completed"
    },
    "D3": {
      "id": "D3",
      "managerSessionId": "manager-session-1",
      "agentId": "writer",
      "task": "根据 D2 的调研结论和交付物撰写正式报告",
      "parentDelegationId": "D2",
      "handoffKind": "request",
      "status": "completed"
    },
    "D4": {
      "id": "D4",
      "managerSessionId": "manager-session-1",
      "agentId": "reviewer",
      "task": "独立核验 D1 中的关键数字",
      "parentDelegationId": "D1",
      "handoffKind": "request",
      "status": "completed"
    }
  }
}
```

为了教程可读性，上例把真实 UUID 缩成 D1-D4，也省略了 `windowId/cwdSnapshot/managerToolCallId/agentRevision/operation/revision/createdAt/updatedAt/result`、Goal 委托的 `intent/expectedOutcome/evidenceRequirements/completionBoundary` 等字段；实际记录结构见 `apps/server/src/agent-runtime/delegation-store.ts`。

因果关系为：

```text
D1 researcher：首次调研
├─ D2 researcher：followup 追问
│  └─ D3 writer：上游结果触发的新 request
└─ D4 reviewer：从 D1 分叉出的新 request
```

落盘时序与用途：

1. manager 产生 `agent_<worker>__delegate` toolCall，PuddingTeams Runtime 立即创建不可变 `id`，以 `status:"running"` 和 `revision:0` 写入 `delegations.json`；此时 UI 已能用 `delegationId` 打开执行过程或终止单个 Run。
2. worker 启动后回填 `sessionHandle/runHandle`；需审批时变为 `waiting_input`，完成/失败/取消时通过 revision 校验转入终态。completed 边界会先把完整 `NormalizedResult` 写入该 record 的 `result`，再向 manager 投影 toolResult。
3. outcome 中若有 `sessionHandle`，`AgentInvoker` 使用同一个已更新的 `DelegationRecord` 内存对象调用 `rememberWorkerSession()`，把它写成 manager Session 属主窗口的 `state/windows.json.workerBindings[managerSessionId][agentId]`；不是落盘后重新读取 `delegations.json` 再复制。binding 同时冻结 `targetWindowId`；写入前校验 manager Session 归属、合法执行窗口，以及 `targetWindowId/workspaceId/cwdSnapshot/agentRevision`，避免跨窗口复用或旧 Run 晚完成后污染已删除会话、已切换项目、已重建执行窗口或已升级 Connector 的上下文。
4. `parentDelegationId` 写入前必须指向同一 `managerSessionId` 中已存在的委托；`followup` 无 parent 直接拒绝。这保证不能把其他会话的 delegationId 拿来串链。
5. 查单条记录用 `delegations[id]`；查某 manager 会话的链先按 `managerSessionId` 过滤，子向父追溯时循环读 `parentDelegationId`，展示树时预先构建 `parentDelegationId -> children[]`。上例不是单链表，而是以 D1 为根的分叉树。
6. 文件不 append：平台在进程内串行化变更，每次读取全部 map、更新指定 record、写临时文件后原子 `rename`。教程不要把它当成事件日志；历史活动要去读 Session JSONL 或 `delegation-timelines/*.jsonl`。

Delegation 历史 handle 与房间 Session 最新指针的关系例如：

```text
D1.sessionHandle = S1 ─┐
D2.sessionHandle = S2 ─┴─ 历史记录都保留在 delegations.json

windows.json
  workerBindings[managerSessionId][researcher].sessionHandle = S2
  # 仅当前房间 Session 下次 continue 使用
```

下一次续接由 `AgentInvoker.sessionHandleFor(windowId, managerSessionId, agent)` 直接读取 `workerBindings[managerSessionId][agentId]` 并再次校验房间 Session 归属、workspace/cwd/revision，不扫描 D1/D2 推断“最新”。

#### 2.2.1 连续对话的标准入口：delegate 参数、因果链与 Worker Session

Manager 最终回复中出现“几个 Worker 的接力/追问 delegationId 如下”只是便于用户继续下指令的自然语言汇总，**不是连续对话机制唯一依赖的提示词，也不是平台自动注入父结果的协议**。真正的执行入口是每个 Worker 独立注册的 `agent_<worker>__delegate` 工具；Worker 身份编码在工具名中，标准参数由 `DelegateParams` 约束。普通非 Goal 委托的完整接力调用例如：

```json
{
  "task": "继续核对第三条新闻，并给出原始来源",
  "parentDelegationId": "D1",
  "handoffKind": "followup",
  "session": "continue"
}
```

参数语义必须按三条相互独立的轨道理解：

| 参数/状态 | 负责什么 | 不负责什么 |
|---|---|---|
| `task` | 本次实际发送给目标 Worker 的新消息；承载上游摘要、要求、验收边界和交付物路径 | 不建立结构化父子关系 |
| `parentDelegationId + handoffKind` | 在当前 `managerSessionId` 内建立执行因果；`followup` 表示追问/返修，带 parent 的 `request` 表示上游触发的新下游任务 | 不选择 Worker Session，也不自动注入父 `result.content`、父会话、附件或 timeline |
| `session` / `workerBindings[managerSessionId][agentId].sessionHandle` | `"continue"`（缺省）要求 PuddingTeams 从当前房间 Session 的 binding 选择不透明 handle，再交给 Driver 恢复 Worker 私有会话；`"new"` 走新会话 | 不决定 Delegation 是否为父子关系 |

工具 Schema 的推断规则是：省略 `session` 等价于 `"continue"`；提供 `parentDelegationId` 但省略 `handoffKind` 时按 `"followup"` 记录；显式 `handoffKind:"followup"` 却没有 parent 时直接拒绝。若当前 Goal 已有 WorkPlan，还必须传入合法 `workItemId`，并由 Goal 委托提供 `intent`、`expectedOutcome`、`completionBoundary`，可选 `evidenceRequirements`。

`"continue"` 的 handle **由 PuddingTeams 指定，不由 Worker 临场选择**：`AgentInvoker` 读取 manager Session 属主窗口的 `workerBindings[managerSessionId][agentId]`，再以目标执行窗口校验 workspace、cwd 和 Agent revision 后，把 handle 传给 `Driver.continue()`；Claude Code/Codex 等 Connector 即使为本轮重新 spawn CLI 进程，也会通过 `--resume`/`exec resume` 恢复同一个逻辑 Worker Session。没有有效 binding 时，本轮从新 Worker Session 开始。进程是否新 spawn 与模型会话是否续接是两件事。

`parentDelegationId` 与 Worker Session binding 的授权边界都是 Manager/房间 Session：parent 必须已经存在并满足 `parent.managerSessionId === currentManagerSessionId`；binding 也必须位于同一个 `managerSessionId` 桶内。新开房间 Session 后既不能把旧 Delegation 串成 parent，也不会恢复旧 Worker Session。切回旧房间 Session 时才恢复该 Session 自己的 Delegation 历史和 Worker bindings。

因此连续对话的最小心智模型是：

```text
delegationId / parentDelegationId = Manager Session 内的执行因果与审计
task Prompt / Artifact 路径       = 实际跨 Worker 信息交接
Room Session worker binding      = 该房间 Session 下一次 continue 使用的 Worker 指针
```

同 Worker 追问通常使用 `followup + continue`。跨 Worker 接力则以 A 的 `delegationId` 作为 B 新委托的 parent（通常是带 parent 的 `request`），但 Manager 仍必须把 B 真正需要的摘要、分页回读内容或 `.pudding/handoff/` 路径写入 `task`；A 的隐藏模型上下文不会共享给 B。每次调用都会创建新的 Delegation，旧记录不被覆盖。

三份事实源不要混淆：

| 事实源 | 回答的问题 |
|---|---|
| `state/windows.json` | 当前窗口的活动 pi Session 是哪个；当前房间 Session 的每个 Worker 下次续接应使用哪个 `sessionHandle` 与执行窗口 |
| `state/delegations.json` | 这次委托是谁、当前状态、父委托是谁、最终结果是什么 |
| manager/worker Session JSONL | manager 调了哪个工具、模型看到了什么 toolResult；pi worker 内部的完整会话是什么 |
| `state/delegation-timelines/<id>.jsonl` | 非 pi Driver worker 在该 Delegation 内部逐步做了什么 |

### 2.3 超长 worker 结果与 manager toolResult

completed 委托的完整 `NormalizedResult` 先进入 `delegations.json`。当正文超过 Harness 阈值时，`LargeWorkerResultStore` 再把原文无损、原子地写入 `state/large-worker-results/<delegationId>.txt`（0600）；manager toolResult 只携带 head/tail 预览、`originalChars/estimatedTokens`、`offloaded` 与受权回读说明。Manager 通过 `read_delegation_result({delegationId, offset, limit})` 分页读取，服务端校验当前 Manager Session 确实拥有该 Delegation，且不暴露宿主路径。pi worker Session JSONL 与 spawn timeline 仍只是各自执行事实源，不能替代该完整归一化结果。这里的“完整”以 Driver 输出的 `NormalizedResult` 为边界，Connector 在归一化前已经丢弃的上游数据不在此承诺内。

配置位于“设置 -> Harness -> 上下文工程 -> Worker 结果上下文”，存入 `config/product.json` 的 `harness.workerResults`；默认阈值/预览/分页预算见接入方案 §7.2.2。无损外置是安全基线，UI 不提供退回静默硬截断的开关。

#### B. manager Session JSONL：模型真正看到的 toolCall/toolResult

manager 会话文件中相关行大致为：

```jsonl
{"type":"message","id":"a1","parentId":"u1","timestamp":"2026-08-20T08:00:00.000Z","message":{"role":"assistant","content":[{"type":"text","text":"我先委托数据分析 worker。"},{"type":"toolCall","id":"call-01","name":"agent_puddingclaw__delegate","arguments":{"task":"调研 Agent 产品趋势并给出完整证据","handoffKind":"request"}}],"stopReason":"toolUse","timestamp":1787212800000}}
{"type":"custom_message","customType":"pudding:task_assign","content":"调研 Agent 产品趋势并给出完整证据","display":false,"details":{"taskId":"call-01","delegationId":"11111111-1111-4111-8111-111111111111","worker":"puddingclaw","windowId":"window-group-01","from":"group","status":"running","processView":true},"id":"c1","parentId":"a1","timestamp":"2026-08-20T08:00:00.050Z"}
{"type":"message","id":"r1","parentId":"a1","timestamp":"2026-08-20T08:03:00.000Z","message":{"role":"toolResult","toolCallId":"call-01","toolName":"agent_puddingclaw__delegate","content":[{"type":"text","text":"[结果 head 预览……]\n\n…(中间正文已无损外置)…\n\n[结果 tail 预览……]\n\n[完整结果已外置] delegationId=11111111-1111-4111-8111-111111111111，originalChars=42600，estimatedTokens=10650（估算方法 ceil(chars/4)）。用 read_delegation_result 分页精确读取。\n\n交付物（可在接力任务中按路径引用）：\n- report.md：.pudding/handoff/11111111-1111-4111-8111-111111111111/report.md"}],"details":{"worker":"puddingclaw","status":"completed","delegationId":"11111111-1111-4111-8111-111111111111","sessionHandle":"pc-session-77","processView":true,"offloaded":true,"originalChars":42600,"estimatedTokens":10650},"isError":false,"timestamp":1787212980000}}
```

manager 模型的下一次推理使用 B 中 toolResult 的 `content`，不会自动去读 A 中 `result.content`。`details` 会跟 toolResult 持久化，供 UI 渲染和 Extension 重建状态，但不会作为工具正文交给模型。所以本例中 A 有 42,600 字符，B 的 manager 先看到 head/tail 与精确回读说明，需要中间内容时调用 `read_delegation_result`。

这里必须区分 pi 0.83 的两层统一格式。第一层是 Extension 的 `tool.execute()` 成功返回值，SDK 类型为 `AgentToolResult<TDetails>`：

```ts
interface AgentToolResult<TDetails> {
  content: (TextContent | ImageContent)[]; // 返回给模型的正文
  details: TDetails;                      // 日志/UI 使用的任意结构化数据
  usage?: Usage;
  addedToolNames?: string[];
  terminate?: boolean;
}
```

PuddingTeams manager Extension 返回的正是这一层：

```ts
return {
  content: [{ type: "text", text: resultText }],
  details: { worker, status, delegationId, sessionHandle, processView: true }
};
```

`{content, details}` 这个外壳是 pi 的统一 `AgentToolResult` 契约；`worker/status/delegationId/sessionHandle/processView` 的字段名和语义是 PuddingTeams 自定义投影。当前 `AgentToolResult` 本身没有 `role/toolCallId/toolName/isError/timestamp`。

第二层是 pi 工具执行器把第一层包装成会话消息后的 `ToolResultMessage<TDetails>`：

```ts
interface ToolResultMessage<TDetails> {
  role: "toolResult";
  toolCallId: string;
  toolName: string;
  content: (TextContent | ImageContent)[];
  details?: TDetails;
  usage?: Usage;
  addedToolNames?: string[];
  isError: boolean;
  timestamp: number;
}
```

最终写入 manager Session JSONL、并在后续上下文中作为工具结果重放的是第二层。pi 执行层根据工具是否正常完成生成 `isError`，同时补齐工具调用身份和时间戳；模型消费其中的 `content`，而不是把 `details` 序列化进工具正文。`details` 仍会落盘，供日志、UI renderer 和状态重建使用。

manager inline pi Extension 从 factory 装配、`registerTool()`、`execute()`、`ScopedAgentInvoker` 到 Driver 的完整实际路径见接入方案 §3.2.2；双宿主 Connector 的纯 pi `pi/` 门面是另一条不经过 PuddingTeams Delegation 的路径，见该文 §9.5.1。

**B 不是通过重新读取 A 的 JSON 文件组装的。** completed 路径中，Runtime 先用 `event.result` 转移并持久化 Delegation，`transitionDelegation()` 成功后返回已写入的 `DelegationRecord` 内存对象；`AgentInvoker` 直接把这个 outcome 映射成 `AgentInvokeResult`，manager Extension 再由它组装 `{content, details}` 返回 pi SDK。因此 A 和 B 是同一次运行结果的两个分流，不是“先落 A，再把 A 当数据库回读生成 B”：

```text
Driver event.result
  → Runtime transitionDelegation（写 A，返回 transitioned.record）
  → RuntimeOutcome { result: event.result, delegation: transitioned.record }
  → AgentInvoker 生成 AgentInvokeResult
  → manager Extension 生成 AgentToolResult { content, details }
  → pi SDK 包装为 ToolResultMessage，补 role/toolCallId/toolName/isError/timestamp 并写 B
```

示例 `details` 的字段来源为：

| 字段 | 来源 |
|---|---|
| `worker` | Extension 对当前 Agent 的已知身份投影（Invoker details 有值时优先，否则回退 `agent.name`） |
| `status` | `AgentInvokeResult.status` |
| `delegationId` | Runtime outcome 中 `DelegationRecord.id` |
| `sessionHandle` | Runtime outcome 中已更新的 `DelegationRecord.sessionHandle` |
| `processView` | manager Extension 固定加入的 UI 能力标志 |
| `isError` | pi SDK 工具执行结果标志；正常 return 为 `false`，throw/错误路径为 `true` |
| `timestamp` | pi SDK 向 manager Session 追加 toolResult 时生成 |

这个顺序还意味着：Delegation 终态持久化失败时，不应继续伪造一条成功 toolResult；正常 completed toolResult 是已成功落盘的运行结果投影。

### 2.5 Goal 执行计划、恢复与幂等落盘（v4 已实现）

## 3. 条目全集：记录了什么

### 3.1 元信息条目

| type | 记录内容 |
|---|---|
| `session` | 首行头：`version`（当前 3）、`id`、`timestamp`、`cwd` |
| `model_change` | 会话当前模型（`provider` / `modelId`） |
| `thinking_level_change` | 思考档位 |
| `session_info` | 自动生成的会话标题（`name`），首回合后写入 |

### 3.2 `message` 条目（LLM 对话主链）

三种 role，均带 `id` / `parentId` / `timestamp`：

- **user**：用户输入原文。带附件时由 `chat.ts` 在文本末尾追加冻结路径块：
  `用户附件（平台冻结路径，可按需读取并在委托任务中原样传递）：\n- <文件名> (<mime>, <size> bytes): <绝对路径>`。
- **assistant**：一轮一条。`content[]` 依次含 `thinking`、`text`、`toolCall`
  （`id`/`name`/`arguments`）；另有 `api`/`provider`/`model`、逐项 `usage`
  （input/output/cacheRead/cacheWrite/reasoning/totalTokens）与 `cost`、`stopReason`。
  usage 是 provider 响应的原始计数经 pi-ai 按协议归一化：OpenAI 兼容协议取
  `prompt_tokens_details.cached_tokens`（DeepSeek 为 `prompt_cache_hit_tokens`）→ `cacheRead`，
  Anthropic 取 `cache_read_input_tokens` / `cache_creation_input_tokens` → `cacheRead`/`cacheWrite`；
  `input` 是扣除缓存后的净新输入。`cost` 不是 provider 给的，是 pi 按模型价目表
  （含缓存读/写单价）换算。缓存命中率统计见 SDK `core/cache-stats.js`。
- **toolResult**：`toolCallId` 回指 assistant 的 toolCall，`content[]` 为工具输出文本，含 `isError` 标记。
  若该工具调用扩大了 active tools 集合（如 `search_agent_tools` 激活新工具），SDK 额外标注
  `addedToolNames: string[]`（SDK 只写不读）；平台在会话重建时回放该字段恢复激活态（接入方案 §3.3）。

### 3.3 `custom_message` 条目（平台卡，`customType: "pudding:*"`）

展示卡由 `PiSessionStore.sendCustomMessage` 写入，形如
`{type:"custom_message", customType, content, display:true, details, id, parentId, timestamp}`。
群聊 manager 或 solo manager 来源会话在 delegate 工具仍执行时，另用 `appendCustomMessageProjection` 立即追加
`display:false` 的审计投影；它不进入模型队列、不单独渲染，只供刷新/WS 重连后恢复原工具卡。
solo 委托同时在 worker direct Session 写可见 `from:"solo"` 镜像，在来源 manager Session
写同 `taskId` 的隐藏恢复投影；direct-dispatch 仍只写 worker 单聊内的 `from:"direct"` 可见卡。
全集与 `details` 字段（以写入方为准）：

| customType | 写入方 / 时机 | details |
|---|---|---|
| `pudding:user_message` | direct-dispatch：direct 窗口用户气泡（展示文本，不含附件冻结路径块） | `windowId` |
| `pudding:task_assign` | 委派发起的 running 投影。solo：`announceToWindow` 写可见镜像；direct：`direct-dispatch` 写可见卡；group：Runtime 接单后向 manager Session 立即写隐藏审计投影。Runtime 取得更多信息时以同 `taskId` 追加富化投影，前端按 `taskId` 对账 | `taskId`/`worker`/`windowId`/`from`("solo"｜"direct"｜"group")/`status:"running"`；富化后带 `delegationId`（委托级终止）与 `processView:true`；pi worker 有 handle 后另带 `sessionHandle`，spawn worker 由 `delegationId` 打开 §2.1 时间线 |
| `pudding:task_result` | 委派落定。direct 路径另带 `delegationId`/`interactionId`；有 token 统计时另带 `usage`（`turns`/`inputTokens`/`outputTokens`/`cost`，pi worker 按 Run 聚合，口径同 manager 统计条：输入含缓存读写） | `taskId`/`worker`/`windowId`/`status` |
| `pudding:interaction_required` | worker 需人工审批（invoker 向 manager 会话的安全投影 + 镜像到对方窗口）。**无 token** | `interactionId`/`delegationId`/`goalId?`/`worker`/`status:"pending"`/`revision`/`requests[]`（`requestId`/`prompt`/`command?`/`path?`/`risk`/`options`）；Goal 审批写操作必须回传 `expectedGoalId` |
| `pudding:interaction_resolved` | 审批处理结果。批准在 Runtime 受理并把 Delegation 从 `waiting_input` 原子推进为 `running` 后立即写入，不等待 worker 最终完成；拒绝/取消走终态 | `interactionId`/`delegationId`/`worker`/`status`（批准为 `"approved"`） |
| `pudding:artifact_created` | §15.6 交付物登记 | `artifact`（完整记录） |
| `pudding:decision_answered` | 工作状态面板的决策已回答 | 见 `routes/work-state.ts` |
| `pudding:work_state_context` | 工作快照注入 | 见 `pi-bridge/agent-extensions.ts` |
| `pudding:work_plan_update` | Goal、WorkPlan、Submission 或 review 原子提交后的隐藏恢复投影；`display:false`，不是权威状态，不进入模型上下文 | `eventId` + `goalId` + outbox `payload`（`action`/`workPlanId?`/`workItemId?`/`status?`/`revision`） |
| `pudding:goal_recovery` | Goal 获得恢复 lease 后的可见/唤醒投影；与 outbox 使用同一 `eventId` 做接收端去重，不是权威状态 | `eventId` + `goalId` + `lease`/`interruption` |
| `pudding:goal_interrupted` | Goal 中断后的可见审计投影，不触发模型轮次 | `eventId` + `goalId` + `interruption` |

## 4. 一次委派的完整记录链路

solo 里 manager 派活会把可见 running 卡镜像到 worker 单聊，落定后补结果卡；solo/group
manager 都保留原始 delegate 工具卡，并在 Runtime 创建 Delegation 后立即向来源 manager Session
追加一条 `display:false` 的 running 投影。该投影带 `taskId`/`delegationId`，不会形成第二张卡，
但刷新时能把「执行过程」入口与状态重新折回原工具卡：

```
assistant  { thinking, text:说明, toolCall: agent_<worker>__delegate {task,…} }   ← 发起
custom_message  pudding:task_assign (status:"running")                            ← solo 单聊可见镜像；solo/group manager 隐藏恢复投影
toolResult { toolCallId 回指, content: manager 可见的 worker 结果投影, isError }       ← 阈值内全文；超阈值 head/tail + 分页读取入口
custom_message  pudding:task_result                                               ← 落定镜像
assistant  { text: 转述给用户的最终答复 }                                          ← 收尾
```

direct 单聊没有 manager 回合，消息落盘即 `pudding:user_message` + `pudding:task_assign`(running)
两张卡，后台委派落定后补 `pudding:task_result`（needs_input 时改由 invoker 直接写审批卡进本窗口）。

审批会打断主链：插入 `pudding:interaction_required`；用户批准后立即追加
`pudding:interaction_resolved(status:"approved")`，把同 `delegationId`（或
`interactionId`）的原委派卡从“等待审批”对账为“执行中”。worker 最终落定后才追加
`pudding:task_result`；若又一次需要输入，则改追加下一轮
`pudding:interaction_required`。整个过程只追加 JSONL，不改写旧条目。

Harness 消费 `display:false` 的 manager `pudding:task_assign` 时不能直接丢弃（`from:"solo"|"group"`）：无论来自历史回放还是 store 订阅实时广播，都应先按
`details.taskId === toolCall.id` 对原 delegate 工具调用合并 `delegationId`、`sessionHandle`、
`processView` 与 running 状态，再跳过该 custom message 自身的展示。实时流中的后续
`message_update`/`message_end` 也必须保留工具调用已获得的 `details`、`progress` 与结果字段，
不能用模型消息里只有 name/args 的 toolCall 块覆盖运行态元数据。
镜像到 worker direct Session 的终态 `pudding:task_result` 也必须保留
`delegationId`/`sessionHandle`/`processView:true`；终态卡只结束 running 状态，不撤销对该 Delegation 执行过程的只读查看能力。
消费端还应按同 `taskId` 把前置 `pudding:task_assign` 的过程元数据继承给终态卡，
保证 append-only 事件在历史回放、实时流和终态展示中表达同一条 Delegation。

## 6. Harness 消费约定

- **按 `parentId` 链读**，不要按行序假设会话结构（镜像卡、迟到的 toolResult 都可能插队）。
- **usage/cost 逐轮在 assistant 条目上**，做成本统计直接累加，不用解析文本。
- **前端渲染**与本文同一份事实源：`apps/web/src/lib/events.ts` 的 `renderHistory` 把这些条目映射成消息卡；
  新增 `customType` 时前后端要一起加。
- **spawn 执行过程**不要从 task 卡的最新 `details` 猜历史，必须按 `delegationId` 读取 `state/delegation-timelines/*.jsonl`；增量消费以平台 `seq` 为准。
- **Goal 执行计划**从 `state/work-states.json` 的 `SessionWorkState.plan` 读取当前 WorkItem、依赖和验收；选择某个 `delegationId` 后再进入现有执行过程。不得把 `pudding:work_plan_update`、`pudding:goal_recovery` 或 Worker timeline 反推成权威 Goal/WorkItem 状态。
- **审计/排障入口**：委派链路问题先看 delegate toolCall 与 toolResult 的时间差与 `isError`；
  窗口状态对不上时对照 `state/windows.json` 的 `activeSession` 与文件名里的 sessionId。
