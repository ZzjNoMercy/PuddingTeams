# 通用 Agent 接入方案：Runtime、Driver、Extension 与可恢复交互

> 日期：2026-08-06  
> 状态：待审核，未实施  
> 适用仓库：PuddingTeams、PuddingClaw  
> 目标：让 PuddingTeams 以同一套底层生命周期接入 PuddingClaw、Pi、Hermes、OpenClaw、Grok Build、Codex、Claude Code 等 Agent，同时正确处理 Session 连续性、当前 Run 的人工审批、流式进度和凭证隔离。

## 0. 结论先行

这次方案的核心不是再造一套“统一 CLI 命令”，而是统一四个**操作语义**，再由每个 Driver 映射到真实 Agent：

1. `run`：创建新 Session 并启动第一条 Run；
2. `continue`：在已有 Session 中创建下一条 Run；
3. `respond`：给当前仍在等待输入的同一条 Run 提交审批或回答；
4. `cancel`：取消当前 Run，不删除 Session。

其中最容易混淆、也正是当前故障来源的是：

- `continue` 面向 **Session**，前一条 Run 必须已结束；
- `respond` 面向 **Run/Interaction**，当前 Run 仍处于 `waiting_input`；
- 两者不能互相替代，也不能都叫 `resume`。

PuddingClaw 当前已经具备后端 `respond` 能力：`POST /api/headless/runs/{run_id}/resume` 会恢复原 Run；它当前的 Session 连续性则是 `puddingclaw run ... --session <session_id>`。因此：

- **不新增** `puddingclaw resume <session_id>`；
- **新增**公开、非 TTY 的 `puddingclaw respond <run_id> --input-json - --json`；
- PuddingTeams Driver 把统一的 `continue(...)` 映射到现有 `run --session`，把 `respond(...)` 映射到新命令。

PuddingTeams 当前遇到 `needs_input` 后把它转成普通文本，让 manager 下一轮重新调用 `team_task`。这会创建新 Run，而 PuddingClaw 原 Run 仍在等待授权，于是得到 `Session already has an active Run or pending input`。正确修复是：**保存待处理 Interaction，由消费端审批后调用 `respond`，绝不重跑任务。**

产品能力采用两层组合，而不是把所有逻辑继续堆进 Driver：

- **基础 Driver SPI 负责接入规范**：安装探测、认证、run/continue/respond/cancel、Session/Run handle 和事件归一化；具体 Agent 的协议映射由 Connector Extension 实现；
- **每个 Agent 实例通过 Pi Extension 扩展能力**：给 manager 注册该 Agent 的专属工具、参数 Schema、提示规则和结果投影；
- Agent 管理页同时管理 Connector Extension 和 Capability Extension：每个 Agent 必须绑定一个 Connector，可再绑定零到多个 Capability Extension；同一个 Extension 也可用不同配置绑定到多个 Agent；
- Driver 不注册业务工具，Extension 不理解或调用 Agent 私有 CLI/HTTP 协议，所有执行必须回到 scoped `AgentInvoker`。

## 1. 第一性原理

### 1.1 平台真正需要统一的是什么

PuddingTeams 对任意 Agent 只承担六类稳定职责：

| 职责 | 平台不变量 | Agent 变量 |
| --- | --- | --- |
| 路由 | Agent 目录、能力筛选 | 描述、适用任务、专属选项 |
| 执行 | 启动、超时、取消、错误分类 | CLI、HTTP、RPC、ACP |
| 连续性 | 保存不透明 Session handle | handle 的生成和消费方式 |
| 交互 | 保存 pending Interaction、接收用户决定 | 权限、问题、规则确认等类型 |
| 可观测 | 统一事件与终态 | Agent 能提供的进度丰富度 |
| 凭证 | 加密存储、最小化注入 | 各 Agent 所需的环境变量或 token |
| 产物 | 工作区绑定、产物登记与大小限制 | 交付物如何产生与取出（push / observe） |

因此正确边界是：

```text
pi Extension（给模型看的工具与说明）
        ↓ 只拿 AgentInvoker，不拿凭证明文
Agent Runtime（生命周期、状态机、持久化、事件）
        ↓
Agent Driver（PuddingClaw / Codex / Claude 的语义映射）
        ↓
Transport（spawn / HTTP / RPC / ACP）
```

职责判定规则非常简单：

- “如何联系这个 Agent、如何恢复同一 Run”属于 Driver；
- “模型何时应该使用它、要填哪些业务参数、结果怎么投影”属于 Extension；
- “是否允许本次调用、状态如何持久化、事件怎么广播”属于 Runtime；
- “CLI 参数模板”和“数据库分析工具 Schema”不得出现在同一个模块里。

### 1.2 必须分开的三个身份

| 身份 | 生命周期 | 用途 |
| --- | --- | --- |
| `sessionHandle` | 多条 Run | 让下一条用户消息继承 Agent 历史 |
| `runHandle` | 一条 Run | 标识本次执行，用于取消、追踪和定位错误 |
| `interactionHandle` | 一次或一组待输入 | 只用于恢复当前 Run；可能含 bearer token，不能进模型上下文 |

`requestId` 不是第四种 handle。它只标识一次 Interaction 中的某个具体问题；并行工具可能一次返回多个 `requestId`，必须完整回答当前集合。

### 1.3 状态机不允许“靠自然语言重试”

```text
无 Session ── run ──> running ───────────────> completed/failed/blocked
                         │
                         └──> waiting_input ── respond ──> running
                                     │                         │
                                     └── reject ───────────────┘

已有空闲 Session ── continue ──> 新 Run 的 running
```

约束：

- `continue` 只允许 Session 空闲时调用；
- `respond` 必须携带服务端返回的 Interaction 句柄，并恢复原 `runHandle`；
- `waiting_input` 不是 `failed`，也不是“提示用户后重新运行”；
- 同一 Interaction 的重复提交必须幂等；
- 用户拒绝也是合法响应，Run 应继续到可解释终态，而不是让平台伪造成功。

## 2. 两个仓库的源码事实

### 2.1 PuddingTeams 当前行为

源码位置：

- `apps/server/src/store/teams.ts`
- `apps/server/src/pi-bridge/team-task.ts`
- `apps/server/src/pi-bridge/session-store.ts`
- `apps/server/src/routes/chat.ts`

已确认事实：

1. `TeamsStore.runAgent()` 每次用 `spawn(..., stdio: ["pipe", "pipe", "pipe"])` 启动 Worker；stdin 写一份 JSON，stdout 只按**单个 JSON**解析。
2. Session 连续性保存在 `WindowConfig.workerSessions`；继续任务时，把 `session_id` 放回 stdin。
3. `team_task` 遇到 `needs_input` 后只生成一段文本，默认指导 manager “等用户回复后重试”。这对业务参数澄清尚可，对仍占用原 Run 的权限 HITL 是错误的。
4. `session-store.ts` 当前通过 `customTools` 注入单个 `team_task`；并未使用方案文档设想的 per-agent Extension。
5. WebSocket 已能转发 pi tool update 和 custom message，前端也已有 `pudding:task_assign`、`pudding:task_result` 的渲染入口，可扩展为审批卡，无需新建第二套实时通道。
6. 当前 `CredentialsStore` 直接归 `TeamsStore` 持有并在 spawn 前注入环境变量；这一安全边界应该保留，不应把 `CredentialsStore` 传给 Extension。

### 2.2 PuddingClaw 当前行为

源码位置：

- `backend/api/headless.py`
- `backend/graph/deepagents_manager.py`
- `backend/graph/permission_resume.py`
- `packages/puddingclaw-cli/dist/cli.js`

已确认事实：

1. `puddingclaw run <message> --session <session_id> --json` 已能在同一 Session 中创建下一条 Run；stdin 的 `session_id` 也保留兼容。
2. Headless API 在权限中断时返回：`run_id`、`session_id`、`needs_input`、`continuation_token`，并保持原 Agent stream、LangGraph checkpoint thread 和 Run 存活。
3. `POST /api/headless/runs/{run_id}/resume` 会校验 continuation token，要求一次解决完整 pending request 集合，然后恢复**同一条 Run**。
4. CLI 在交互式 TTY 中可在一次 `run` 进程内询问用户并自动调用 Resume API；在 `--json` 或非 TTY 下会原样返回 `needs_input` 并退出，不会私自授权。
5. CLI 尚无公开的、可由另一个进程调用的 `respond` 子命令。这正是 PuddingTeams `stdio: pipe` 集成的缺口。
6. 当前 Headless 外送交互只支持 permission；其他业务 HITL 仍 fail-closed。协议可以通用，但 PuddingClaw Driver 第一版必须声明 `interactionKinds: ["permission"]`。
7. PuddingClaw 的 live execution 目前保存在后端进程内。PuddingClaw 后端重启后，旧 continuation token 无法恢复该 Run，Resume API 会返回 410。这是现有限制，不能由 PuddingTeams 文档假装解决。

### 3.1 Driver 是唯一理解 Agent 私有协议的层

```ts
interface AgentDriver {
  id: string;
  capabilities(): Promise<DriverCapabilities>;
  run(input: RunInput, ctx: InvocationContext): AsyncIterable<AgentEvent>;
  continue(input: ContinueInput, ctx: InvocationContext): AsyncIterable<AgentEvent>;
  respond(input: RespondInput, ctx: InvocationContext): AsyncIterable<AgentEvent>;
  cancel?(input: CancelInput, ctx: InvocationContext): Promise<void>;
  probe(ctx: InvocationContext): Promise<ProbeResult>;
}

interface DriverCapabilities {
  operations: Array<"run" | "continue" | "respond" | "cancel">;
  interactionKinds: Array<"permission" | "question" | "confirmation">;
  progress: "none" | "coarse" | "stream";
  // spawn=子进程 CLI；http/rpc/acp=网络协议；sdk=进程内 SDK（如本地 pi）。
  transport: "spawn" | "http" | "rpc" | "acp" | "sdk";
}
```

注意：这是 TypeScript 内部接口，不要求外部 CLI 出现同名命令。统一的是语义，不是字符串。

PuddingTeams 核心只内置 Driver SPI 和 Registry，不长期内置所有第三方 Agent 的具体映射。具体映射由可独立安装、升级的 Connector Extension 注册到 Driver Registry。必须区分五层状态：

1. `available`：本地、团队或社区目录中存在相应 Connector Extension；
2. `installed`：Connector Extension 已安装并通过 manifest/engine 校验；
3. `detected`：本机已找到对应 CLI，或已配置可访问的服务端；
4. `configured`：认证和必要参数可用；
5. `enabled`：用户明确允许该 Agent 实例进入 roster 并被委托。

默认发行预装四个第一方 Connector：PuddingClaw（产品首条链路）、本地 pi（§9.1 Pi 调 Pi 标杆）、Codex 与 Claude Code（路线图 P1 主流 coding agent 样本，均为 spawn + JSONL 流式，无 HITL 承诺、`interactionKinds: []`）；核心 delegation 是 Runtime 生成能力，不算用户 Capability Extension。Hermes、OpenClaw、Grok Build 等只作为 Connector 编写指南中的协议案例或社区扩展候选，不承诺在默认目录预置。用户或团队可以二次开发并安装自己的 Connector；更新 Connector 不要求发布整个 PuddingTeams。

### 3.2 Extension 只能拿窄接口

```ts
interface ScopedAgentInvoker {
  readonly agentId: string;
  capabilities(): Promise<DriverCapabilities>;
  invoke(operation: AgentOperation, input: unknown, ctx: ToolContext): Promise<NormalizedResult>;
}

interface AgentExtensionContext<TConfig = unknown> {
  agent: Readonly<AgentSummary>;
  config: Readonly<TConfig>;
  invoker: ScopedAgentInvoker;       // 已绑定 agentId，Extension 不能改投其他 Agent
  events: ExtensionEventPublisher;   // 只能发命名空间内的可观测事件
}
```

Extension 不得拿到：

- `CredentialsStore`；
- Worker token 明文；
- continuation token；
- 任意 spawn 能力。

凭证仍由 Runtime 在调用 Driver/Transport 前注入。这样 Extension 即使被模型诱导，也无法把密钥写进 tool result。

还必须明确一个现实安全边界：Pi Extension 是可执行 TypeScript/JavaScript。TypeScript 接口只能约束正常代码，不能把恶意第三方 Extension 变成沙箱。第一版只允许 PuddingTeams 内置、经过审核的 Extension 进程内加载；后续用户安装的第三方 Extension 必须显式显示来源和代码执行风险，并放到隔离 Extension Host 中，不能直接把任意本地路径 `import()` 进 server 进程。

### 3.3 Extension 动态加载的真实边界

当前 pi 0.83 支持 `extensionFactories`、运行时 `registerTool()` 和 `setActiveTools()`；但方案不能宣称“成员变化后旧会话自动删除工具”。源码与 SDK 文档没有通用 `unregisterTool()`。

可落地策略：

1. 新建 manager Session 时，按当前 Window 成员及其 `extensionBindings` 构造具名 `extensionFactories`；
2. 每个启用的 Agent 都获得一个平台生成的基础 `agent-delegation` Extension factory；额外 Extension 在它之后装配；
3. factory 创建时由 Runtime 注入绑定该 `agentId` 的 `ScopedAgentInvoker`，Extension 无权在调用参数里改投其他 Agent；
4. Extension 使用 `pi.registerTool()` 注册业务工具；工具名由平台统一命名空间化，避免两个 Agent/Extension 注册同名工具；
5. Agent、Extension 绑定或 Window 成员变化后，相关 manager Session 的 `extensionRevision` 增加并标记 `runtimeDirty`；
6. Runtime 先立即从 active tools 中移除被禁用的工具，并在 `AgentInvoker` 入口拒绝陈旧调用；Session 空闲时再重建 ResourceLoader/AgentSession，彻底移除遗留 hooks；
7. Session 的原 JSONL 历史继续作为唯一会话事实，不复制消息；重建只改变运行时装配；
8. `team_task` 在 per-agent Extension 就绪后直接删除，不设兼容期（决策 20）。

对应现有源码的直接改造是：

- `apps/server/src/pi-bridge/session-store.ts` 当前在 `create()`/`open()` 中用 `customTools` 单独注入 `team_task`，并且只有 direct/group 才显式构造 ResourceLoader；
- 将 `relayLoader(guidance)` 泛化为 `managerResourceLoader(windowContext)`，对 solo/direct/group 都创建同一类 ResourceLoader；
- loader 同时组合原有 guidance、core Extension factory，以及当前 Window 内 Agent 的基础/专属 Extension factories；
- `create()` 和从 JSONL `open()` 都调用同一装配函数，保证重启前后 Extension 集合一致；
- per-agent Extension 验证通过后，`team_task` 连同 `customTools` 注入路径一并删除。

工具命名使用不可变 Agent ID 和 Extension ID，而不是可修改展示名：

```text
agent_<agentId>__delegate
agent_<agentId>__<extensionId>__<toolName>
```

界面可显示友好标签，例如“PuddingClaw · 配置分析”，但发送给模型的工具名必须稳定、唯一、可审计。

当 Extension 很多时，不把全部工具默认塞进模型上下文：

- direct Window：默认激活该 Agent 的基础委托工具和标为 `always` 的 Extension 工具；
- solo/group Window：默认只激活 `search_agent_tools`，其余 Extension 工具预先注册但保持 inactive，由 `search_agent_tools` 按需执行纯加法 `setActiveTools()`；
- `search_agent_tools` 匹配全量受管工具（含已激活的）：搜到已激活工具时明确返回"已是激活状态，可直接调用"，而不是"没有匹配"——否则模型会在 direct 窗口里搜默认激活的 delegate 工具时被误导；roster prompt 同时给已激活工具标注「（已激活）」，避免无谓搜索；
- roster（成员名单）不做成工具：它是窗口绑定的静态事实，由 core Extension 的 `before_agent_start` 每轮重读并注入 system prompt，成员/启用变化下一轮即生效，安全性仍由 `AgentInvoker` 入口校验兜底；
- 配置禁用属于安全撤权，不依赖“纯加法加载”，仍走立即门控加空闲重建。

## 4. PWCP v1：统一事件契约，不强制统一 CLI 形态

PWCP（Pudding Worker Coordination Protocol）是 Runtime 和 Driver 之间的规范化事件契约。外部 CLI 可原生输出，也可由 Driver/shim 翻译。

### 4.1 操作输入

```ts
type AgentOperation = "run" | "continue" | "respond" | "cancel";

interface RunInput {
  message: string;
  requestId: string;
  options?: Record<string, unknown>;
}

interface ContinueInput extends RunInput {
  sessionHandle: string;
}

interface RespondInput {
  runHandle: string;
  interactionHandle: string; // 仅 Runtime/Driver 可见
  responses: InteractionResponse[];
  requestId: string;         // 本次提交的幂等键
}

interface InteractionResponse {
  requestId: string;
  action: "approve" | "reject" | "answer" | "confirm";
  scope?: "once" | "run" | "session";
  value?: unknown;
  message?: string;
}
```

### 4.2 事件输出

```ts
type AgentEvent =
  | { type: "started"; sessionHandle?: string; runHandle?: string }
  | { type: "progress"; stage?: string; message: string; percent?: number }
  | { type: "input_required"; result: NeedsInputResult }
  | { type: "completed"; result: CompletedResult }
  | { type: "failed"; result: FailedResult };
```

若走 CLI JSONL，stdout 每行只允许一个事件，stderr 只放诊断。未知事件类型可忽略，但每次操作必须恰好到达一个边界：`input_required`、`completed` 或 `failed`。

### 4.3 归一化结果

```ts
interface ResultBase {
  agentId: string;
  sessionHandle?: string;
  runHandle?: string;
  content?: string;
  artifacts?: ArtifactRef[];      // 交付物声明，见 §15
  usage?: {
    turns?: number;
    inputTokens?: number;
    outputTokens?: number;
    cost?: number;
  };
  meta?: Record<string, unknown>;
}

interface ArtifactRef {
  name: string;
  path: string;                   // workspace 内相对路径
  kind?: string;                  // report | data | diff | …，agent 自定
  size?: number;
  origin: "push" | "observe";     // agent 主动导出 / Driver 观察收集
}

interface CompletedResult extends ResultBase {
  status: "completed";
}

interface NeedsInputResult extends ResultBase {
  status: "needs_input";
  interaction: {
    id: string;                       // PuddingTeams 本地公开 id
    kind: "permission" | "question" | "confirmation";
    requests: InteractionRequest[];
    expiresAt?: string;
  };
}

interface InteractionRequest {
  requestId: string;
  prompt: string;
  permissionType?: string;
  toolName?: string;
  command?: string;
  path?: string;
  paths?: string[];
  risk?: string;
  reason?: string;
  options?: Array<"once" | "run" | "session" | "reject">;
}

interface FailedResult extends ResultBase {
  status: "failed" | "blocked" | "cancelled";
  errorCode: string;
  error: string;
  recoverable: boolean;
}
```

`interactionHandle` 不出现在 `NeedsInputResult`，也不进入 pi Session JSONL。浏览器只拿 PuddingTeams 生成的本地 `interaction.id`。

## 5. PuddingClaw Driver 的精确映射

### 5.1 Session 连续性：`continue`

```text
PWCP run(message)
  -> puddingclaw run --input-json - --json
     stdin: {"message":"...","request_id":"..."}

PWCP continue(sessionHandle, message)
  -> puddingclaw run --input-json - --json
     stdin: {"message":"...","session_id":"worker-session-...","request_id":"..."}
```

也可映射为 `puddingclaw run "..." --session worker-session-... --json`。二者语义相同。

### 5.2 当前 Run 恢复：`respond`

PuddingClaw CLI 新增：

```text
puddingclaw respond <run_id> --input-json - --json
```

stdin：

```json
{
  "continuation_token": "opaque-token",
  "request_id": "puddingteams-response-uuid",
  "decisions": [
    {"request_id":"permission-request-id","decision":"approve","scope":"once"}
  ]
}
```

CLI 内部映射到现有：

```text
POST /api/headless/runs/{run_id}/resume
```

输出仍使用现有 Headless 结果：可能再次 `needs_input`，也可能进入最终 `completed/failed/blocked`。

为保证跨进程重试安全，PuddingClaw Backend 同步给 `HeadlessResumeRequest` 增加可选 `request_id`，并按 `run_id + request_id + request hash` 缓存本次 Resume 结果。当前 Resume schema 还没有这个字段；如果不补，PuddingTeams 在“上游已恢复、自己尚未来得及落盘”时重试，只能得到 409，无法判断上一次是否成功。

必须增加的 CLI 校验：

- `run_id`、token、完整 decisions 集合必填；
- `--input-json` 只接受 `-`；
- 非 TTY 不弹交互提示；
- stdout 保持 JSON-only；
- 410 映射为 `interaction_expired`；
- 409 映射为 `interaction_conflict`；
- continuation token 只允许出现在机器可读 JSON 协议字段中，不打印到 human output、stderr 或日志。

### 5.3 为什么不新增 `puddingclaw resume <session_id>`

因为它会把两类恢复再次混淆：

- Session 续聊已经由 `run --session` 完整表达；
- 同 Run HITL 必须依赖 `run_id + continuation_token + requestId 集合`，只有 session_id 不足以安全恢复；
- Codex 的 `codex exec resume <id>` 虽然命令名叫 resume，语义更接近这里的 `continue`，不是 PuddingClaw 权限 `respond`。

统一层应适配语义，不应为了命令外观一致而增加别名。

## 6. PuddingTeams 的 HITL 完整闭环

### 6.1 当前错误路径

```text
team_task -> PuddingClaw Run A -> needs_input
manager 把 needs_input 当文字告诉用户
用户回复 -> team_task 再调用 -> PuddingClaw Run B
Run A 仍 waiting_input -> 409 Session already has active Run or pending input
```

### 6.2 正确路径

```text
team_task / agent-specific tool
  -> Runtime.run 或 Runtime.continue
  -> Driver 返回 input_required
  -> DelegationStore 保存 pending Interaction
  -> tool result 返回“等待审批”结构，manager 本轮可正常结束
  -> WebSocket/历史消息显示审批卡
  -> 用户点击允许/拒绝
  -> POST /api/interactions/{localId}/responses
  -> Runtime.respond（不是 run/continue）
  -> PuddingClawDriver 调 `puddingclaw respond ...`
  -> 若再次 needs_input：更新同一 Delegation revision
  -> 若 completed：写入 task_result，并触发 manager follow-up 汇总
```

### 6.3 为什么采用“暂停并外送”，而不是让 tool call 一直阻塞

审批可能持续数分钟甚至跨页面。一直挂住 pi tool execution、WebSocket 和 HTTP 链路会造成：

- backend 重启后上下文不可恢复；
- manager Session 长时间保持 streaming，其他消息无法正常进入；
- 浏览器断开就容易误取消；
- timeout 含义变得混乱。

因此 Parent manager Run 可以在展示审批卡后结束；真正悬挂的是 Child Agent Run。审批完成后，通过 pi 已支持的：

```ts
session.sendCustomMessage(
  {
    customType: "pudding:task_result",
    content: workerResult,
    display: true,
    details: { delegationId, worker, status: "completed" }
  },
  { triggerTurn: true, deliverAs: "followUp" }
)
```

让 manager 在同一 pi Session 中继续汇总。`AgentSession.sendCustomMessage` 的 `triggerTurn` 已由当前依赖版本支持。

### 6.4 PuddingTeams API

```text
GET  /api/interactions?sessionId=...
GET  /api/interactions/{id}
POST /api/interactions/{id}/responses
POST /api/interactions/{id}/cancel
```

提交示例：

```json
{
  "revision": 1,
  "request_id": "ui-submit-uuid",
  "responses": [
    {"requestId":"perm-1","action":"approve","scope":"once"}
  ]
}
```

服务端必须校验：

- Interaction 属于当前窗口/manager Session；
- `revision` 未过期；
- responses 恰好覆盖当前 request 集合；
- 选定 scope 在该 request 的 options 内；
- 同一 `request_id` 重试返回相同结果；
- 非 pending 状态拒绝二次消费。

### 6.5 UI 与 Session 历史

历史中只存安全投影：

```json
{
  "customType": "pudding:interaction_required",
  "display": true,
  "details": {
    "interactionId": "int_local_x",
    "delegationId": "dlg_x",
    "worker": "puddingclaw",
    "status": "pending",
    "revision": 1,
    "requests": [{"requestId":"perm-1","command":"...","risk":"moderate"}]
  }
}
```

continuation token、Worker access token、原始 provider payload 不写进 pi JSONL、不发给 LLM、不下发浏览器。

历史卡状态由 `GET /api/interactions/{id}` 对账；pending/approved/rejected/expired/completed 都可重放。状态变化时追加一条 `pudding:interaction_resolved` 事件，前端按 `interactionId` 折叠到原卡片，不修改旧 JSONL，也不新增一张重复授权卡。

## 7. PuddingTeams 数据模型

### 7.1 Window 只保存 Session 绑定

```ts
interface WorkerBinding {
  sessionHandle?: string;
  updatedAt: string;
}

interface WindowConfig {
  // existing fields...
  workerBindings?: Record<string, WorkerBinding>;
  /** 房间绑定的工作区根目录（绝对路径）；缺省 <平台数据目录>/workspaces/<windowId>/。
   *  coding agent 以此为 cwd，同时作为各 agent 写权限的收敛边界，见 §15。 */
  workspace?: string;
}
```

不把 pending Interaction 塞进 `windows.json`；它不是窗口配置。

### 7.2 Delegation 和 Interaction 独立存储

```ts
interface DelegationRecord {
  id: string;
  windowId: string;
  managerSessionId: string;
  managerToolCallId?: string;
  agentId: string;
  operation: "run" | "continue";
  sessionHandle?: string;
  runHandle?: string;
  status: "running" | "waiting_input" | "completed" | "failed" | "cancelled";
  revision: number;
  createdAt: string;
  updatedAt: string;
  result?: Omit<NormalizedResult, "interaction">;
}

interface InteractionRecord {
  id: string;                    // 浏览器可见的本地 id
  delegationId: string;
  kind: string;
  requests: InteractionRequest[];
  status: "pending" | "responding" | "approved" | "rejected" | "expired" | "failed";
  revision: number;
  providerStateRef: string;      // 指向加密存储，不是明文 token
  expiresAt?: string;
  createdAt: string;
  updatedAt: string;
}
```

建议新增 `InteractionSecretStore`，复用 `CredentialsStore` 内部 AES-256-GCM 基元，但不要伪装成 Agent env secret。公开记录和密文分文件保存：

- `.teams/delegations.json`：可诊断、无敏感 token；
- `~/.puddingteams/interactions.json`：加密 provider state，权限 0600。

### 7.3 重启语义必须诚实

第一版可做到：

- PuddingTeams 重启、PuddingClaw 未重启：从加密 InteractionStore 恢复并继续 `respond`；完成后通过 custom message 触发 manager 新 turn；
- PuddingClaw 重启：其 live `_HeadlessExecution` 丢失，PuddingTeams 将 Interaction 标记 `expired`，提示用户重新启动该任务；
- 不承诺恢复原来的 manager tool call；恢复的是业务 Delegation，随后在同一 manager Session 追加结果。

只有当 PuddingClaw 把 live execution/中断恢复做成持久化协议后，才能把第二种情况升级为真正跨进程恢复。

## 8. Spawn、JSONL、超时与取消

### 8.1 Spawn Runtime

把 `TeamsStore.spawnWorker()` 抽到 `agent-runtime/transport/spawn.ts`，保留现有正确行为：

- `shell: false`；
- stdout/stderr 分离；
- SIGTERM 后 5 秒 SIGKILL；
- AbortSignal 取消；
- stdin EPIPE 吞掉；
- stdout、stderr、单行长度分别限额；
- 子进程退出和协议终态分开判断。

增加：

- 逐行 JSONL decoder，保留尾部半行 buffer；
- 首个 `started/progress` 事件延迟指标；
- exactly-one-boundary 校验；
- 不把 stderr 原样送入模型，仅存 Trace 的有界诊断摘要。

### 8.2 JSONL 不是第一阶段前置条件

PuddingClaw 当前 CLI/Headless API仍是单 JSON 边界。第一阶段 Driver 可以把单 JSON翻译成 `input_required/completed/failed`，先完成语义正确性。

真正的流式进度需要 PuddingClaw Backend 提供 SSE/JSONL streaming endpoint，CLI 只是把该流转发出来；只给 CLI 增加 `--jsonl` 而后端仍同步等待，不会产生真实进度。

### 8.3 超时分三类

| 超时 | 含义 | 默认建议 |
| --- | --- | --- |
| 启动超时 | 进程未进入 started | 30 秒 |
| 活跃超时 | running 且长期无事件 | 120 秒，可按 Agent 配置 |
| Interaction TTL | 等用户审批 | 24 小时，受上游更短 TTL 限制 |

`waiting_input` 期间不计 active timeout；否则用户看审批卡几分钟就会被误杀。

## 9. Connector Extension 目录与接入边界

### 9.1 最小预置，其他接入依靠 Extension 二开

**定位（贯穿整个开发周期）**：Connector Extension 的本质是**给 pi 扩充连接其他 Agent 的能力**——每个 Connector 包都是可以发布到 pi 社区、`pi install` 可装的独立生态产物；但**完整的房间能力（manager-worker 编排、HITL 审批闭环、workspace 交接）只有 PuddingTeams 提供**。因此每个包采用"共享核心 + 双宿主入口"结构（§9.5），纯 pi 用户得到真实可用的轻量 delegation，PuddingTeams 用户得到完整 worker 接入，协议翻译核心只维护一份。

PuddingTeams 提供 Extension 安装入口、SDK、模板和编写指南，不维护一个不断膨胀的内置 Agent 列表：

| 内容 | 默认发行 | 定位 |
| --- | --- | --- |
| PuddingClaw Connector Extension | 安装 | 第一方可运行基线，完成 run/continue/respond/cancel |
| Codex Connector Extension | 安装 | P1 主流样本：spawn + JSONL 流式，run/continue/cancel，无 HITL |
| Claude Code Connector Extension | 安装 | P1 主流样本：spawn + stream-json 流式，run/continue/cancel，无 HITL |
| 核心 delegation 投影 | 内置 Runtime | 为每个 Agent 生成基础 Pi 委托工具，不是 Capability 包 |
| Capability Extension | 预置一个未绑定的 `minimal-tool` 开发样例 | 用户按业务需要绑定；默认不进入任何 Agent 工具集 |
| Generic CLI Connector 模板 | 仅开发模板 | 演示声明式 Connector，不作为万能运行时兜底 |
| Pi/Hermes/OpenClaw/Grok Build | 文档案例 | 提供协议选型与样例片段，不承诺默认实现和持续跟版 |

例如，Grok Build 的本地源码可以作为代码型 Connector 编写指南的 ACP 案例：

- Headless 支持 `-p`、`--output-format streaming-json`、`--resume`、`--continue` 和 Session ID；
- `grok agent stdio` / `serve` 提供长连接 ACP；
- ACP 生命周期覆盖 `session/new`、`session/prompt`、流式 update、permission request 和取消；
- 因此用户编写 Grok Build Connector 时应首选 ACP。Headless 只作为无交互降级路径，不用正则解析终端文案来模拟 HITL。

Pi 可以调用另一个 Pi，但必须是新的 child `AgentSession`/独立 Session 目录，而不是让同一会话重入自身。PuddingTeams 对这类委托统一执行：

- 默认不向 child Pi 注册 PuddingTeams 的团队委托工具，避免无意递归；
- 显式允许递归时，传播 `delegationDepth`，默认最大深度为 2；
- 父 Run 取消必须向所有仍在运行的 child Pi 传播；
- 每个 child 都有独立的 `sessionHandle`、`runHandle` 和事件流。

### 9.2 能力必须由 Driver 声明，不能由 UI 猜测

Driver 必须通过 `capabilities()` 暴露真实能力，并通过 `probe()` 返回安装、认证、版本和 Transport 健康状态。若 `respond` 不支持：

- Runtime 不生成“可以恢复原 Run”的虚假审批动作；
- 若上游在当前模式下会阻塞交互，启动前就返回 `interaction_unsupported`，或要求用户选择明确的自动审批策略；
- 不把用户审批转换成新的 `run`/`continue`；
- UI 显示“审批外送不支持”，而不是笼统的“不可用”。

ACP/RPC/HTTP Gateway 的价值是把长期连接、权限请求和取消变成原生协议。编写 Pi、Hermes、Grok Build 等 Connector 时应直接采用其结构化协议；只有确实没有结构化协议的 Agent 才使用 spawn 适配。这是 SDK 指导原则，不等于 PuddingTeams 默认维护这些 Connector。

### 9.3 目录、安装、绑定、启用是四个不同动作

默认策略：

1. 本地、团队或用户配置的 Connector 源可在“添加 Agent”目录中展示，但目录项不是已安装代码；
2. 用户选择目录项后先查看来源、权限、支持的上游版本和工具能力，再确认安装；
3. 安装完成后创建 Agent 实例并填写配置；只有显式启用后才进入 roster 和调度候选；
4. `probe()` 检测到本机 CLI 不代表自动启用，更不能自动读取或迁移第三方凭证；
5. 升级已有安装时，现有 PuddingClaw 配置直接重建为第一方 Connector binding，不做数据迁移（决策 20）；默认不新增其他 Agent；
6. 禁用后保留配置和历史绑定，但拒绝新委托；已经运行或等待审批的 Run 由用户选择“继续保留”或“取消”，不能静默杀死；
7. 同一个 Connector 可以创建多个 Agent 实例，例如两个 Codex 实例使用不同工作目录、模型策略或账号；
8. 卸载 Connector 前必须确认没有启用 Agent 和 active/waiting Run；历史保留，但对应 Agent 进入 `connector_missing`，不能静默回退到 Generic CLI。

### 9.4 Connector Extension 如何降低上游维护成本

维护成本不会凭空消失，但可以从核心仓库解耦并自动暴露风险：

- Connector manifest 声明 `supportedUpstreamVersions` 和 `versionProbe`；
- `probe()` 同时返回 Connector 版本和真实 CLI/服务版本；
- 上游版本超出已验证范围时状态变为 `untested` 或 `incompatible`，不静默假设兼容；
- 每个 Connector 独立版本、独立发布、可固定版本或选择自动更新；
- Connector 作者维护针对上游 CLI 的契约 fixture/集成测试，不阻塞 PuddingTeams 核心发布；
- 社区或用户可维护自己的 Connector，PuddingTeams 只保证 Driver SPI 的兼容周期。

版本策略建议：Driver SPI 使用独立 `apiVersion`，至少跨一个 PuddingTeams 大版本保持兼容。Connector manifest 同时声明：

```json
{
  "kind": "connector",
  "engines": { "puddingteams": ">=1.0 <2" },
  "connector": {
    "id": "grok-build",
    "apiVersion": "1",
    "supportedUpstreamVersions": ">=0.9 <1.1"
  }
}
```

### 9.5 双宿主包：一个包，pi 与 PuddingTeams 两种激活路径

Connector/Capability 包统一为 **pi 兼容的 npm/git 包**，发布到 pi 社区，`pi install <source>` 可装。包内是"共享核心 + 两个薄适配层"：

```text
pi-connector-openclaw/
├── package.json            # pi.extensions 声明 pi 入口；puddingteams 字段承载 §10 manifest
├── pi/
│   └── index.ts            # default export (pi: ExtensionAPI) => void：注册 delegate 工具，pi 当 manager 派活
├── driver/
│   └── index.ts            # createDriver 命名导出：接 Driver SPI（PWCP 事件、probe、HITL、多实例）
└── core/                   # 共享核心：spawn/ACP/JSONL 翻译、session 连续性、取消、错误归一化，不依赖任何宿主
```

两条激活路径互不相干，同一个 `pi install` 动作行为不同：

| | 纯 pi | PuddingTeams |
| --- | --- | --- |
| 加载器 | pi resource-loader（找 `pi.extensions` 入口） | ExtensionRegistry（读 manifest + `createDriver`） |
| 激活内容 | pi 内注册 delegate 工具，pi 自己当 manager | agent 进 roster，平台自动投影 `agent_<id>__delegate`，走房间体系 |
| HITL | 降级为 pi 自身权限提示或不支持 | 完整审批闭环（web 审批卡、409、拒绝也是合法响应） |
| 配置/密钥 | 包自管（如环境变量） | connector binding API + secretRefs |
| 生命周期 | 跟随 pi 会话 | server 托管：重启诚实、取消传播、多实例 |

工程约定：

- **下载安装复用 pi**：PuddingTeams 的安装渠道接受与 `pi install` 相同的 npm/git source，内部复用 pi SDK 的 `DefaultPackageManager`（固定目录、版本固定、update 检查现成），不重复造下载器；
- **manifest 折叠**：`pudding-extension.json` 的 §10 字段折叠进 `package.json` 的 `puddingteams` 字段，一个包一份元数据（过渡期两者都接受）；
- **加载器已兼容**：`ExtensionRegistry` 加载模块时同时识别 `mod.default`（pi 工厂）、`mod.createDriver`、`mod.driver`（extension-registry.ts），双导出包无需改加载逻辑；
- **目录管理**：仓库根 `extensions/` 是所有插件的唯一落点——`extensions/connectors/<agent>/` 放 Connector 包，`extensions/capabilities/<name>/` 放 Capability 包，`extensions/shared/` 放共享核心模板；`extensions/README.md` 维护全量索引（每个包的 kind、宿主入口、状态一目了然）；
- pi 入口是包的**门面**，Driver SPI 才是 Connector 的**本体**；不允许把 Driver 伪装成 pi extension（ExtensionAPI 没有 spawn、server 持久化和审批路由能力）；
- **Connector 的上游可以是另一个 pi**：本地 child `AgentSession`（独立 Session 目录，约束见 §9.1 的 Pi 调 Pi 铁律）或远程 pi（RPC transport）；**以本地 pi 为主**，作为 Phase 6 的第一个参考样例——协议双边可控，能跑满 Driver SPI 全语义（run/continue/cancel/stream 进度），给外部 Agent 的 Connector 当标杆；
- **pi 只是 worker 中的一种，产品上不特殊化**：pi connector 走与其他 Connector 完全相同的"目录 → 创建 Agent 实例 → 配置 → 启用"流程；"新增不同的 pi"即创建多个实例。Connector schema 只保留 `model`、`thinkingLevel`、`sessionDir` 等“怎样运行”的参数；系统提示词、skills、prompt templates、Workspace context 开关统一属于 `AgentConfig.piResources`，pinned manager 与 Pi worker 共用同一模型和“提示词与资源”表单。`manager.prompt` 与 Pi Connector `config.systemPrompt` 已直接删除，不兼容双写。cwd 由 Window/Delegation 快照传入；child session 不注册团队委托工具，递归默认关闭。Driver 能力诚实声明仍为 `operations: [run, continue, cancel]`、`interactionKinds: []`、`transport: "sdk"`。

> 实现状态（P2/P3-0，2026-08）：双宿主包已落地并真机验证。已落地：折叠 manifest（`readManifestFromDir`，pudding-extension.json 优先、package.json `puddingteams` 字段兜底，安装与 `extension validate` 同一入口）；共享核心 `extensions/shared/pwcp`（@puddingteams/pwcp：Driver SPI 类型 + spawnWorker + JsonlLineParser + observe 收集，server 侧 agent-runtime 对应文件均为 re-export）；两个真实包 `extensions/connectors/codex` 与 `claude-code`（pi/ 门面注册 codex_delegate/claude_delegate，driver/ 导 createDriver，core/ 事件归一），server 启动时 `installOrUpdateFromDir` 按仓库路径预置（不再是 builtin，改动即时生效）；`pi -e` 无头调用 codex_delegate/claude_delegate 成功，driver run/continue 会话记忆成功。P3-0 又增加宿主 `engines.puddingteams` semver 强制匹配、ESM cache busting 和事务式更新：候选模块先 import/校验，激活或落盘失败时恢复旧 runtime hooks 与持久化记录。仍 TODO：隔离 Extension Host（§10.3 第 2 级的进程隔离 + 权限 Broker）、npm/pi 社区发布渠道（发布前把 `workspace:*` 依赖改 semver）、puddingclaw/pi 两个内置 Connector 迁入 `extensions/connectors/`。作者指南：`docs/extensions/connector-extension.md`、`docs/extensions/connector-declarative-schema.md`。

```ts
}

}

type PuddingTeamsExtensionManifest = ConnectorExtensionManifest | CapabilityExtensionManifest;
```

Connector Extension 和 Capability Extension 是两种独立包，禁止一个 manifest 同时贡献两类能力：

- Connector 的发布、升级和兼容性围绕上游 CLI/服务协议；
- Capability 的发布、升级和兼容性围绕 Pi 工具 Schema 与业务工作流；
- 二者混包会迫使“上游 CLI 参数变更”和“业务工具改版”同步升级，重新制造耦合；
- 若同一作者同时提供两类扩展，应发布两个独立 package，并用文档声明推荐组合。

它们的执行位置也不同：

- Connector Extension 安装到服务端 Connector Extension Host，向动态 DriverRegistry 注册 Driver；它不进入 Pi ResourceLoader，也不直接向模型注册工具；
- Capability Extension 通过具名 `extensionFactories` 装配到 Pi manager Session，向模型注册工具；它不注册 Driver，也不直接操作 CLI/HTTP/ACP；
- 二者的唯一业务连接点是 Runtime 创建的 `ScopedAgentInvoker`。

不要在通用配置中写 `runArgs`、`resumeArgs` 并让用户手工拼模板。命令映射是 Driver 代码的一部分；用户只配 executable、transport 和安全设置。

`probe()` 的结构化结果至少包含：

```ts
interface ProbeResult {
  extensionInstalled: boolean;
  extensionVersion?: string;
  detected: boolean;
  configured: boolean;
  authenticated: boolean | "unknown";
  enabled: boolean;
  compatibility: "supported" | "untested" | "incompatible" | "unknown";
  upstreamVersion?: string;
  version?: string;
  transport?: "spawn" | "http" | "rpc" | "acp" | "sdk";
  capabilities: DriverCapabilities;
  issues: Array<{ code: string; message: string; fixAction?: string }>;
}
```

智能体管理按产品角色分层展示：pinned `manager` 独立成组；Worker 再按所绑定 Connector 的目录来源标签分为「内置」与「第三方」。目录 `origin: "builtin"` 的 Connector（如 PuddingClaw、本地 pi）产生的所有 Worker 实例都属于内置 Worker；`bundled` / `local` Connector（包括预置的 Codex、Claude Code），以及没有 Connector 标签的 legacy 命令接入，归入第三方 Worker。因此同一个 pi Connector 衍生出的多个 pi Worker 都稳定落在内置分组，新安装 Connector 的默认 `local` 来源也自然进入第三方。

前端“Agent 接入”页面按 Connector 目录项展示 `扩展未安装 / CLI 未检测 / 待认证 / 已配置但未启用 / 已启用 / 版本未经验证 / 不兼容`，并展示真实支持的四项操作。安装扩展、安装上游 CLI、登录、创建 Agent 和启用是不同动作，不合并成一个含糊按钮。

### 10.1 Agent 管理页

每个 Agent 的管理抽屉/详情页固定分为三项：

1. **基础接入**：当前 Connector Extension、Transport、服务/CLI 状态、认证、工作目录、权限策略、四操作能力和 probe 状态；
2. **Extensions**：只管理 Capability Extensions（零到多个），展示版本、来源、工具、激活方式和配置，并提供“添加 Extension”；
3. **运行状态**：Session/Run、待审批 Interaction、最近错误和审计事件。

Connector 只在“基础接入”中安装、选择或更换；“Extensions”页签中的“添加 Extension”只展示与当前 `connectorId` 兼容的 Capability。前端根据 manifest Schema 生成普通配置表单，根据 secret schema 单独写入 CredentialsStore 并只保存 `secretRefs`。保存前展示来源、权限、版本范围和将注册的工具。

Agent 总开关优先级高于所有 Capability Extension 开关：Agent 禁用时全部不可调用，但保留配置；Agent 再启用时恢复之前的选择。Capability 单独禁用只撤销该绑定提供的工具，不影响 Connector 和其他 Capability。Connector 不提供普通开关；更换或卸载属于基础接入变更，必须先处理 Session/Run 兼容性。

建议 API：

```text
GET    /api/extensions/catalog
POST   /api/extensions/install
POST   /api/extensions/:extensionId/update
DELETE /api/extensions/:extensionId
GET    /api/agents/:agentId/connector
PUT    /api/agents/:agentId/connector
GET    /api/agents/:agentId/extensions
POST   /api/agents/:agentId/extensions
PATCH  /api/agents/:agentId/extensions/:bindingId
DELETE /api/agents/:agentId/extensions/:bindingId
POST   /api/agents/:agentId/extensions/:bindingId/probe
```

Connector/Capability 写操作增加 Agent 的 `extensionRevision`。响应返回受影响的 manager Session 数量和 `active_now / reload_pending`，让界面如实显示“已撤权，运行时将在当前回合结束后刷新”。

`GET /api/extensions/catalog` 必须支持 `kind=connector|capability`，前端不得把两类结果混在同一个选择器中。

### 10.2 基础 Extension 与专属 Extension

每个已绑定 Connector 的 Agent 由平台生成基础 `agent-delegation` Pi Extension，只注册稳定委托能力，并从 Connector 暴露的 Driver capabilities 决定允许哪些操作。它是运行时投影，不是第二份安装包；用户通过 Agent 总开关整体禁用。

专属 Extension 才承载业务语义。例如：

- PuddingClaw 可绑定“智能问数”“产品配置分析”“知识库编译”；
- 代码类 Agent 可由用户绑定自建的“代码审查”“CI 修复”“发布流程”；
- Hermes/Pi 可绑定各自擅长的研究或自动化工具。

这些 Capability Extension 可以定义不同参数和提示规则，但执行远端/子 Agent 时必须调用 `ScopedAgentInvoker`。这样更新 Connector、Transport、CLI 版本或恢复机制时，不需要重写业务 Capability；同一个 Capability 也可以复用于多个兼容 Connector。

### 10.3 两级 Connector 实现模型

为了让用户自己接入简单 CLI，又不要求所有人编写高权限 Node 扩展，提供两级模型：

1. **声明式 Connector**：manifest 声明 executable 探测、四操作的参数构造、stdin framing、JSON/JSONL 解码和能力矩阵；实际 spawn、超时、取消、网络及 secret 注入全部由核心 Transport Broker 执行。适合常见一次性/Session CLI；
2. **代码型 Connector**：用于 ACP、RPC、WebSocket、复杂 HITL 和自定义恢复协议。代码运行在隔离 Connector Extension Host，通过受限 RPC 使用 Transport Broker，不直接进入 PuddingTeams server 进程。

> 实现状态（P2-c，2026-08）：第 1 级已落地——manifest 的 `connector.declarative` 声明由核心 `DeclarativeDriver`（`apps/server/src/agent-runtime/declarative-driver.ts`）直接执行（Transport Broker 的独立形态仍是 Phase 6）；`connector.declarative` 与顶层 `entry` 互斥。样例包：`extensions/connectors/echo`（纯 manifest，无 entry、无 pi 门面）。

用户接入流程：

```text
puddingteams extension init --type connector|capability
  -> 生成 manifest、声明式模板或代码 Host 模板、契约 fixture
puddingteams extension validate <path>
  -> 校验 schema、权限、版本探测和 PWCP 事件
puddingteams extension install <path|package>
  -> 展示权限并安装到本地扩展目录
Agent 管理页 -> 选择该 Connector -> 配置 -> probe -> 启用
```

> 实现状态（P2-d，2026-08）：`extension init` / `extension validate` 已落地（`apps/server/bin/puddingteams.mjs` 引导 tsx 跑 `src/cli/extension-cli.ts`）。init 支持 `--type connector [--declarative]` 与 `--type capability`，模板在 `extensions/shared/templates/`（connector 代码型双宿主骨架 / connector-declarative 纯 manifest 骨架 / capability 工具骨架）；validate 与安装流程共用 `readManifestFromDir`（`extensions.ts`）做 manifest 全量校验，再查 entry 存在性、代码型包导出和声明式包的 `{packageDir}` 引用文件。`extension install` 子命令留待后续。

Connector Extension Host 只能获得 manifest 声明并获用户批准的能力，例如特定 executable 的 spawn、特定域名网络访问、工作区访问和命名 secret reference。核心仍持有 CredentialsStore；能由 Transport Broker 代填的 secret 不把明文交给 Connector Host。

PuddingClaw 的 agent-specific tool 不应暴露 `model`：当前 CLI 明确拒绝 `model/analytics_model_id`，由 Backend 根据 question 自动路由。`team_task.model` 随 `team_task` 一并移除；任何 Driver 收到 `model` 字段都应拒绝并给出明确提示。

**configSchema 的前端渲染约定**（JSON Schema 子集 + 平台注解）：`type: string/number/boolean` 映射为输入框/数字框/勾选；`enum`（string 数组）渲染为下拉，非必填项带「不设置」清除项（回写时删 key）；`format: "model"` 是平台注解——渲染为可用模型下拉（数据源 `/api/models`，含自定义 provider 的模型），任何 Connector 都可声明（pi connector 的 `model` 字段即此用法）。

### 10.6 模型与 Provider 控制面（借鉴 PuddingClaw，映射到 pi 原生分层）

平台的模型层就是 pi 的 `ModelRuntime`（builtin 目录 + `models.json` 自定义层 + `auth.json` 凭证层），不自建 registry。借鉴 PuddingClaw `ProviderRegistry` 的交互模式，落点是 pi 原生文件：

- **自定义 Provider**：任意 OpenAI-compatible 端点（vLLM/Ollama/网关）经 `PUT/DELETE /api/providers/custom/:id` 写入 `<agentDir>/models.json`（原子写 + 0600），条目含 `name/baseUrl/api/models[]`；凭证不进 models.json，走 pi 凭证存储（`setProviderKey`/`removeProviderKey` 同一通道）。写操作后重建进程级共享 `ModelRuntime`（`pi-bridge/model-runtime.ts`），新会话即刻可见；
- **连通性测试与模型发现是两个显式动作**：`POST /api/providers/test`（带鉴权 `GET {baseUrl}/models` 探针，响应体丢弃，401/403 单独映射，返回 latency）与 `POST /api/providers/discover`（拉模型 id 清单，用户挑选后随 provider 登记）；两者都支持测未保存的新 key；
- **binding（按用途分派）**：manager 默认模型（§10.5）、会话级模型（composer 切换）、worker 实例模型（connector config `model`，`format: "model"` 下拉）三层各自独立，解析优先级：worker 实例 config > pi 默认；
- 明确不抄的部分：明文 credentials.json（复用 pi auth.json）、遗留迁移/backfill（未上线无包袱）、硬编码 preset 清单（builtin 目录由 pi SDK 维护，自定义层开放增删）。

### 10.5 Pi Manager 作为可编辑的内置 Agent

manager 目前硬编码在 `PiSessionStore`（`apps/server/src/pi-bridge/session-store.ts`）：模型走运行时默认、solo 没有 prompt 入口、工具策略写死。目标是让它以 pinned 内置条目出现在智能体管理界面，与 worker 共用一套编辑 UI。

**可编辑项（按 pi SDK 能力映射）**：

| 配置 | SDK 支撑 | 生效时机 |
| --- | --- | --- |
| 默认模型 | `createAgentSession({ model })` | 新建会话 |
| Agent Resource Profile（system prompt / skills / templates / context） | `AgentConfig.piResources` + `DefaultResourceLoader` | manager/Pi worker 统一；新建或重开会话生效，Window collaboration prompt 独立组合 |
| 内置工具开关 | `tools` / `noTools` | 新建/重开会话 |
| 资源加载开关（skills/prompt templates/context files/extensions） | loader 的 `noSkills`/`noPromptTemplates`/`noContextFiles`/`noExtensions` | 新建/重开会话 |
| thinking level | `session.setThinkingLevel()` | 运行时即改 |
| 压缩策略 | `session.compact(customInstructions)` / compaction settings | 运行时 |
| 名称、头像、描述 | 平台自存，复用 avatar 接口 | 即改 |

**实现要点**：

- `teams.json` 放一条 pinned 保留条目（`name: "manager"`，`invoke: { type: "pi" }`），`upsertAgent` 目前只收 `command`（`teams.ts:258`），需放开 `pi` 类型且只允许这一个保留名；不可删除、不可禁用；
- direct/group 的 relay guidance 优先级不变：window.prompt > manager 全局 prompt > 内置 relay guidance；
- `PiSessionStore.create()/open()` 读该配置装配会话，改动只对新建/重开的会话生效（运行中会话用 `setModel`/`setThinkingLevel` 即时项除外）；
- 与 worker 的差异在 UI 上体现为表单分区：manager 没有 invoke command/probe/secrets，替换为上述 SDK 配置区。

## 12. 验收标准

### 12.1 协议与状态机

- 新任务使用 `run`，续聊使用 `continue`，待授权只使用 `respond`；
- 同一 Session 同时最多一个 active/waiting Run；
- `respond` 后 `runHandle` 不变；
- 一次返回多个 request 时必须一次完整处理；
- 重复 response request_id 不重复执行授权；
- Interaction 过期明确显示，不自动创建新 Run。

### 12.2 PuddingClaw

- TTY `run` 仍可原地交互审批；
- 非 TTY/`--json` 返回结构化 `needs_input`；
- 新 `respond` 可从另一个 CLI 进程恢复同一 Run；
- continuation token 只出现在 `--json`/stdin 机器协议中，不进入 human output、stderr、普通日志和 Session 历史；
- `continue` 仍使用现有 `run --session`，历史 Session 不回归。

### 12.3 PuddingTeams

- `needs_input` 不再指导 manager 重跑 `team_task`；
- 页面刷新后审批卡仍能从存储恢复状态；
- 用户批准后不发送新的 child task，而是调用 Driver.respond；
- 完成结果写入原 direct/group manager Session，并自动触发后续汇总；
- 非当前窗口不能审批该 Interaction；
- Extension 无法读取凭证明文和 provider continuation token；
- 配置的 Extension 源中的 Connector 可被发现，但只有已安装、已配置且启用的 Agent 实例进入 roster；
- 禁用 Agent 后，旧 Session 即使仍持有旧 tool schema，也无法发起新委托；
- Driver 能力、安装、认证与启用状态在 API 和 UI 中一致；
- 每个 Agent 管理页可独立绑定多个 Capability Extension，并显示实际注册工具与信任来源；
- Agent/Capability 禁用后立即阻断新调用，空闲重建后不再出现在 manager 的 active tools；
- Extension 只能调用绑定 Agent 的 `ScopedAgentInvoker`，不能越权指定其他 Agent；
- Extension 配置变化不复制或重写 Pi Session JSONL 历史。

### 12.4 Connector Extension SDK

- PuddingClaw 第一方 Connector 完成完整回归；
- 声明式 Connector 样例可由用户复制后二开，并通过 validate/fixture 测试；
- ACP 代码型样例证明 stream/respond/cancel 可经 Extension Host 归一化；
- 未声明或未验证 `respond` 的 Connector 不展示可恢复审批能力；
- 任一 Connector 未安装、未认证、服务不可达时，`probe()` 返回可操作原因而不是运行时模糊失败；
- Connector 版本和真实上游版本可见，超出已验证范围时显示 `untested/incompatible`；
- 用户可用声明式 Connector 接入简单 CLI，并通过 validate 契约测试；
- 代码型 Connector 在隔离 Extension Host 中运行，未经授权不能 spawn、联网、读取工作区或使用 secret；
- 更新单个 Connector 不要求升级 PuddingTeams 核心，固定旧版本仍可回滚。

### 12.5 故障场景

- PuddingClaw Backend 重启：卡片转 expired，允许用户显式“重新执行”，不静默重跑；
- PuddingTeams Backend 重启：加密 provider state 可恢复；
- 浏览器断开：Child Run 仍 waiting_input；
- 用户拒绝：Run 收到 reject 并给出终态；
- worker stdout 非 JSON、重复终态、超大行、进程忽略 SIGTERM 都有测试。

## 15. 工作区与产物交接（Workspace & Handoff）

> 2026-08-06 补充。回答两个问题：agent 间共享文件怎么做（对比 AgentTeams 的 MinIO）；中间产物与交付物如何分界。

### 15.1 两个概念必须分开

| 概念 | 含义 | 归属 |
| --- | --- | --- |
| **workspace** | 房间可选绑定的本地项目，agent"对什么干活"（用户项目/数据本身） | 用户在房间指定；未选择时保持平台原有默认 cwd |
| **handoff 产物** | Run 结束时的交付物，需要在 agent 之间、agent 与用户之间交接 | 平台登记管理 |

中间过程产物（scratch、临时文件、agent 私有 workspace 内部状态）**各 agent 自理，平台不介入**。AgentTeams 用 MinIO 是因为多节点容器必须走网络存储；PuddingTeams 单机形态下等价物就是本地目录约定，第一阶段不引入对象存储。

### 15.2 workspace 绑定

> 实现状态（P3-1，2026-08-10）：Workspace/Session 正确性已按平台实体收口，不再把路径直接挂在 Window 上。

- Workspace 是可选增强，不是聊天前置条件。未选择时 `WindowConfig.workspaceId` 缺省，并把创建时的平台默认 cwd 持久化为 `WindowConfig.cwdSnapshot`；manager 与 worker 都使用该快照，保持原有聊天入口且不创建伪 Workspace；
- `WorkspaceRecord` 保存 `rootPath + canonicalPath + gitRoot?`，按 `realpath` 后的 canonical path 去重；只有仍解析为同一可读目录时才标记可用。路径失效不阻断服务启动，只阻断对应 Window 执行，绝不回退到默认 cwd；
- 本地产品可通过 server-side native picker 取得真实服务端目录：macOS 调系统 `choose folder`，Windows 调 `FolderBrowserDialog`，取消不改变 UI；Web 内嵌目录浏览与未来 Electron 主进程选择器复用同一“返回 canonical 服务端路径”协议；
- `WindowConfig.workspaceId?` 只引用显式项目身份；direct Window 去重键为 `(worker, workspaceId ?? cwdSnapshot)`，无项目单聊在默认 cwd 变化后也不会复用旧目录的 Session；
- `DelegationRecord.workspaceId? + cwdSnapshot` 在委托创建时冻结。即使没有 Workspace，也必须冻结默认 cwd；run/continue/respond/cancel/artifact 全部读取快照，不重读 Window 当前值；
- 委托创建、respond/cancel admission 与原地切换共享 Window 生命周期门；Run 记录落盘后才释放 admission，切换可枚举并取消所有已接纳任务（包括 solo 路由到 direct 的任务）；
- manager 的 `SessionManager`、`ResourceLoader`、内置工具与 worker Driver 使用同一 workspace cwd；
- worker binding 同时记录 `workspaceId? + cwdSnapshot + agentRevision + sessionHandle`，项目/cwd 或 Agent 配置修订变化后不得续接旧 Session；
- Runtime 自持每个 active Run 的 AbortController；取消先封存 `cancelled` 终态、触发真实子进程中止并等待有界 settle，迟到 completed 不得复活状态或登记 artifact；
- 上下文切换支持显式 Workspace 与“不绑定项目”双向切换；默认创建成员相同的新 Window，显式原地切换先取消 active/waiting Delegation，再清空 worker binding 并以新 cwd 重建 manager Session；
- workspace 是项目上下文和默认操作范围，不是平台承诺的通用文件权限沙箱。Codex sandbox、Claude permission mode、Agent 自身权限与 OS 隔离才负责强制执行；
- artifact 登记和下载以 Delegation `cwdSnapshot` 做 realpath containment，项目外绝对路径与越界 symlink 在登记时拒绝；下载使用 `O_NOFOLLOW` 文件描述符并以 dev/ino 复核，校验后不再按可变路径重开文件。

### 15.3 目录布局

```text
<workspace>/
├─ …（用户项目本身，agent 直接读写）
└─ .pudding/
   └─ handoff/<delegationId>/     # 本次 Run 的交付物
```

### 15.4 handoff 的两种来源，一个登记接口

"怎么知道交付物是什么"是 Driver/Connector 的事；"交付物的登记与交接"是 Runtime 的事。两种来源对 Runtime 无差别：

| 模式 | 适用 | 机制 |
| --- | --- | --- |
| **push** | PuddingClaw（自家 CLI） | `puddingclaw run --export <dir>`：执行完把交付物导出到指定目录，result 中声明清单 |
| **observe** | Codex / Claude / Pi（改不了的第三方） | Driver 从事件流机械收集（`apply_patch` / `Write` / `Edit` 事件触碰的文件集），git 仓库用 diff、非 git 用目录快照 diff 兜底 |

关键原则：**不依赖模型自觉声明，也不扫描目录猜测**。observe 模式下模型在最终回复里的清单只作为命名/kind 元数据补充，事实源是事件流和文件系统。coding agent 的交付物往往就是 workspace 里的改动本身，git diff 天然表达；`.pudding/handoff/` 只装报告、导出物这类"工作区之外的产物"。

### 15.4.1 为什么 PuddingClaw 不向 observe 对齐

push/observe 的分工不是"自家 CLI 没改"，而是两类 agent 的本质差异：

| | 修改型（Codex/Claude/Pi） | 生成型（PuddingClaw） |
| --- | --- | --- |
| 输入 | workspace 里的项目文件 | 数据库/数据源 API，不读文件系统 |
| 输出 | 对 workspace 的就地修改（有 before/after） | 报告、导出数据（生成物，无 before） |
| 文件产生地 | 平台可见的 cwd | backend 管理的 workspace（可能远程） |

git/fs diff 观察对 PuddingClaw 不成立：房间目录里没有它要写的东西；文件在 backend 侧（远程时另一台机器），CLI 侧不可见；生成物没有 diff 语义，untracked 文件堆分不清交付物与内部 scratch。即使把 `PUDDINGCLAW_PROJECTS_ROOT` 指向房间目录，落入 diff 视野的也是 session 状态等内部文件，恰恰制造"扫描目录猜测"。

统一发生在**语义层**（四操作、PWCP 事件、artifacts 清单），机制层保留差异正是 Driver 存在的意义。流式落地（Phase 7）后，事件流观察对 PuddingClaw 同样成立，进度体验与 coding agent 一致；只有 fs diff 这条轨迹不适用它。

### 15.5 软引导入口（提升质量，不作事实源）

1. **`AGENTS.md` / `CLAUDE.md`**：平台在绑定 workspace 时写入 handoff 约定（报告类交付物写入 `.pudding/handoff/`，最终回复列出清单）——Codex、Claude、Pi 都自动读取；
2. **任务 prompt 包装**：Capability Extension 派活时在任务文本中附带交付约定；
3. **Pi 子 agent**：`createAgentSession` 时进 system prompt 片段。

### 15.6 产物数据流

```text
Run 结束
  → Driver 汇总 artifacts 清单（push / observe）
  → CompletedResult.artifacts（§4.3）
  → Runtime artifacts store 登记（名称/路径/kind/大小/产出者/delegationId）
  → artifact.created 事件 → UI 产物面板（下载/预览）
  → 接力派活：manager 在任务文本中引用路径（传路径不传内容）
```

超限额的大结果沿用旧方案结论：转 artifact 引用，不进 tool result 正文。产物面板列为后续阶段（原平台设计文档阶段四备忘），第一阶段只要求登记和 API 可查。

### 15.7 PuddingClaw CLI 改造补充

在 §11 Phase 2 清单之外增加：`run`/`respond` 支持 `--export <dir>`，执行终态时把交付物（报告、导出数据）复制到该目录并在 result JSON 中声明 `artifacts`。CLI 不知道平台目录结构，导出路径由 Driver 按 §15.3 约定生成并传入。

---

这套方案的最小正确闭环是：**PuddingTeams 先能区分 Session 续聊和 Run 恢复，PuddingClaw CLI 再补公开 `respond`，最后由 InteractionBroker 把浏览器审批准确送回原 Run。** Extension、JSONL 和更多 Agent 都建立在这个闭环之上，而不是反过来。
