# 通用 Agent 接入方案：Runtime、Driver、Extension 与可恢复交互

> 日期：2026-08-06  
> 状态：持续实施；PuddingClaw 本机 Connector 已接通
> 适用仓库：PuddingTeams、PuddingClaw  
> 目标：让 PuddingTeams 以同一套底层生命周期接入 PuddingClaw、Pi、Hermes、OpenClaw、Grok Build、Codex、Claude Code 等 Agent，同时正确处理 Session 连续性、当前 Run 的人工审批、流式进度和凭证隔离。
>
> 2026-08-30 增量已实现：ExecutionReceipt、Driver 对账/取消确认能力、Workspace execution scope、Verification capabilities 与三轴状态已落地；完整门禁和首期边界见 `docs/2026-08-26-真实环境复验与可信验收方案.md`。项目未上线，相关状态文件直接升级并拒绝旧结构，不保留兼容映射。

## 0. 结论先行

这次方案的核心不是再造一套“统一 CLI 命令”，而是统一四个**操作语义**，再由每个 Driver 映射到真实 Agent：

1. `run`：创建新 Session 并启动第一条 Run；
2. `continue`：在已有 Session 中创建下一条 Run；
3. `respond`：给当前仍在等待输入的同一条 Run 提交审批或回答；
4. `cancel`：取消当前 Run，不删除 Session。

其中最容易混淆、也正是当前故障来源的是：

- `continue` 面向 **Session**，前一条 Run 必须已结束；
- `respond` 面向 **Run/Interaction**，当前 Run 仍处于 `waiting_input`；
- 两者不能互相替代，也不能都叫 `resume`。

PuddingClaw 当前已经具备后端 `respond` 能力：`POST /api/headless/runs/{run_id}/resume` 会恢复原 Run；它当前的 Session 连续性则是 `puddingclaw agent run ... --session <session_id>`。因此：

- **不新增** `puddingclaw resume <session_id>`；
- **新增**公开、非 TTY 的 `puddingclaw agent respond <run_id> --input-json - --json`；
- PuddingTeams Driver 把统一的 `continue(...)` 映射到现有 `run --session`，把 `respond(...)` 映射到新命令。

PuddingTeams 当前遇到 `needs_input` 后把它转成普通文本，让 manager 下一轮重新调用 `team_task`。这会创建新 Run，而 PuddingClaw 原 Run 仍在等待授权，于是得到 `Session already has an active Run or pending input`。正确修复是：**保存待处理 Interaction，由消费端审批后调用 `respond`，绝不重跑任务。**

产品能力采用两层组合，而不是把所有逻辑继续堆进 Driver：

- **基础 Driver SPI 负责接入规范**：安装探测、认证、run/continue/respond/cancel、Session/Run handle 和事件归一化；具体 Agent 的协议映射由 Connector Extension 实现；
- **每个 Agent 实例通过 Pi Extension 扩展能力**：给 manager 注册该 Agent 的专属工具、参数 Schema、提示规则和结果投影；
- Agent 管理页同时管理 Connector Extension 和 Capability Extension：每个 Agent 必须绑定一个 Connector，可再绑定零到多个 Capability Extension；同一个 Extension 也可用不同配置绑定到多个 Agent；
- Driver 不注册业务工具，Extension 不理解或调用 Agent 私有 CLI/HTTP 协议，所有执行必须回到 scoped `AgentInvoker`。

### 0.1 北向 Headless Gateway 与南向 Connector 必须分开

本文的 Connector/Driver SPI 是**南向接入**：PuddingTeams 已经决定调用哪个 Worker 后，由 Driver 映射其 spawn/HTTP/RPC/ACP/SDK 协议。它不定义外部系统如何把 PuddingTeams 整体当作一个团队 Agent 调用。

PuddingTeams 的**北向接入**另由 Headless Gateway 承担。北向调用方只提交 `query`，不提供 target、workerId、roomId、Connector 或 transport；Teams 内部 Manager 自主决定自己处理、单 Worker 或多 Worker 编排，并自动创建/复用所需房间。HTTP 采用 REST 控制面 + SSE 事件流，spawn CLI 是同一 Gateway 的薄客户端并把 SSE 转为 stdout JSONL。完整契约、事件模型与开发顺序见 [`2026-08-24-PuddingTeams北向Headless-Gateway方案.md`](./2026-08-24-PuddingTeams北向Headless-Gateway方案.md)。

## 1. 第一性原理

### 1.1 平台真正需要统一的是什么

PuddingTeams 对任意 Agent 只承担六类稳定职责：

| 职责 | 平台不变量 | Agent 变量 |
| --- | --- | --- |
| 路由 | Agent 目录、能力筛选 | 描述、适用任务、专属选项 |
| 执行 | 启动、超时、取消、错误分类 | CLI、HTTP、RPC、ACP |
| 连续性 | 保存不透明 Session handle | handle 的生成和消费方式 |
| 交互 | 保存 pending Interaction、接收用户决定 | 权限、问题、规则确认等类型 |
| 可观测 | 统一事件与终态 | Agent 能提供的进度丰富度 |
| 凭证 | 加密存储、最小化注入 | 各 Agent 所需的环境变量或 token |
| 产物 | 工作区绑定、产物登记与大小限制 | 交付物如何产生与取出（push / observe） |

因此正确边界是：

```text
pi Extension（给模型看的工具与说明）
        ↓ 房间链路只拿 ScopedAgentInvoker，不拿凭证明文
Agent Runtime（生命周期、状态机、持久化、事件）
        ↓
Agent Driver（PuddingClaw / Codex / Claude 的语义映射）
        ↓
Transport（spawn / HTTP / RPC / ACP）
```

职责判定规则非常简单：

- “如何联系这个 Agent、如何恢复同一 Run”属于 Driver；
- “模型何时应该使用它、要填哪些业务参数、结果怎么投影”属于 Extension；
- “是否允许本次调用、状态如何持久化、事件怎么广播”属于 Runtime；
- “CLI 参数模板”和“数据库分析工具 Schema”不得出现在同一个模块里。

### 1.2 必须分开的三个身份

| 身份 | 生命周期 | 用途 |
| --- | --- | --- |
| `sessionHandle` | 多条 Run | 让下一条用户消息继承 Agent 历史 |
| `runHandle` | 一条 Run | 标识本次执行，用于取消、追踪和定位错误 |
| `interactionHandle` | 一次或一组待输入 | 只用于恢复当前 Run；可能含 bearer token，不能进模型上下文 |

`requestId` 不是第四种 handle。它只标识一次 Interaction 中的某个具体问题；并行工具可能一次返回多个 `requestId`，必须完整回答当前集合。

### 1.3 状态机不允许“靠自然语言重试”

```text
无 Session ── run ──> running ───────────────> completed/failed/blocked
                         │
                         └──> waiting_input ── respond ──> running
                                     │                         │
                                     └── reject ───────────────┘

已有空闲 Session ── continue ──> 新 Run 的 running
```

约束：

- `continue` 只允许 Session 空闲时调用；
- `respond` 必须携带服务端返回的 Interaction 句柄，并恢复原 `runHandle`；
- `waiting_input` 不是 `failed`，也不是“提示用户后重新运行”；
- 同一 Interaction 的重复提交必须幂等；
- 用户拒绝也是合法响应，Run 应继续到可解释终态，而不是让平台伪造成功。

## 2. 两个仓库的源码事实

### 2.1 PuddingTeams 当前行为

源码位置：

- `apps/server/src/store/teams.ts`
- `apps/server/src/pi-bridge/team-task.ts`
- `apps/server/src/pi-bridge/session-store.ts`
- `apps/server/src/routes/chat.ts`

已确认事实：

1. `TeamsStore.runAgent()` 每次用 `spawn(..., stdio: ["pipe", "pipe", "pipe"])` 启动 Worker；stdin 写一份 JSON，stdout 只按**单个 JSON**解析。
2. Session 连续性保存在 `WindowConfig.workerBindings[managerSessionId][agentId].sessionHandle`；继续任务时，经对应 Driver 把当前房间 Session 的不透明 handle 映射回 Worker 私有字段（PuddingClaw 为 stdin `session_id`）。新建房间 Session 没有 binding，必须创建新的 Worker Session。
3. `team_task` 遇到 `needs_input` 后只生成一段文本，默认指导 manager “等用户回复后重试”。这对业务参数澄清尚可，对仍占用原 Run 的权限 HITL 是错误的。
4. `session-store.ts` 当前通过 `customTools` 注入单个 `team_task`；并未使用方案文档设想的 per-agent Extension。
5. WebSocket 已能转发 pi tool update 和 custom message，前端也已有 `pudding:task_assign`、`pudding:task_result` 的渲染入口，可扩展为审批卡，无需新建第二套实时通道。
6. 当前 `CredentialsStore` 直接归 `TeamsStore` 持有并在 spawn 前注入环境变量；这一安全边界应该保留，不应把 `CredentialsStore` 传给 Extension。

### 2.2 PuddingClaw 当前行为

源码位置：

- `backend/api/headless.py`
- `backend/graph/deepagents_manager.py`
- `backend/graph/permission_resume.py`
- `packages/puddingclaw-cli/dist/cli.js`

已确认事实：

1. `puddingclaw agent run <message> --session <session_id> --json` 已能在同一 Session 中创建下一条 Run；stdin 的 `session_id` 也保留兼容。
2. Headless API 在权限或 `request_user_input` 业务问答中断时返回：`run_id`、`session_id`、`needs_input`、`continuation_token`，并保持原 Agent stream、LangGraph checkpoint thread 和 Run 存活。
3. `POST /api/headless/runs/{run_id}/resume` 会校验 continuation token，要求一次解决完整 pending request 集合，然后恢复**同一条 Run**。
4. CLI 在交互式 TTY 中可在一次 `run` 进程内询问用户并自动调用 Resume API；在 `--json` 或非 TTY 下会原样返回 `needs_input` 并退出，不会私自授权。
5. CLI 已提供公开、非 TTY 的 `respond` 子命令，PuddingTeams 通过 `stdio: pipe` 恢复原 Run。
6. Headless 外送交互支持 permission 与结构化 `user_input`；后者保留 1–3 个 question 的原始 id/选项，`respond` 用 `action + answers` 恢复同一 Run。PuddingClaw Driver 因此声明 `interactionKinds: ["permission", "question", "confirmation"]`；其他未接入 Resume API 的业务 HITL 仍 fail-closed。
7. PuddingClaw 的 live execution 目前保存在后端进程内。PuddingClaw 后端重启后，旧 continuation token 无法恢复该 Run，Resume API 会返回 410。这是现有限制，不能由 PuddingTeams 文档假装解决。
8. 2026-08-23 起 PuddingClaw Connector 同时支持 `spawn`（本机 CLI）与 `http`（直连 Headless NDJSON）两种 transport；二者都受 PuddingClaw 的本机回环限制，不读取或传递 Worker Access Key、`PUDDINGCLAW_TOKEN`、`PUDDINGCLAW_HEADLESS_TOKEN`。Connector manifest 因此申请 `spawn`、`network`，但不声明 secret；Platform 也不展示 PuddingClaw Token 配置。

### 3.1 Driver 是唯一理解 Agent 私有协议的层

```ts
interface AgentDriver {
  id: string;
  capabilities(): Promise<DriverCapabilities>;
  run(input: RunInput, ctx: InvocationContext): AsyncIterable<AgentEvent>;
  continue(input: ContinueInput, ctx: InvocationContext): AsyncIterable<AgentEvent>;
  respond(input: RespondInput, ctx: InvocationContext): AsyncIterable<AgentEvent>;
  cancel?(input: CancelInput, ctx: InvocationContext): Promise<void>;
  reconcileRun?(input: { runHandle: string; lastObservedAt?: string }, ctx: InvocationContext): Promise<ReconciledRun>;
  reattachRun?(input: { runHandle: string; afterCursor?: string }, ctx: InvocationContext): AsyncIterable<AgentEvent>;
  probe(ctx: InvocationContext): Promise<ProbeResult>;
}

interface DriverCapabilities {
  operations: Array<"run" | "continue" | "respond" | "cancel">;
  interactionKinds: Array<"permission" | "question" | "confirmation">;
  progress: "none" | "coarse" | "stream";
  // spawn=子进程 CLI；http/rpc/acp=网络协议；sdk=进程内 SDK（如本地 pi）。
  transport: "spawn" | "http" | "rpc" | "acp" | "sdk";
  reconciliation?: "none" | "query_run" | "reattach_stream";
  cancelConfirmation?: "none" | "acknowledged" | "observable";
  workspace?: {
    honorsInvocationCwd: boolean;
    readOnlyEnforcement: "none" | "sandbox" | "remote_policy";
    mutationObservation: Array<"event_stream" | "git_diff" | "filesystem_diff">;
  };
  verification?: {
    modalities: Array<"cli" | "gui">;
    freshSession: boolean;
    workspaceIsolation: Array<"none" | "mutation_guard" | "isolated_copy">;
    commandExecution: boolean;
    guiObservation: boolean;
    networkObservation: boolean;
  };
}
```

注意：这是 TypeScript 内部接口，不要求外部 CLI 出现同名命令。统一的是语义，不是字符串。

PuddingTeams 核心只内置 Driver SPI 和 Registry，不长期内置所有第三方 Agent 的具体映射。具体映射由可独立安装、升级的 Connector Extension 注册到 Driver Registry。必须区分五层状态：

1. `available`：本地、团队或社区目录中存在相应 Connector Extension；
2. `installed`：Connector Extension 已安装并通过 manifest/engine 校验；
3. `detected`：本机已找到对应 CLI，或已配置可访问的服务端；
4. `configured`：认证和必要参数可用；
5. `enabled`：用户明确允许该 Agent 实例进入 roster 并被委托。

默认发行预装四个第一方 Connector：PuddingClaw（产品首条链路）、本地 pi（§9.1 Pi 调 Pi 标杆）、Codex 与 Claude Code（路线图 P1 主流 coding agent 样本，均为 spawn + JSONL 流式，无 HITL 承诺、`interactionKinds: []`）；核心 delegation 是 Runtime 生成能力，不算用户 Capability Extension。Hermes、OpenClaw、Grok Build 等只作为 Connector 编写指南中的协议案例或社区扩展候选，不承诺在默认目录预置。用户或团队可以二次开发并安装自己的 Connector；更新 Connector 不要求发布整个 PuddingTeams。

### 3.2 Extension 只能拿窄接口

```ts
interface ScopedAgentInvoker {
  readonly agentId: string;
  capabilities(): Promise<DriverCapabilities>;
  delegate(input: ScopedDelegateInput): Promise<AgentInvokeResult>;
}

interface AgentExtensionContext<TConfig = unknown> {
  agent: Readonly<AgentSummary>;
  config: Readonly<TConfig>;
  invoker: ScopedAgentInvoker;       // 已绑定 agentId，Extension 不能改投其他 Agent
  events: ExtensionEventPublisher;   // 只能发命名空间内的可观测事件
}
```

Extension 不得拿到：

- `CredentialsStore`；
- Worker token 明文；
- continuation token；
- 任意 spawn 能力。

凭证仍由 Runtime 在调用 Driver/Transport 前注入。这样 Extension 即使被模型诱导，也无法把密钥写进 tool result。

还必须明确一个现实安全边界：Pi Extension 是可执行 TypeScript/JavaScript。TypeScript 接口只能约束正常代码，不能把恶意第三方 Extension 变成沙箱。第一版只允许 PuddingTeams 内置、经过审核的 Extension 进程内加载；后续用户安装的第三方 Extension 必须显式显示来源和代码执行风险，并放到隔离 Extension Host 中，不能直接把任意本地路径 `import()` 进 server 进程。

#### 3.2.1 `AgentInvoker` 发起委托，但不等于 OS `spawn`

在 PuddingTeams 房间链路里，`AgentInvoker` 是 manager 工具与 Runtime 之间唯一的业务调度/治理入口，不是统一的子进程启动器。实际调用顺序固定为：

```text
manager Extension tool.execute()
  → ScopedAgentInvoker.delegate()       # 已绑定 agentId 的窄接口
  → AgentInvoker.delegate()             # 鉴权、窗口成员校验、cwd/凭证/sessionHandle 解析
  → AgentRuntime.delegate()             # 创建 Delegation、会话锁、状态机、持久化与事件处理
  → AgentDriver.run()/continue()        # 解释具体 Agent 的运行/续接协议
  → Transport                           # spawn / HTTP / RPC / ACP / SDK
```

因此要区分两种口语中的“spawn agent”：

- 如果指“接受并创建一次 worker 委托”，可以说由 `AgentInvoker` 发起，且 Runtime 会在 Driver 启动前先创建 Delegation；
- 如果指 Node.js `child_process.spawn()` 创建 OS 子进程，则只在 `transport:"spawn"` 的 Driver 内发生，当前通过共享 `spawnWorker()` 实现。Codex、Claude Code、PuddingClaw CLI 和声明式 CLI Connector 属于这一类；
- 本地 pi worker 的 `LocalPiDriver` 使用进程内 pi SDK Session，`transport:"sdk"`，不会创建 worker 子进程；HTTP/RPC/ACP Connector 也按各自 Transport 执行，不经过 `spawnWorker()`。

这也是为什么 Extension 只获得 `ScopedAgentInvoker`：上层只表达“委托哪个已绑定 Agent、run 还是 continue”，真正的进程、网络或 SDK 执行策略必须留在 Driver/Transport。`AgentInvoker` 返回的 `AgentInvokeResult` 是平台业务投影，不是某一种 Transport 的原始进程结果。

源码定位：治理入口在 `apps/server/src/agent-runtime/invoker.ts`，生命周期引擎在 `agent-runtime/runtime.ts`，本地 pi SDK Driver 在 `agent-runtime/pi-driver.ts`，CLI 真正调用 `spawnWorker()` 的参考实现分别在 `extensions/connectors/codex/driver/index.ts`、`extensions/connectors/claude-code/driver/index.ts` 与 `agent-runtime/puddingclaw-driver.ts`。

这里的“Extension 只获得 `ScopedAgentInvoker`”专指装配进 **PuddingTeams manager Session** 的平台基础委托 Extension 和 Capability Extension。双宿主 Connector 包供纯 pi 使用的 `pi/` 门面运行在 PuddingTeams 房间体系之外，执行路径见 §9.5；它不会获得、也不会经过 PuddingTeams 的 `AgentInvoker`。

#### 3.2.2 manager 侧 pi Extension 的实际样式与执行路径

PuddingTeams 并不是让 manager 模型直接调用 `AgentInvoker`。平台按 roster 为每个 Agent 生成一个具名 inline pi Extension，实际形态是 `(pi: ExtensionAPI) => void` factory，在 factory 内通过 `pi.registerTool()` 注册工具。下面是当前 `agentDelegationFactory()` 的等价缩略版；省略了 solo 单聊镜像、Goal 字段校验、HITL 和 Artifact 文案，但保留真实边界：

源码定位：factory 构造与工具 `execute()` 在 `apps/server/src/pi-bridge/agent-extensions.ts`；`extensionFactories` 注入 `DefaultResourceLoader` 并交给 `createAgentSession()` 的装配入口在 `apps/server/src/pi-bridge/session-store.ts`。

```ts
function agentDelegationFactory(agent, deps) {
  return (pi: ExtensionAPI) => {
    pi.registerTool({
      name: `agent_${toolSafeId(agent.name)}__delegate`,
      label: `${agentDisplayName(agent)} · 委托`,
      description: "把任务委托给这个 worker 并返回最终结果",
      parameters: DelegateParams,

      async execute(toolCallId, params, signal, onUpdate) {
        const scoped = new ScopedAgentInvoker(agent.name, deps.invoker);
        const result: AgentInvokeResult = await scoped.delegate({
          windowId: resolveTargetWindow(),
          managerSessionId: deps.getSessionId(),
          managerToolCallId: toolCallId,
          message: params.task,
          mode: params.session === "new" ? "run" : "continue",
          parentDelegationId: params.parentDelegationId,
          handoffKind: params.handoffKind,
          signal,
          onUpdate: (content, details) =>
            onUpdate?.({ content: [{ type: "text", text: content }], details })
        });

        if (result.status === "failed") throw new Error(result.content);

        const resultText = await projectManagerText(result); // 阈值内全文；超阈值无损外置并返回 head/tail、分页读取说明、Artifact 与接力信息
        return {
          content: [{ type: "text", text: resultText }],
          details: {
            worker: result.details.worker ?? agent.name,
            status: result.status,
            delegationId: result.delegationId,
            interactionId: result.interactionId,
            sessionHandle: result.sessionHandle,
            processView: true
          }
        };
      }
    });
  };
}
```

装配和一次调用的完整路径是：

```text
PiSessionStore.managerResourceLoader()
  → planManagerTools() 计算当前窗口可见/激活工具
  → buildManagerExtensionFactories()
       生成 core roster factory
       + 每个 roster Agent 的 agentDelegationFactory
       + 已绑定 Capability factories
  → DefaultResourceLoader({ extensionFactories })
  → createAgentSession({ resourceLoader })
  → loader 调用 factory，factory 执行 pi.registerTool()

manager 模型输出 toolCall(agent_<id>__delegate, args)
  → pi 校验 DelegateParams 并调用 tool.execute()
  → ScopedAgentInvoker.delegate()
  → AgentInvoker.delegate()
  → AgentRuntime.delegate() 先创建/落盘 Delegation
  → Driver.run()/continue()
  → Driver 事件流经 Runtime 归一、持久化并通过 onUpdate 回到 pi/UI
  → terminal NormalizedResult 先写入 Delegation
  → RuntimeOutcome → AgentInvokeResult
  → Extension 投影 AgentToolResult {content, details}
  → pi 包装 ToolResultMessage，写 manager Session JSONL
  → manager 下一次推理只消费 toolResult.content
```

所以所谓“上层 Extension”就是上面这段注册模型工具、校验业务参数并投影结果的 pi factory；它负责模型接口，不负责理解 Codex/PuddingClaw/pi worker 的私有执行协议。`onUpdate` 是同一次阻塞工具调用的流式 UI 更新，不是最终 Session `toolResult`；只有 `execute()` settle 后的返回值才会被 pi 包装为最终结果消息。

### 3.3 Extension 动态加载的真实边界

当前 pi 0.83 支持 `extensionFactories`、运行时 `registerTool()` 和 `setActiveTools()`；但方案不能宣称“成员变化后旧会话自动删除工具”。源码与 SDK 文档没有通用 `unregisterTool()`。

可落地策略：

1. 新建 manager Session 时，按当前 Window 成员及其 `extensionBindings` 构造具名 `extensionFactories`；
2. 每个启用的 Agent 都获得一个平台生成的基础 `agent-delegation` Extension factory；额外 Extension 在它之后装配；
3. factory 创建时由 Runtime 注入绑定该 `agentId` 的 `ScopedAgentInvoker`，Extension 无权在调用参数里改投其他 Agent；
4. Extension 使用 `pi.registerTool()` 注册业务工具；工具名由平台统一命名空间化，避免两个 Agent/Extension 注册同名工具；
5. Agent、Extension 绑定或 Window 成员变化后，相关 manager Session 的 `extensionRevision` 增加并标记 `runtimeDirty`；
6. Runtime 先立即从 active tools 中移除被禁用的工具，并在 `AgentInvoker` 入口拒绝陈旧调用；Session 空闲时再重建 ResourceLoader/AgentSession，彻底移除遗留 hooks；
7. Session 的原 JSONL 历史继续作为唯一会话事实，不复制消息；重建只改变运行时装配；
8. `team_task` 在 per-agent Extension 就绪后直接删除，不设兼容期（决策 20）。

对应现有源码的直接改造是：

- `apps/server/src/pi-bridge/session-store.ts` 当前在 `create()`/`open()` 中用 `customTools` 单独注入 `team_task`，并且只有 direct/group 才显式构造 ResourceLoader；
- 将 `relayLoader(guidance)` 泛化为 `managerResourceLoader(windowContext)`，对 solo/direct/group 都创建同一类 ResourceLoader；
- loader 同时组合原有 guidance、core Extension factory，以及当前 Window 内 Agent 的基础/专属 Extension factories；
- `create()` 和从 JSONL `open()` 都调用同一装配函数，保证重启前后 Extension 集合一致；
- per-agent Extension 验证通过后，`team_task` 连同 `customTools` 注入路径一并删除。

工具命名使用不可变 Agent ID 和 Extension ID，而不是可修改展示名：

```text
agent_<agentId>__delegate
agent_<agentId>__<extensionId>__<toolName>
```

界面可显示友好标签，例如“PuddingClaw · 配置分析”，但发送给模型的工具名必须稳定、唯一、可审计。

Agent 的 name 与 id 已解耦（name 即 id）：`AgentConfig.name` 是不可变内部 id——工具命名空间、windows/credentials/delegations 存储键、REST 路径参数全部用它，创建后不可改；用户可见的显示名是独立的 `AgentConfig.displayName`（任意 unicode、≤40 字符、允许重复、可随时改，缺省回退 name）。创建时不显式给 name 则由服务端从 displayName 派生（ASCII slug，无 ASCII 时 `worker-<随机>`，撞名加 `-2` 后缀）。提示词材料（roster、guidance、delegate 工具描述、审批/结果卡正文）渲染 displayName，工具名仍含 id；前端只有 id 的展示位（委托卡、审批卡、等待提示）经 `avatars.ts` 注册表的 name→displayName 缓存映射。

当 Extension 很多时，不把全部工具默认塞进模型上下文；但基础委托工具是例外——schema 常驻成本远低于「先 search 激活再调用」的整轮上下文重发：

- 基础委托工具（`agent_<id>__delegate`）在 solo/direct/group 全窗口默认激活，roster 里的工具名可直接调用，不需要先搜索；
- capability Extension 工具仍按激活策略懒加载：`always` 随 direct 默认激活，其余（`searchable`）预注册但保持 inactive，由 `search_agent_tools` 按需执行纯加法 `setActiveTools()`；
- `search_agent_tools` 匹配全量受管工具（含已激活的）：搜到已激活工具时明确返回"已是激活状态，可直接调用"，而不是"没有匹配"——否则模型会在 direct 窗口里搜默认激活的 delegate 工具时被误导；查询按空格分词逐词 AND 匹配工具名与描述（描述含责任边界），模型惯用的「worker 名 + 职责关键词」组合查询可以命中；roster prompt 同时给已激活工具标注「（已激活）」，避免无谓搜索；
- 激活态只存在于内存（`setActiveTools` 不落盘），重启/空闲重建会清零，而 JSONL 历史里留着直接调用成功的记录，模型会模仿历史跳过 search 导致 "Tool … not found"。装配时从当前分支 JSONL 历史回放 SDK 标注的 `addedToolNames`（SDK 只写不读），恢复重建前的激活集合；回放仍受装配计划约束——已禁用/移出窗口的 worker 不进 `plan.managed`，其工具不会被回放，撤权语义不变。roster prompt 区分两种失败：调用返回 "Tool … not found" = 未激活，先 search 激活再重试一次；搜索不到该 worker 的工具、或激活后仍被明确拒绝 = worker 不可用，不重试；
- roster（成员名单）不做成工具：它是窗口绑定的静态事实，由 core Extension 的 `before_agent_start` 每轮重读并注入 system prompt，成员/启用变化下一轮即生效，安全性仍由 `AgentInvoker` 入口校验兜底；
- 配置禁用属于安全撤权，不依赖“纯加法加载”，仍走立即门控加空闲重建。

## 4. PWCP v1：统一事件契约，不强制统一 CLI 形态

PWCP（Pudding Worker Coordination Protocol）是 Runtime 和 Driver 之间的规范化事件契约。外部 CLI 可原生输出，也可由 Driver/shim 翻译。

### 4.1 操作输入

```ts
type AgentOperation = "run" | "continue" | "respond" | "cancel";

interface RunInput {
  message: string;
  requestId: string;
  options?: Record<string, unknown>;
}

interface ContinueInput extends RunInput {
  sessionHandle: string;
}

interface RespondInput {
  runHandle: string;
  interactionHandle: string; // 仅 Runtime/Driver 可见
  responses: InteractionResponse[];
  requestId: string;         // 本次提交的幂等键
}

interface InteractionResponse {
  requestId: string;
  action: "approve" | "reject" | "answer" | "confirm";
  scope?: "once" | "run" | "session";
  value?: unknown;
  message?: string;
}
```

### 4.2 事件输出

```ts
type AgentEvent =
  | { type: "started"; sessionHandle?: string; runHandle?: string }
  | { type: "progress"; stage?: string; message: string; percent?: number }
  | { type: "input_required"; result: NeedsInputResult }
  | { type: "completed"; result: CompletedResult }
  | { type: "failed"; result: FailedResult };
```

若走 CLI JSONL，stdout 每行只允许一个事件，stderr 只放诊断。未知事件类型可忽略，但每次操作必须恰好到达一个边界：`input_required`、`completed` 或 `failed`。

Codex `exec` 非零退出时，若 JSONL 已有明确的 `error` / `turn.failed`，终态错误优先采用该结构化原因；只有缺少结构化原因时才退回退出码和有界、脱敏的 stderr。实际 CLI 可能在 stderr 仅写“Reading additional input from stdin...”，而 JSONL 才包含账号不支持当前模型的 400 原因。Connector 的模型配置应从该账号的 `model/list` 显式选择，不能假定宿主 Codex 默认模型在另一个调用入口也可用。

Codex Connector 的 `exec`/`resume` 以 `thread.started` 和 `turn.completed` 共同证明完成；进程退出码 0、空流、仅有正文事件或截断流都不能被补成成功边界，必须返回 `protocol_incomplete`。pi 门面也同时检查非零退出码。这个协议终态检查不证明 CLI 身份或 T03 编译隔离；受保护编译仍须另外锁定可执行文件与执行环境。

### 4.4 分发与回收：delegate 阻塞语义与边界事件结算（2026-08-17 补记）

manager 派活与结果回收的完整机制，之前散落在代码里，此处固化：

- **阻塞式分发**：manager 的 `agent_<id>__delegate` 工具在 `execute` 内 `await ScopedAgentInvoker.delegate`（`pi-bridge/agent-extensions.ts`），委派不结算，tool call 不返回。因此委派执行期间 manager 的 agent run 保持 active——pi SDK 只在 run 完全结束（无排队 turn、无重试）时发 `agent_settled`，"等 worker"期间会话 UI 仍处于 running 是真实状态，不是卡死。
- **事件驱动回收**：Runtime 以 `for await` 消费 driver 的 `AsyncIterable<AgentEvent>`（`agent-runtime/runtime.ts`），遇边界事件推进 delegation 状态机并 return，解开 manager 侧 await 的那把锁。completed/failed 是终态；`input_required`（needs_input）不是终态——delegation 挂起等 HITL respond（§6），审批闭环后 driver `respond` 继续驱动同一 run。
- **Driver 启动前的终态也必须解锁 manager 工具**：Workspace admission、验证环境绑定等预检可能在 Runtime 已创建不可变 Delegation、但尚未调用 `onCreated` 时就封存 `reported_failed` Receipt（如 `workspace_policy_blocked`）。`AgentInvoker` 的受理门闩必须同时监听 `onCreated` 与 Runtime Promise 的早期 settle：前者让正常长 Run 受理即返回，后者让启动前失败立即结束 delegate 工具并落盘失败 `toolResult`。worker 单聊结果镜像是 best-effort 展示工作，不得延迟已终态的 manager 工具边界，否则 UI 会把已失败 Delegation 继续显示为「执行中」。
- **无边界兜底**：driver 事件流结束却没有到达任何边界（协议错误），按 `no_boundary_event` 记 failed 结算，delegate 工具不会无限悬挂。
- **失效会话透明重跑**：continue 撞上 session-not-found（`isStaleSessionFailure`）时，Runtime 丢弃失效 handle、以新会话重跑一次，不抛给 manager 连环试错；重跑仍失败才走正常 failed。
- **取消不是“断流即成功”**：每个 run 注册 `AbortController`（按 delegationId），但 Manager/用户的 AbortSignal 只表示平台停止等待。Runtime 必须先进入 `cancel_requested`，本地 `spawn/sdk` 只有在执行流已确认退出后才能封存 `cancelled` Receipt；远端 `http/rpc/acp` 若没有上游确认或可观察终态，必须进入 `observation_lost` 并 fence 写 scope，不能把流中断伪封为 `reported_failed/driver_error`，也不能宣称已经取消。刷新回填只消费这套 Delegation 权威终态。
- **前端状态拆分**：等待文案据此区分——消息流中存在 running 态 delegate 工具调用（`isDelegateCall`）时，composer 显示「等待 <worker> 返回…」；否则才显示笼统的「agent 正在处理…」。数据全部来自既有 `tool_execution_start/end` 事件折叠出的工具卡状态，不新增通道。

**Manager 停止与并行工具收口（2026-08-30）**：pi 的并行工具会按完成顺序发出 `tool_execution_end`，但要等同批工具全部 settle 后才按 assistant 源顺序追加原生 `toolResult`。因此平台不得在 `AgentSession.abort()` settle 前抢写原生结果，否则 SDK 随后会再写一份。`PiSessionStore` 先按 `sessionId + toolCallId` 记录所有工具的进程内 lifecycle；停止时等待 SDK abort 完成，再重读当前 branch，以 branch 中已有 `toolResult` 为最高优先级，对仍未闭合的调用依次采用已观测 `tool_execution_end`、与 `managerSessionId + managerToolCallId + delegate toolName` 一致的 Delegation 终态，最后才写“停止等待、效果未知”。补写在单 Session 串行闸门内再次判重，并在同一边界同步 `SessionManager`、驻留消息镜像和 WS。刷新发生在 streaming 期间时只返回 terminal overlay 与全部工具的 running id，不物理补写；idle 后才幂等修复 JSONL。前端严格按 `toolCallId` 合并，不能把迟到结果绑定到最新 assistant。

2026-08-31 起，Stop 还是 durable Goal fence：服务端在取消 Manager/Worker 前先把 active Goal 推进到新的 execution epoch 并标记 `interrupted`。所有 Manager 写工具与 Delegation 回调都必须携带发起时 epoch；旧 epoch 的迟到调用只能作为审计事实保留，不能再改 WorkPlan、Decision、Submission 或完成状态。AbortSignal 是尽快停止计算的优化，epoch 才是防止迟到副作用污染当前 Goal 的权威边界。

## 5. PuddingClaw Driver 的精确映射

### 5.0 本机边界与调用方标记

PuddingClaw Driver 是双传输参考实现：`spawn` 启动已安装的本机 `puddingclaw`，`http` 直接调用 `<endpoint>/api/headless/*` 并增量解码 `application/x-ndjson`。两条路径把相同 `{event,data}` envelope 送进同一个 activity observer/终态 normalizer，因此房间只看到统一的 `WorkerActivity` 与 `NormalizedResult`。HTTP transport 的 probe 直接请求 `GET /api/headless/health`，以 `agent_id=puddingclaw`、`protocol_version=1`、`progress=jsonl` 以及 run/continue/respond/cancel 操作矩阵判断 API 契约兼容性；`server_version` 只作为 Backend 版本展示，不参与协议兼容判定，更不以 `cli_version` 代替 API 协议。PuddingClaw Backend 当前仍强制 `localhost`、`127.0.0.1` 或 `::1`；Driver 不注入调用凭据，metadata 固定附加 `caller_id=puddingteams`、`caller_name=PuddingTeams`，仅供调用日志筛选，不作为身份或权限依据。

两种 transport 的 `run`、`continue`、无 token 澄清重跑和 `respond` 都必须透传同一个绝对 `workspace_path`。spawn 不得因为 CLI 在本机启动就省略该字段，否则 PuddingClaw 会退回自己的默认 workspace，造成 Worker 声称写入目标房间而文件实际落在另一目录。

### 5.1 Session 连续性：`continue`

```text
PWCP run(message)
  -> spawn: puddingclaw agent run --input-json - --jsonl
  -> http:  POST /api/headless/runs?stream=true
     body: {"message":"...","workspace_path":"...","request_id":"..."}

PWCP continue(sessionHandle, message)
  -> spawn: puddingclaw agent run --input-json - --jsonl
  -> http:  POST /api/headless/runs?stream=true
     body: {"message":"...","session_id":"worker-session-...","request_id":"..."}
```

也可映射为 `puddingclaw agent run "..." --session worker-session-... --json`。二者语义相同。

### 5.2 当前 Run 恢复：`respond`

PuddingClaw CLI 新增：

```text
puddingclaw agent respond <run_id> --input-json - --json
```

stdin：

```json
{
  "continuation_token": "opaque-token",
  "request_id": "puddingteams-response-uuid",
  "decisions": [
    {"request_id":"permission-request-id","decision":"approve","scope":"once"},
    {"request_id":"user-input-id","action":"submit","answers":[{"question_id":"choice","option_ids":["B"],"text":""}]}
  ]
}
```

CLI 内部映射到现有：

```text
POST /api/headless/runs/{run_id}/resume
```

输出仍使用现有 Headless 结果：可能再次 `needs_input`，也可能进入最终 `completed/failed/blocked`。

为保证跨进程重试安全，PuddingClaw Backend 的 `HeadlessResumeRequest` 带可选 `request_id`，并按 `run_id + request_id + request hash` 缓存本次 Resume 结果。PuddingTeams 在“上游已恢复、自己尚未来得及落盘”时重试，会获得同一边界结果而不是创建替代 Run。

必须增加的 CLI 校验：

- `run_id`、token、完整 decisions 集合必填；
- `--input-json` 只接受 `-`；
- 非 TTY 不弹交互提示；
- stdout 保持 JSON-only；
- 410 映射为 `interaction_expired`；
- 409 映射为 `interaction_conflict`；
- continuation token 只允许出现在机器可读 JSON 协议字段中，不打印到 human output、stderr 或日志。

### 5.3 为什么不新增 `puddingclaw resume <session_id>`

因为它会把两类恢复再次混淆：

- Session 续聊已经由 `run --session` 完整表达；
- 同 Run HITL 必须依赖 `run_id + continuation_token + requestId 集合`，只有 session_id 不足以安全恢复；
- Codex 的 `codex exec resume <id>` 虽然命令名叫 resume，语义更接近这里的 `continue`，不是 PuddingClaw 权限 `respond`。

统一层应适配语义，不应为了命令外观一致而增加别名。

## 6. PuddingTeams 的 HITL 完整闭环

HITL 有两个来源，均由 Teams 持久化和展示，但恢复路径严格分开：

- `source:"worker"`：Worker Run 已经存在，Delegation 为 `waiting_input`，批准时必须调用同一 Driver Run 的 `respond`；
- `source:"platform_policy"`：Teams 在 Driver 启动前发现能力缺口，Delegation 为 `waiting_admission`、`workerStarted:false`。用户可以继续当前 Worker、从服务端筛出的合格候选中换 Worker，或取消；继续不调用 Driver `respond`、不修改 Worker 配置或权限。换 Worker 会封存原 Delegation，并创建带 `parentDelegationId` 的新 Delegation，不复用旧 `managerToolCallId`、`sessionHandle` 或 `runHandle`。replacement 在 Driver 启动前必须持久化生命周期复核/WorkState reservation 已提交的 `replacementAdmissionReady`；恢复只接受唯一且带该证明的 child，`application` 只允许从 applying 单向进入 applied/failed。

Worker 原生 `input_required/respond` 在 WorkPlan 中必须始终建模为一个 WorkItem：询问只是同一 Delegation、同一 Run 的暂停边界，用户通过审批卡提交后由 Runtime 直接恢复。Manager 不得把询问前后拆成两个 WorkItem，也不得在回答后另发 followup、验证委托或替代委托来完成、提交或验收原流程。

只读任务遇到 `readOnlyEnforcement:none` 时，Runtime 先持久化 platform-policy Interaction 并立即闭合 delegate toolResult。用户拒绝、取消或 TTL 过期均直接封存 `cancelled` Receipt；用户继续后，Runtime 在启动 Driver 前重算 capability fingerprint，配置或能力漂移则返回 stale 且不启动 Worker。`isolated_worktree` 是稳定的外部策略名，但本地实现使用独立的共享对象 Git checkout（独立 `.git` 元数据），再物化源 checkout 的 staged/unstaged/untracked 基线；Runtime 同时把“当前 cwd 已是平台隔离 checkout，直接使用其 `.git`，不得再次 `git clone`/`git worktree add`”作为平台边界追加到 Worker 消息，避免通用 coding agent 再创建不可采集的嵌套仓库。Codex 的 `workspace-write` 会保护 `.git`：只有 Runtime 签发 `workspaceBoundary=platform_isolated_checkout` 时，Connector 才改用 Codex 的 `--approve-for-me`，仍由 workspace-write 与命令级自动审核处理 Git 元数据写入；目标 checkout、普通 workspace 和显式 `danger-full-access` 配置都不会由平台暗中升级。Worker 因此可以在自己的 checkout 内执行 `git add/commit`，不会写目标仓库共享的 `.git/worktrees/*`。该隔离 checkout 与 exclusive lease 只负责协作目录和调度，不能替代 Worker 原生只读能力，也不能被描述为通用 OS 沙箱。

### 6.1 当前错误路径

```text
team_task -> PuddingClaw Run A -> needs_input
manager 把 needs_input 当文字告诉用户
用户回复 -> team_task 再调用 -> PuddingClaw Run B
Run A 仍 waiting_input -> 409 Session already has active Run or pending input
```

### 6.2 正确路径

```text
team_task / agent-specific tool
  -> Runtime.run 或 Runtime.continue
  -> Driver 返回 input_required
  -> DelegationStore 保存 pending Interaction
  -> tool result 与审批卡落盘，manager 本轮由宿主停止，不再发起模型续轮
  -> WebSocket/历史消息显示审批卡
  -> 用户点击允许/拒绝
  -> POST /api/interactions/{localId}/responses
  -> Runtime.respond（不是 run/continue）
  -> 审批受理后 HTTP 立即返回 {status:"approved", details:{admitted:true}}，
     Delegation 原子地从 waiting_input 恢复为 running；同时向 manager 与
     worker 单聊立即追加 interaction_resolved(approved)，前端按 delegationId /
     interactionId 把原任务卡从“等待审批”对账为“执行中”，不等 worker 续跑落定
     （拒绝/冲突/幂等重放为快速路径，仍返回真实终态）
  -> PuddingClawDriver 调 `puddingclaw agent respond ...`（后台续跑）
  -> 若再次 needs_input：更新同一 Delegation revision，新审批卡投影到两边窗口
  -> 若 completed：写入 task_result，并触发 manager follow-up 汇总
  -> 四种结局（completed/rejected/failed/needs_input）都同时扇出到
     manager session 和 delegation 所属窗口的 active session（两边同步）
```

### 6.3 为什么采用“暂停并外送”，而不是让 tool call 一直阻塞

Manager 停轮与 Runtime 挂起是两个独立边界：Teams 准入保留 `waiting_admission`，Worker 原生交互保留 `waiting_input`，业务 DecisionRequest 保留 `pending`。宿主在 pi `shouldStopAfterTurn` 中查询当前 Manager Session 的持久化委托和当前 Goal 的待回答决策，工具批次完成后停止模型续轮，不调用 Session abort，不取消原 Run，也不推进 Goal epoch。已在执行的其他 Worker 可到达自己的边界。用户通过原卡片回答后，由既有 Runtime/Decision 闭环恢复；普通聊天中的“继续”不会自动消费审批。

等待期间 `tool_call` 统一拒绝 Manager 工具，并提示沿原卡片回答；核心写操作和 delegate 入口另作执行期校验，防止改派其他 Worker、改 WorkPlan 或重复创建 `request_human_decision`。业务决策工具使用顺序执行，避免同一批次重复建卡。`context` hook 每个模型请求注入当前真实等待项，无 Goal 的普通房间委托也受门禁约束；不能只依赖 `execution.status=waiting_human` 或提示词。

审批可能持续数分钟甚至跨页面。一直挂住 pi tool execution、WebSocket 和 HTTP 链路会造成：

- backend 重启后上下文不可恢复；
- manager Session 长时间保持 streaming，其他消息无法正常进入；
- 浏览器断开就容易误取消；
- timeout 含义变得混乱。

因此 Parent manager Run 可以在展示审批卡后结束；真正悬挂的是 Child Agent Run。审批完成后，通过 pi 已支持的：

```ts
session.sendCustomMessage(
  {
    customType: "pudding:task_result",
    content: workerResult,
    display: true,
    details: { delegationId, worker, status: "completed" }
  },
  { triggerTurn: true, deliverAs: "followUp" }
)
```

让 manager 在同一 pi Session 中继续汇总。`AgentSession.sendCustomMessage` 的 `triggerTurn` 已由当前依赖版本支持。

### 6.4 PuddingTeams API

```text
GET  /api/interactions?sessionId=...
GET  /api/interactions/{id}
POST /api/interactions/{id}/responses
POST /api/interactions/{id}/cancel
```

列表接口只返回 `pending` / `responding` 的当前待处理项；单条接口保留 `approved`、`rejected`、`expired`、`failed` 的历史状态供旧卡片对账。本地生命周期绑定 Worker 在 Backend 重启后由启动对账封存 `server_restart` 失败 Receipt，并将原待审批 Interaction 置为 `expired`；停放 Workspace 返回后也不能重新批准它。列表不再把过期审批呈现为待办，单条查询仍可解释终态。

审批 API 使用明确的公开字段白名单。单条查询的 `delegation` 只供卡片读取 `goalId` 与 `workerStarted`；内部 `sessionHandle`、`runHandle`、执行 cwd、任务选项、Receipt、provider state 引用和幂等键都不返回。`policySummary`、`decision`、`application` 只保留卡片实际使用的状态字段。提交响应只返回状态、Delegation/Interaction ID 与等待标记；Worker 任意 meta 和私有句柄不能随成功或失败结果透出，错误正文先做凭证遮盖。

solo Manager 在待审批期间切换 Workspace 时，先取消关联委托并将 Interaction 置为 `expired`，再停放原 Session；返回原 Workspace 不恢复旧 Worker Run。旧项目未激活时提交该审批返回 HTTP 409 `interaction_context_inactive`，返回原项目后再次提交返回 HTTP 409 `not_pending`，均不能启动 Worker 续跑。

提交示例：

```json
{
  "revision": 1,
  "request_id": "ui-submit-uuid",
  "responses": [
    {"requestId":"perm-1","action":"approve","scope":"once"}
  ]
}
```

服务端必须校验：

- Interaction 属于当前窗口/manager Session；
- `revision` 未过期；
- responses 恰好覆盖当前 request 集合；
- 选定 scope 在该 request 的 options 内；
- 同一 `request_id` 重试返回相同结果；
- 非 pending 状态拒绝二次消费。

### 6.5 UI 与 Session 历史

历史中只存安全投影：

```json
{
  "customType": "pudding:interaction_required",
  "display": true,
  "details": {
    "interactionId": "int_local_x",
    "delegationId": "dlg_x",
    "worker": "puddingclaw",
    "status": "pending",
    "revision": 1,
    "requests": [{"requestId":"perm-1","command":"...","risk":"moderate"}]
  }
}
```

continuation token、Worker access token、原始 provider payload 不写进 pi JSONL、不发给 LLM、不下发浏览器。

历史卡状态由 `GET /api/interactions/{id}` 对账；pending/approved/rejected/expired/completed 都可重放。状态变化只追加事件，不修改旧 JSONL：`pudding:interaction_resolved(approved)` 在审批受理、Delegation 已恢复 `running` 时立即写入，前端按 `delegationId`（`interactionId` 兜底）同时折叠审批卡并校正原委派任务卡；最终边界稍后由 `pudding:task_result` 或下一轮 `pudding:interaction_required` 表达。

审批卡提交前必须从单条接口取得当前 `revision`、`kind` 和完整 `requests`；首渲染的 JSONL 快照仅供定位，不能作为提交依据。新一轮 `needs_input` 即使复用原 Interaction ID，也以新 revision 的 requestId、选项和问题正文替换旧轮，并清空旧轮的本地选择。一次 Interaction 可有多个 request，前端按 requestId 分别选择 scope 或回答，再一次性提交恰好覆盖当前集合的 responses；对账未完成时不开放提交按钮。

question/confirmation 的选项原文同时作为 `scope`（由 Broker 按对应 request 的 options 校验）和 Worker 可读的 `value`；自由文本只传 `value`。不能把任意文本当作已校验的选项。

**两边同步（respond 扇出）**：审批提交后的恢复态与后续边界都会经 `managerSender` 同时写入 manager session 和 delegation 所属窗口的 active session（单聊镜像）；两者相同则只发一次，镜像目标解析失败不影响主流程。消息形态：

- approved/admitted：立即写 `interaction_resolved(approved)`，原委派卡进入执行中；
- completed：随后只写 `task_result(completed, 含 artifacts/usage)`；
- rejected：`interaction_resolved(rejected)` + `task_result(cancelled)`；
- failed：随后只写 `task_result(failed, 含 errorCode)`；
- needs_input（又一轮提问）：先有本轮 `interaction_resolved(approved)`，随后写 `interaction_required(pending, 同 interactionId, revision+1)`。

manager session 的 `task_result` 用 `triggerTurn: true, deliverAs: "followUp"` 唤醒 manager 汇总；单聊窗口全部 `triggerTurn: false`，仅展示。由此用户只待在 solo 窗口也能完成全部审批并看到所有 worker 结果。前端审批卡对多轮 needs_input 以对账后的 live revision 重新进入 pending，不会误显"已批准"。

**回写（2026-08-12 Direct 直派与派活即镜像）**：

- **Direct 直派**：direct 窗口不再经 pi manager relay。`POST /api/sessions/:id/messages` 命中 direct 窗口时由 `agent-runtime/direct-dispatch.ts` 消费——依次写入 `pudding:user_message`（用户气泡）与 `pudding:task_assign(status:"running")` 两张 custom message，后台直接 `AgentInvoker.delegate` 给窗口唯一成员（`managerSessionId` = 该窗口自己的 active session，`mode: "continue"`，stale handle 由 Runtime 透明回退新会话）；completed/failed/conflict 补 `pudding:task_result` 卡，needs_input 审批卡沿用 invoker 原有投影直接落回本窗口。窗口的 pi session 永不触发 manager 回合，仅作消息流容器（首条消息前经 `PiSessionStore.ensureSessionFile` 复制 SDK 首刷，避免延迟落盘丢历史）。
- **扇出不唤醒 direct**：respond 扇出时若 manager session 的属主窗口是 direct，`task_result` 降级为 `triggerTurn: false`（无 manager 可唤醒）。
- **派活即镜像**：solo 派活在 `scoped.delegate` 阻塞前先写 `pudding:task_assign(status:"running")` 到 worker direct 窗口（`announceToWindow`），`syncToWindow` 只在 outcome 后补结果/审批卡。前端把 manager 路由的 solo 镜像展示为「Manager 委派任务气泡 → worker 执行行 → worker 最终结果」；直接在 worker 单聊输入的 direct-dispatch 仍是普通用户气泡 → worker 执行行，不引入 manager 语义。同 `taskId` 的结果/审批卡到达后 running 行落定收起，任务气泡保留为对话上下文。结果卡继续携带 `delegationId`/`sessionHandle`/`processView:true`，因此委托完成后单聊仍可查看执行过程。
- **manager 运行态持久化（2026-08-21，2026-08-26 补充一致性约束）**：group 不另画一张指派卡，solo manager 来源窗口也仍以原始 delegate 工具卡为唯一展示。Runtime 创建不可变 Delegation 后，通过 `PiSessionStore.appendCustomMessageProjection` 直接向正在执行中的 manager Session 追加 `display:false` 的 `pudding:task_assign(from:"group"|"solo")`，随后可再富化 `sessionHandle`。它不等待 manager 空闲、不进入模型队列；直写时必须在同一写入点同时更新持久化事实源 `SessionManager` 与驻留 `AgentSession.messages` 展示镜像，再经 store 订阅通道广播同一隐藏 `message_start`。只写 SessionManager + 广播会造成当前页面正常、切换会话后 `/messages` 从旧内存镜像回放却丢失入口的分叉。前端按 `taskId` 把 `delegationId`/`sessionHandle`/`processView` 折回原工具卡，因此「执行过程」与「终止任务」入口在最终 toolResult 前不会消失；历史回放与实时 `message_update/message_end` 合并都必须保留已有工具运行元数据。委托参数 `session:"new"` 在 solo 与 group 都映射为 Runtime `run`，只有缺省/`"continue"` 才续接窗口内 worker binding。

## 7. PuddingTeams 数据模型

### 7.1 房间 Session 保存每个 Worker 的独立 Session 绑定

```ts
interface WorkerBinding {
  sessionHandle?: string;
  /** 该 Worker Session 的实际执行窗口。 */
  targetWindowId: string;
  /** 缺省表示未选择显式项目。 */
  workspaceId?: string;
  /** 产生该 handle 时冻结的运行目录。 */
  cwdSnapshot: string;
  /** 产生该 handle 时的 Agent/Connector 配置修订。 */
  agentRevision: number;
  updatedAt: string;
}

interface WindowConfig {
  // 外层 key 是本 Window 拥有的 room/manager Session id；内层 key 是 agentId。
  workerBindings?: Record<string, Record<string, WorkerBinding>>;
  workspaceId?: string;
  cwdSnapshot: string;
}
```

实际落点是 `<PUDDINGTEAMS_HOME>/state/windows.json`。`workerBindings` 不是 Worker Session 内容，只是 PuddingTeams 保存的“这个房间 Session 下次 `continue` 应把哪个不透明 handle 交回哪个 Worker”的指针；Worker 自己的 Session 历史仍由对应 Connector 后端负责（本地 pi 例外，落在平台 `sessions/workers/`）。新建房间 Session 创建空桶，切换会话只切换当前桶，删除会话同时删除对应桶。

写入链路必须按当前实现理解：Driver 的边界事件先让 Runtime 更新 `DelegationRecord.sessionHandle`，Runtime 随 outcome 返回同一个已更新的 `DelegationRecord` 内存对象；`AgentInvoker` 再调用 `TeamsStore.rememberWorkerSession()` 更新 `windows.json`。这不是先写 `delegations.json`、然后把它当数据库重新读取并复制：

```text
Driver boundary event.sessionHandle
  → Runtime 更新 DelegationRecord.sessionHandle
     ├─> state/delegations.json：保留“这一次 Delegation 用了哪个 handle”
     └─> RuntimeOutcome.delegation（同一次结果的内存对象）
           → AgentInvoker.rememberSession()
           → TeamsStore.rememberWorkerSession()
           → manager Session 属主 Window
              .workerBindings[managerSessionId][agentId]
              保存“这次房间会话下次续接用哪个 handle”
```

因此同一房间 Session 内同一 Worker 若先后产生 `D1 → S1`、`D2 → S2`：`delegations.json` 中 D1 仍保留 S1、D2 保留 S2，`windows.json.workerBindings[managerSessionId][worker]` 更新为 S2。另一个房间 Session 对同一 Worker 可独立保存 S3，互不覆盖。下一次 `continue` 由 `AgentInvoker.sessionHandleFor()` 按 `managerSessionId` 读取，而不是扫描 Delegation 历史。

Pi Worker 的历史回放还以 Delegation 创建时的 `driverId` 和 `workerSessionDir` 为准：`workerSessionDir=null` 表示平台默认目录，显式路径则与该 Run 一起封存。后来修改 Agent 的 `sessionDir` 或更换 Connector 只影响新 Run，不改变旧委托的历史视图或查找目录；冷重启后同样按旧委托快照读取。单次消息端点仍按 Delegation 时间边界裁剪共享 Pi Session。

Worker direct 页的“执行过程”内联入口也按当前 Session 的历史委托判断：当前 Connector 是 Pi 时照常显示；改绑为非 Pi 后，只要该 Session 的索引仍有已启动的 Pi `view=session` 委托，入口继续可用并按旧委托快照回放。没有 Pi 历史的非 Pi 房间不显示该入口；执行详情仍可独立查看其他 Connector 的 Timeline。

旧 Run 落定得很晚时不能覆盖已经删除或切换后的房间 Session binding。`rememberWorkerSession()` 写入前必须重新读取权威窗口和 Agent 配置，并同时确认：

- `managerSessionId` 仍属于一个现存 Window；
- 目标窗口仍是该 binding 的 `targetWindowId`，且关系合法（普通房间只能自身执行；solo 只能路由到对应 Worker 的 direct）；
- Delegation 的 `workspaceId` 仍等于窗口当前 `workspaceId`；
- Delegation 的 `cwdSnapshot` 仍等于窗口当前实际 cwd；
- Delegation 的 `agentRevision` 仍等于当前 Agent/Connector 修订。

删除房间 Session/Window 与 `delegate/respond/cancel` 共用 Window lifecycle gate：先在闸门内拒绝新委托并取消所有 `running/waiting_input` Run，再删除 Session JSONL、Goal 状态与对应 binding。通用 Session 删除接口不得删除 Window 的最后一个 Session，避免底层 JSONL 已消失但 `activeSession` 仍悬空。

读取 `continue` handle 时重复执行同样三项校验；任一不匹配就把旧 handle 视为不可续接。pending Interaction 不放进 `windows.json`，因为它属于某一条尚未结束的 Run，而不是窗口的跨 Run Session 绑定。源码入口：`agent-runtime/invoker.ts` 的 `sessionHandleFor()/rememberSession()` 与 `store/teams.ts` 的 `rememberWorkerSession()`。

#### 7.2.1 Delegation 因果链的落盘与消费

`state/delegations.json` 是可变的 Delegation 索引/账本，不是 Session JSONL，也不是逐事件 timeline。当前文件版本是 v2，外层固定为 `{version:2, delegations}`，并直接拒绝旧版；`delegations` 以 `DelegationRecord.id` 为 key。新委托先以 `admitted` 落盘，平台完成 Workspace admission 后才进入 `running`；收到终态边界后先原子写入 `pendingTerminal` recovery journal，再收集 Workspace change-set/Artifact，最后通过 CAS 封存 `ExecutionReceipt` 并清除 journal。这样进程在跨 Store 收集中断时，重启只补封存同一结果，不把已完成 Worker 改成 server_restart 或重新运行。Receipt 一旦存在，契约、句柄、终态、结果、scope/change-set 与验证绑定字段不可再改。`DelegationStore` 在进程内串行化变更，每次写入先生成临时文件再 `rename`，因此它是原子快照，不应按 append-only 日志解析。

> 2026-09-06 scope 接力边界：`parentDelegationId` 仅表示因果关系。只有同 Session、Workspace/cwd、Goal/epoch、Plan、WorkItem 与策略的串行 attempts 可隐式复用 active scope，且全部既有 owner 必须确知终态。跨 WorkItem、无 WorkItem 普通委托不继承；隐式 parent scope 已 released/promoted 则新建，fenced/缺失则阻塞。显式 scope 请求必须满足同样所有权约束且仍 active，失败不降级为新 scope。请求单独记录在 `requestedWorkspaceExecutionScopeId`，Teams 准入恢复重新验证；只有 begin 成功后才能写 `workspaceExecutionScopeId` 并进入 capture/release。Coordinator 另外校验 scope 状态、Workspace、Goal/epoch、mode/root、owner token 与 Lease。
>
> 独占租约释放依赖完整生命周期：绑定 WorkItem 的写任务终态仍保留 scope 供返修；后续独占准入遇到租约时，只有全体 owner 已封存终态 Receipt，且其权威 WorkState 显示对应 scope 已验收或 WorkItem/Goal 已取消，才幂等释放。仅 Driver 完成不能释放。普通无 WorkItem 的 exclusive Run 在终态释放自身租约；只读任务沿用终态释放。状态不明和 fenced 租约不能因此绕过。
>
> 审批后的异步失败投影保留 `blocked.error`；Manager 正文包含 errorCode、delegationId、executionState、workerStarted、waitingInput 及只读准入评估，避免把准入后启动失败解释为等待审批。同步和异步 completed 正文均可附平台 change-set 的 handoff 路径观测（基于 executionRoot，最多 20 条），明确是相对基线的累计变更，含删除可能，不等价于存在性/内容验收或隔离变更已合入。原始 Worker result 保持不变。


`parentDelegationId` 是子记录指向上游记录的因果边：缺省 parent 的 `request` 是根任务，`followup` 沿 parent 继续追问，带 parent 的 `request` 表示上游结果触发了新的有返回义务的子任务。每条记录只有一个 parent，但一个 parent 可以被多条记录引用，所以所谓“链”实际可以是分叉的因果树/森林。写入前必须验证 parent 已存在且 `managerSessionId` 与子委托一致；读取时按 `managerSessionId` 取候选集，由子向父追溯上游，或建立 `parentId -> children[]` 反向索引展示分支。这只表示 `Worker A -> manager -> Worker B` 的因果，不允许 worker 绕过 manager 直连。可直接用于教程的完整 D1-D4 示例与三份事实源的关系见 `docs/2026-08-14-会话记录格式与Harness消费.md` §2.2。

**连续对话的三轨边界（规范）**：Manager 调用的是按 Worker 注册的 `agent_<worker>__delegate`，其标准输入以 `task` 承载本轮真实消息，以 `parentDelegationId/handoffKind` 记录当前 Manager Session 内的因果，以 `session:"new"|"continue"` 决定是否使用当前房间 Session 的 Worker binding。`parentDelegationId` 既不从父记录选择 `sessionHandle`，也不自动把父 `result.content`、会话、附件或 timeline 注入下游 Worker；跨 Worker 的实际材料必须由 Manager 写入 `task` 或引用 Workspace/Artifact 路径。缺省 `session` 为 `continue`，PuddingTeams 校验并指定 `workerBindings[managerSessionId][agentId].sessionHandle` 后调用 Driver；即使 Driver每轮 spawn 新 CLI 进程，resume 后仍可属于同一逻辑 Worker Session。parent 与 binding 都只允许同一 `managerSessionId`：新建房间 Session 不继承旧 Worker 上下文，切回旧房间 Session 才恢复它自己的 handle。完整参数、推断规则、Goal 额外字段和示例见 `docs/2026-08-14-会话记录格式与Harness消费.md` §2.2.1。

#### 7.2.2 超长 worker 结果（已实现）

**实现边界**：Runtime 的 `DelegationRecord.result` 保留 Driver 产生的完整 `NormalizedResult`；pi worker 的原始回答另在 worker Session JSONL，而 spawn timeline 只是有界活动投影，不是全文备份。`LargeWorkerResultStore` 负责 completed worker 正文的无损外置与分页回读。此处的“完整”以 Driver 已归一化的 result 为边界；如果 Connector 自身已对上游内容做有界投影，PuddingTeams 无法凭空恢复上游原文。

**处理方式**：超过阈值时把 worker 原文按 delegation 落到 `<PUDDINGTEAMS_HOME>/state/large-worker-results/<delegationId>.txt`（平台受控、0600、原子写），manager toolResult 只投影 head/tail 预览、`originalChars/estimatedTokens`、`offloaded:true`、`delegationId` 与精确回读说明。平台核心工具 `read_delegation_result({delegationId, offset, limit})` 分页读取全文，并校验调用者当前 `managerSessionId` 拥有该 Delegation；不向模型暴露宿主真实路径，不把预览覆盖成唯一持久化结果。Artifact 仍是 worker 主动交付的用户产物，large-worker-result 只是 harness 的上下文外置层，两者不混用。

**设置归属**：像 PuddingClaw 一样放在全局“设置 -> Harness -> 上下文工程”下，子项名为“Worker 结果上下文”，落盘到 `config/product.json` 的 `harness.workerResults`。无损外置是始终生效的安全基线，不提供“改回静默硬截断”开关；可调参数为：

```json
{
  "harness": {
    "workerResults": {
      "offloadThresholdTokens": 20000,
      "previewHeadTokens": 6000,
      "previewTailTokens": 2000,
      "readChunkTokens": 8000
    }
  }
}
```

token 值为上下文保护预算，当前以 `ceil(chars/4)` 估算并记录原始字符数；`previewHeadTokens + previewTailTokens` 必须小于 `offloadThresholdTokens`，各值由服务端施加上下界，前端校验不是安全边界。

#### 7.2.3 WorkPlan/WorkItem 是 Harness 计划层，不是新 Driver 协议（已实现）

完整契约见 `docs/2026-08-21-Manager-WorkPlan与Delegation-Timeline融合方案.md`。solo/group 的 Session Goal 已增加结构化执行面 `GoalWorkPlan/WorkItem`，没有创建脱离 Goal 的独立计划对象：

- `WorkItem.dependsOn` 是 Manager 业务任务 DAG；`Delegation.parentDelegationId + handoffKind` 仍是执行因果。二者必须分开验证和展示；
- 一个 WorkItem 可以绑定多次 Delegation，`DelegationRecord` 仅新增可选 `workPlanId/workItemId/attempt` 引用，不把计划状态复制进 Driver SPI；
- execution Delegation 只有在 `reported_completed` 且存在匹配契约的 sealed Receipt 时才生成 Submission 并把 WorkItem 推进到 `submitted`；verification Delegation 永不生成 Submission。Manager 通过 PuddingTeams core tool 明确 accept/revision/blocked，只有 accepted 解锁下游；
- 第三方 Worker 不需要适配 WorkPlan。Connector 仍只负责现有 `run/continue/respond/cancel`、`NormalizedResult` 和可选 `WorkerActivity`；提交验收、DAG、并发 revision 与 Goal 门禁都属于上层 Harness；
- WorkPlan 直接内聚到现有 `state/work-states.json` 的 Goal 聚合，与 recovery epoch、operation ledger 和 outbox 原子提交，不新增 `work-plans.json` 或 WorkItem timeline；选中一次执行后继续复用 pi Session 回放或 `state/delegation-timelines/<delegationId>.jsonl`。
- direct Session 也可有 Goal，但没有 Manager WorkPlan；统一抽屉从 `SessionWorkState` 读取 Goal/完成条件，再直接路由到该 Worker 的现有执行过程，Driver SPI 仍无新要求。

执行路径为：

```text
Manager update_work_plan
  → delegate(workItemId)
  → ScopedAgentInvoker → AgentInvoker → Runtime → Driver
  → Delegation/result 先落盘
  → GoalCommandGateway 幂等生成 Submission
  → Manager review_work_item
  → accepted 后解锁 dependsOn
```

这不会改变 §3.2.1 的边界：`AgentInvoker` 仍是委托门面，不等于 OS spawn；也不会把 WorkPlan 能力下放给 pi Extension 或 Connector 包。

### 7.3 重启语义必须诚实

第一版可做到：

- PuddingTeams 重启、PuddingClaw 未重启：从加密 InteractionStore 恢复并继续 `respond`；完成后通过 custom message 触发 manager 新 turn；
- PuddingClaw 重启：其 live `_HeadlessExecution` 丢失，PuddingTeams 将 Interaction 标记 `expired`，提示用户重新启动该任务；
- 不承诺恢复原来的 manager tool call；恢复的是业务 Delegation，随后在同一 manager Session 追加结果。

只有当 PuddingClaw 把 live execution/中断恢复做成持久化协议后，才能把第二种情况升级为真正跨进程恢复。

> 实现状态（2026-08-30，启动对账；2026-09-03 补充启动证据）：server 启动统一调用 `AgentRuntime.reconcileOrphanedRuns()`。生命周期绑定的本地 Run 可确认进程已消失，因此封存 `reported_failed/server_restart` Receipt、过期审批并通知 Manager；远端 HTTP/RPC/ACP Run 仅在 Driver 声明 `query_run` 或 `reattach_stream` 时查询/重挂原 Run。重挂先持久化为活跃的 `reconciling`，继续占用原 Run/Session 与写 scope；查询或流返回真实运行、等待输入、完成、失败或取消边界时，该上游观察同时构成 `workerStarted:true` 的启动证据，终态 Receipt 使用同一证据封存；仍在运行/等待输入时恢复对应状态。上游不可查询、返回 unknown、重挂流丢失或无边界结束时进入 `observation_lost/effect_unknown`，不伪造 failed/cancelled Receipt，并 fence 写 scope，禁止不明副作用自动重试。

> `environment_verified` 首期只接受本地 `spawn/sdk` Driver：Runtime 必须能把平台签发的 Verification Environment 直接绑定为实际 cwd 并收集 observation。HTTP/RPC/ACP 在尚无可校验环境绑定回执的协议版本中 fail closed，不能仅凭远端声称使用了某路径就签发真实环境复验结论。

> 用户控制面提供 `POST /api/delegations/:id/reconcile` 与 `POST /api/delegations/:id/takeover`。前者只调用原 Driver 的 query/reattach，不创建替代 Run；后者要求 `confirmation:"upstream_stopped"` 和人工依据，才封存人工确认的 cancelled Receipt，并显式释放 fenced scope（保留隔离 worktree，不自动提升）。

> 实现状态（2026-08-21，Goal v5 恢复）：启动收割后由 Goal 恢复协调逻辑按 `goalId` 对账 Goal 聚合、增加 recovery epoch，并通过持久 outbox 与接收端 `eventId` 去重唤醒同一 manager Session；进程运行期间 dispatcher 继续串行重试未确认事件。恢复开启新 Delegation 尝试，不把旧 D 改回 running；所有 Goal 写入口都携带 `expectedGoalId`，本地状态变更以 Goal 级 operationId 幂等，旧 Goal/旧 epoch 回调被 fence。Connector 可选接收 `idempotencyKey/operationId`，不支持时对外部副作用不承诺 exactly-once，结果不明时先人工对账。完整协议见 Goal/Timeline 融合方案 §10。

## 8. Spawn、JSONL、超时与取消

### 8.1 Spawn Runtime

把 `TeamsStore.spawnWorker()` 抽到 `agent-runtime/transport/spawn.ts`，保留现有正确行为：

- `shell: false`；
- stdout/stderr 分离；
- SIGTERM 后 5 秒 SIGKILL；
- AbortSignal 取消；
- stdin EPIPE 吞掉；
- stdout、stderr、单行长度分别限额；
- 子进程退出和协议终态分开判断。

增加：

- 逐行 JSONL decoder，保留尾部半行 buffer；
- 首个 `started/progress` 事件延迟指标；
- exactly-one-boundary 校验；
- 不把 stderr 原样送入模型，仅存 Trace 的有界诊断摘要。

### 8.2 PuddingClaw Headless JSONL（Backend 与 Driver 已接通）

CLI 非零退出、未返回 JSON 终态且 stderr 明确包含 `HTTP 5xx` 时，Driver 归类为上游 `http_error`，保留脱敏的有界诊断；不再误报 `protocol_error`。这类错误可由调用方处理，但 Driver 不据此自动重跑任务。审批受理与后续上游运行失败仍是独立状态。

Workspace 的 `filesystem_manifest` 在 Git 项目中选择已跟踪文件和未忽略的新文件，另显式纳入 `.pudding/handoff` 交付物，使忽略的 pnpm 安装目录、Electron 打包产物不再阻断基线、write-set 和验证副本；非 Git 目录保持完整文件扫描，选中范围内符号链接继续拒绝。完整边界见《2026-08-26-真实环境复验与可信验收方案》§5.3。

单 JSON 仍是兼容边界；PuddingTeams 的正式运行链路应使用 `puddingclaw agent run --jsonl`，审批续跑使用 `puddingclaw agent respond ... --jsonl`。

真正的流式进度需要 PuddingClaw Backend 提供 SSE/JSONL streaming endpoint，CLI 只是把该流转发出来；只给 CLI 增加 `--jsonl` 而后端仍同步等待，不会产生真实进度。

**2026-08-20 PuddingClaw 0.1.19 源码落地**：Backend 已把 execution 创建与 response streaming 解耦，立即输出 `run_starting`，随后转发 allowlist 内的 lifecycle、工具、可见 content、HITL 和 final content；reasoning/内部 Trace 不外送。同一 execution 支持多观察者和按 `seq` 有界重放，PuddingClaw Web 可通过 Session SSE 与 CLI 同时观察。Resume API 与 CLI `respond --jsonl` 也保持流式；本机调用协议不包含 PuddingClaw Token。

**2026-08-20 PuddingTeams 接入完成，2026-08-31 补充业务 HITL**：PuddingClaw Driver 的 `run`、`continue`、`respond` 全部使用 `--jsonl`，`progress: "stream"`；公开事件（run/preflight/outcome 生命周期、response/token/segment、tool、permission、user_input、final/done/error）都投影成 `WorkerActivity` 后写入 delegation 时间线。PuddingClaw 明确不公开 reasoning，因此 UI 不伪造思考事件。上游 CLI 当前不把 Backend `seq` 原样带到 PuddingTeams 也不影响连续性：平台始终使用自己的 delegation-local `seq`，未来拿到 `sourceSeq` 时只把它作为诊断字段保存。

同步边界仍可能出现“上游已经完成，但代理/网关先关闭连接”的情况。PuddingTeams Driver 对**运行超过 30 秒后**的 `connection_error/fetch failed` 不再立即结束委托：它使用原 `request_id` 重提同一请求，遇到 `An identical Worker Run is already in progress` 就短轮询，直到读到 PuddingClaw 的幂等终态或耗尽本 Run 的 active timeout。快速连接失败仍直接返回，避免把服务不可达误判成长任务恢复。该恢复只补“最终响应丢失”，不伪装成流式。

### 8.3 超时分三类

| 超时 | 含义 | 默认建议 |
| --- | --- | --- |
| 启动超时 | 进程未进入 started | 30 秒 |
| 活跃超时 | running 且长期无事件 | 120 秒，可按 Agent 配置 |
| Interaction TTL | 等用户审批 | 24 小时，受上游更短 TTL 限制 |

`waiting_input` 期间不计 active timeout；否则用户看审批卡几分钟就会被误杀。

## 9. Connector Extension 目录与接入边界

### 9.1 最小预置，其他接入依靠 Extension 二开

**定位（贯穿整个开发周期）**：Connector Extension 的本质是**给 pi 扩充连接其他 Agent 的能力**——每个 Connector 包都是可以发布到 pi 社区、`pi install` 可装的独立生态产物；但**完整的房间能力（manager-worker 编排、HITL 审批闭环、workspace 交接）只有 PuddingTeams 提供**。因此每个包采用"共享核心 + 双宿主入口"结构（§9.5），纯 pi 用户得到真实可用的轻量 delegation，PuddingTeams 用户得到完整 worker 接入，协议翻译核心只维护一份。

PuddingTeams 提供 Extension 安装入口、SDK、模板和编写指南，不维护一个不断膨胀的内置 Agent 列表。

**首装种子与路由材料（2026-08-28）**：`DEFAULT_TEAMS` 预置 Designer（本地 pi）、Claude Code 与 Codex 三个可见 Worker，并只携带用户明确要求的基线名称/描述；不固化开发机的 model、provider、skills、密钥或登录态。这三个种子在首次创建 `agents.json` 时落盘，后续仍以 `agents.json` 为唯一事实源，用户可在前台修改描述与责任边界。Connector manifest 本身仍不携带 Manager 路由内容。

| 内容 | 默认发行 | 定位 |
| --- | --- | --- |
| PuddingClaw Connector Extension | 安装 | 第一方可运行基线，完成 run/continue/respond/cancel |
| Codex Connector Extension | 安装 | P1 主流样本：spawn + JSONL 流式，run/continue/cancel，无 HITL |
| Claude Code Connector Extension | 安装 | P1 主流样本：spawn + stream-json 流式，run/continue/cancel，无 HITL |
| 核心 delegation 投影 | 内置 Runtime | 为每个 Agent 生成基础 Pi 委托工具，不是 Capability 包 |
| Capability Extension | 预置未绑定的 `lark-cli` 业务能力 | 用户按业务需要绑定；默认不进入任何 Agent Session |
| Generic CLI Connector 模板 | 仅开发模板 | 演示声明式 Connector，不作为万能运行时兜底 |
| Pi/Hermes/OpenClaw/Grok Build | 文档案例 | 提供协议选型与样例片段，不承诺默认实现和持续跟版 |

例如，Grok Build 的本地源码可以作为代码型 Connector 编写指南的 ACP 案例：

- Headless 支持 `-p`、`--output-format streaming-json`、`--resume`、`--continue` 和 Session ID；
- `grok agent stdio` / `serve` 提供长连接 ACP；
- ACP 生命周期覆盖 `session/new`、`session/prompt`、流式 update、permission request 和取消；
- 因此用户编写 Grok Build Connector 时应首选 ACP。Headless 只作为无交互降级路径，不用正则解析终端文案来模拟 HITL。

Pi 可以调用另一个 Pi，但必须是新的 child `AgentSession`/独立 Session 目录，而不是让同一会话重入自身。PuddingTeams 对这类委托统一执行：

- 默认不向 child Pi 注册 PuddingTeams 的团队委托工具，避免无意递归；
- 显式允许递归时，传播 `delegationDepth`，默认最大深度为 2；
- 父 Run 取消必须向所有仍在运行的 child Pi 传播；
- 每个 child 都有独立的 `sessionHandle`、`runHandle` 和事件流。

**Pi Worker 单聊内联显示（2026-09-23）**：单聊顶部提供「执行过程」开关，默认关闭，按房间在本地保存偏好。开启后，委托卡片替换为同一 child Pi 会话的思考、工具调用与回复；保留主对话的用户输入，不重复显示 child 的 user 消息。首次加载或重新开启内联显示时，主历史、委托索引及当前展示的 Worker 历史共用一个加载提示，全部加载结束后一次展示 query 和回复；失败项展示降级内容，不阻塞整段历史。展示后新增任务继续实时更新，不再隐藏整段对话。历史按委托创建时间、Receipt 封存时间和同一 worker session 的下一次委托边界切分；仅活动委托订阅实时事件。关闭后恢复原有卡片及抽屉入口。该开关只改变展示，不改变消息路由、会话落盘、审批或取消流程；其他 Connector 不提供此开关。

**执行过程可视化（2026-08-23 更新，2026-08-26 补充计时语义）**：执行过程按来源分为两种只读视图。pi worker 继续从 child `AgentSession` 实时订阅并从 pi Session JSONL 回放完整 assistant/thinking/tool 历史；当前 thinking 的计时起点必须使用 assistant message 自带的 turn `timestamp`，不得使用 React 组件挂载时间，否则关闭抽屉、切换会话或历史重对齐都会从 0 重新计时。该计时表达当前 model turn 的端到端进行时间，不等同于整个 Delegation 用时，也不能进一步区分 Provider 排队、首 token 等待和 token 生成。若 child Session 已建立但本次委托尚无 assistant/toolResult，抽屉明确显示「等待 Provider 首个模型事件」，而不是伪造 thinking 或把静止误判为 Driver 过滤。其他 Driver worker（spawn/http/rpc/acp）统一使用 delegation 活动时间线。Codex 仍走 `codex exec --json` / `codex exec resume --json`，不强制启动 `app-server`，并投影 `thread/turn/item/error` 以及 agent message、reasoning、command、file change、MCP/collab tool、web search、todo 等 item；多条 completed agent message 全部留在时间线，终态 `result.content` 只取最后一条。PuddingClaw 的 CLI JSONL 与 Headless HTTP NDJSON 把同一公开事件流送入同一个 observer，终态只采用明确的 `final_response`（旧 Backend `reply` 兜底），不拼接 token/segment。PuddingClaw Driver 在落盘前把连续 token 合并成一条 `token.batch`，保留合并文本、事件数和可用的上游 seq 范围；非 token 事件仍一对一追加，其中 `user_input_required` 与 `user_input_resolved` 分别投影为“等待业务选择”和“业务选择已提交”，保留 request/run 关联字段而不与 permission 混淆。两者统一写入 `<PUDDINGTEAMS_HOME>/state/delegation-timelines/<delegationId>.jsonl`，按本地 `seq` 追加，聊天卡片只保存最新委派状态和最终交付，不承载高频事件。单委托读接口为 `GET /api/delegations/:id/process/timeline?afterSeq=` 与 `/api/delegations/:id/process/timeline/ws?afterSeq=`；房间侧栏通过 `GET /api/rooms/:id/delegation-processes?managerSessionId=` 获取当前会话的委托索引：服务端取 manager session 拥有的委托，并合并当前房间 Session 里以 `pudding:task_assign` 明确镜像的委托，按 delegationId 去重；不能对执行窗口与 managerSessionId 做 AND 过滤，因为 solo/群聊任务实际运行在 worker direct 窗口。这样 manager 房间和对应 worker 单聊都能在同一右侧 Inspector 中看到、切换并行 worker，又不会混入该 direct 窗口其他历史会话的任务。pi 与非 pi Driver 只在详情 Router 内分流。展示层可以隐藏 token batch 与 final、done 与 runtime terminal 等重复行并使用紧凑阶段行，但不得修改事实源或跨 Delegation 合并。执行过程视图保持只读，审批与终止走独立控制面。

**委托级终止（2026-08-20，2026-08-30 修订）**：执行过程视图仍只读，但所有 running 委托卡在 Runtime 创建不可变 Delegation 后立即获得 `delegationId`，并显示「终止任务」。`POST /api/delegations/:id/cancel` 只取消该 Run，不终止 manager Session；Runtime 先持久化 `cancel_requested`，在已取得 `runHandle` 时调用 Connector 的 `cancel`，并 abort 本地 Driver 流。只有 Connector 明确确认或本地生命周期可观察到执行流退出后才封存 `cancelled` Receipt；远端无法确认时进入 `observation_lost`。取消不是静默操作：running 委托仍占用原 delegate tool call，终态确认后以相应 toolResult 自然回到 manager；waiting_input 的 tool call 已在审批边界结束，因此额外投影 `pudding:interaction_resolved` + `pudding:task_result`，并用 follow-up 唤醒 manager 完成闭环。worker 单聊只同步展示，不启动 manager 回合。外部 CLI 尚未给出 `runHandle` 时只能先终止本地子进程；是否能同步取消上游取决于其协议是否及早流出 Run handle（PuddingClaw 0.1.17 尚不满足，见 §8.2）。

2026-09-24 补充：waiting_input 取消后，上述两张消息卡必须读取 Delegation 的实际落盘状态。只有 `cancelled` 才显示「已确认取消」；若落为 `observation_lost`，卡片显示「失去观测、效果未知、先对账」，不得把 Interaction 过期误写成上游已终止。项目切换时亦遵守此约束。

**pi 瞬时限流续跑（2026-08-21）**：child AgentSession 自带短退避仍无法跨过 RPM 窗口时，LocalPiDriver 不把本次工作立即结算为失败，也不要求 Manager 用完整任务创建新 Delegation。它保留同一 `delegationId`、`sessionHandle` 与累计 usage，进入可由 AbortSignal 终止的冷却等待，随后在同一会话中要求从已有进度继续；只有有限次冷却续跑耗尽才输出 failed 边界。

### 9.2 能力必须由 Driver 声明，不能由 UI 猜测

Driver 必须通过 `capabilities()` 暴露真实能力，并通过 `probe()` 返回安装、认证、版本和 Transport 健康状态。若 `respond` 不支持：

- Runtime 不生成“可以恢复原 Run”的虚假审批动作；
- 若上游在当前模式下会阻塞交互，启动前就返回 `interaction_unsupported`，或要求用户选择明确的自动审批策略；
- 不把用户审批转换成新的 `run`/`continue`；
- UI 显示“审批外送不支持”，而不是笼统的“不可用”。

ACP/RPC/HTTP Gateway 的价值是把长期连接、权限请求和取消变成原生协议。编写 Pi、Hermes、Grok Build 等 Connector 时应直接采用其结构化协议；只有确实没有结构化协议的 Agent 才使用 spawn 适配。这是 SDK 指导原则，不等于 PuddingTeams 默认维护这些 Connector。

### 9.3 目录、安装、绑定、启用是四个不同动作

默认策略：

1. 本地、团队或用户配置的 Connector 源可在“添加 Agent”目录中展示，但目录项不是已安装代码；
2. 用户选择目录项后先查看来源、权限、支持的上游版本和工具能力，再确认安装；
3. 安装完成后创建 Agent 实例并填写配置；只有显式启用后才进入 roster 和调度候选；
4. `probe()` 检测到本机 CLI 不代表自动启用，更不能自动读取或迁移第三方凭证；
5. 升级已有安装时，现有 PuddingClaw 配置直接重建为第一方 Connector binding，不做数据迁移（决策 20）；默认不新增其他 Agent；
6. 禁用后保留配置和历史绑定，但拒绝新委托；已经运行或等待审批的 Run 由用户选择“继续保留”或“取消”，不能静默杀死；
   新发起 direct/group、跨项目打开另一个房间、Manager `create_group_window` 和自动建 direct 都要在房间存储写入队列内复核 Agent 仍启用；先复核再创建 Session/窗口，停用不能借旧 direct 去重命中继续发起。已有房间历史仍可回读。此处只保证同进程 Agent Registry 与房间创建的队列顺序，不等同于 Session 文件和窗口文件的跨文件持久事务。
   新 Session 创建成功但窗口写入在 rename 前明确失败时，建房调用方删除该 Session；rename 后目录同步失败意味着窗口可能已引用它，必须保留 Session、封锁继续写入、重启回读，不将模糊结果提示为可直接重试。清理也失败则返回恢复错误。为覆盖进程强制终止，创建初始房间 Session 前先在 `room-creation-journal.json` 持久预约其随机 ID；启动在开放路由前按窗口归属恢复，仅删除账本指向且无归属的 Session，清理失败则拒绝启动。该机制不扫描或删除其他流程的无窗口 Session；真实 Pi SDK JSONL 与当前发行 bundle 的两侧进程中断回读已验证，npm 包从零安装与真实目录同步故障仍需独立验证。
7. 同一个 Connector 可以创建多个 Agent 实例，例如两个 Codex 实例使用不同工作目录、模型策略或账号；
8. 卸载 Connector 前必须确认没有启用 Agent 和 active/waiting Run；历史保留，但对应 Agent 进入 `connector_missing`，不能静默回退到 Generic CLI。
9. 删除 Agent 只接受已停用且没有正在准入、运行、等待输入或取消收尾 Run 的身份；启用状态或活动 Run 均返回 409，后者附 `runs[].executionState` 等定位信息。先停用以阻断新委托，再处理已有 Run，最后重新检查删除。删除冲突不能被前端当作普通失败后自动关闭确认框。

删除先原子写入 `agents.json.retiredAgentIds` 与移除身份，再清理独立 CredentialsStore。若身份已删除但凭证清理失败，`DELETE` 返回 202，明确告知删除已生效、清理待重试；UI 从列表移除该 Agent 并提示部分结果，不能把它说成删除失败而诱导再次删除。下次 `TeamsStore.init()` 根据持久退役 ID 批量清理孤儿凭证，失败则启动报错，避免把仍需处理的清理问题隐去。

### 9.4 Connector Extension 如何降低上游维护成本

维护成本不会凭空消失，但可以从核心仓库解耦并自动暴露风险：

- Connector manifest 声明 `supportedUpstreamVersions` 和 `versionProbe`；
- `probe()` 同时返回 Connector 版本和真实 CLI/服务版本；
- 上游版本超出已验证范围时状态变为 `untested` 或 `incompatible`，不静默假设兼容；
- 每个 Connector 独立版本、独立发布、可固定版本或选择自动更新；
- Connector 作者维护针对上游 CLI 的契约 fixture/集成测试，不阻塞 PuddingTeams 核心发布；
- 社区或用户可维护自己的 Connector，PuddingTeams 只保证 Driver SPI 的兼容周期。

版本策略建议：Driver SPI 使用独立 `apiVersion`，至少跨一个 PuddingTeams 大版本保持兼容。Connector manifest 同时声明：

```json
{
  "kind": "connector",
  "engines": { "puddingteams": ">=1.0 <2" },
  "connector": {
    "id": "grok-build",
    "apiVersion": "1",
    "supportedUpstreamVersions": ">=0.9 <1.1"
  }
}
```

### 9.5 双宿主包：一个包，pi 与 PuddingTeams 两种激活路径

Connector/Capability 包统一为 **pi 兼容的 npm/git 包**，发布到 pi 社区，`pi install <source>` 可装。包内是"共享核心 + 两个薄适配层"：

```text
pi-connector-openclaw/
├── package.json            # pi.extensions 声明 pi 入口；puddingteams 字段承载 §10 manifest
├── pi/
│   └── index.ts            # default export (pi: ExtensionAPI) => void：注册 delegate 工具，pi 当 manager 派活
├── driver/
│   └── index.ts            # createDriver 命名导出：接 Driver SPI（PWCP 事件、probe、HITL、多实例）
└── core/                   # 共享核心：spawn/ACP/JSONL 翻译、session 连续性、取消、错误归一化，不依赖任何宿主
```

两条激活路径互不相干，同一个 `pi install` 动作行为不同：

| | 纯 pi | PuddingTeams |
| --- | --- | --- |
| 加载器 | pi resource-loader（找 `pi.extensions` 入口） | ExtensionRegistry（读 manifest + `createDriver`） |
| 激活内容 | pi 内注册 delegate 工具，pi 自己当 manager | agent 进 roster，平台自动投影 `agent_<id>__delegate`，走房间体系 |
| HITL | 降级为 pi 自身权限提示或不支持 | 完整审批闭环（web 审批卡、409、拒绝也是合法响应） |
| 配置/密钥 | 包自管（如环境变量） | connector binding API + secretRefs |
| 生命周期 | 跟随 pi 会话 | server 托管：重启诚实、取消传播、多实例 |

#### 9.5.1 纯 pi 门面的具体样式与路径

双宿主包里的 `pi/index.ts` 与 §3.2.2 的 PuddingTeams manager inline Extension 都使用 `ExtensionAPI.registerTool()`，但不是同一条运行链。以当前 Codex Connector 为例，纯 pi 门面可以缩略为：

```ts
// extensions/connectors/codex/pi/index.ts
export default function codexConnector(pi: ExtensionAPI) {
  pi.registerTool({
    name: "codex_delegate",
    parameters: Type.Object({ task: Type.String(), cwd: Type.Optional(Type.String()) }),
    async execute(_toolCallId, params, signal, onUpdate, ctx) {
      const parser = new JsonlLineParser();
      const reducer = new CodexEventReducer();
      const result = await spawnWorker({
        command: "codex",
        args: ["exec", "--json", "-C", params.cwd ?? ctx.cwd, params.task],
        cwd: params.cwd ?? ctx.cwd,
        signal,
        onStdout: chunk => {
          for (const raw of parser.push(chunk)) {
            const progress = reducer.push(raw);
            if (progress) onUpdate?.({ content: [{ type: "text", text: progress }], details: undefined });
          }
        }
      });
      for (const raw of parser.flush()) reducer.push(raw);
      const boundary = reducer.boundary("codex");
      return {
        content: [{ type: "text", text: projectBoundary(boundary, result) }],
        details: { threadId: reducer.threadId, usage: reducer.usage, exitCode: result.exitCode }
      };
    }
  });
}
```

纯 pi 激活路径为：

```text
pi package loader 读取 package.json 的 pi.extensions
  → import pi/index.ts 的 default factory
  → factory 注册 codex_delegate
  → pi manager 产生 toolCall
  → pi 直接调用门面的 execute()
  → 门面经共享 spawn/归一化核心执行 Codex CLI
  → 返回 AgentToolResult
  → pi 包装并持久化 ToolResultMessage
```

这条纯 pi 路径**不会经过** PuddingTeams 的 roster、`ScopedAgentInvoker`、`AgentInvoker`、`AgentRuntime`、`state/delegations.json`、delegation timeline 或 Web HITL。相同包被 PuddingTeams 激活时则不加载 `pi/` 门面来承担房间委托：ExtensionRegistry 读取 `puddingteams.entry`，从 `driver/index.ts` 取得 Driver；manager 工具由平台的 §3.2.2 inline Extension 统一生成，再走 `ScopedAgentInvoker → AgentInvoker → Runtime → Driver`。这正是“pi 入口是轻量门面、Driver SPI 是 PuddingTeams Connector 本体”的含义。

工程约定：

- **下载安装复用 pi**：PuddingTeams 的安装渠道接受与 `pi install` 相同的 npm/git source，内部复用 pi SDK 的 `DefaultPackageManager`（固定目录、版本固定、update 检查现成），不重复造下载器；
- **manifest 折叠**：`pudding-extension.json` 的 §10 字段折叠进 `package.json` 的 `puddingteams` 字段，一个包一份元数据（过渡期两者都接受）；
- **加载器已兼容**：`ExtensionRegistry` 加载模块时同时识别 `mod.default`（pi 工厂）、`mod.createDriver`、`mod.driver`（extension-registry.ts），双导出包无需改加载逻辑；
- **目录管理**：仓库根 `extensions/` 是所有插件的唯一落点——`extensions/connectors/<agent>/` 放 Connector 包，`extensions/capabilities/<name>/` 放 Capability 包，`extensions/shared/` 放共享核心模板；`extensions/README.md` 维护全量索引（每个包的 kind、宿主入口、状态一目了然）；
- **Capability 双端绑定**：pinned Manager 与本地 Pi Worker 都能独立绑定 Pi-compatible Capability；每个 binding 拥有独立配置与状态目录，不能因为 Manager 是内置 Agent 就只给 Manager 开入口。托管 CLI 默认使用 binding 隔离状态；只有用户选择本机 CLI/本机认证模式时，才显式沿用该机器已有的共享登录态；
- pi 入口是包的**门面**，Driver SPI 才是 Connector 的**本体**；不允许把 Driver 伪装成 pi extension（ExtensionAPI 没有 spawn、server 持久化和审批路由能力）；
- **Connector 的上游可以是另一个 pi**：本地 child `AgentSession`（独立 Session 目录，约束见 §9.1 的 Pi 调 Pi 铁律）或远程 pi（RPC transport）；**以本地 pi 为主**，作为 Phase 6 的第一个参考样例——协议双边可控，能跑满 Driver SPI 全语义（run/continue/cancel/stream 进度），给外部 Agent 的 Connector 当标杆；
- **pi 只是 worker 中的一种，产品上不特殊化**：pi connector 走与其他 Connector 完全相同的"目录 → 创建 Agent 实例 → 配置 → 启用"流程；"新增不同的 pi"即创建多个实例。Connector schema 只保留 `model`、`thinkingLevel`、`sessionDir` 等“怎样运行”的参数；Agent 追加运行指令、skills、prompt templates、Workspace context 开关统一属于 `AgentConfig.piResources`，pinned manager 与 Pi worker 共用同一模型和“提示词与资源”表单。`manager.prompt` 与 Pi Connector `config.systemPrompt` 已直接删除，不兼容双写。这里的运行指令只给当前 Agent 自己，不是 Manager 路由描述；cwd 由 Window/Delegation 快照传入；child session 不注册团队委托工具，递归默认关闭。Driver 能力诚实声明仍为 `operations: [run, continue, cancel]`、`interactionKinds: []`、`transport: "sdk"`。

### 10.0 控制面信息架构（2026-08-15）

主导航顺序（2026-09-30）：工作台 → 对话 → 通讯录 → 知识库 → 稍后读 → 智能体 → 扩展 → 日历。通讯录、知识库、稍后读紧邻对话排列；仅调整位置，不改路由、选中态或未读数量。

通讯录提供列表与人脉图谱两个视图，图谱通过 `/contacts?view=graph&vault=` 进入，人物详情继续使用 `person` 查询参数。`GET /api/contacts/graph` 复用 ContactsProjection 的当前可访问、已采纳 Wiki 快照与类型解析，只将 `type: person` 投影为节点，只将人物页中解析成功、目标也是人物的直接 wikilink/Markdown 笔记链接投影为边。明确关系保留类型和方向；普通人物链接只表示引用，不推测朋友、同事等关系。重复同向同类型链接去重，自链、代码示例、断链、歧义链接以及非人物节点排除，不通过同公司、项目、往来或共同话题推断人物关系。

图谱沿用人物稳定身份与库隔离、快照 revision、读取后授权复核，不新建联系人或图谱数据库。支持搜索、圈层筛选、缩放、画布平移、节点拖拽、邻居高亮与点击档案；点击关系显示源人物笔记及对应引用行。公司、项目、话题、圈层和往来记录可留在人物档案中，图谱不渲染这些节点。首版每次最多展示 300 位匹配人物，只返回两端均可见的边，同时明确返回真实 total/matched/truncated；无关系的人物保留孤立节点。

前端将两个概念拆成独立一级入口：`/agents` 管理 Manager/Worker 角色与运行状态，`/extensions` 管理 Skills、MCP 与插件。Agent 配置页只保留该 Agent 自身的概览、模型与运行、提示词、模板以及该 Agent 的 MCP Server 勾选；Skills 不再作为隐藏在 Manager/Worker 编辑页中的二级入口。服务端 Extension SPI 的真实目录仍是 Connector/Capability，故“插件”页展示两者；MCP 页维护平台全局 Server Catalog，而不是把 MCP Server 伪装成 Connector/Capability 包。

**设置页滚动边界（2026-09-30）**：`/settings` 的外层面板和分类布局约束在剩余视口高度内，顶部应用导航、设置标题与分类导航不随内容滚动；仅 `.settings-content` 纵向滚动，并阻止滚轮向外层传递。切换设置分类或 Harness 子页签时将内容滚动复位到顶部，不重挂载已经访问过的 Harness 草稿面板。窄屏分类导航仍只在自己的横向页签行内滚动。

Skills 资源库首次读取失败须显示错误和重试，不保持无限加载；已有成功读取的列表在后续失败时只作为上次结果展示。导入或手动刷新后，早于该次刷新发起的列表请求即使晚返回，也不得覆盖更新后的列表、数量或错误状态；离开页面后未完成的请求也不得回写。Skill 预览的 Agent 启用范围读取失败须单独报错，不能展示“尚未被任何 Agent 启用”；顶部数量读取失败也不能伪装为零。

### 10.0.1 平台托管 MCP Server Catalog（2026-09-02）

MCP 的事实模型分成两层：

- **Server 全集**：`<PUDDINGTEAMS_HOME>/config/mcp-servers.json` 保存 Server id、显示名和 adapter definition；前端 `/extensions?tab=mcp` 提供添加、查看和删除。Server 被任一 Agent 引用时删除返回 409，必须先取消勾选；
- **前端归类**：MCP 页只展示 Server 本身；无 Server 时把“添加 Server”作为居中的唯一主动作。默认运行依赖 `pi-mcp-adapter` 作为内置项展示在“插件”列表，不在 MCP 页重复解释平台实现；
- **读取状态**：Catalog 读取失败时显示错误与重试，不把故障呈现为零个 Server；曾成功读取的列表可作为上次结果留在页内，同时标明它可能已过期，重新确认前不得依据旧条目添加、编辑或删除。顶部 MCP 数量在读取失败时显示错误状态，不把失败写成 0；新增、编辑或删除后发起的回读必须覆盖较早的在途列表请求，旧响应不能把界面或数量改回写入前；
- **Agent 选择**：pinned Manager 与 `connectorId=pi` 的 Worker 在独立“MCP”分区勾选，并在 `AgentConfig.mcpServerIds` 中保存白名单；缺省为空，不因全局目录存在就自动获得任何 MCP 工具。非 Pi Connector 不支持这条进程内注入路径，前端与 API 都明确拒绝。选择页必须同时确认 Server Catalog 与 Agent 当前选择；任一读取失败显示错误与原位重试，不能永久显示加载中或提交旧草稿。`PUT /api/agents/:name/mcp` 整体替换白名单时必须携带 `GET` 返回的 `extensionRevision` 作为 `expectedRevision`；服务端在持久化串行区再次核对，旧版提交返回 409 且不改白名单。冲突后前端保留本地意图，但只有用户明确读取最新选择并重新勾选后才能再次保存；保存成功到新 revision 回读前暂停编辑，避免迟到结果覆盖较新的选择；
- **运行依赖**：`pi-mcp-adapter` 是 Server 的默认基础依赖，随 PuddingTeams server 发行并默认启用，不要求用户另装一个 Extension 包。创建 Manager/Pi Worker `AgentSession` 时，平台按当前 Agent 白名单构造 inline Extension，只传入选中 Server 的显式 config；发行 runtime 同时携带 adapter 的 worker/App Bridge/keyring helper 资源，CLI 依赖声明系统 keyring 原生模块，避免 OAuth 只在源码态可用；
- **禁止旁路发现**：adapter 的 `hostConfigDiscovery` 固定为 `off`，Pi Resource Loader 的全局 Extension 发现结果同时剔除外部 `pi-mcp-adapter`，防止 `~/.pi` 或其他宿主配置绕过平台 Server Catalog、Agent 白名单和 Workspace 边界；
- **密钥隔离**：Server definition 禁止明文 `bearerToken`、OAuth client secret 以及常见认证 header/env 值。明文仅在写入 API 的 `secrets` 字段出现，随后以 AES-256-GCM 存入 `<PUDDINGTEAMS_HOME>/secrets/mcp/`；列表 API 只返回 key 名，运行时才解析 `${KEY}` 并注入选中 Server；
- **目录与密钥提交**（2026-09-26）：MCP 创建、更新、删除若改变密钥，先在 `secrets/mcp/binding-transaction.json` 持久记录加密凭据的前后镜像，再写凭据，最后持久写入 Catalog 的唯一事务标记；目录文件使用 `0600` 临时文件、文件同步、原子重命名和目录同步。服务冷启动在开放路由前按 Catalog 标记恢复前镜像或后镜像，再清除记录；记录未清时目录读取和 Worker 定义解析拒绝继续。目录重命名后同步失败时当前进程返回 503 并保留待对账记录。此协议处理本机进程中断，不把真实断电或外部 pi CLI 共写纳入已验证范围；
- **Pi Worker 执行快照**（2026-09-26）：新委托在 Agent 接单门禁内解析所选 MCP Server 定义及密钥，并把结果固定在该 Run 的 Driver 装配中。Delegation 落盘后即使 Worker 延迟启动，也不重新从 Catalog 读取新版本；后续新 Run 才读取更新后的定义。审批续跑在同一 Agent 接单门禁内核对原 `runConfigRevision`、抓取 MCP 快照并再次核对修订；变更先提交则旧 Run 拒绝恢复，快照先取得则续跑沿用当时版本。无 MCP 选择的 Pi Worker 不因无关 Catalog 故障阻断接单。普通 Catalog/密钥读取错误在接单点冻结本轮空 MCP 集合并记服务端诊断，Worker 可继续执行；若错误表明 Catalog 提交状态未知，必须先冷启动对账，不接纳该 Run。源码层真实 Pi SDK 与本地 MCP 的受控交错已验证持久接单后延迟启动仍用旧密钥，下一条 Run 用新密钥；发行安装态已验证顺序两轮，尚未验证安装态同一延迟交错；
- **会话生效**：增删、更新 Server 或修改 Agent 勾选都会递增相关 Agent 的 `extensionRevision` 并触发会话 dirty/reload；已有 Worker binding 也会因修订不一致而重建，避免陈旧 Server 继续驻留。
- **Manager 装配交错**（2026-09-26）：Manager 新建与从 JSONL 重开会话时，装配可能跨越 MCP Catalog/Agent 配置变更；尚未进入活跃会话表的实例无法收到 dirty 标记。`PiSessionStore` 在配置同步入口递增装配代次，创建与重开记录起始代次；若装配结束时代次已变，释放候选实例并重读当前配置，最多尝试四次，持续变化则明确失败并允许重试。配置同步发生在实例进入活跃表后时，仍由原有 dirty/reload 路径处理。该门禁仅覆盖本进程内经过配置同步入口的写入，不声称外部 pi CLI 共写或跨进程装配原子性。
- **Sessionless HTTP 兼容**：Streamable HTTP 握手未下发 `Mcp-Session-Id` 时，运行时保持 POST-only，不建立无法路由的独立 GET SSE 流；有 Session 的 Server 仍正常建立 GET 通知流。该约束避免 DeepWiki 等无 Session 端点接受 GET 后阻塞后续 `tools/list`/tool call。
- **逐请求动态签名**：Catalog 允许可信 HTTP Server 声明 `requestHeadersCommand`；adapter 每次请求把精确 `method`/`url`/`bodyBase64` 通过 stdin 交给签名程序，并将其 stdout JSON 合并为 Header。平台保存层校验 command/args/env/timeout，对敏感 env 仍强制 `${KEY}` + 独立密钥区，运行时只解析当前 Agent 选中 Server 的引用。
- **启动装配策略**：当前阶段每个 Agent 勾选的 Server 与工具数量有限，受管 MCP 在 Pi Session 启动时把非 `keep-alive` lifecycle 统一提升为 `eager`，完成 `initialize`/`tools/list`；adapter 使用 `directTools=true` 把发现的 MCP tools 直接注册为一等 Pi tools。单一 `mcp` 网关仍保留作状态、搜索、认证与重连入口。后续工具规模增长后再引入按 Server/tool 子集控制，不提前增加配置复杂度。
- **故障降级边界**：MCP 始终是 Agent 的可选工具面，不能成为 Manager/Worker 启动依赖。单个 Server 的连接、认证或 `tools/list` 失败由 adapter 按 Server 隔离并保留重连诊断；平台给请求设置 10 秒默认上限。Catalog/密钥解析或 adapter 同步装载异常也在 inline Extension 边界被截断，Agent 继续启动，只是本轮没有对应 MCP tools。

当前 adapter 同时使用直接 MCP tools 与单一 `mcp` 代理工具（`directTools=true`、`scriptMode=false`），并开启输出保护；MCP Server 进程/远端工具以当前本地用户和 Agent Workspace 权限运行。平台现阶段没有为每次 MCP tool call 再增加独立的 PuddingTeams HITL 审批，用户添加 Server 与对 Agent 勾选就是当前授权边界。

```ts
  secretRefs?: Record<string, string>;
  activation?: "always" | "searchable";
  versionPin?: string;
}

interface ExtensionManifestBase {
  id: string;
  publisher: string;
  displayName: string;
  version: string;
  source: "builtin" | "trusted" | "external";
  engines: { puddingteams: string };
  permissions?: ExtensionPermission[];
}

interface ConnectorExtensionManifest extends ExtensionManifestBase {
  kind: "connector";
  connector: ConnectorContribution;
}

interface CapabilityExtensionManifest extends ExtensionManifestBase {
  kind: "capability";
  capability: CapabilityContribution;
}

type PuddingTeamsExtensionManifest = ConnectorExtensionManifest | CapabilityExtensionManifest;
```

### 10.0 Agent 元数据、运行指令与提示词可见性

PuddingTeams 的核心提示词管理事实源是 `docs/2026-08-11-PuddingTeams核心提示词管理方案.md`。本节固定通用 Agent/Extension 边界：

- `description` 保留通用字段名，不改成 `routingSummary`；它既用于普通 UI 展示，也作为 manager 的简短路由摘要；
- `responsibility` 是给 manager 的结构化责任、停止与升级边界；`description + responsibility + capabilities + delegate tool` 共同构成 Manager 路由卡。平台在每个 manager 回合开始前，按 Window 候选集合把最新路由卡投影进 pi manager system prompt：Solo=全部启用 Worker，Group=全部已启用成员（2026-08-12 起 Direct 无 manager 回合，用户消息直派唯一 Worker，不再注入 roster/relay，见 §6 回写）；
- Pi Agent 的 `piResources.systemPrompt` 是**当前 Agent 自己读取的追加运行指令**，不是给 manager 选择该 Worker 的描述。产品文案称“Agent/Worker 运行指令”，不再称含糊的“Agent Profile”；
- Worker 运行指令不得进入 manager roster；Manager 路由卡也不作为 Worker 的 system prompt 重复注入；
- Window collaboration 只给窗口 manager。Solo 无协作段；Direct 无 manager 回合、无协作段（2026-08-12 起直派 worker）；Group 才允许用户编辑群聊协作提示词；
- `~/.pi/agent/AGENTS.md` 是 pi global context，显式 Workspace 的 `AGENTS.md` / `CLAUDE.md` 是项目 context。两者正文都不由 Agent 配置页编辑；Workspace 开关只控制后者；
- PuddingTeams 不覆盖 pi 内嵌默认 system prompt。Agent 运行指令与 Group collaboration 必须经 append 槽注入并保留 pi 原生 `APPEND_SYSTEM.md`，不得用 `systemPromptOverride` 把它们变成替代内嵌 base 的 `customPrompt`。

这是两条控制面，不因产品以 pi manager 为中心就合并：Pi manager 路由控制面回答“选谁、如何协作”，Pi Agent 运行控制面回答“被选中后如何执行”。本提示词装配建立在 Pi ResourceLoader 上；非 Pi Worker 由各自 Connector/Driver 管理私有运行提示，平台不得把 Pi 资源模型自动套给它们。

Connector Extension 和 Capability Extension 是两种独立包，禁止一个 manifest 同时贡献两类能力：

- Connector 的发布、升级和兼容性围绕上游 CLI/服务协议；
- Capability 的发布、升级和兼容性围绕 Pi 工具 Schema 与业务工作流；
- 二者混包会迫使“上游 CLI 参数变更”和“业务工具改版”同步升级，重新制造耦合；
- 若同一作者同时提供两类扩展，应发布两个独立 package，并用文档声明推荐组合。

它们的执行位置也不同：

- Connector Extension 安装到服务端 Connector Extension Host，向动态 DriverRegistry 注册 Driver；它不进入 Pi ResourceLoader，也不直接向模型注册工具；
- Capability Extension 的工具 contribution 通过具名 `extensionFactories` 投影给 Pi manager；可选 Session runtime contribution 还能给**绑定目标自身**（pinned Manager 或本地 Pi Worker）的 Pi Session 追加 Skill 路径与 bash 子进程环境。它不注册 Driver，也不在宿主进程里直接执行业务 CLI/HTTP/ACP；CLI 只能由目标 Pi Session 的 bash 工具在其 cwd/env 中调用；
- 二者的唯一业务连接点是 Runtime 创建的 `ScopedAgentInvoker`。

不要在通用配置中写 `runArgs`、`resumeArgs` 并让用户手工拼模板。命令映射是 Driver 代码的一部分；用户只配 executable、transport 和安全设置。

`probe()` 的结构化结果至少包含：

```ts
interface ProbeResult {
  extensionInstalled: boolean;
  extensionVersion?: string;
  detected: boolean;
  configured: boolean;
  authenticated: boolean | "unknown";
  enabled: boolean;
  compatibility: "supported" | "untested" | "incompatible" | "unknown";
  upstreamVersion?: string;
  version?: string;
  transport?: "spawn" | "http" | "rpc" | "acp" | "sdk";
  capabilities: DriverCapabilities;
  issues: Array<{ code: string; message: string; fixAction?: string }>;
}
```

智能体管理按产品角色分层展示：pinned `manager` 独立成组；「Worker（内置）」仅包含绑定本地 pi（`connectorId: "pi"` 且目录 `origin: "builtin"`）的角色，包括 Designer、Wiki 管理员和用户创建的 Pi Worker。PuddingClaw 的 spawn / HTTP Worker 均归入「Worker（第三方）」；其连接插件随平台提供不代表 Worker 是平台内置角色。Codex、Claude Code、其他外部 Connector 及没有 Connector 标签的 legacy 命令接入同样归入第三方。PuddingClaw 不再首装预置，已有实例保留原配置并按此规则展示；此分类不改变 Worker 的启停、连接或运行配置。

前端“Agent 接入”页面按 Connector 目录项展示 `扩展未安装 / CLI 未检测 / 待认证 / 已配置但未启用 / 已启用 / 版本未经验证 / 不兼容`，并展示真实支持的四项操作。安装扩展、安装上游 CLI、登录、创建 Agent 和启用是不同动作，不合并成一个含糊按钮。

### 10.1 Agent 管理页

每个 Worker 的管理抽屉/详情页固定分为三项；pinned Manager 没有 Connector 接入区，但同样提供 Extensions 配置：

1. **基础接入**：当前 Connector Extension、Transport、服务/CLI 状态、认证、工作目录、权限策略、四操作能力和 probe 状态；
2. **Extensions**：只管理 Capability Extensions（零到多个），展示版本、来源、工具、激活方式和配置，并提供“添加 Extension”；
3. **运行状态**：Session/Run、待审批 Interaction、最近错误和审计事件。

Connector 只在“基础接入”中安装、选择或更换；Manager 与 Worker 的“Extensions”页签都可添加 Capability，只展示与当前 `connectorId` 兼容的条目（pinned Manager 的宿主按 `pi` 判断）。前端根据 manifest Schema 生成普通配置表单，根据 secret schema 单独写入 CredentialsStore 并只保存 `secretRefs`。CredentialsStore 的环境变量名在同一 Agent 内共享：清空某绑定的 key 时移除该绑定的引用，若另一绑定仍引用则保留密文；绑定接口不得用不同值悄然覆盖共享 key，Agent 通用密钥接口不得在仍被绑定引用时删除该 key。提交密钥时，空字符串表示清除该 key；无效或未声明的 key、非布尔的启用状态、非对象配置或非字符串版本锁定必须先被拒绝，不能在校验失败前改动已有凭证。Capability 绑定清空最后一个 key 后也必须持久化空引用集合，不能让旧引用继续显示为已配置。保存前展示来源、权限、版本范围和将注册的工具。

Connector manifest 的 `secretSchema.required` 是启用门槛：允许先创建停用 Worker 再填写凭证；立即启用的创建、从停用转为启用、启用状态下更换 Connector 或清空必填 key，都必须确认绑定有对应引用且 CredentialsStore 中有实际值。通用 Agent 更新入口同样不能绕过。创建弹窗在“创建后立即启用”时先提示缺少的必填项，服务端仍独立校验；无凭证的停用草稿可以保留以便后续配置。

绑定重配若需同时撤销旧 key、写入新 key，须在一次 CredentialsStore 写入中提交两类改动；新密钥写入失败不能先删旧密钥，再把原绑定留在 Registry。更换不同 Connector 时即使新旧 manifest 声明同名 key，也不继承旧引用或旧值；新 Connector 只能使用本次明确提交的值。Connector/Capability 绑定 API 在任何密文写入前须拒绝非字符串 `versionPin` 和非对象 `secrets`（包括 `null`、数组、字符串），不能静默忽略错误字段。CredentialsStore 与 Agent Registry 是两个独立文件：绑定 API 现先写 `0600` 加密前后快照事务记录，再写 CredentialsStore，最后以同次 `agents.json` 写入的 `credentialCommitIds[agentName]` 标记提交；启动时根据标记回滚或前滚，并在完成恢复前不开启派发。同 Agent 的绑定/密钥/完整配置写入口串行，运行时与探测读取密钥后复查 Agent 修订。Capability 删除绑定时按其他 Connector/Capability 引用计算最后引用，未被引用的密文与绑定删除进入同一恢复事务；停用绑定仍保留密文以便重新启用。事务记录清理失败返回 202 并封锁后续配置写入，提交后响应边界异常通过标记回读后返回 202。真实进程崩溃矩阵已由子进程强制退出验证，浏览器部分结果提示仍须验收。

运行时给 Connector/Capability 的环境变量密钥集合按当前 Connector 与**已启用** Capability 绑定的 `secretRefs` 过滤，包含 Driver 执行、健康探测和动态配置选项；停用后保留的密文不能继续注入。多个已启用绑定共用同一 key 时保留该 key 的运行时可用性。无 Connector 的旧版 command Worker 仍使用 Agent 级通用密钥。Capability 删除和 Connector 更换时，失去最后绑定引用的 key 随绑定提交回收；其他绑定仍引用的共享 key 保留密文。该规则同时由存储回收与运行时引用过滤保障。

Capability 绑定卡的“配置”与“探测结果”是互斥状态：打开配置或修改草稿时清除旧探测结果，发起新探测时收起配置并先移除旧结果；配置保存成功后必须收起编辑区、清空密钥草稿并给出成功反馈，保存失败则保留草稿与编辑区并展示错误，不能让按钮表现为无响应。

Agent 总开关优先级高于所有 Capability Extension 开关：Agent 禁用时全部不可调用，但保留配置；Agent 再启用时恢复之前的选择。Capability 单独禁用只撤销该绑定提供的工具，不影响 Connector 和其他 Capability。Connector 不提供普通开关；更换或卸载属于基础接入变更，必须先处理 Session/Run 兼容性。

Connector Worker 卡片提供“复制 Worker”；legacy command Worker 因命令参数可能内嵌凭证，不提供复制。复制是创建新实例，不是共享身份。服务端必须在同一注册表写锁内生成新的不可变 Agent id，并为每个 Capability 绑定生成新的 binding id；`agents.json.retiredAgentIds` 持久保存所有已删除 id，任何创建路径均不得复用，避免历史 Window/binding、迟到 Run 或孤儿 CredentialsStore 记录重新绑定到新实例。复制 Connector/Capability 普通配置、角色描述、责任边界与 Pi 资源设置，但不复制 CredentialsStore 凭证及其 `secretRefs`、任意 `env`、上传头像、Capability 运行状态、Session handle、Window 成员关系或运行记录。副本默认停用，创建后进入配置页，由用户补齐/确认凭证并显式启用后才进入 manager roster。pinned Manager 不支持复制。

建议 API：

```text
GET    /api/extensions/catalog
POST   /api/extensions/install
POST   /api/extensions/:extensionId/update
DELETE /api/extensions/:extensionId
GET    /api/agents/:agentId/connector
PUT    /api/agents/:agentId/connector
POST   /api/agents/:agentId/duplicate
GET    /api/agents/:agentId/extensions
POST   /api/agents/:agentId/extensions
PATCH  /api/agents/:agentId/extensions/:bindingId

```

Connector/Capability 写操作增加 Agent 的 `extensionRevision`。响应返回受影响的 manager Session 数量和 `active_now / reload_pending`，让界面如实显示“已撤权，运行时将在当前回合结束后刷新”。

`PUT /api/agents/:name/connector` 整份替换 Connector 绑定时必须携带表单读取时的 `extensionRevision` 作为 `expectedRevision`；缺失/非法版本返回 400，旧版本在任何凭据事务前返回 409 `binding_conflict`。实际 Store 串行提交再次核对同一客户端版本，避免请求通过路由预检后被其他配置写入抢先。冲突不得覆盖较新的 Connector 配置、`secretRefs` 或密文；前端保留表单和密钥输入，暂停重复提交，要求用户核对并明确读取最新配置。新建 Worker 随后的首次凭据配置使用创建响应中的 revision。

`GET /api/extensions/catalog` 必须支持 `kind=connector|capability`，前端不得把两类结果混在同一个选择器中。

扩展总览可以同时陈列两类独立包，但必须分别读取 Connector 与 Capability 目录。一侧读取失败时保留另一侧已确认结果，并明确标记目录不完整；失败侧的上次结果可供查看，重新加载完整成功前不得依据未确认目录执行安装、更新、卸载或引导绑定。较早的目录响应不能覆盖较新的重新加载结果。首次两侧都失败时显示错误与重试，不显示伪空目录。

### 10.2 基础 Extension 与专属 Extension

每个已绑定 Connector 的 Agent 由平台生成基础 `agent-delegation` Pi Extension，只注册稳定委托能力，并从 Connector 暴露的 Driver capabilities 决定允许哪些操作。它是运行时投影，不是第二份安装包；用户通过 Agent 总开关整体禁用。

专属 Extension 才承载业务语义。例如：

- PuddingClaw 可绑定“智能问数”“产品配置分析”“知识库编译”；
- 代码类 Agent 可由用户绑定自建的“代码审查”“CI 修复”“发布流程”；
- Hermes/Pi 可绑定各自擅长的研究或自动化工具。

这些 Capability Extension 可以定义不同参数和提示规则，但执行远端/子 Agent 时必须调用 `ScopedAgentInvoker`。这样更新 Connector、Transport、CLI 版本或恢复机制时，不需要重写业务 Capability；同一个 Capability 也可以复用于多个兼容 Connector。

### 10.3 两级 Connector 实现模型

为了让用户自己接入简单 CLI，又不要求所有人编写高权限 Node 扩展，提供两级模型：

1. **声明式 Connector**：manifest 声明 executable 探测、四操作的参数构造、stdin framing、JSON/JSONL 解码和能力矩阵；实际 spawn、超时、取消、网络及 secret 注入全部由核心 Transport Broker 执行。适合常见一次性/Session CLI；
2. **代码型 Connector**：用于 ACP、RPC、WebSocket、复杂 HITL 和自定义恢复协议。代码运行在隔离 Connector Extension Host，通过受限 RPC 使用 Transport Broker，不直接进入 PuddingTeams server 进程。

> 实现状态（P2-c，2026-08）：第 1 级已落地——manifest 的 `connector.declarative` 声明由核心 `DeclarativeDriver`（`apps/server/src/agent-runtime/declarative-driver.ts`）直接执行（Transport Broker 的独立形态仍是 Phase 6）；`connector.declarative` 与顶层 `entry` 互斥，并且当前校验为唯一 `transport:"spawn"`，不能仅靠 manifest 虚标 HTTP。HTTP/RPC 等传输必须使用代码型 Driver。样例包：`extensions/connectors/echo`（纯 manifest，无 entry、无 pi 门面）。

用户接入流程：

```text
puddingteams extension init --type connector|capability
  -> 生成 manifest、声明式模板或代码 Host 模板、契约 fixture
puddingteams extension validate <path>
  -> 校验 schema、权限、版本探测和 PWCP 事件
puddingteams extension install <path|package>
  -> 展示权限并安装到本地扩展目录
Agent 管理页 -> 选择该 Connector -> 配置 -> probe -> 启用
```

> 实现状态（P2-d，2026-09）：`extension init` / `extension validate` 已落地（`apps/server/bin/puddingteams.mjs` 引导 tsx 跑 `src/cli/extension-cli.ts`）。init 支持 `--type connector [--declarative]` 与 `--type capability`，模板在 `extensions/shared/templates/`。validate 与安装流程共用 `readManifestFromDir` 做 manifest 校验，并静态检查 entry 路径和声明式包的 `{packageDir}` 引用文件；**不会 import 待校验代码，因此不证明代码导出或运行能力**。普通模式的用户复制包若含代码 entry，在隔离 Host 尚未落地前拒绝安装、更新和冷启动激活；开发者模式可显式承担进程内执行风险。manifest id 与 version 限为安全包路径段，拒绝目录穿越。`extension install` 子命令留待后续。

Connector Extension Host 只能获得 manifest 声明并获用户批准的能力，例如特定 executable 的 spawn、特定域名网络访问、工作区访问和命名 secret reference。核心仍持有 CredentialsStore；能由 Transport Broker 代填的 secret 不把明文交给 Connector Host。

### 10.4 Extension 作者指南与模板

默认发行不靠大量预置扩展制造“开箱即用”的假象，而是把二开体验做成产品能力。至少交付以下文档和模板：

```text
docs/extensions/
├─ README.md                         # 两类 Extension 的选择与生命周期
├─ connector-extension.md            # Driver SPI、PWCP、Session/HITL/cancel
├─ connector-declarative-schema.md   # 简单 CLI 声明式接入
├─ connector-code-host.md            # ACP/RPC/HTTP 代码型接入与权限
├─ capability-extension.md           # Pi registerTool、参数、guidelines、结果投影
├─ security-and-permissions.md        # Extension Host、secretRefs、供应链风险
├─ compatibility-and-testing.md      # engine/upstream 版本、fixture、validate
└─ migration.md                      # API version 升级规则

extensions/examples/
├─ connector-declarative-echo/
└─ connector-acp-reference/
```

两套 `init` 模板必须生成不同入口和测试：

- Connector 模板生成 manifest、probe、capabilities、run/continue/respond/cancel mapper 和 PWCP fixture；
- Capability 模板生成 Pi Extension factory、`registerTool()`、配置 Schema、ScopedAgentInvoker mock 和工具快照测试；
- `validate` 必须拒绝 Connector manifest 中出现 Pi tool contribution，也拒绝 Capability manifest 请求 Driver/Transport contribution。

第一版预装为四个第一方 Connector（PuddingClaw、本地 pi、Codex、Claude Code）与一个未绑定 Capability：`lark-cli` 业务能力。它进入 catalog 但不自动绑定，因此默认不进入任何 Agent Session，并验证双宿主包、Manager/Pi Worker 双端 Session 资源注入与 CLI 自管认证闭环。纯开发用的 Capability 样例不进入预装目录，模板闭环由 `extension init --type capability` 的临时测试包验证。

`lark-cli` Capability 不重写飞书 API，也不依赖第三方再封装包。CLI 探测与安装必须解耦：binding probe 只查找本机 `PATH` 或平台共享目录中的官方 CLI，并以短超时读取版本及 `auth status --json --verify`；未命中立即返回 `cli_not_installed`，绝不在 probe、页面加载或保存绑定时调用 npm。缺少 CLI 时，插件详情、连接状态卡和 binding probe 的连续流程会展示“安装飞书 CLI”确认弹窗；只有用户确认后，Capability 的显式连接动作才通过 npm 把官方 `@larksuite/cli@latest` 安装到 `<PUDDINGTEAMS_HOME>/secrets/capabilities/lark-cli/shared/official-cli/`，完成后自动重新探测。实际 Session 装配使用本机或这个共享 CLI；本机版本按六小时新鲜度通过官方 `lark-cli update --json --skills-layout separate` 同步，并以 CLI 为唯一事实源调用 `lark-cli skills list/read`，把二进制内嵌、天然同版本的 `lark-*` Skill 文本资源导出到 binding 缓存。自动认证模式在使用本机 CLI 时沿用本机认证目录，在平台安装 CLI 时使用 `<PUDDINGTEAMS_HOME>/secrets/capabilities/<extension>/<agent>/<binding>/auth/`。运行时通过每个 Session 的自定义 bash `spawnHook` 合成 PATH 与 `LARKSUITE_CLI_CONFIG_DIR`，不修改进程全局环境；probe 只回传中文化的 CLI 来源、版本、用户名/状态摘要和必要登录命令，不回传 CLI 路径、token 或原始认证输出。官方同步失败时保留当前可用版本并形成诊断，不以第三方固定版本回退。

扩展总览增加“连接状态”页签，数据来自 `GET /api/extensions/connections`。Capability 可选实现 `listConnections(ctx)` 贡献一个或多个只读状态，宿主统一补充 Extension 身份并聚合；单个插件探测异常只形成该连接的失败状态，不拖垮整个列表。状态投影只允许包含系统名称、连接状态、CLI/客户端版本、用户可读账号名、身份类型、摘要、检查时间，以及当前状态下可执行的声明式动作，禁止返回 token、secret、认证目录、CLI 绝对路径或可复用的上游用户 ID。动作通过 `POST /api/extensions/:extensionId/connections/:connectionId/actions/:actionId` 显式执行；宿主会在执行前重新验证该动作仍由当前状态声明，防止旧页面绕过状态闸门。`lark-cli` 的只读探测只执行可用 CLI 的 `--version` 与 `auth status --json --verify`；安装是单独的 `install-cli` 动作，不会因打开页面、保存绑定或点击探测而触发。后续其他系统沿同一贡献与动作契约扩展。

连接页再次检查失败时，可保留带原检查时间的上次成功结果供用户核对，但必须标明检查失败并禁用基于旧状态的动作；重新检查成功后才能恢复动作。前端以请求序号丢弃晚到的旧探测结果，显式动作开始时也使先前在途探测失效。首次检查失败不能展示伪空列表。

Pi Extension 的 TUI `renderCall/renderResult` 不会自动成为 PuddingTeams Web UI。第一版 Web 端继续渲染统一 Tool/Interaction 事件；若以后支持 Extension 自定义 Web 卡片，必须通过受控的 renderer registry 和声明式 payload，不能让 Extension 向浏览器注入任意组件代码。

运行时有两层门控：Extension 只把已启用且属于当前 Window 的 Agent 暴露给 manager；`AgentInvoker.delegate()` 再次检查启用状态和成员关系，防止旧 Session 的陈旧 tool schema 越权调用。

PuddingClaw 的 agent-specific tool 不应暴露 `model`：当前 CLI 明确拒绝 `model/analytics_model_id`，由 Backend 根据 question 自动路由。`team_task.model` 随 `team_task` 一并移除；任何 Driver 收到 `model` 字段都应拒绝并给出明确提示。

**configSchema 的前端渲染约定**（JSON Schema 子集 + 平台注解）：`type: string/number/boolean` 映射为输入框/数字框/勾选；`enum`（string 数组）渲染为下拉，非必填且没有 schema 默认值时带「不设置」清除项（回写时删 key）；有字符串 `default` 时，下拉直接展示对应默认项。扩展可用 `"x-puddingteams-enum-labels": { "stored-value": "展示文案" }` 为字符串枚举提供本地化显示名，前端只替换展示文案，配置仍保存原始枚举值。字段可用 `"x-puddingteams-visible-when": { "field": "mode", "equals": "custom" }` 声明只在同级控制字段取指定值时显示；控制下拉切换后，已不再可见的关联配置会从回写值中移除，避免隐藏配置继续生效。`format: "model"` 是平台模型目录注解——渲染为可用模型下拉（数据源 `/api/models`，含自定义 provider 的模型），pi connector 的 `model` 字段使用此方式。字段可用 `"x-puddingteams-transports": ["spawn"]` 或 `["http"]` 声明仅对哪些 transport 显示，值必须是该 Connector `supportedTransports` 的子集；transport 本身不放进 provider config，而由 `AgentConnectorBinding.transport` 独立保存。若选项只能由上游 Agent 按当前账号/版本动态给出，Connector 可声明 `"x-puddingteams-options": "driver"`，并实现可选的 `AgentDriver.listConfigOptions(field, ctx)`；Web 经 `GET /api/agents/:name/connector/config-options/:field` 获取选项，宿主只负责注入该 binding 的 cwd/env/secrets 和转发结果，不猜测 provider 模型。

配置页从 Connector Catalog 读取运行参数 schema 时，以 `extensionId + connectorId` 精确定位条目。Catalog 请求失败意味着 schema 未确认，页面显示错误与原位重试，不自动把当前 Connector 当作内置 Pi schema 继续编辑；Catalog 成功但内置 Pi 条目没有声明 schema 时才用内置 Pi 字段回退。智能体列表读取失败与“目标 Agent 不存在”也须分开，前者提供原位重试。

Connector 绑定分区的 Catalog、执行能力声明和 Capability 绑定分区的 Catalog、绑定快照是不同的读取事实。任一请求失败时显示对应错误及重试，不让加载指示无限持续；Catalog 未确认前不把已知绑定标成“插件未安装”，执行能力未确认前不展示旧的只读保证。绑定快照失败时隐藏旧卡片的操作入口，等新快照和 revision 回读成功再开放；删除、启停与配置修改的最终授权仍由服务端版本门禁裁决。

多 transport 的代码型 Connector 必须提供 `createDriver(config, transport)` 工厂；静态 `driver` 只允许单 transport。宿主在 probe、能力查询和委托入口核对实例 `DriverCapabilities.transport` 与 Worker binding，防止声明 HTTP 却静默落到 spawn。

Codex connector 的 `model` 使用 Driver 动态选项：每次打开已有 Agent 的配置页时，短暂启动 `codex app-server --stdio`，初始化后分页调用 `model/list`（`includeHidden: false`），读取当前 Codex 账号实际可选模型与默认标记，完成后立即关闭进程。这里只借用 app-server 做控制面发现；任务数据面仍是 `codex exec --json` / `codex exec resume --json` 的 spawn + JSONL，不切换为常驻 app-server。发现失败时前端降级为可手输文本框，避免配置页因 CLI 版本、登录状态或网络问题不可用；留空表示继续使用 Codex 默认模型。

Claude Code connector 同样声明 Driver 动态选项，但不能照搬 Codex 协议：Claude Code 只有交互式 `/model` picker 与 `--model <alias|name>`，没有稳定的无头 model-list 命令。Driver 因此读取用户配置目录（`CLAUDE_CONFIG_DIR` 或 `~/.claude/settings.json`）与当前 workspace 的 `.claude/settings.json` / `.claude/settings.local.json`，按 Claude Code 的合并语义收集 `availableModels`、`modelOverrides`、`model` 和 `env` 中的 `ANTHROPIC_MODEL` / `ANTHROPIC_DEFAULT_*_MODEL` / `ANTHROPIC_CUSTOM_MODEL_OPTION`；未声明 allowlist 时补充官方稳定别名 `best`、`sonnet`、`opus`、`haiku`、`sonnet[1m]`、`opus[1m]`、`opusplan`。若显式 allowlist 为空，下拉只保留“不设置”，从而继续使用账号层默认模型。最终账号套餐、企业策略和 provider 可用性仍由真正执行的 Claude Code 校验，PuddingTeams 不伪造账号级目录，也不直接读取 Claude OAuth 凭证。

### 10.5.1 平台联网能力（2026-09-30）

- `DEFAULT_TEAMS` 不再种子创建 `puddingclaw` / `puddingclaw-http` Worker。PuddingClaw Connector 保持可手工接入；已有用户配置与会话不由启动过程静默删除。
- 联网由 Teams 独立提供，配置入口 `/settings?section=network`，不是委托 PuddingClaw Worker，也不是按 Agent 绑定密钥。共享核心位于 `extensions/capabilities/web-research/core`，无宿主依赖；独立 Pi 门面只使用 ExtensionAPI。
- 每个智能体配置页新增「联网」分区，搜索/网页阅读开关修改后自动保存，独立于普通页面配置草稿；复用同一份平台授权，密钥仍只在设置页管理。浏览器内通知、同源跨页通知与重新聚焦读取保证入口同步；有未保存平台草稿时提示冲突并保留草稿，不自动覆盖。
- 设置 → 联网拆为「搜索供应商」「Worker 授权」标签；Worker 授权通过标签进入，标题右侧只保留保存操作，不重复放置同目标快捷入口。Tavily/DeepSeek/Grok 在同一面板切换，路由与代理默认折叠。网页阅读对应 `fetch_url`，与联网搜索 `web_search` 分开授权。
- 搜索供应商标签和详情共用品牌标记，本地静态 SVG 随 web 导出，不请求第三方图床；Tavily 使用官方深浅素材，DeepSeek 使用官网鲸鱼标记，Grok 使用开源品牌图标库的 Grok 标记（素材来源见 `apps/web/public/brands/README.md`）。图标仅标识服务，不改变授权、凭据、测试或路由行为。
- 搜索供应商有密钥（已配置或当前输入）时允许「测试并保存」：`POST /api/settings/web-research/:provider/test-and-save` 先校验草稿和原 revision，使用当前输入构建临时配置执行真实搜索，通过后才在一次串行事务内保存本页配置、密钥、授权与测试指纹。失败不落盘并保留草稿；测试期间有外部修改或模型页凭据变化时拒绝提交，不能用旧测试认可新配置。测试期间冻结配置写入，不自动开启供应商、平台总开关或 Worker 授权。仅输入密钥不能再因 dirty 状态被禁用测试。
- Manager Solo 与所有本地 Pi Worker（包括知识库管理 Wiki）均支持配置，**默认均不授权**；停用的智能体也可预先配置，启用后才能使用。配置中的 `grants[agentId] = {search, fetch}` 分别与平台总开关取交集，目标必须仍是启用的支持目标才装载对应工具。每次执行检查当前目标身份、启用状态及授权，撤权立即阻断已有工具引用；Worker 续聊以有效工具授权指纹判定驻留会话是否重建，该指纹经 Pi 工厂透传；Manager 保存授权后标记空闲重建。密钥统一管理，不按 Worker 复制。
- Wiki 的 `wiki_curator` 交互路径由宿主专用 `webResearchToolsFor` 注入授权的联网工具，与知识工具共同形成明确白名单；不装载 MCP、通用 Extension/Capability、原生文件或执行工具。独立后台候选编译执行器继续只消费冻结来源及操作契约，不从交互联网授权自动扩大工具面。Direct/Group 的 Manager relay 保持原边界。Codex / Claude / PuddingClaw 等第三方 Driver 继续使用自身上游工具，授权页仅将第三方列入不可平台注入的目标。
- `GET|PUT /api/settings/web-research`、`POST /api/settings/web-research/:provider/test` 提供配置和显式探测；`PUT /api/settings/web-research/workers/:agentId` 只合并该目标授权并使用同一 revision 检测，不能覆盖供应商、凭据或其他目标。配置、Worker 授权、密钥、测试指纹按单一加密快照落在 `<PUDDINGTEAMS_HOME>/secrets/web-research/credentials.json`；GET 只投影配置、目标清单、授权、是否配置、凭据来源和测试状态。PUT 用 revision 冲突检测。DeepSeek/Grok 可沿用平台模型页凭据，独立联网密钥优先；模型凭据变化会使旧测试失效。
- 搜索供应商为 Tavily、DeepSeek、Grok；国内/全球顺序独立，自动回退最多三家；明确指定供应商不自动换家。X、图片/视频搜索仅 Grok 支持。多源核验仅在平台开关和请求同时启用时发生，未凑齐两家则报告未完成。
- DeepSeek 沿用 PuddingClaw 的 Responses `web_search` / 强制 tool_choice 方式和 `deepseek-v4-flash`，针对实测推理截断把输出预算提高为 8192。成功条件必须包含真实搜索事件和来源；不得把模型正文生成的链接当联网成功。是否可用以当前账户真实测试为准。
- `fetch_url` 逐跳验证公开 HTTP(S) 标准端口与 DNS，连接固定到校验后的 IP；响应 5 MiB / 正文 50,000 字符上限，截断明确投影。支持显式 HTTP(S) CONNECT 代理；198.18/15 Fake-IP 只允许域名 HTTPS，未配置代理时可由本地 TUN 直连，固定已校验地址并明确开启证书/原域名校验，不再强制要求额外代理。有代理时 Fake-IP CONNECT 原域名，普通公网仍 CONNECT 已校验 IP。网页材料只作为不可信来源，不作为用户指令。
- DeepSeek 检索使用 `reasoning.effort="none"`，避免默认长推理吞尽输出预算。2026-09-30 核对 [官方 Responses 兼容性文档](https://api-docs.deepseek.com/guides/responses_api/)，`web_search` 当前被忽略；保留 PuddingClaw 请求格式，但必须取得真实搜索记录及引用才能判定 ready。TLS/API 通、普通模型回答或文中 URL 都不能升级为联网通过。

### 10.6 模型与 Provider 控制面（借鉴 PuddingClaw，映射到 pi 原生分层）

平台的模型层就是 pi 的 `ModelRuntime`（builtin 目录 + `models.json` 自定义层 + `auth.json` 凭证层），不自建 registry。借鉴 PuddingClaw `ProviderRegistry` 的交互模式，落点：**模型目录层用 pi 原生文件（与 pi CLI 共享），凭证层用平台自有文件（与 pi CLI 解耦）**——provider key 只写入 `<PUDDINGTEAMS_HOME>/secrets/auth.json`（`configureSharedModelRuntime({ authPath })`，`pi-bridge/model-runtime.ts`），不读写 pi 全局 `~/.pi/agent/auth.json`；所有 `createAgentSession` 调用显式传入共享 `modelRuntime`，会话不再各自回退到 agentDir 的 auth.json。这样平台与独立使用的 pi 各管各的 key，互不出现。

Provider key 设置先让当前 `ModelRuntime` 接收新运行时 key，再通过 SDK 凭证通道持久化到平台 auth.json；若持久写入失败，必须清除本次运行时 override，使旧持久 key 重新成为有效值，不能让失败响应后的当前进程继续使用一个重启后消失的新 key。该失败清理不等于解决目录与凭证的跨文件删除事务。

- **自定义 Provider**：任意 OpenAI-compatible 端点（vLLM/Ollama/网关）经 `PUT/DELETE /api/providers/custom/:id` 写入 `<agentDir>/models.json`（0600 临时文件先同步、rename 后同步父目录），条目含 `name/baseUrl/api/models[]`；凭证不进 models.json，走平台凭证存储（`setProviderKey`/`removeProviderKey` 同一通道）。`GET /api/providers/custom` 从同一文件快照返回目录与原始内容哈希修订；无效 JSON 或 `providers`、Provider 条目、模型数组结构损坏时，目录读写返回 422 `provider_catalog_invalid`，保留原文件且不得先撤销 key。PUT 请求体必须携带 `expectedRevision`，DELETE 用 `x-expected-revision` 请求头携带打开确认时的修订，过期请求在写目录或撤销 key 前返回 409 `provider_conflict`。同进程写入在串行锁内再次核对客户端版本，生成临时文件后还要比较源文件内容，尽量避免覆盖已可见的外部文件改动。目录 rename 后若同步失败，PUT 返回 503 `provider_write_uncertain` 并封锁当前进程后续目录及 key 写入；DELETE 保留删除日志并返回 503 `provider_recovery_required`，由重启后的目录实际状态裁决，不能把不确定提交报为普通失败或成功。删除在平台 secrets 下先以 0600 文件和目录同步持久记录目标 Provider、原凭证与阶段，再撤销 key 和提交目录；服务端启动、开放监听前按实际目录终态恢复旧 key 或完成撤销并清除日志。日志未决或恢复失败时，Provider 目录与 key 写入返回 503 `provider_recovery_required`；目录已提交但日志清理不确定时返回 202 并提示重启确认。恢复时若目标 Provider 被外部修改，拒绝覆盖其现有状态并要求人工核对。写操作后重建进程级共享 `ModelRuntime`（`pi-bridge/model-runtime.ts`），并标记活跃 Session 的运行时装配待重建；空闲且已有 JSONL 的 Session 下次打开时绑定新 runtime，新增 Provider 的模型与已保存 key 才能用于原有 solo 会话。运行中 Session 不在当前轮中途替换 runtime；删除 Provider 也不让原有 Session 永久保留旧目录。`models.json` 的同进程读改写按文件路径串行，临时文件名含随机身份并在失败后清理，避免多标签并发登记/删除时丢其他条目或争用临时文件；该检查不构成跨进程原子锁，外部 pi CLI 若在最终比较与 rename 之间写入仍可能冲突。删除入口先验明该 id 确属自定义 Provider，避免不存在的自定义 id 误撤销同名内置 Provider 的 key；凭证撤销失败时保留目录并返回错误，不能把不确定撤销伪装成删除成功；
- **自定义 Provider 编辑边界**：首次目录读取、后续刷新或读取失败时，不把未知列表显示为零个可编辑项；仅在最新一次目录回读成功后允许新增、编辑和删除。新增/编辑弹窗与删除确认框打开时冻结目录修订；若其后列表修订变化或读取失败，保留草稿但禁止旧版保存，要求关闭弹窗后重开；服务端仍核对版本，409 后页面回读目录。新增弹窗不得用已有 id 静默覆盖条目；删除还须防止重复提交。每次打开新增/编辑弹窗都从当前对象初始化全新草稿；连接测试、发现、保存请求在途时冻结本次表单并禁止关闭/重复提交。保存先写 Provider 模型目录，再写可选 API Key；若后者失败或响应未确认，界面明确告知目录已保存、凭证状态待核对，刷新目录与模型选择器，不把整单说成保存失败。
- **连通性测试与模型发现是两个显式动作**：`POST /api/providers/test`（带鉴权 `GET {baseUrl}/models` 探针，收到状态码后取消响应正文，401/403 单独映射，返回 latency）与 `POST /api/providers/discover`（拉模型 id 清单，用户挑选后随 provider 登记；正文最多读取 1 MiB，超限时拒绝发现而非报告成功）；两者都支持测未保存的新 key；
- **设置页回读时序**：Provider、Custom Provider 与默认模型的并行读取按请求代次丢弃迟到结果；默认模型设置另有独立回读代次。设置默认模型时跨 Provider 行只允许一个在途写操作，并暂时显示“正在设置”，成功回读后才确认默认标记；在途刷新不能把旧默认值写回界面，写入失败后重新读取服务端状态。单个 Provider 的模型读取也按请求代次丢弃迟到结果。替换或删除 key 后重新读取模型目录，同一 Provider 的凭证写操作在请求期间串行，防止迟到的旧列表覆盖新状态或重复提交。
- **会话模型选择器**：composer 只把 Session/Room 回读的模型当作当前值，本地新会话偏好不冒充已选择模型；提交期间同一选择器只允许一个请求。服务端返回实际模型 ID 后才更新当前显示、父级对应 Session 与本地偏好；失败保留旧值，响应迟到时按提交时的 Session ID 更新，不以当前 active Session 代替。模型目录读取失败保留可重试入口；浏览器本地存储不可用不阻断模型切换。
- **Worker 单聊会话覆盖（2026-09-30）**：输入区提供 model / effort 选择和恢复 Worker 默认。优先级为当前房间 Session 覆盖 > Worker Connector 配置 > 上游默认。`GET|PUT /api/sessions/:id/worker-runtime-model` 只接受 Worker direct 通道，PUT 支持键级修改、`null` 清除；不修改 Agent 默认、其他 Session 或 Manager 模型。`GET /api/sessions/:id/worker-runtime-model/options` 按该会话 cwd 与 Worker 凭证读取目录；Pi 前端直接复用现有 `useModelCatalog.levelsFor/gradedFor` 与 `/api/models` 同源目录（含平台能力 map 补丁），不新增模型与强度匹配表；切换模型时清除不再匹配的会话档位覆盖。其他 Driver 通过 `listConfigOptions("model", ctx)` 发现。DriverCapabilities 的 `runtimeModel.effortLevels` 声明支持范围，模型目录可用 `DriverConfigOption.effortLevels` 进一步收窄。未声明支持的 Connector 显示配置入口，服务端拒绝覆盖设置。
- **覆盖的执行落点**：Direct dispatch 在生命周期门内读取并冻结 JSONL 的 `pudding:worker-runtime-model`，Invoker 仅向本房间 Worker 委托的 `options.runtimeModel: {model?, effort?}` 透传；与已有业务选项 `options.model` 分开。Driver SPI 本体映射上游参数：Codex run/resume 使用 `-m` 与 `-c model_reasoning_effort=...`，Claude Code run/resume 使用 `--model` 与 `--effort`，Pi 在新建/续接 SDK Session 上调用 setModel/setThinkingLevel。切换从下一条发送生效，正在执行的 Run/审批恢复保持原参数。恢复默认保留上游 sessionHandle 与对话连续性；Pi 用私有默认基线恢复没有显式配置时的 SDK 初始值。pi 门面适配层不依赖 PuddingTeams 的房间设置接口。
- **binding（按用途分派）**：manager 默认模型（§10.5）、会话级模型（composer 切换）、worker 实例模型（connector config `model`，`format: "model"` 下拉）三层各自独立，解析优先级：worker 实例 config > pi 默认；pi worker 改配置模型后对**驻留/恢复中的旧会话**也生效——`LocalPiDriver.reconcileModel` 在每次开会话（内存驻留命中或 JSONL 恢复）后对比 `session.model` 与配置解析结果，不一致即 `setModel` 纠偏（2026-08-19）；
- **思考强度 binding 分层（2026-09-29 补齐并落地，与模型同构）**：thinking level 此前只作为 §10.5 表中 manager 的一个可编辑项存在，从未进入本 binding 表，等价于「只有 Agent 默认一层、且该层向全部活跃会话广播」。这与模型的两层形态不一致，且因 pinned manager 身份单例却同时持有 N 个会话（solo 单例房间 + 群聊房间各一个 manager session），单值必须扇出，无法表达「这条会话想多想一点」。现补齐为两层：`manager.thinkingLevel` 是**新建/重开会话的默认档位**（语义对齐 `manager.model`，缺席或显式 `null` 表示不设、走 SDK 恢复链），会话级档位是**用户在聊天中对该 Session 的选择**，优先级高于 manager 默认。**不采用 pi 原生 `settings.modelThinkingLevels`**：那是 pi 全局 `settings.json` 里以 `provider/modelId` 为键的 per-model 默认，manager 与全部 pi worker 共享同一份，把它当作 manager 配置会破坏 §10.6「manager 配置归平台所有、与 pi CLI 及 worker 解耦」的边界；且它只解决默认值，不解决覆盖顺序。平台需要的分层必须自持，与模型走同一条路。
- **思考强度的能力表与上游目录补丁（2026-09-29）**：SDK 判定思考强度分两层且数据源不同——第 1 层 `pi-ai/models.js` 的 `getSupportedThinkingLevels` 只读目录的 `reasoning`/`thinkingLevelMap`；第 2 层由 `api/<protocol>.js` 按 `model.api`（协议）再按 `compat.thinkingFormat`（该协议下的方言）分派，多数方言受 `compat.supportsReasoningEffort` 门控。**分派键是协议与方言，不是 provider 名**（`deepseek` 只是 `openai-completions` 下的一个方言，baseten/together/openrouter 托管的 DeepSeek 系模型可能共用同一条分支）。两层不一致时会出现「菜单给了 N 档、线上只有开/关两种行为」：实测 DeepSeek 官方 Chat Completions 明确支持 `reasoning_effort=[none,low,high,max]`（默认 high，minimal→low、medium/xhigh→high，`GET /models` 亦下发 `effort.supported_levels`），而 pi-ai 0.84.4~0.87.1 实测均把 `compat.supportsReasoningEffort` 留空，adapter 因此只发 `thinking:{type:enabled}`，把三档压成一种行为。**升级 pi 不能解决**（六个版本目录与 adapter 分支逐字未变，且 0.87.0 有 `shouldStopAfterTurn` 移除等 breaking change 直接打到平台用法）。平台因此自持一张能力表 `pi-bridge/thinking-capabilities.ts`：**只声明上游目录与官方文档不一致的模型**，经 pi 官方 `models.json` 的 `modelOverrides` 顶层覆盖层修正，不重实现 adapter、不自造 clamp 规则，SDK 目录修好后删表即恢复上游行为；每条声明必须附官方文档 URL 供复核。当前仅声明 DeepSeek 三个模型（`kimi-k3`、`glm-5.2/5.3` 目录本已正确，不重复声明）。写入在冷启动、`configureSharedModelRuntime` 之前完成，逐字段幂等（无变化不写盘），失败只告警不阻断启动（退回上游目录仍可用）。**副作用修复**：`upsertCustomProvider` 原为同 id 条目整体替换，会静默抹掉 `modelOverrides`（平台能力声明与用户手写的 per-model 覆盖都会丢），改为保留表单未建模的字段。
- **归一化档位单一来源（2026-09-29）**：7 档枚举此前在平台被复制成多份且**长度不一**——pi Connector `configSchema` 的 enum 只有 6 档（缺 `max`），而 manager 表单用另一份 7 档常量，渲染 pi worker 的表单由前者驱动，于是同一平台两处给出不同选项（Kimi K3 / GLM / DeepSeek 都支持 `max` 却选不到）。现归一为单一来源：前端 `lib/model-catalog.ts` 的 `THINKING_LEVELS` 为准，`pi-extension.ts` 的 `configSchema` enum、`teams.ts` 的 manager 校验枚举、`config-transfer` 的导入导出校验逐项对齐，并由 `model-catalog.test.ts` 用源码断言锁死（含「不得在别处再硬编码一份」的扫描）。**静态 schema 只能声明归一化全集**，某模型真正可选的档位由 `ModelSummary.thinkingLevels` 决定；Connector 侧用声明式注解 `x-puddingteams-thinking-levels-from: "model"` 让通用 schema 表单按所选 model 字段收敛（不硬编码字段名，其它 connector 声明同一注解即同样生效）。所有模型/强度选择器（聊天 composer、工作台新工作、Manager 配置、Pi Worker 配置）统一走 `useModelCatalog()`，与 composer 同一份 map（含平台能力表修正）。已存档位若不再被新模型支持，仍作为「（当前模型不支持）」项可见可改，不得静默改写用户配置。
- **思考强度是否真分级必须如实告知（2026-09-29）**：能力表解决的是「官方支持却被目录漏掉」，但仍有一类模型目录与 adapter **一致地**只支持开/关（如 `kimi-k2.5`/`k2.6`/`k2.7-code`、`glm-4.7`/`glm-5-turbo`，其 `compat.supportsReasoningEffort` 为 false 是正确的）。这类模型菜单上出现多档会让用户以为强度可调。`ModelSummary` 因此新增 `thinkingGraded`：把每个非 off 档位经 clamp 归一后映射到该 api 实际会发出的字段，去重后多于一种才算分级（判定复刻 adapter 出参逻辑，不发请求）。为 false 时各选择器显示「该模型只支持思考开/关，各档在链路上无差别。」——**宁可少给选项，不给假刻度**。
- **思考强度落点（2026-09-29 实现）**：`SessionSummary.thinkingLevel` 与 `RoomSessionSummary.thinkingLevel` 与 `model` 同构投影（存活会话取 `session.thinkingLevel`，磁盘会话取 JSONL 最后一条 `thinking_level_change`），作为 composer 选择器的真值来源；写入口为 `POST /api/sessions/:id/thinking-level`（与 `POST /api/sessions/:id/model` 同一 `withActiveSessionLifecycle` 门禁，返回服务端 clamp 后的生效档位）。`PiSessionStore.setThinkingLevel` 校验归一化枚举、拒绝非法值，并登记进程内 `thinkingOverrides`；`assembleSession` 的 `preferRecordedThinkingLevel` 使重开已有会话不传显式档位，由 SDK 从 JSONL 恢复。**进程重启后 `thinkingOverrides` 为空**，因此 `open()` 装配完成后按「落盘档位 ≠ manager 默认档位按当前模型 clamp 后的值」登记会话级选择（发散判定），保证后续配置变更不会覆盖用户选择；该判定在「用户曾手动切换过档位」与「manager 默认在停机期间被改过」之间不可区分，保守地按前者处理（不覆盖用户，宁可让过期默认不刷新）。`ModelSummary.thinkingLevels` 按各模型 `thinkingLevelMap` 归一化下发可用档位，composer 只渲染该集合、非推理模型（`reasoning:false`）不显示思考强度入口。
- **思考强度的入口位置与新工作预约（2026-09-29）**：两处入口都在「运行参数区」，与模型选择器同组、紧邻发送键——聊天 composer 的发送键左侧，以及工作台「发起新工作」框的发送键左侧（该框原把模型选择器放在左侧工具列，与模型相关的运行参数被拆散，本轮一并归位）。`POST /api/rooms/:id/new-work` 接受可选 `thinkingLevel`，与 `modelRef` 同样计入 `contentHash`——**改档位等同改模型，必须换操作键**，草稿 `modelRef`/`thinkingLevel` 一起进入 `ManagerWorkDraft` 与 `pendingSubmission` 的同一份身份比对（`pendingManagerWorkMatches`），首发前与 `setModel` 相邻落到预约 Session。工作台的档位选择只作用于**这一次新工作**，不是全局默认。
- **思考强度的 SDK 归一化语义**：平台只暴露 7 档归一化枚举 `off|minimal|low|medium|high|xhigh|max`（与 `pi-ai` `EXTENDED_THINKING_LEVELS` 一致），不对用户暴露 token 数或 provider effort 字符串。**不做 per-provider 配置**——SDK 没有这个概念，provider 差异由两层吃掉：模型目录的 `model.thinkingLevelMap` 决定「该档此模型能否选择、选完映射成什么」（`null` = 不支持，`xhigh`/`max` 仅在 map 显式声明时可用），各 provider 适配器（`anthropic-messages` 的 `effort`/`budget_tokens`、`openai-responses` 的 `reasoning.effort`、`openai-completions` 的 `reasoning_effort`/`enable_thinking`、`google-generative-ai` 的 thinkingBudget、`bedrock-converse-stream` 的 `output_config.effort`）决定用哪个 HTTP 字段。选档超出模型能力时按 `clampThinkingLevel` 先向上再向下钳制，不静默降到底档。
- **思考强度必须与模型一样对称处理恢复**：`pi-agent-core` `agent-loop` 每轮把 `thinkingLevel` 映射为 `reasoning`（`"off"` → `undefined`），SDK 侧 `setThinkingLevel` 会向会话 JSONL 追加 `thinking_level_change`，且 `sdk.js` 在 `options.thinkingLevel === undefined` 时才从最后一条 `thinking_level_change` 恢复。因此会话级选择要真正持久，必须像 `preferRecordedModel` 一样给 `assembleSession` 一个 `preferRecordedThinkingLevel` 开关：重开已有会话时以落盘档位为准，不用 manager 默认覆盖用户选择；`SessionSummary`/`RoomSessionSummary` 需与 `model` 同构地暴露该字段，作为 composer 的真值来源。
- **思考强度的配置变更不得广播覆盖会话级选择**：`revokeChangedTools` 在任何 Agent 配置写入后把 `manager.thinkingLevel` 推给**全部**活跃会话，语义上只能是「刷新仍无会话级选择的会话的默认值」，对 `thinkingOverrides` 里的 Session 必须跳过；判空不得写成 `if (thinkingLevel && ...)`，否则在配置页清除档位对运行中会话不生效（`null` 分支缺失）——实现按 `settings?.thinkingLevel ?? sdkDefaultThinkingLevel(session)` 取目标，清除配置时回退 SDK 默认链（per-model override → 全局默认 → `medium`）。这条与模型一致：manager 改默认模型不会去改用户已选模型的会话。
- 明确不抄的部分：明文 credentials.json（用 pi 的 AuthStorage 机制但落平台路径）、遗留迁移/backfill（未上线无包袱）、硬编码 preset 清单（builtin 目录由 pi SDK 维护，自定义层开放增删）。

### 10.5 Pi Manager 作为可编辑的内置 Agent

manager 目前硬编码在 `PiSessionStore`（`apps/server/src/pi-bridge/session-store.ts`）：模型走运行时默认、solo 没有 prompt 入口、工具策略写死。目标是让它以 pinned 内置条目出现在智能体管理界面，与 worker 共用一套编辑 UI。

**可编辑项（按 pi SDK 能力映射）**：

| 配置 | SDK 支撑 | 生效时机 |
| --- | --- | --- |
| 默认模型 | `createAgentSession({ model })` | 新建会话 |
| Agent 运行指令与资源（append prompt / skills / templates / context / Capability runtime） | `AgentConfig.piResources` + `DefaultResourceLoader` | manager/Pi worker 分别读取自己的配置与 Capability bindings；新建或重开会话生效，Group collaboration 独立组合 |
| 内置工具开关 | `tools` / `noTools` | 新建/重开会话 |
| 资源加载开关（skills/prompt templates/context files/extensions） | loader 的 `noSkills`/`noPromptTemplates`/`noContextFiles`/`noExtensions` | 新建/重开会话 |
| 库技能/模板选用名单 | `skillsOverride`/`promptsOverride` 按名单过滤（2026-08-10 落地） | 新建/重开会话 |
| thinking level | `session.setThinkingLevel()` | 新建会话用 `manager.thinkingLevel`；会话级覆盖见 §10.6 binding 表 |
| 压缩策略 | `session.compact(customInstructions)` / compaction settings；Pi SDK 0.84.4 起，同一次 `session.prompt()` 工具循环中的工具结果越过自动压缩阈值时，必须在下一次模型请求前先压缩，不得将未压缩的大工具结果直接送往 provider | 运行时 |
| 名称、头像、描述 | 平台自存，复用 avatar 接口 | 即改 |

Manager 配置采用键级合并：`manager.model`、`manager.thinkingLevel` 缺席表示保留旧值，显式 `null` 表示删除设置并恢复运行时默认。配置页的空模型和「默认（不设置）」必须提交 `null`，保存后按服务端回读展示；不能省略字段却报告清除成功。空字符串不是清除协议，应拒绝。

`manager.model` 与 `manager.thinkingLevel` 在本层都只是**默认值**，不是会话实际值的唯一来源：两者都存在会话级覆盖层，优先级与恢复语义见 §10.6 binding 表。§10.5 表中「生效时机」列描述的是「本层配置变更的传播范围」，不等于「该值只能由本层设置」——thinking level 一行尤其容易被误读为「改配置即广播覆盖所有会话」，实际广播只在目标 Session 没有会话级选择时才发生。

头像上传与删除在配置页共用单实例提交锁，避免连续点击造成写入交错。`DELETE /api/agents/:name/avatar` 成功时返回 Store 写入后的 `{ agent }`；前端据此更新 Agent，而不把删除前的旧对象改一个 `avatar` 字段后覆盖较新的配置。上传或删除失败不报告成功，用户可保留当前页面状态重试。

**技能 / 模板列表一页 10 条**：库里有 30+ 项（装完 lark 全家桶就是 32 个），一次铺完会把分区拉到几屏，而真正要勾的通常只有个位数。分页器在勾选列表下方：左侧「第 x–y 个 / 共 N 个」，右侧「上一页 / n / 页数 / 下一页」，总数不超过一页时不渲染。搜索词变化时页码在 render 期间拨回第一页（不要写 effect + setState，会被 `react-hooks/set-state-in-effect` 拦下），页码再按 `Math.min` 夹回合法范围，避免停在一片空白的越界页。分页只切可见行，不影响 `enabledSkills` 草稿——翻页前后勾选状态完全一致。

**配置页分区节奏（2026-09-30 精简）**：首个分区没有顶部留白（与左侧导航顶边平齐），后续分区 `padding: 24px 0`，用标题与留白区分，不再叠加分区底线。注意分区组件的根节点不统一——技能 / MCP 直接返回 `<section>`，概览 / 模型 / 提示词外面包一层 `<div>`——所以"首个分区去掉顶部留白"必须同时命中 `.agent-config-column > .agent-config-card:first-child` 和 `.agent-config-column > * > .agent-config-card:first-child`，只写前者会让概览 / 模型 / 提示词的标题比导航低 24px。切换分区时滚动容器回到顶部，否则从长分区切到长分区会落在页面中段。分区命名沿用原型的「模型 / 运行资源」。列表只在相邻条目之间留浅色分隔线，末尾不留装饰线；开关同理。管理位置与保存方式说明集中在标题区，不再放在列表后的独立 callout；读取失败、冲突与保存未确认等动态告警仍原位保留。

**配置页滚动边界（2026-09-30）**：路由主容器与配置 shell 使用 `min-height: 0` 的剩余空间 flex 布局，不给配置 shell 另设 `height: 100%`。顶部导航与页面操作头留在视口中，只有 `.agent-config-scroll` 滚动。否则导航高度会叠加到配置区高度上，聚焦长列表底部控件时 Chromium 会滚动外层隐藏容器，把顶部导航挤出视野。

**配置页的控件语言（2026-09-30 对齐全界面审核原型）**：输入框 / 文本域 / 下拉一律 **白底 + 1px 发丝描边**（`--config-surface`，与顶部 banner 同一个白），不是灰填充、也不是页面底色——原型 `.field input` 用的是 `--bg`，在近白画布（`#f9fbfc`）上等于隐形，控件读不出来，审核后改为白色物体浮在画布上，圆角 8px、内边距 10px 12px、正文 12px、行高 1.6（文本域 1.8、下限 85px），聚焦用 `2px solid --accent` 外描边加 3px 偏移。字段标签 11px 用 `--sub`，说明文字 10px 用 `--muted`。分区标题 14px/560 + 12px 副标题，标题块下 19px、字段之间 17px；两列并排按 `1.5fr 1fr 1fr`（`内部标识` 比 `角色` 宽）。左侧导航 142px、圆角 7px、内边距 10px 13px、说明文字 9px；`删除智能体` 用 `--amber` 而不是 `--destructive`——它是导航里的次级动作，不是页面主危险按钮。只读值（内部标识 / 角色）用真实 `disabled` 控件（`:disabled{opacity:.45}`）而不是自绘的灰底 `div`，这样读屏能念出、用户也能选中复制。

**模型字段用按 Provider 分组的选择器，不用扁平下拉**：模型目录有上百项，扁平 `Select` 会一路撑到满屏（shadcn 的 `max-h-(available-height)` 上限就是"视口剩余高度"），既像坏掉又没法快速定位。因此 `format: "model"` 字段走 `DropdownMenu` + Provider 二级菜单（复用 composer 的 `.model-picker-*`：当前 Provider 打点、当前模型打勾、二级菜单限高 420px），一级菜单顶部是「不设置（用默认模型）」，目录里没有的存档值单列一条并标注「当前值，目录中没有」——不静默改写用户配置。触发器与同分区其他字段同高同底色，只显示模型名，Provider 用 11px 弱化色跟在右侧。顺带给所有 `[data-slot="select-content"]` 加 `max-height: min(360px, available)`，任何长下拉都不会再撑满视口。Manager 路径的模型字段仍是自由输入 + `datalist`（Manager 允许目录外的模型 id），与 Worker 路径的差异是刻意的，不要为了统一把它改成只能选。

**有效提示词预览：触发器和结果必须在同一分区**。选工作目录 + 「拼装并预览」按钮原本放在「上下文注入」里，结果却渲染在下面另一个分区，用户会以为那是个设置项。现在下拉与按钮移到「有效提示词预览」分区头，下拉明确是预览参数（32px 高的小控件，不套字段样式，不写入任何设置），空态有一句话说明。名称分工固定：**预览** = 你写的这段 Markdown；**有效提示词** = 服务端实际拼装的结果。

**`loadWorkspaceContext` 开关恒可编辑**。它只是每个 Agent 的一个布尔量，运行时会和会话实际所在目录的授权状态取交集（`piResourceLoaderOptions`：`loadWorkspaceContext !== false && workspaceAccess.context`），与"选哪个工作目录"无关。此前 UI 把它挂在预览用的目录下拉上（没先选目录就打不开开关），控件之间的从属关系是假的；现在开关常开，规则写在说明里，工作目录选择归预览分区。

**提示词补充分区：编辑 / 预览双视图**。这一节要给"写的"和"读的"两种视图——预览走 `ClipboardSafeStreamdown`（与对话、交付物同一套渲染与剪贴板兜底，链接只放行 http/https/mailto，外部图片不自动加载），不做第二套 Markdown 渲染器。切到预览时不改草稿，编辑器和预览面板同高同内边距。编辑器高度**随内容自动增长**（`field-sizing: content`，下限 132px、上限 60vh 后内部滚动），不要求用户拖右下角几像素的手柄——实测那个命中区太小，实际拖不动；不支持 field-sizing 的浏览器仍可手动纵向拉伸。这一节不放字符数、也不放生效时机脚注：生效时机由「模型」分区统一交代。

**分区副标题只在"这一节在解决什么问题"时写**：单字段分区不写副标题——只会把字段名再说一遍（内置 pi 的「运行资源」只有一个代码搜索字段，副标题原本是"代码搜索的实现方式。"；原型 model 分区的「运行资源」同样没有副标题）。多字段分区才写，且不能是字段标题的复述。

**字段说明写在标题下面，不写在控件下面**：`configSchema` 的 `description` 解释"这个字段是干什么的"，所以渲染在字段标题与控件之间；控件下面只留给随当前值变化的动态提示（例如"该模型只支持思考开/关"、thinking 档位随模型收敛的说明）。生效时机一类不属于字段语义的说法统一成分区末尾脚注，并**必须区分"进行中"和"已有但未运行"的会话**——事实是 `sessionStore.runtimeDirty`：写操作把每个活跃会话标脏，当前轮结束后空闲重建才换配置；thinking level 是唯一的运行时即改项（不覆盖有会话级选择的会话）；被删掉的工具立即撤权。文案只有一份，在 `agent-config/session-effect.ts`，改之前先读 `agentSessionStats` / `revokeChangedTools`。注意 `agentSessionStats` 的 `activeNow` 恒等于 `affectedSessions`（都在活跃集合里），所以保存提示只能说"N 个进行中的会话本轮结束后切换"，不能说"N 个立即生效"。

**模型与思考强度并排一行**：`format: "model"` 字段与 `x-puddingteams-thinking-levels-from` 指向它的 enum 字段（当前是思考强度）是同一件事的两面，在配置页占一行（`.agent-config-columns`，1.5fr 1fr），各占一整行会把「模型」这一节拉得过长。配对要求两侧都可见；任一侧被隐藏时不配对、也不渲染空的第二列。运维向字段（`x-puddingteams-hidden`）不生成表单，但已存档的值会随草稿原样回写，不会被静默清掉。

**配置页的界面契约（2026-09-30 对齐全界面审核原型）**：页面头只放「当前 Agent 名称 + 一句职责说明 + 返回列表 / 导入导出 / 探测 / 保存 / 删除」，身份信息（头像、名称、描述、来源徽章、启停开关）独立成 banner，不再挤在头部一行里；左侧分区导航是**纯文字**列表，不再附「配置按智能体独立生效」说明或删除入口；删除移到右上角操作区末尾（固定 Manager 不显示，保留停用前置条件、确认弹窗与并发禁用），不铺底色、不带图标；右侧内容是**无框分区**，靠发丝分隔线切分，只有执行能力摘要这类"卡片中的卡片"才保留实体卡边框（技能 / 模板 / MCP / 能力插件一律用勾选式 choice-line）。开关统一为右侧原生 toggle 行，标签与说明在左。**唯一超出原型的部分**：概览「基本信息」保留产品已有的头像上传行（原型只把头像当只读展示，没有上传入口），因此页面会出现"banner 里一个只读头像 + 分区里一个可编辑头像"——这是保留既有能力的选择，不是漏改。

**配置页色板不继承 `--home-*`**：原型的页面底色是近白 `#f9fbfc`，只有导航、hover 与输入框才是灰阶，与聊天页的蓝灰画布是两套。因此配置页自带一组 `--config-*` token，逐值对齐原型 `handoff/2026-09-23-full-ui-review/styles.css` 的 `:root`（浅色 `--bg/--surface/--raised/--hover/--selected/--line/--sub/--muted/--accent/--accentText`，深色同源取 `[data-theme="dark"]`）。改配置页配色时改这一组，不要引用 `--home-surface-*` 或 `--muted-foreground`，否则页面基调会退回蓝灰。

**技能 / 模板列表的来源语义（勾选到底管什么）**：`previewPiResources` 返回**全部**资源并按路径分三类（`pi-resources.ts` 的 `sourceOf`）：`global` = `getAgentDir()/skills`，也就是 `/extensions` 管的库资源；`workspace` = `<cwd>/.pi/skills`；`extra` = pi 自己扫到的其他目录。白名单**只作用于 global**（`!isUnderDir(s.filePath, globalSkillsDir) || enabledSkills.has(s.name)`），所以非 global 的确实勾不到——实测：白名单为空时装载器只留下 1 个 pi 自带技能，32 个库技能全部被过滤掉。因此配置页那个折叠块只列 `source !== "global"` 的条目，并按来源分组说明（工作目录 / pi 自动发现）。**不要把整个 `preview.skills` 塞进"其他来源"**——那是同一批库资源，会把上面的列表原样再列一遍，还会贴上"始终启用"的错误标签（2026-09-30 已修）。多数环境里非 global 条目为 0，折叠块不出现。

**配置页只管"启用范围"，不管资源本体**：技能 / 模板的内容管理在 `/extensions` 完成。「提示词模板」作为与 Skills、MCP、插件、连接状态并列的一级标签，使用 `/extensions?tab=templates`；不再放在 Skills 下做二级入口。模板有独立的数量与读取失败状态，新增、删除、导入和刷新后同步数量，管理链接直达该分类；页面刷新保持当前标签。模板，提供新建、编辑、导入与删除，复用现有资源库 API；内容保存影响共享库，不自动为 Agent 勾选启用。配置页对应分区只有勾选列表（`choice-line` 形态：勾选框 + 名称说明 + 右侧已启用/未启用状态）、额外来源只读展示、Workspace 开关与额外挂载路径。管理链接、保存草稿说明和可见刷新入口放在标题区，库内已选计数与名称 / 描述 / 参数提示搜索放在列表顶部；搜索仅过滤展示，不修改启用名单，清空后恢复原顺序。两处不得各自长出一套资源库 CRUD。例外是 MCP：它走独立的 revision 冲突协议（草稿 `pending` / `unconfirmed` / `conflict` 三态），因此仍在本分区自带「保存选择」，但形态同样收敛为勾选列表；不将其伪装成页面级保存草稿。插件分区同样使用轻量标题与右侧操作，不再叠加概览卡，绑定的权限、状态与诊断保持可见。

**分区内的字段标签一律来自 `configSchema.title`**：内部 key（`model` / `thinkingLevel` / `sessionDir` / `permissionMode`）不得出现在界面上。第一方 Connector（`pi-extension.ts`、`puddingclaw-extension.ts`、`codex` / `claude-code` 的 `package.json`）与 connector 脚手架模板已全部补齐 `title`；第三方 Connector 缺 `title` 仍会退化成 key，属已知缺口，不要在宿主侧加 key→中文的猜测映射（猜错标签比暴露 key 更糟）。

**实现要点**：

- `teams.json` 放一条 pinned 保留条目（`name: "manager"`，`invoke: { type: "pi" }`），`upsertAgent` 目前只收 `command`（`teams.ts:258`），需放开 `pi` 类型且只允许这一个保留名；不可删除、不可禁用；
- Direct 不接受用户可编辑的 Window Prompt（2026-08-12 起 direct 窗口无 manager 回合，固定 relay 已废弃）；Group 的 `window.prompt` 是仅给该群聊 manager 的协作提示词；Solo 不注入 Window collaboration；
- `PiSessionStore.create()/open()` 读该配置装配会话，改动只对新建/重开的会话生效（运行中会话用 `setModel`/`setThinkingLevel` 即时项除外；两者都只作用于没有会话级覆盖的 Session，见 §10.6）；
- 与 worker 的差异在 UI 上体现为表单分区：manager 没有 invoke command/probe/secrets，替换为上述 SDK 配置区。

**实现回写（2026-08-10 资源库与统一配置页，2026-08-15 UI 信息架构调整，2026-08-25 Capability 双端配置，2026-09-02 MCP）**：技能/模板资源库直接使用 pi 全局目录（`<agentDir>/skills`、`/prompts`，与 pi CLI 共享），存储层 `pi-bridge/resource-library.ts` + 路由 `/api/resources/skills|templates`（含 `import`）；Agent 级选用是白名单语义——`PiResourceConfig.enabledSkills/enabledPrompts`（缺省不启用，取代已删除的 `loadGlobalSkills/loadGlobalPrompts`），装配经 `piResourceLoaderOptions()` 返回的 `skillsOverride/promptsOverride` 按 filePath 前缀过滤全局目录条目，Workspace 与额外挂载资源不受管；manager 与 worker 编辑入口合并为 `PUT /api/agents/:name/config` 一条合并更新接口（旧 `PATCH /manager`、`PUT /connector`、`PUT /pi-resources` 保留给非 pi 管理抽屉）。当前前端独立配置页 `/agents/config?name=` 的 Manager 与 Pi Worker 都提供 Extensions 与 MCP 两个独立分区，普通 Skills/模板仍由各自资源区管理；MCP Server 全集在一级 `/extensions?tab=mcp` 维护，Manager/Pi Worker 则在自身 MCP 分区通过 `GET|PUT /api/agents/:name/mcp` 保存白名单。Catalog API 为 `GET|POST /api/extensions/mcp/servers` 与 `PUT|DELETE /api/extensions/mcp/servers/:serverId`，协议执行由默认启用的 `pi-mcp-adapter` 提供。

独立配置页的页面级保存与 Agent 启停共用同步占用门禁，避免快速重复提交或两个 Agent 快照交错回写；保存期间仍允许继续编辑草稿，响应只更新已保存基线，后续编辑保留为待保存状态。`PUT /api/agents/:name/config` 与 legacy 全量 `PUT /api/agents/:name` 必须携带读取草稿时的 `extensionRevision` 作为 `expectedRevision`；服务端在实际串行写入区重核版本，旧版返回 409 且不改较新配置，缺版本返回 400。配置页遇到冲突保留草稿，暂停再次保存，要求用户核对并明确读取最新配置后再编辑；同页其他分区的写入不能悄悄将旧草稿升级到新版本。Connector/Capability/MCP 分区各自的写操作仍按其独立接口处理，不将页面级门禁视为跨接口事务。

独立旧管理入口 `PATCH /api/agents/:name/manager` 与 `PUT /api/agents/:name/pi-resources` 同样必须携带用户读取表单时的 `expectedRevision`。Manager 设置合并与 Pi 资源整份替换都在路由预检后进入 Store 串行写入区核对该客户端版本；缺版本 400、旧版 409，不覆盖较新描述、设置或资源白名单。旧 Manager 表单遇到冲突保留输入并暂停保存，用户明确读取最新 Agent 后再编辑。

Agent 列表与独立配置页的停用入口必须使用同一 `PUT /api/agents/:name/enabled` 冲突闭环。若 409 附活动 Run 清单，当前页面就展示 Run 的执行状态和所在窗口，并让用户明确选择继续保留 Agent、`resolve=keep` 保留 Run 后停用，或 `resolve=cancel` 取消 Run 后停用；不能只提示返回另一页面处理。未附 Run 清单的其他 409 保持错误呈现，不能假设它是可用 keep/cancel 解决的冲突。

独立配置页的概览草稿与 MCP、Connector、Capability、头像、legacy 接入及启停共享同一 Agent `extensionRevision`。同页分区写入成功时，页头草稿的 `expectedRevision` 必须同步到该成功响应的新修订，不能把自己刚完成的写入误报为外部 409；未保存的概览草稿仍保持原内容。外部冲突或显式回读不得自动提升旧草稿版本，必须让用户核对后主动丢弃。MCP 选择提交期间及成功后的回读期间禁止继续编辑勾选，避免新选择被回读覆盖。

MCP 选择 PUT 的响应丢失不能当成确定失败：服务端可能已提交并递增 Agent 修订。页面将当前勾选草稿保留在同标签页存储，标记结果未确认并阻止再次保存；切换分区或刷新后仍可恢复。用户显式读回服务器最新值时，若已包含草稿则确认成功、无需重复提交；若尚未包含，则保留草稿和当前修订，供核对后决定是否保存。服务器明确返回 409 时仍按冲突处理，不用旧修订重试。读取失败不得丢失草稿。

停用冲突清单覆盖 `admitted`、`waiting_admission`、`running`、`waiting_input`、`cancel_requested`、`reconciling`。Agent 的 `extensionRevision` 继续用于启停与配置写入的客户端 CAS；Run 与 Worker Session 使用独立的 `runConfigRevision` 识别执行配置。单纯启停不改变 `runConfigRevision`，因此 `resolve=keep` 后的待审批 Run 可按原执行配置续跑；Connector、凭证、Capability 或其他 Agent 配置变化仍须递增它，旧 Run 不得用新配置恢复。停用时应先持久提交状态，再对用户指定的已有 Run 执行取消。Invoker 最终校验 Agent 启用状态直至 Delegation 持久创建，与停用/删除及 Agent 配置/凭证写入路由共用同 Agent 的进程内串行门禁：先接单则后续写入只影响新 Run，先写入则新接单读取新状态；门禁在接单落盘后释放，不等待 Worker 完成。Extension 包生命周期的进程内顺序见下；跨进程写入仍需独立验证。

平台 MCP Server 目录更新须先固定当前引用该 Server 的 Agent 集合，再按 Agent id 排序取得这些 Agent 的接单门禁；目录及独立密钥写入、关联 Agent 修订号递增与 Session 撤权在门禁内完成。Agent MCP 选择、新建、复制和 legacy 全量更新与目录更新共用 Agent 引用目录门禁，防止目录更新时增减引用集合。

2026-09-26 加固：取得接单门禁后、MCP 目录变更前持久写入 `state/mcp-mutation-pending.json`，列明受影响 Agent。若目录已提交而修订号写入失败，当前进程保守递增这些 Agent 的执行修订并同步 Session；对账失败则持续阻断接单，返回 503。冷启动先恢复 MCP 密钥事务，再对待对账 Agent 递增修订并同步 Session，最后才开放路由。目录未改变且密钥事务已清理的确定性拒绝可清除待对账记录，不误增修订。只有目录、凭据、Agent 修订与 Session 同步完成，才删除待对账记录。进程内修订写入故障注入、Catalog 已提交后真实 `SIGKILL` 与独立安装 CLI 的冷启动修订 2→3 已验证；真实运行中 Worker 和实际 HTTP 路由中断仍待验收。

Extension 包安装、更新、卸载及开发者模式切换同样先取得 Agent 引用目录门禁。更新、卸载与模式切换读取当前引用者并按 Agent id 取得其接单门禁，随后改变模块注册、递增引用者修订号并同步 Session；Agent 绑定及身份增删与之同序，不能在引用者集合冻结后加入或移除。安装来源目录可能在两次读取之间变化，因此安装在目录门禁内短暂取得所有当前 Agent 的接单门禁，以实际激活包的 id 递增历史引用者修订号。

Extension 目录与 Agent 注册表不是同一文件：路由在包变更前以 `0600` 临时文件写入受影响 Agent 的待对账记录，先同步文件、原子重命名并同步所在目录，成功后才允许改变模块。只有模块变更、修订号递增和 Session 同步完成后才删除记录并同步目录。若重命名后目录同步失败，包变更不能继续；当前可见的待对账记录保留，后续变更拒绝。若写入修订号失败，当前进程阻断这些 Agent 的新接单并保留记录；服务冷启动时先保守递增记录中的执行修订号、同步 Session，再开放路由。恢复中再退出允许重复递增，不允许重用旧执行身份。若请求失败且 Extension Registry 与开发模式状态均未改变，则清除记录而不递增 Agent 修订号。受控写入/目录同步故障、合成待对账冷启动，以及包记录已提交而 Agent 修订未写入时真实 `SIGKILL`→同 Home 安装态冷启动，均有证据；本机多个服务进程共享 Home 的单写者门禁和 MCP/密钥跨文件事务已有独立进程验证。真实断电、外部 pi CLI 共写和真实 Worker 恢复仍需单独验证。

启停请求必须携带用户所见 Agent 的 `extensionRevision` 作为 `expectedRevision`；缺版本 400，旧版本在任何 Run 取消副作用前返回 409。Store 串行写入区再次核对该客户端版本。`resolve=cancel` 先成功提交停用状态、阻断新委托，再执行 Runtime 取消；Store 版本冲突时绝不取消 Run。列表和配置页对无 Run 清单的版本冲突重新读取 Agent，清除过期确认；新建 Worker 的创建→Connector 凭据配置→启用链使用配置响应中的最新 revision。

非 pinned Agent 的独立配置页也提供删除入口，与列表页共用 `DELETE /api/agents/:name` 的结果语义：先停用以阻断新委托，活动 Run 清空后才能删除；两处确认弹窗均说明现有会话历史保留、Agent 配置无法恢复。启用中禁用确认按钮并引导先停用；服务端再次校验前置条件。409 错误与 Run 清单留在弹窗供处理后重试；身份已删除但凭证清理待恢复的 202 属成功删除，前端移除头像缓存并返回列表。

独立配置页的分区导航在窄屏不能隐藏而无替代入口。按冻结原型的移动端行为，将侧栏改为可横向滚动的分区导航，保留概览、模型、提示词、技能、模板、MCP、插件以及非 pinned Agent 的删除入口；当前分区仍以可见状态和 `aria-current` 标识。宽屏保持侧栏布局。

配置 JSON 导入只修改当前页面草稿，保存后才调用配置 API；文件必须包含至少一个可导入字段，且字段类型在进入草稿前验证。Manager 的 `manager` 与 Pi Worker 的 `connectorConfig` 属于不同运行配置，跨类型导入须明确拒绝，不能提示成功后在保存时静默丢弃；用户可用“从其他 Agent 复制”迁移共同的模型与思考强度。Pi Worker 的 `model`、`sessionDir` 和 `thinkingLevel` 要按运行配置类型校验。独立 CredentialsStore 中的密钥不属于配置导出格式。

UI065 按冻结原型使用“导入与导出配置”弹窗：可选本地 JSON 或粘贴文本，先校验并预览本次要修改的分区，用户确认后才写入草稿；弹窗内仍提供当前草稿的 JSON 下载和从其他 Agent 复制。未识别字段须明确报错，不能预览成功后静默丢弃。切换文件、继续编辑或关闭弹窗时废止旧预览和未完成的文件读取，避免较晚返回的文件覆盖用户新输入。

Pi Worker 的 `codeSearch` 是 Agent 级运行策略，配置 JSON 导出/导入必须保留 `inherit|builtin|fff`；该字段不写入 `connectorConfig`，也不能作为 Manager 的 `codeSearch`（其枚举另含 `off`）导入。导入后保存须按同一 Worker 配置 API 请求体提交，避免界面草稿已变而实际策略丢失。

**代码搜索 Harness（2026-08-28）**：搜索实现属于 Harness 对 Pi 工具装配的策略，不属于 Connector Driver SPI。Harness 保存 Worker 默认 `builtin|fff`，Pi Worker 保存 `inherit|builtin|fff`；Manager 独立保存 `off|builtin|fff`、默认关闭，并只在 Solo 生效，Direct/Group relay 始终不注册搜索工具。`builtin` 激活 pi 原生 `grep/find`；`fff` 由共享核心把 `@ff-labs/pi-fff` 作为受控 inline Extension 注入，固定 override 模式、关闭 root/home scan、屏蔽 `/fff-mode`，同时通过 `extensionsOverride` 剔除 pi 全局发现的非受控 `pi-fff`。FFF 只有在 `workspaceId` 对应的 Workspace 仍为 trusted 时才装配，数据库路径按 `sha256(workspaceId + canonicalPath)` 隔离到 `<PUDDINGTEAMS_HOME>/runtime/fff/workspaces/`；无 Workspace、未信任或身份漂移时 fail closed。Pi 的 SDK embedding 不会自动发出 Extension 生命周期事件，因此 Manager/Worker 在 `createAgentSession` 后必须调用 `bindExtensions`；受控 FFF 还会把 `session_start.cwd` 钉死到登记的 canonical Workspace，禁止退回 Server 的 `process.cwd()`。`path` 与 `multi_grep.constraints` 只接受 Workspace 内相对约束；调用 FFF 前重新检查现存非 glob 路径前缀并拒绝任何符号链接，防止通过 Workspace 内 symlink 搜索外部目录。配置变化会使 Manager Session 标记 dirty；Worker 恢复时比较有效策略/Workspace 指纹，不一致即以同一 JSONL 重建 AgentSession，避免陈旧工具驻留。

**Goal 独立复核的宿主边界（2026-08-10，2026-08-31 补充）**：独立 reviewer 复用 Pi SDK 作为一次性推理宿主，但不是 Connector、Capability Extension、房间成员或 Delegation。PuddingTeams 在 manager 提交完成申请后创建全新的 `SessionManager.inMemory()` Session，关闭全部工具、Extension、Skill、模板与 context file，只注入冻结 Goal/完成条件和平台投影的只读证据；可选择与 manager 相同或不同 provider/model。Reviewer 只返回结构化 `CompletionReview`，无权调用 Driver SPI、委托 worker、修改 workspace 或写 `SessionWorkState`。它也不生成验收标准：`completionBoundary` 的每个非空行由用户在当前创建流程中冻结，Reviewer 返回的 criterion 必须逐行、原序、原文覆盖，只能补充 `status/explanation/evidenceRefs`；主观或授权条件证据不足时返回 `needs_human`。若条件要求“汇报/总结”，manager 提交完成申请时冻结的 `currentBrief` 会作为 `prepared_final_report` 证据进入 reviewer：reviewer 核验报告内容是否覆盖要求，Goal 原子完成后宿主立即把该报告发送给用户，不能因“完成前尚未发送”形成循环阻塞；只有条件明确要求用户确认收到、同意或满意时，才必须有 HumanDecision。复核 verdict、revision 对账、活动委托/待决策门禁与最终 resolved 提交全部属于 PuddingTeams 控制面，因此不改变“pi 入口只用 ExtensionAPI、Connector 本体只用 Driver SPI、完整房间编排只属于 PuddingTeams”的边界。

Goal 与当前工作是会变化的控制面状态，manager 必须在每次 Pi 模型请求的 `context` 阶段读取并注入最新 revision，形成仅对本次请求可见的隐藏上下文消息；不能把它作为 `before_agent_start` 的粘性 system prompt 覆盖。后者不会覆盖由 custom message 触发的 DecisionRequest 回答和续接路径，会造成状态陈旧。房间 roster 等 Session 启动级上下文仍可留在 `before_agent_start`。

### 10.7 内置 Wiki 管理员与受限 pi 运行面（2026-09-30）

宿主默认头像另投影 `defaultAvatarRevision`（资源文件修改时间与字节数），前端将其作为头像 URL 的 `default` 查询参数，并在上传/删除时保留该版本；默认资源变化自动形成新 URL，避免固定 `v=0` 命中缓存的旧 Connector 头像。

内置 Wiki 管理员默认使用宿主资源 `apps/server/assets/wiki-fox.png`（狐狸档案员）。头像接口按用户上传 → 宿主内置角色默认 → Connector 默认回退，列表通过 `hasDefaultAvatar` 告知前端，上传后该默认可用标记仍保留，避免刷新列表后删除上传无法即时恢复默认；删除上传头像后恢复狐狸。角色默认由 `builtinId="wiki"` 判定，新建和已有内置实例均直接读取随包发布的资源，不写入用户 `avatar` 字段，也不改变其他 pi Worker 的品牌默认头像。发行构建沿现有 server assets 整目录复制链携带该图片。

Wiki 管理员是宿主预置、可修改运行指令的本地 pi Worker，身份为 `AgentConfig.builtinId="wiki"`；不是 Codex 的别名，也不是任意 pi Agent 都能担任的授权角色。宿主只接纳启用且绑定 `pi/sdk` 的该内置身份。内部 pi Driver 配置 `executionProfile="wiki_curator"` 由宿主根据内置身份签发，通过 pi Driver/桥接透传，不新增公共 Driver SPI 权限字段；用户提示词、Worker 自报名字与库正文均不能签发该 profile。这里的知识运行、审核与 Publisher 属于 PuddingTeams 宿主，未下沉为 pi Extension 的完整房间能力。

知识库挂载独立于 Workspace/cwd。`KnowledgeRuntimeService` 为本轮签发 owner、session、选择 revision、binding/root/trust revisions 与已采纳快照的上下文；模型工具不能传 owner、context 或任意磁盘绝对路径。会话选择使用 `session:<sid>`，新 Session 首次从其 workbench 范围继承，显式空选择不回退，后续 cwd 变化不改库。工具执行复核当前选择与绑定；知识 pi Worker、独立整理执行器与 Manager 在 provider `streamFunction` wrapper 中再次核权，失败在进入 provider 前拒绝外发。SDK 的 context/before-provider 类 hook 会吞异常，只承担上下文装配，不能作为这道安全门。pi Driver 将搜索配置、执行 profile 和知识挂载 fingerprint 一起纳入会话复用判定，变化时建立干净的模型会话，不把已撤销或收窄库的旧内容带入续接。Teams 聊天记录仍独立保留。Manager 的持久 profile 变化则阻止续跑并要求新建工作会话，避免用新库继续旧模型上下文。

受限 Wiki pi 会话保留 pi 内嵌提示词与宿主追加指令，关闭原生 extensions、skills、prompt templates、context files 和本地设置装配；不装配通用 bash/read/write、MCP、Capability runtime 或团队递归委托工具。聊天 Worker 仅使用宿主知识检索工具和 `knowledge_request_curation`，后者只请求独立整理任务；任务执行器在独立 cache cwd 运行，工具只有知识读取与 `knowledge_submit_candidate`。这是一条工具白名单边界，不是 OS 沙箱证明。普通 pi 和外部 Connector 保持各自原有资源/工具策略，不能把普通 pi 的宽能力复用给 Wiki 候选生成。

工作台 Manager 和直接 Wiki 对话均可调用 `knowledge_request_curation(bindingId,task)`，复用独立 CuratorJob、审核与来源聊天通知。聊天 HTTP 入站的用户原话和 UploadStore 已验证附件字节由 `ChatKnowledgeIntake` 冻结到独立素材库；不根据模型文字解析路径，也不把 Manager/Worker 改写的委派任务冒充用户事实。`task` 是单独的整理指令，素材 `sourceIds` 只能由宿主关联签发。Manager 在真实 provider stream fence 中先确保本轮 user JSONL 落盘，再比对新 user 条目、完整文本与图片字节，才持久绑定来源；被准入拒绝的消息和尚未接收的未来消息没有可引用关联。工具按其 assistant toolCall 的前置 user 条目解析素材，委派晚到也不会吸收后续聊天；direct 则按已同步 `pudding:user_message` 的 operationId/sourceRefs 精确关联。关联保存在 `chat-knowledge-intakes.sqlite`，与模型提示和素材原件分离；不能从历史会话全量推断授权来源。不支持的附件在请求整理时明确报错，不能静默省略后声称完整整理。库选择/绑定权限仍在工具执行与 provider 发送前复核，聊天接收凭据不授予知识库写权限。

Manager 保留原生 input transform、`/skill:name` 和已加载 prompt-template 命令。真实 SDK `before_agent_start` 的 expanded prompt/images 只更新本轮执行匹配期望，不改独立素材原话/hash。HTTP 接收凭据复用该执行期望并采用同一正文规范；提前到达但尚未同步的 message_end 不确认消息。首 token 的 SDK `/skill:name` 与实际已加载模板名不当作绝对路径附件，命令参数中的绝对路径与未知路径仍遵循原路径检查/冻结规则。

`POST /api/wiki/curator-jobs` 是当前默认素材整理入口，接收 `operationId,bindingId,agentId,task,uploads?`；GET 列表/详情恢复任务。原话与附件由独立素材账本冻结原件、文本、SHA-256 与行定位；图片由声明 image input 的 Wiki 模型提取为独立待核对来源，失败为 `needs_attention`、保留原件且不生成候选；PDF 仍仅保留原件，解析/OCR 尚未接入。Job 冻结来源、已采纳基线、Agent revision、schema、库根 `AGENTS.md` 操作契约 hash。候选提交校验来源引用、路径、结构、字节预算与磁盘基线，正文及 index/log 同属固定批次。`running → submitting` 先持久化唯一 `frozenCandidate`，再登记 ReviewStore、转 `pending_review`；恢复已冻结提交不重跑模型。取消只允许 queued/running/needs_attention，不把已固定待审批次伪装成取消。旧 `/api/wiki/compile-jobs` 保留为已采纳来源的 Codex 次级编译入口；上文 2026-09-28 的“唯一入口”等描述是当日阶段记录。

当前审核以 ReviewStore 为决定事实源：approve 要求固定 manifest、批次代际与全部目标已阅；reject 允许真实已阅的空集或唯一合法目标子集。批准后由不调用模型的 MarkdownWikiPublisher 发布，复核权限/基线并记录逐文件回执；approved 无 journal 的启动空窗已补入对账，journal 与落盘决定/manifest 共同校验。index/log 使用独立 `controlEntries` 与正文在同一次 acceptance revision 采纳，不能用普通笔记采纳入口绕过控制文档审核；AGENTS/CLAUDE 不属于此候选发布支持面。审核 API 授权后聚合跨库分页，离线库保留历史，撤销库不进入名称、标题及计数；当前身份仍是本机 `localViewerIdentity`，不代表多用户认证完成。

截至本轮，全局待审核入口收敛到知识库主页，抽屉/主导航不再单列审核；已接默认 Wiki 管理员、显式逐文件已阅、整批二次确认、固定差异及原始来源查看。隔离浏览器演练使用真实 HTTP/ReviewStore/Publisher，仅模型生成被固定候选替代；真实模型、完整发行运行、退回修订、手动修改候选、左右/合并 diff 和页面修订历史仍需后续实现或验证。详见 `.pudding/handoff/2026-09-30-wiki-worker/知识库Worker与审核机制-开发交付-20260930.md`，不可将此增量视为总体功能全完成。

## 12. 验收标准

### 12.1 协议与状态机

- 新任务使用 `run`，续聊使用 `continue`，待授权只使用 `respond`；
- 同一 Session 同时最多一个 active/waiting Run；
- `respond` 后 `runHandle` 不变；
- 一次返回多个 request 时必须一次完整处理；
- 重复 response request_id 不重复执行授权；
- Interaction 过期明确显示，不自动创建新 Run。

### 12.2 PuddingClaw

- TTY `run` 仍可原地交互审批；
- 非 TTY/`--json` 返回结构化 `needs_input`；
- 新 `respond` 可从另一个 CLI 进程恢复同一 Run；
- continuation token 只出现在 `--json`/stdin 机器协议中，不进入 human output、stderr、普通日志和 Session 历史；
- `continue` 仍使用现有 `run --session`，历史 Session 不回归。

### 12.3 PuddingTeams

- `needs_input` 不再指导 manager 重跑 `team_task`；
- 页面刷新后审批卡仍能从存储恢复状态；
- 用户批准后不发送新的 child task，而是调用 Driver.respond；
- 完成结果写入原 direct/group manager Session，并自动触发后续汇总；
- 非当前窗口不能审批该 Interaction；
- Extension 无法读取凭证明文和 provider continuation token；
- 配置的 Extension 源中的 Connector 可被发现，但只有已安装、已配置且启用的 Agent 实例进入 roster；
- 禁用 Agent 后，旧 Session 即使仍持有旧 tool schema，也无法发起新委托；
- Driver 能力、安装、认证与启用状态在 API 和 UI 中一致；
- 每个 Agent 管理页可独立绑定多个 Capability Extension，并显示实际注册工具与信任来源；
- Agent/Capability 禁用后立即阻断新调用，空闲重建后不再出现在 manager 的 active tools；
- Extension 只能调用绑定 Agent 的 `ScopedAgentInvoker`，不能越权指定其他 Agent；
- Extension 配置变化不复制或重写 Pi Session JSONL 历史。

### 12.4 Connector Extension SDK

- PuddingClaw 第一方 Connector 完成完整回归；
- 声明式 Connector 样例可由用户复制后二开，并通过 validate/fixture 测试；
- ACP 代码型样例证明 stream/respond/cancel 可经 Extension Host 归一化；
- 未声明或未验证 `respond` 的 Connector 不展示可恢复审批能力；
- 任一 Connector 未安装、未认证、服务不可达时，`probe()` 返回可操作原因而不是运行时模糊失败；
- Connector 版本和真实上游版本可见，超出已验证范围时显示 `untested/incompatible`；
- 用户可用声明式 Connector 接入简单 CLI，并通过 validate 契约测试；
- 代码型 Connector 在隔离 Extension Host 中运行，未经授权不能 spawn、联网、读取工作区或使用 secret；
- 更新单个 Connector 不要求升级 PuddingTeams 核心，固定旧版本仍可回滚。

### 12.5 故障场景

- PuddingClaw Backend 重启：卡片转 expired，允许用户显式“重新执行”，不静默重跑；
- PuddingTeams Backend 重启：加密 provider state 可恢复；
- 浏览器断开：Child Run 仍 waiting_input；
- 用户拒绝：Run 收到 reject 并给出终态；
- worker stdout 非 JSON、重复终态、超大行、进程忽略 SIGTERM 都有测试。

## 13. 默认决策

以下不再作为开放问题，按此实施：

1. **协议统一语义，不统一命令名。**
2. **Session handle、Run handle、Interaction handle 分离。**
3. **PuddingClaw 不新增 `resume <session_id>`，只新增公开 `respond`。**
4. **Interaction token 不进 LLM、浏览器或普通 Session 历史。**
5. **HITL 采用暂停并外送；manager 不靠自然语言重试。**
6. **先抽 Runtime/Driver，再做 Extension 和 JSONL，避免一次改完所有层。**
7. **PuddingClaw 只声明已完成契约测试的 permission 与结构化 user_input；其他业务 HITL 不虚假声明支持。**
8. **任何用户/社区 Connector 只暴露已由上游协议和契约测试验证的操作能力。**
9. **核心只内置 Driver SPI/Runtime；具体 Agent 接入通过可独立安装升级的 Connector Extension 提供。**
10. **默认只安装 PuddingClaw 第一方 Connector，不预置大量第三方 Agent；其他接入依靠用户/团队二开。**
11. **Connector 作者应优先使用上游原生结构化协议，禁止用 TUI 文本猜测可恢复交互。**
12. **禁用是运行时授权状态，不删除历史 Session、Agent 配置或 Driver 代码。**
13. **每个 Agent 必须绑定一个 Connector Extension，并可通过零到多个 Pi Capability Extension 扩展业务能力。**
14. **每个启用 Agent 自动生成基础 delegation Pi Extension；其他 Capability Extension 由用户在 Agent 管理页添加和启用。**
15. **Extension 绑定 Agent 实例并只获得 ScopedAgentInvoker，不得直接 spawn、读取 Driver 凭证或消费私有 continuation token。**
16. **Connector Extension 与 Capability Extension 是两种独立包、独立 Manifest、独立版本和独立管理入口。**
17. **房间绑定 workspace 根目录，它同时是各 agent 写权限的安全边界。**
18. **交付物事实源是 push（agent 主动导出）或 observe（事件流/git diff 机械收集），不依赖模型声明，不扫描目录猜测；中间产物各 agent 自理。**
19. **第一阶段产物共享用本地目录约定，不引入 MinIO/对象存储。**
20. **项目未上线，不做任何向后兼容与历史数据迁移：旧字段直接替换、旧数据文件直接删除、`team_task` 在 per-agent 工具就绪后直接移除、不设兼容期。**

## 15. 工作区与产物交接（Workspace & Handoff）

> 2026-08-06 补充。回答两个问题：agent 间共享文件怎么做（对比 AgentTeams 的 MinIO）；中间产物与交付物如何分界。

### 15.1 两个概念必须分开

| 概念 | 含义 | 归属 |
| --- | --- | --- |
| **workspace** | 房间可选绑定的本地项目，agent"对什么干活"（用户项目/数据本身） | 用户在房间指定；未选择时保持平台原有默认 cwd |
| **handoff 产物** | Run 结束时的交付物，需要在 agent 之间、agent 与用户之间交接 | 平台登记管理 |

中间过程产物（scratch、临时文件、agent 私有 workspace 内部状态）**各 agent 自理，平台不介入**。AgentTeams 用 MinIO 是因为多节点容器必须走网络存储；PuddingTeams 单机形态下等价物就是本地目录约定，第一阶段不引入对象存储。

### 15.2 workspace 绑定

> 实现状态（P3-1，2026-08-10）：Workspace/Session 正确性已按平台实体收口，不再把路径直接挂在 Window 上。

- Workspace 是可选增强，不是聊天前置条件。未选择时 `WindowConfig.workspaceId` 缺省，并把创建时的平台默认 cwd 持久化为 `WindowConfig.cwdSnapshot`；manager 与 worker 都使用该快照，保持原有聊天入口且不创建伪 Workspace；
- `WorkspaceRecord` 保存 `rootPath + canonicalPath + gitRoot?`，按 `realpath` 后的 canonical path 去重；只有仍解析为同一可读目录时才标记可用。路径失效不阻断服务启动，只阻断对应 Window 执行，绝不回退到默认 cwd；
- 本地产品可通过 server-side native picker 取得真实服务端目录：macOS 调系统 `choose folder`，Windows 调 `FolderBrowserDialog`，取消不改变 UI；Web 内嵌目录浏览与未来 Electron 主进程选择器复用同一“返回 canonical 服务端路径”协议；
- `WindowConfig.workspaceId?` 只引用显式项目身份；direct Window 去重键为 `(worker, workspaceId ?? cwdSnapshot)`，无项目单聊在默认 cwd 变化后也不会复用旧目录的 Session；
- `DelegationRecord.workspaceId? + cwdSnapshot` 在委托创建时冻结。即使没有 Workspace，也必须冻结默认 cwd；run/continue/respond/cancel/artifact 全部读取快照，不重读 Window 当前值；
- 委托创建、respond/cancel admission 与原地切换共享 Window 生命周期门；Run 记录落盘后才释放 admission，切换可枚举并取消所有已接纳任务（包括 solo 路由到 direct 的任务）；
- manager 的 `SessionManager`、`ResourceLoader`、内置工具与 worker Driver 使用同一 workspace cwd；
- manager Session 可以共享同一个 `sessionDir`，但目录枚举与重启恢复必须使用不带 cwd 过滤的全量发现，再由 Window 保存的 Session ID 与 `cwdSnapshot` 确定归属；不能用某个 Workspace cwd 过滤共享目录。Session 存活判断还必须包含当前进程内已打开但尚未首次持久化的实例，避免 fresh solo Session 被误建替换；
- worker binding 同时记录 `workspaceId? + cwdSnapshot + agentRevision + sessionHandle`，项目/cwd 或 Agent 配置修订变化后不得续接旧 Session；
- Runtime 自持每个 active Run 的 AbortController；取消先持久化 `cancel_requested`，触发 Connector cancel/本地终止并等待有界确认，再按证据封存 `cancelled` 或进入 `observation_lost`，迟到 completed 由 Delegation CAS 决定且不得覆盖已封存 Receipt 或错误登记 artifact；
- 上下文切换支持显式 Workspace 与“不绑定项目”双向切换。direct/group 的 Workspace 是 Window 身份，切换只打开目标项目既有 Window 或创建新 Window，不允许原地覆盖；solo 因全局单例按 `workspaceId + cwdSnapshot` 停放 context。solo 切走时与消息/审批/委托接纳共用 Window 生命周期闸：先验证目标或创建新 Session，再取消 active/waiting Delegation、强制持久化并静止源 Session，原子提交 context 后才卸载旧内存实例；任一提交前步骤失败都保持源 context active；
- parked Session 不接受用户消息、委托、模型修改、审批恢复、Goal 恢复、业务决策回答或迟到 binding。恢复 JSONL 时必须在提交前校验文件存在且首行 canonical cwd 与 context `cwdSnapshot` 一致，不一致 fail closed；迟到终态只允许非触发式追加审计事实并立即卸载。Goal/Decision 的 durable trigger 若输给切换竞态，必须返回 deferred、使用独立审计 eventId 且不确认真实 outbox；context 再激活后以原 eventId 重试，只有 delivered/duplicate 才可确认。Session 目录只用于验证文件存在，归属始终以 Window active/parked Session ID 为准；
- `windows.json` v1 到 v2 采用一次性就地升级而不是长期兼容读取：先 clone/normalize 并通过完整 v2 不变量校验，再保留所有 Window、Session、active Session 与 handle，把旧 Window 级 `workerBindings[agentId]` 收敛为 `workerBindings[activeSession][agentId]`，补齐空 `parkedContexts`。源文件用临时文件 + fsync + rename 原子备份；同名备份内容不一致时使用 source hash 新名称，验证与备份成功后才原子提交 v2，随后运行时只写 v2；
- workspace 是项目上下文和默认操作范围，不是平台承诺的通用文件权限沙箱。Codex sandbox、Claude permission mode、Agent 自身权限与 OS 隔离才负责强制执行；
- artifact 登记和下载以 Delegation `cwdSnapshot` 做 realpath containment，项目外绝对路径与越界 symlink 在登记时拒绝；下载使用 `O_NOFOLLOW` 文件描述符并以 dev/ino 复核，校验后不再按可变路径重开文件。
- 用户消息中的绝对路径在服务端消息入口解析，不交给模型自行决定权限。Workspace 内路径原样传递；Workspace 外普通文件先以 `O_NOFOLLOW` 文件描述符打开、`fstat` 校验普通文件、大小及预检 `dev/ino` 身份，再复制到 `<PUDDINGTEAMS_HOME>/uploads/<sessionId>/`，随后只把冻结路径送入模型。识别出的绝对路径不存在或不可访问时直接拒绝消息，不能把原 host path 原样留给 Agent 尝试。外部目录直接拒绝，必须登记为 Workspace 或通过显式临时挂载范围授权，粘贴路径本身不构成目录授权。打开附件时仅允许当前 active Session 的附件子目录，不允许整个 uploads 根或同 Window 历史 Session 跨会话读取。

> 实现状态（2026-08-11，Workspace 信任门）：`WorkspaceRecord` 增加 `WorkspaceTrust{state: pending|trusted|denied, decidedAt, policyVersion: 1, canonicalPathAtDecision, approvedResources?}`（`approvedResources` 缺省为 context/skills/prompts 三类全批准）。managed Workspace 默认 trusted，外部项目初始 pending，`realpath` 与决定时记录不一致自动退回 pending；信任决定经 `PUT /api/workspaces/:id/trust` 保存，`GET /api/workspaces/:id` 只返回资源类型与数量摘要、未批准前不返回正文。Workspace context/skills/prompts 进入装配候选的判定收敛为单点——`显式 workspaceId && trust = trusted && approvedResources 含对应 kind`，再与 Agent 自身资源开关相与；Preview、会话创建/重开与 Delegation 统一消费该判定。撤销信任将相关活跃 Session 标记 `runtimeDirty`。无 `workspaceId` 时 cwd 快照固定为 `PUDDINGTEAMS_HOME/workspaces/unscoped` 并强制关闭全部 Workspace 资源发现。详见 `docs/2026-08-11-用户数据目录与Workspace上下文迁移方案.md` §6.3/§7。

### 15.3 目录布局

```text
<workspace>/
├─ …（用户项目本身，agent 直接读写）
└─ .pudding/
   └─ handoff/<delegationId>/     # 本次 Run 的交付物
```

### 15.4 handoff 的两种来源，一个登记接口

"怎么知道交付物是什么"是 Driver/Connector 的事；"交付物的登记与交接"是 Runtime 的事。两种来源对 Runtime 无差别：

| 模式 | 适用 | 机制 |
| --- | --- | --- |
| **push** | PuddingClaw（自家 CLI） | `puddingclaw agent run --export <dir>`：执行完把交付物导出到指定目录，result 中声明清单 |
| **observe** | Codex / Claude / Pi（改不了的第三方） | Driver 从事件流机械收集（`apply_patch` / `Write` / `Edit` 事件触碰的文件集），git 仓库用 diff、非 git 用目录快照 diff 兜底 |

关键原则：**不依赖模型自觉声明，也不扫描目录猜测**。observe 模式下模型在最终回复里的清单只作为命名/kind 元数据补充，事实源是事件流和文件系统。Git observe 在任务开始同时冻结两类基线：既有 porcelain dirty 路径集合与任务前 HEAD；完成时合并“新增 dirty 路径”和 `baseline HEAD..HEAD` 的已提交路径。不能只看任务结束时的 `git status`，因为 Worker 正确执行 `git add/commit` 后工作树会 clean，只看 porcelain 会错误地产生 `artifact 0`。任务前已经 dirty 且保持原状的路径仍不归因给 Worker；如果 Worker 把它们纳入新提交，则 HEAD diff 会诚实暴露为本次变更。coding agent 的交付物往往就是 workspace 里的改动本身，git diff 天然表达；`.pudding/handoff/` 只装报告、导出物这类"工作区之外的产物"。

### 15.4.1 为什么 PuddingClaw 不向 observe 对齐

push/observe 的分工不是"自家 CLI 没改"，而是两类 agent 的本质差异：

| | 修改型（Codex/Claude/Pi） | 生成型（PuddingClaw） |
| --- | --- | --- |
| 输入 | workspace 里的项目文件 | 数据库/数据源 API，不读文件系统 |
| 输出 | 对 workspace 的就地修改（有 before/after） | 报告、导出数据（生成物，无 before） |
| 文件产生地 | 平台可见的 cwd | backend 管理的 workspace（可能远程） |

git/fs diff 观察对 PuddingClaw 不成立：房间目录里没有它要写的东西；文件在 backend 侧（远程时另一台机器），CLI 侧不可见；生成物没有 diff 语义，untracked 文件堆分不清交付物与内部 scratch。即使把 `PUDDINGCLAW_PROJECTS_ROOT` 指向房间目录，落入 diff 视野的也是 session 状态等内部文件，恰恰制造"扫描目录猜测"。

统一发生在**语义层**（四操作、PWCP 事件、artifacts 清单），机制层保留差异正是 Driver 存在的意义。流式落地（Phase 7）后，事件流观察对 PuddingClaw 同样成立，进度体验与 coding agent 一致；只有 fs diff 这条轨迹不适用它。

### 15.5 软引导入口（提升质量，不作事实源）

1. **`AGENTS.md` / `CLAUDE.md`**：平台在绑定 workspace 时写入 handoff 约定（报告类交付物写入 `.pudding/handoff/`，最终回复列出清单）——Codex、Claude、Pi 都自动读取；
2. **任务 prompt 包装**：Capability Extension 派活时在任务文本中附带交付约定；
3. **Pi 子 agent**：`createAgentSession` 时进 system prompt 片段。

### 15.6 产物数据流

```text
Run 结束
  → Driver 汇总 artifacts 清单（push / observe）
  → CompletedResult.artifacts（§4.3）
  → Runtime artifacts store 登记（名称/路径/kind/大小/产出者/delegationId）
```

### 15.6.1 运行文件与交付物查看边界

运行文件不是第二套 Artifact，也不是“扫描 Workspace 后把所有文件都列出来”。列表的权威范围是 Delegation 绑定的 `workspaceExecutionScopeId`：运行中由平台把当前 manifest 与入场 baseline 比较，终态优先读取已封存的 `WorkspaceChangeSet.changedPaths`。前端只能提交 scope 内的相对路径；Server 会再次核对 Delegation ↔ scope ↔ changed path 绑定，并拒绝绝对路径、穿越、符号链接和 baseline 中未变化的文件。

- `GET /api/delegations/:id/files`：本次执行工作副本的变更文件清单；
- `GET /api/delegations/:id/files/content?path=`：至多 2 MiB 的完整 UTF-8 文本预览；即使文件在大小检查后增长，也只按文件描述符读取上限加 1 字节并拒绝超限，不输出局部内容；
- `GET /api/artifacts/:id/preview`：只对受支持扩展名返回至多 2 MiB 的完整 UTF-8 冻结文本；读取后核对登记时的 SHA-256，不完整、超限或哈希不符时拒绝预览；
- `GET /api/artifacts/:id/content`：先复制冻结 blob 并核对登记 SHA-256，再从本次请求的独立已验证副本下载完整文件；哈希冲突返回 409，不发送未验证内容或哈希响应头；下载不受内联预览上限影响；
- `POST /api/delegations/:id/files/open`：让 Server 所在本机的系统默认应用打开当前工作副本；
- `POST /api/artifacts/:id/open`：以原扩展名物化只读副本，复制过程中核对登记 SHA-256，一致后才交给系统默认应用，避免把 UUID blob 或已损坏快照交给错误应用。

UI 必须明确标注“工作副本会变化”和“冻结快照 + 内容哈希”，不能把两者混成同一种完成证据。Markdown 预览不自动加载外部图片，防止仅查看 Worker 产物就触发未授权的网络请求。Excel 不在浏览器内伪造编辑器：`.xlsx/.xls` 默认走系统关联的 Excel、Numbers 或其他工具；Web/远端部署仍保留下载作为可迁移退路。
Markdown 预览中的链接仅允许明确的 HTTP(S) 与 mailto 目标在新标签打开；相对路径、`file:`、`javascript:` 等未经解析或不允许的目标只显示文字。要打开本地相对文件须经工作区路径 resolver 与授权校验，不能直接把 Markdown href 当应用路由或本机文件路径使用。
交付物下载按钮依赖成功响应的 `Content-Disposition: attachment` 保存文件，不设置会把 HTTP 错误也保存为交付物的链接 `download` 属性。下载在新标签发起，浏览器导航请求失败时显示纯文本原因，原执行详情保留；API 客户端继续收到结构化 JSON 错误。

Artifact 列表中的 `size` 与 `contentHash` 均从登记时冻结副本的实际读取中取得，不采用 Worker 对源文件长度的声明。下载的逐请求临时副本存放在 Home 内部临时目录，请求结束清理；服务端取得 Home 单写者 Lease 后初始化时清理前次进程中断留下的副本，不触碰登记 blob。

登记交付物时先解析源路径是否落在本次 `cwdSnapshot`，随后用 `O_NOFOLLOW` 打开源文件，重新核对 root/路径与文件描述符的 inode；复制、大小统计和 SHA-256 计算都绑定该描述符。blob 在元数据落盘前设为只读；若源路径身份变化或登记元数据落盘失败，拒绝登记并清理未登记 blob，不能把范围外文件或孤儿副本当作交付物。

运行文件/交付物列表实时回读只接受本视图最新请求；自动轮询不在旧请求仍在途时继续发起新请求，避免慢网络下不断使结果失效；手动刷新可取代旧请求。刷新失败时旧列表只能标为“上次读取”，不能伪装成当前状态。交付物文本超过内联上限时明确拒绝预览并指向完整下载或系统打开，不把局部字节冒充完整冻结证据。CSV/TSV 表格预览最多呈现前 200 行、每行前 30 列；达到上限且仍有未显示数据时明确提示预览被截断，引导下载或系统打开完整文件，不能把局部预览作为完整审核证据。
选中文件变化时，预览正文和错误必须匹配当前委托、视图、文件及可见元数据；新请求进入前即显示加载态，不能把上一文件的正文或失败原因短暂显示在新文件名与哈希下。

### 15.7 PuddingClaw CLI 改造补充

在 §11 Phase 2 清单之外增加：`run`/`respond` 支持 `--export <dir>`，执行终态时把交付物（报告、导出数据）复制到该目录并在 result JSON 中声明 `artifacts`。CLI 不知道平台目录结构，导出路径由 Driver 按 §15.3 约定生成并传入。

这套方案的最小正确闭环是：**PuddingTeams 先能区分 Session 续聊和 Run 恢复，PuddingClaw CLI 再补公开 `respond`，最后由 InteractionBroker 把浏览器审批准确送回原 Run。** Extension、JSONL 和更多 Agent 都建立在这个闭环之上，而不是反过来。


### 2026-09-07：Pi Worker 输出截断的终态处理

LocalPiDriver 以本次 prompt 新增的 assistant 消息判断边界，不能复用旧任务结果。Provider `stopReason=length` 表示输出被截断（额度可能被思考消耗），不代表完成；不硬编码 8192，也不擅自提高模型额度。在原 Session/Run 中保留全部工具结果，发送缩短输出、核对已有交付物并分步执行的续接提示，最多自动续接一次；期间发出 `output_limit_recovery` progress。再次截断返回可恢复 `failed/output_limit_exceeded`，保留部分正文、停止原因和累计 token 用量。自动续接提示不能保证所有外部工具幂等，仍受原工具权限与审批约束。

只有本次 prompt 正常 `stop` 且最终正文非空时才报告 completed。只有思考或空白正文返回 `empty_worker_result`；缺少新 assistant 或未结算工具等边界返回 `incomplete_worker_turn`。取消及 Provider error 保留原有语义；length 续接次数与限流重试计数分别有界。原始思考、工具结果仍由 Session JSONL 保存，不把思考文本拼成最终交付。

### 2026-09-30 后续增量：图片提取、退回修订与页面历史

本增量在知识库主页继续使用统一待审核入口，抽屉不增加“待审核”。图片经现有 pi SDK 的独立无工具视觉会话解析，模型须声明 image input（自定义 Provider 可勾选支持图片）；原件、提取正文、区域/告警及提取模型/配置摘要是独立固定证据。解析失败保留原件，重试创建新任务，不跳过人工审批；PDF 解析/OCR 仍未接入。

`WikiRevisionService` 以 ReviewStore 的 returned 操作为 durable outbox：必填反馈与真实已阅子集固定后，幂等创建新 CuratorJob。新任务保留原候选、原来源及被实际读取的旧采纳证据，反馈作为独立文字来源；每轮生成全新候选重新审核。原始 job 因果不变，后续 retry 链用于详情投影，不用旧 approval 批准新字节。

页面历史由当前来源快照与同次原子写入的 historyOutbox 驱动，SQLite 按 operation/noteId 幂等投影，启动与查询修复未确认 outbox。Publisher 真正 committed 的组和自动观察到的外部文件版本可进入历史；候选、退回、拒绝、未生效组不进入。Agent 发布记录审核人/渠道/时间及 operation/batch/decision；外部同步只记录平台观察到的字节与同步时间，不推断实际编辑者或声称用户确认。查询按库权限保护，支持原型正文、全文与变化视图。手改候选、完整管理操作与 PDF 尚不属本增量完成范围，用户实测验收独立于自动测试。

### 2026-09-30 Wiki 图片随库发布

页面采纳的图片原件与 Markdown 一起发布到 `binding.contentRoot`，标准 Wiki 是绑定根下的 `wiki/`，普通 Markdown 库是绑定根本身。资产路径为 `assets/images/<originalHash>.<真实格式后缀>`；页面引用按自身所在目录生成 Markdown 相对路径，不能写应用上传绝对路径、对象库路径或 API URL。用户复制整个 Wiki 内容文件夹后，页面与原图仍可独立打开。

原图字节只取宿主已冻结且该页面实际引用的来源；模型只获得 source→asset 映射，不能指定任意磁盘文件。图片作为 `PublicationFile(kind="image",mediaType,sourceIds)` 纳入同一固定批次，manifest 覆盖原图 hash / 目标 / 基线，审核 expectedTargets 与 reviewedFiles 也覆盖图片。依赖组先资产后 Markdown，拒绝与退回零写 Wiki。已存在的同哈希图列入批次安全复用：预检与组提交重新核对实际字节，不能覆盖同路径的第三态内容。图片不登记为 Markdown 采纳条目、搜索页或独立页面历史；发布中断复用 journal 对账，不能仅因图片存在就声称页面发布成功。

候选图片从 `/api/wiki/batches/:id/assets?path=` 的固定批次读取；历史图片从 `/api/knowledge/:id/history/:versionId/assets?path=` 读取该已生效版本的固定原件。两者核对权限、文件类型、hash 与实际引用，不从当前磁盘替换图推断旧版本。当前正文用库内 asset 端点，允许用户在 Obsidian 替换图片或使用普通文件名；原图 hash 强校验属于固定候选、固定发布历史与 Publisher，不能成为当前用户文件阅读的审批门。pi 适配层和 Driver SPI 均不直接写 Wiki。

本轮图片发布入口为 Wiki 管理员整理通道（知识库页面、Manager 转交或直接对话）。原有 Codex 编译通道只交付已采纳 Markdown 快照，没有原图来源与固定 receipt，故图片候选在准入前明确拒绝并引导改走管理员整理，不能审批后才失败或隐式读取当前图库。图片识别质量仍需真实商业视觉模型单独验收。

### 2026-09-30 用户外部编辑直接生效

用户在 Obsidian 或其他外部编辑器直接保存到已绑定知识库的文件，是该库当前内容的事实源。平台自动观察新建、修改、重命名和删除，更新内部快照与检索引用；不创建待审核或待采纳任务，不要求 schema 合格才可阅读，不修改或修复用户文件。删除后不继续把旧文本当当前 Agent 来源；历史文本属于只读记录，不能自动恢复已删文件。未绑定的 Workspace 与原始上传素材仍不能借此自动入库。

只有平台 Agent 生成的候选变更走固定批次审核与 Publisher。扫描和发布/恢复共享绑定级协调；平台已写但未完成依赖组的残留必须按持久 journal 隔离，不能被扫描重新命名为“外部修改”后跳过审核或组提交。用户随后写出的不同外部内容则可正常同步，不按未完成候选回写用户修改。

外部版本历史使用 `external_sync` 渠道及平台观察身份，表示同步时间和实际文件快照，不声称知道真实编辑者，也没有关联审批决定。当前图片读取服从用户当前文件；已有 Agent 发布版本的原图仍从其独立固定对象读取。上述直接生效替换此前 `pending_new/pending_changed → 显式采纳` 的外部编辑政策；平台内候选、发布保护和库权限边界继续成立。


## 2026-09-30：稍后读宿主能力

稍后读使用独立侧边栏与 /read-later 静态路由；用户收藏无需知识库。普通 Teams pi 业务 Worker 可获得宿主 read_later_save_url，只收藏并排队，不自动整理或发布；Manager 通过现有委派工具交给 Worker 处理；受限 Wiki Worker 不增加此工具。抓取复用 web-research 无宿主共享网络核心，Fake-IP 域名 HTTPS 可经本地 TUN 直连或在可信配置代理中 CONNECT 原域名，普通公网 DNS 仍固定校验 IP；TLS 校验不变。网页正文和图片晋升冻结为 KnowledgeSource 后继续走已有 Curator、来源核对及人审 Publisher，房间与完整审核能力仍属于 Teams。实现、字段及验证边界见 [稍后读迁移实现](2026-09-30-稍后读迁移实现.md)。

### 2026-09-30：人脉结构 v2 的公司实体与任职关系

内置 people 预置 revision=2，公司/组织统一为 org（Orgs），不另设 company 实体。affiliation（Affiliations）把人物、公司和相应身份/职位联系起来：held_by 从 affiliation 指向 person，at_org 从 affiliation 指向 org；role/status/startDate/endDate 属于 affiliation，人物页不再声明 org/company/role 标量。多人共享公司页、一人可有多个任职页；来源与正式发布沿既有知识候选/人审/Publisher 边界。
