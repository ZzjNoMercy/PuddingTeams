# 通用 Agent 接入方案：Runtime、Driver、Extension 与可恢复交互

> 日期：2026-08-06  
> 状态：持续实施；PuddingClaw 本机 Connector 已接通
> 适用仓库：PuddingTeams、PuddingClaw  
> 目标：让 PuddingTeams 以同一套底层生命周期接入 PuddingClaw、Pi、Hermes、OpenClaw、Grok Build、Codex、Claude Code 等 Agent，同时正确处理 Session 连续性、当前 Run 的人工审批、流式进度和凭证隔离。

## 0. 结论先行

这次方案的核心不是再造一套“统一 CLI 命令”，而是统一四个**操作语义**，再由每个 Driver 映射到真实 Agent：

1. `run`：创建新 Session 并启动第一条 Run；
2. `continue`：在已有 Session 中创建下一条 Run；
3. `respond`：给当前仍在等待输入的同一条 Run 提交审批或回答；
4. `cancel`：取消当前 Run，不删除 Session。

其中最容易混淆、也正是当前故障来源的是：

- `continue` 面向 **Session**，前一条 Run 必须已结束；
- `respond` 面向 **Run/Interaction**，当前 Run 仍处于 `waiting_input`；
- 两者不能互相替代，也不能都叫 `resume`。

PuddingClaw 当前已经具备后端 `respond` 能力：`POST /api/headless/runs/{run_id}/resume` 会恢复原 Run；它当前的 Session 连续性则是 `puddingclaw agent run ... --session <session_id>`。因此：

- **不新增** `puddingclaw resume <session_id>`；
- **新增**公开、非 TTY 的 `puddingclaw agent respond <run_id> --input-json - --json`；
- PuddingTeams Driver 把统一的 `continue(...)` 映射到现有 `run --session`，把 `respond(...)` 映射到新命令。

PuddingTeams 当前遇到 `needs_input` 后把它转成普通文本，让 manager 下一轮重新调用 `team_task`。这会创建新 Run，而 PuddingClaw 原 Run 仍在等待授权，于是得到 `Session already has an active Run or pending input`。正确修复是：**保存待处理 Interaction，由消费端审批后调用 `respond`，绝不重跑任务。**

产品能力采用两层组合，而不是把所有逻辑继续堆进 Driver：

- **基础 Driver SPI 负责接入规范**：安装探测、认证、run/continue/respond/cancel、Session/Run handle 和事件归一化；具体 Agent 的协议映射由 Connector Extension 实现；
- **每个 Agent 实例通过 Pi Extension 扩展能力**：给 manager 注册该 Agent 的专属工具、参数 Schema、提示规则和结果投影；
- Agent 管理页同时管理 Connector Extension 和 Capability Extension：每个 Agent 必须绑定一个 Connector，可再绑定零到多个 Capability Extension；同一个 Extension 也可用不同配置绑定到多个 Agent；
- Driver 不注册业务工具，Extension 不理解或调用 Agent 私有 CLI/HTTP 协议，所有执行必须回到 scoped `AgentInvoker`。

## 1. 第一性原理

### 1.1 平台真正需要统一的是什么

PuddingTeams 对任意 Agent 只承担六类稳定职责：

| 职责 | 平台不变量 | Agent 变量 |
| --- | --- | --- |
| 路由 | Agent 目录、能力筛选 | 描述、适用任务、专属选项 |
| 执行 | 启动、超时、取消、错误分类 | CLI、HTTP、RPC、ACP |
| 连续性 | 保存不透明 Session handle | handle 的生成和消费方式 |
| 交互 | 保存 pending Interaction、接收用户决定 | 权限、问题、规则确认等类型 |
| 可观测 | 统一事件与终态 | Agent 能提供的进度丰富度 |
| 凭证 | 加密存储、最小化注入 | 各 Agent 所需的环境变量或 token |
| 产物 | 工作区绑定、产物登记与大小限制 | 交付物如何产生与取出（push / observe） |

因此正确边界是：

```text
pi Extension（给模型看的工具与说明）
        ↓ 房间链路只拿 ScopedAgentInvoker，不拿凭证明文
Agent Runtime（生命周期、状态机、持久化、事件）
        ↓
Agent Driver（PuddingClaw / Codex / Claude 的语义映射）
        ↓
Transport（spawn / HTTP / RPC / ACP）
```

职责判定规则非常简单：

- “如何联系这个 Agent、如何恢复同一 Run”属于 Driver；
- “模型何时应该使用它、要填哪些业务参数、结果怎么投影”属于 Extension；
- “是否允许本次调用、状态如何持久化、事件怎么广播”属于 Runtime；
- “CLI 参数模板”和“数据库分析工具 Schema”不得出现在同一个模块里。

### 1.2 必须分开的三个身份

| 身份 | 生命周期 | 用途 |
| --- | --- | --- |
| `sessionHandle` | 多条 Run | 让下一条用户消息继承 Agent 历史 |
| `runHandle` | 一条 Run | 标识本次执行，用于取消、追踪和定位错误 |
| `interactionHandle` | 一次或一组待输入 | 只用于恢复当前 Run；可能含 bearer token，不能进模型上下文 |

`requestId` 不是第四种 handle。它只标识一次 Interaction 中的某个具体问题；并行工具可能一次返回多个 `requestId`，必须完整回答当前集合。

### 1.3 状态机不允许“靠自然语言重试”

```text
无 Session ── run ──> running ───────────────> completed/failed/blocked
                         │
                         └──> waiting_input ── respond ──> running
                                     │                         │
                                     └── reject ───────────────┘

已有空闲 Session ── continue ──> 新 Run 的 running
```

约束：

- `continue` 只允许 Session 空闲时调用；
- `respond` 必须携带服务端返回的 Interaction 句柄，并恢复原 `runHandle`；
- `waiting_input` 不是 `failed`，也不是“提示用户后重新运行”；
- 同一 Interaction 的重复提交必须幂等；
- 用户拒绝也是合法响应，Run 应继续到可解释终态，而不是让平台伪造成功。

## 2. 两个仓库的源码事实

### 2.1 PuddingTeams 当前行为

源码位置：

- `apps/server/src/store/teams.ts`
- `apps/server/src/pi-bridge/team-task.ts`
- `apps/server/src/pi-bridge/session-store.ts`
- `apps/server/src/routes/chat.ts`

已确认事实：

1. `TeamsStore.runAgent()` 每次用 `spawn(..., stdio: ["pipe", "pipe", "pipe"])` 启动 Worker；stdin 写一份 JSON，stdout 只按**单个 JSON**解析。
2. Session 连续性现保存在 `WindowConfig.workerBindings[agentId].sessionHandle`；继续任务时，经对应 Driver 把不透明 handle 映射回 Worker 私有字段（PuddingClaw 为 stdin `session_id`）。
3. `team_task` 遇到 `needs_input` 后只生成一段文本，默认指导 manager “等用户回复后重试”。这对业务参数澄清尚可，对仍占用原 Run 的权限 HITL 是错误的。
4. `session-store.ts` 当前通过 `customTools` 注入单个 `team_task`；并未使用方案文档设想的 per-agent Extension。
5. WebSocket 已能转发 pi tool update 和 custom message，前端也已有 `pudding:task_assign`、`pudding:task_result` 的渲染入口，可扩展为审批卡，无需新建第二套实时通道。
6. 当前 `CredentialsStore` 直接归 `TeamsStore` 持有并在 spawn 前注入环境变量；这一安全边界应该保留，不应把 `CredentialsStore` 传给 Extension。

### 2.2 PuddingClaw 当前行为

源码位置：

- `backend/api/headless.py`
- `backend/graph/deepagents_manager.py`
- `backend/graph/permission_resume.py`
- `packages/puddingclaw-cli/dist/cli.js`

已确认事实：

1. `puddingclaw agent run <message> --session <session_id> --json` 已能在同一 Session 中创建下一条 Run；stdin 的 `session_id` 也保留兼容。
2. Headless API 在权限中断时返回：`run_id`、`session_id`、`needs_input`、`continuation_token`，并保持原 Agent stream、LangGraph checkpoint thread 和 Run 存活。
3. `POST /api/headless/runs/{run_id}/resume` 会校验 continuation token，要求一次解决完整 pending request 集合，然后恢复**同一条 Run**。
4. CLI 在交互式 TTY 中可在一次 `run` 进程内询问用户并自动调用 Resume API；在 `--json` 或非 TTY 下会原样返回 `needs_input` 并退出，不会私自授权。
5. CLI 已提供公开、非 TTY 的 `respond` 子命令，PuddingTeams 通过 `stdio: pipe` 恢复原 Run。
6. 当前 Headless 外送交互只支持 permission；其他业务 HITL 仍 fail-closed。协议可以通用，但 PuddingClaw Driver 第一版必须声明 `interactionKinds: ["permission"]`。
7. PuddingClaw 的 live execution 目前保存在后端进程内。PuddingClaw 后端重启后，旧 continuation token 无法恢复该 Run，Resume API 会返回 410。这是现有限制，不能由 PuddingTeams 文档假装解决。
8. 2026-08-23 起 PuddingClaw Connector 同时支持 `spawn`（本机 CLI）与 `http`（直连 Headless NDJSON）两种 transport；二者都受 PuddingClaw 的本机回环限制，不读取或传递 Worker Access Key、`PUDDINGCLAW_TOKEN`、`PUDDINGCLAW_HEADLESS_TOKEN`。Connector manifest 因此申请 `spawn`、`network`，但不声明 secret；Platform 也不展示 PuddingClaw Token 配置。

### 3.1 Driver 是唯一理解 Agent 私有协议的层

```ts
interface AgentDriver {
  id: string;
  capabilities(): Promise<DriverCapabilities>;
  run(input: RunInput, ctx: InvocationContext): AsyncIterable<AgentEvent>;
  continue(input: ContinueInput, ctx: InvocationContext): AsyncIterable<AgentEvent>;
  respond(input: RespondInput, ctx: InvocationContext): AsyncIterable<AgentEvent>;
  cancel?(input: CancelInput, ctx: InvocationContext): Promise<void>;
  probe(ctx: InvocationContext): Promise<ProbeResult>;
}

interface DriverCapabilities {
  operations: Array<"run" | "continue" | "respond" | "cancel">;
  interactionKinds: Array<"permission" | "question" | "confirmation">;
  progress: "none" | "coarse" | "stream";
  // spawn=子进程 CLI；http/rpc/acp=网络协议；sdk=进程内 SDK（如本地 pi）。
  transport: "spawn" | "http" | "rpc" | "acp" | "sdk";
}
```

注意：这是 TypeScript 内部接口，不要求外部 CLI 出现同名命令。统一的是语义，不是字符串。

PuddingTeams 核心只内置 Driver SPI 和 Registry，不长期内置所有第三方 Agent 的具体映射。具体映射由可独立安装、升级的 Connector Extension 注册到 Driver Registry。必须区分五层状态：

1. `available`：本地、团队或社区目录中存在相应 Connector Extension；
2. `installed`：Connector Extension 已安装并通过 manifest/engine 校验；
3. `detected`：本机已找到对应 CLI，或已配置可访问的服务端；
4. `configured`：认证和必要参数可用；
5. `enabled`：用户明确允许该 Agent 实例进入 roster 并被委托。

默认发行预装四个第一方 Connector：PuddingClaw（产品首条链路）、本地 pi（§9.1 Pi 调 Pi 标杆）、Codex 与 Claude Code（路线图 P1 主流 coding agent 样本，均为 spawn + JSONL 流式，无 HITL 承诺、`interactionKinds: []`）；核心 delegation 是 Runtime 生成能力，不算用户 Capability Extension。Hermes、OpenClaw、Grok Build 等只作为 Connector 编写指南中的协议案例或社区扩展候选，不承诺在默认目录预置。用户或团队可以二次开发并安装自己的 Connector；更新 Connector 不要求发布整个 PuddingTeams。

### 3.2 Extension 只能拿窄接口

```ts
interface ScopedAgentInvoker {
  readonly agentId: string;
  capabilities(): Promise<DriverCapabilities>;
  delegate(input: ScopedDelegateInput): Promise<AgentInvokeResult>;
}

interface AgentExtensionContext<TConfig = unknown> {
  agent: Readonly<AgentSummary>;
  config: Readonly<TConfig>;
  invoker: ScopedAgentInvoker;       // 已绑定 agentId，Extension 不能改投其他 Agent
  events: ExtensionEventPublisher;   // 只能发命名空间内的可观测事件
}
```

Extension 不得拿到：

- `CredentialsStore`；
- Worker token 明文；
- continuation token；
- 任意 spawn 能力。

凭证仍由 Runtime 在调用 Driver/Transport 前注入。这样 Extension 即使被模型诱导，也无法把密钥写进 tool result。

还必须明确一个现实安全边界：Pi Extension 是可执行 TypeScript/JavaScript。TypeScript 接口只能约束正常代码，不能把恶意第三方 Extension 变成沙箱。第一版只允许 PuddingTeams 内置、经过审核的 Extension 进程内加载；后续用户安装的第三方 Extension 必须显式显示来源和代码执行风险，并放到隔离 Extension Host 中，不能直接把任意本地路径 `import()` 进 server 进程。

#### 3.2.1 `AgentInvoker` 发起委托，但不等于 OS `spawn`

在 PuddingTeams 房间链路里，`AgentInvoker` 是 manager 工具与 Runtime 之间唯一的业务调度/治理入口，不是统一的子进程启动器。实际调用顺序固定为：

```text
manager Extension tool.execute()
  → ScopedAgentInvoker.delegate()       # 已绑定 agentId 的窄接口
  → AgentInvoker.delegate()             # 鉴权、窗口成员校验、cwd/凭证/sessionHandle 解析
  → AgentRuntime.delegate()             # 创建 Delegation、会话锁、状态机、持久化与事件处理
  → AgentDriver.run()/continue()        # 解释具体 Agent 的运行/续接协议
  → Transport                           # spawn / HTTP / RPC / ACP / SDK
```

因此要区分两种口语中的“spawn agent”：

- 如果指“接受并创建一次 worker 委托”，可以说由 `AgentInvoker` 发起，且 Runtime 会在 Driver 启动前先创建 Delegation；
- 如果指 Node.js `child_process.spawn()` 创建 OS 子进程，则只在 `transport:"spawn"` 的 Driver 内发生，当前通过共享 `spawnWorker()` 实现。Codex、Claude Code、PuddingClaw CLI 和声明式 CLI Connector 属于这一类；
- 本地 pi worker 的 `LocalPiDriver` 使用进程内 pi SDK Session，`transport:"sdk"`，不会创建 worker 子进程；HTTP/RPC/ACP Connector 也按各自 Transport 执行，不经过 `spawnWorker()`。

这也是为什么 Extension 只获得 `ScopedAgentInvoker`：上层只表达“委托哪个已绑定 Agent、run 还是 continue”，真正的进程、网络或 SDK 执行策略必须留在 Driver/Transport。`AgentInvoker` 返回的 `AgentInvokeResult` 是平台业务投影，不是某一种 Transport 的原始进程结果。

源码定位：治理入口在 `apps/server/src/agent-runtime/invoker.ts`，生命周期引擎在 `agent-runtime/runtime.ts`，本地 pi SDK Driver 在 `agent-runtime/pi-driver.ts`，CLI 真正调用 `spawnWorker()` 的参考实现分别在 `extensions/connectors/codex/driver/index.ts`、`extensions/connectors/claude-code/driver/index.ts` 与 `agent-runtime/puddingclaw-driver.ts`。

这里的“Extension 只获得 `ScopedAgentInvoker`”专指装配进 **PuddingTeams manager Session** 的平台基础委托 Extension 和 Capability Extension。双宿主 Connector 包供纯 pi 使用的 `pi/` 门面运行在 PuddingTeams 房间体系之外，执行路径见 §9.5；它不会获得、也不会经过 PuddingTeams 的 `AgentInvoker`。

#### 3.2.2 manager 侧 pi Extension 的实际样式与执行路径

PuddingTeams 并不是让 manager 模型直接调用 `AgentInvoker`。平台按 roster 为每个 Agent 生成一个具名 inline pi Extension，实际形态是 `(pi: ExtensionAPI) => void` factory，在 factory 内通过 `pi.registerTool()` 注册工具。下面是当前 `agentDelegationFactory()` 的等价缩略版；省略了 solo 单聊镜像、Goal 字段校验、HITL 和 Artifact 文案，但保留真实边界：

源码定位：factory 构造与工具 `execute()` 在 `apps/server/src/pi-bridge/agent-extensions.ts`；`extensionFactories` 注入 `DefaultResourceLoader` 并交给 `createAgentSession()` 的装配入口在 `apps/server/src/pi-bridge/session-store.ts`。

```ts
function agentDelegationFactory(agent, deps) {
  return (pi: ExtensionAPI) => {
    pi.registerTool({
      name: `agent_${toolSafeId(agent.name)}__delegate`,
      label: `${agentDisplayName(agent)} · 委托`,
      description: "把任务委托给这个 worker 并返回最终结果",
      parameters: DelegateParams,

      async execute(toolCallId, params, signal, onUpdate) {
        const scoped = new ScopedAgentInvoker(agent.name, deps.invoker);
        const result: AgentInvokeResult = await scoped.delegate({
          windowId: resolveTargetWindow(),
          managerSessionId: deps.getSessionId(),
          managerToolCallId: toolCallId,
          message: params.task,
          mode: params.session === "new" ? "run" : "continue",
          parentDelegationId: params.parentDelegationId,
          handoffKind: params.handoffKind,
          signal,
          onUpdate: (content, details) =>
            onUpdate?.({ content: [{ type: "text", text: content }], details })
        });

        if (result.status === "failed") throw new Error(result.content);

        const resultText = await projectManagerText(result); // 阈值内全文；超阈值无损外置并返回 head/tail、分页读取说明、Artifact 与接力信息
        return {
          content: [{ type: "text", text: resultText }],
          details: {
            worker: result.details.worker ?? agent.name,
            status: result.status,
            delegationId: result.delegationId,
            interactionId: result.interactionId,
            sessionHandle: result.sessionHandle,
            processView: true
          }
        };
      }
    });
  };
}
```

装配和一次调用的完整路径是：

```text
PiSessionStore.managerResourceLoader()
  → planManagerTools() 计算当前窗口可见/激活工具
  → buildManagerExtensionFactories()
       生成 core roster factory
       + 每个 roster Agent 的 agentDelegationFactory
       + 已绑定 Capability factories
  → DefaultResourceLoader({ extensionFactories })
  → createAgentSession({ resourceLoader })
  → loader 调用 factory，factory 执行 pi.registerTool()

manager 模型输出 toolCall(agent_<id>__delegate, args)
  → pi 校验 DelegateParams 并调用 tool.execute()
  → ScopedAgentInvoker.delegate()
  → AgentInvoker.delegate()
  → AgentRuntime.delegate() 先创建/落盘 Delegation
  → Driver.run()/continue()
  → Driver 事件流经 Runtime 归一、持久化并通过 onUpdate 回到 pi/UI
  → terminal NormalizedResult 先写入 Delegation
  → RuntimeOutcome → AgentInvokeResult
  → Extension 投影 AgentToolResult {content, details}
  → pi 包装 ToolResultMessage，写 manager Session JSONL
  → manager 下一次推理只消费 toolResult.content
```

所以所谓“上层 Extension”就是上面这段注册模型工具、校验业务参数并投影结果的 pi factory；它负责模型接口，不负责理解 Codex/PuddingClaw/pi worker 的私有执行协议。`onUpdate` 是同一次阻塞工具调用的流式 UI 更新，不是最终 Session `toolResult`；只有 `execute()` settle 后的返回值才会被 pi 包装为最终结果消息。

### 3.3 Extension 动态加载的真实边界

当前 pi 0.83 支持 `extensionFactories`、运行时 `registerTool()` 和 `setActiveTools()`；但方案不能宣称“成员变化后旧会话自动删除工具”。源码与 SDK 文档没有通用 `unregisterTool()`。

可落地策略：

1. 新建 manager Session 时，按当前 Window 成员及其 `extensionBindings` 构造具名 `extensionFactories`；
2. 每个启用的 Agent 都获得一个平台生成的基础 `agent-delegation` Extension factory；额外 Extension 在它之后装配；
3. factory 创建时由 Runtime 注入绑定该 `agentId` 的 `ScopedAgentInvoker`，Extension 无权在调用参数里改投其他 Agent；
4. Extension 使用 `pi.registerTool()` 注册业务工具；工具名由平台统一命名空间化，避免两个 Agent/Extension 注册同名工具；
5. Agent、Extension 绑定或 Window 成员变化后，相关 manager Session 的 `extensionRevision` 增加并标记 `runtimeDirty`；
6. Runtime 先立即从 active tools 中移除被禁用的工具，并在 `AgentInvoker` 入口拒绝陈旧调用；Session 空闲时再重建 ResourceLoader/AgentSession，彻底移除遗留 hooks；
7. Session 的原 JSONL 历史继续作为唯一会话事实，不复制消息；重建只改变运行时装配；
8. `team_task` 在 per-agent Extension 就绪后直接删除，不设兼容期（决策 20）。

对应现有源码的直接改造是：

- `apps/server/src/pi-bridge/session-store.ts` 当前在 `create()`/`open()` 中用 `customTools` 单独注入 `team_task`，并且只有 direct/group 才显式构造 ResourceLoader；
- 将 `relayLoader(guidance)` 泛化为 `managerResourceLoader(windowContext)`，对 solo/direct/group 都创建同一类 ResourceLoader；
- loader 同时组合原有 guidance、core Extension factory，以及当前 Window 内 Agent 的基础/专属 Extension factories；
- `create()` 和从 JSONL `open()` 都调用同一装配函数，保证重启前后 Extension 集合一致；
- per-agent Extension 验证通过后，`team_task` 连同 `customTools` 注入路径一并删除。

工具命名使用不可变 Agent ID 和 Extension ID，而不是可修改展示名：

```text
agent_<agentId>__delegate
agent_<agentId>__<extensionId>__<toolName>
```

界面可显示友好标签，例如“PuddingClaw · 配置分析”，但发送给模型的工具名必须稳定、唯一、可审计。

Agent 的 name 与 id 已解耦（name 即 id）：`AgentConfig.name` 是不可变内部 id——工具命名空间、windows/credentials/delegations 存储键、REST 路径参数全部用它，创建后不可改；用户可见的显示名是独立的 `AgentConfig.displayName`（任意 unicode、≤40 字符、允许重复、可随时改，缺省回退 name）。创建时不显式给 name 则由服务端从 displayName 派生（ASCII slug，无 ASCII 时 `worker-<随机>`，撞名加 `-2` 后缀）。提示词材料（roster、guidance、delegate 工具描述、审批/结果卡正文）渲染 displayName，工具名仍含 id；前端只有 id 的展示位（委托卡、审批卡、等待提示）经 `avatars.ts` 注册表的 name→displayName 缓存映射。

当 Extension 很多时，不把全部工具默认塞进模型上下文；但基础委托工具是例外——schema 常驻成本远低于「先 search 激活再调用」的整轮上下文重发：

- 基础委托工具（`agent_<id>__delegate`）在 solo/direct/group 全窗口默认激活，roster 里的工具名可直接调用，不需要先搜索；
- capability Extension 工具仍按激活策略懒加载：`always` 随 direct 默认激活，其余（`searchable`）预注册但保持 inactive，由 `search_agent_tools` 按需执行纯加法 `setActiveTools()`；
- `search_agent_tools` 匹配全量受管工具（含已激活的）：搜到已激活工具时明确返回"已是激活状态，可直接调用"，而不是"没有匹配"——否则模型会在 direct 窗口里搜默认激活的 delegate 工具时被误导；查询按空格分词逐词 AND 匹配工具名与描述（描述含责任边界），模型惯用的「worker 名 + 职责关键词」组合查询可以命中；roster prompt 同时给已激活工具标注「（已激活）」，避免无谓搜索；
- 激活态只存在于内存（`setActiveTools` 不落盘），重启/空闲重建会清零，而 JSONL 历史里留着直接调用成功的记录，模型会模仿历史跳过 search 导致 "Tool … not found"。装配时从当前分支 JSONL 历史回放 SDK 标注的 `addedToolNames`（SDK 只写不读），恢复重建前的激活集合；回放仍受装配计划约束——已禁用/移出窗口的 worker 不进 `plan.managed`，其工具不会被回放，撤权语义不变。roster prompt 区分两种失败：调用返回 "Tool … not found" = 未激活，先 search 激活再重试一次；搜索不到该 worker 的工具、或激活后仍被明确拒绝 = worker 不可用，不重试；
- roster（成员名单）不做成工具：它是窗口绑定的静态事实，由 core Extension 的 `before_agent_start` 每轮重读并注入 system prompt，成员/启用变化下一轮即生效，安全性仍由 `AgentInvoker` 入口校验兜底；
- 配置禁用属于安全撤权，不依赖“纯加法加载”，仍走立即门控加空闲重建。

## 4. PWCP v1：统一事件契约，不强制统一 CLI 形态

PWCP（Pudding Worker Coordination Protocol）是 Runtime 和 Driver 之间的规范化事件契约。外部 CLI 可原生输出，也可由 Driver/shim 翻译。

### 4.1 操作输入

```ts
type AgentOperation = "run" | "continue" | "respond" | "cancel";

interface RunInput {
  message: string;
  requestId: string;
  options?: Record<string, unknown>;
}

interface ContinueInput extends RunInput {
  sessionHandle: string;
}

interface RespondInput {
  runHandle: string;
  interactionHandle: string; // 仅 Runtime/Driver 可见
  responses: InteractionResponse[];
  requestId: string;         // 本次提交的幂等键
}

interface InteractionResponse {
  requestId: string;
  action: "approve" | "reject" | "answer" | "confirm";
  scope?: "once" | "run" | "session";
  value?: unknown;
  message?: string;
}
```

### 4.2 事件输出

```ts
type AgentEvent =
  | { type: "started"; sessionHandle?: string; runHandle?: string }
  | { type: "progress"; stage?: string; message: string; percent?: number }
  | { type: "input_required"; result: NeedsInputResult }
  | { type: "completed"; result: CompletedResult }
  | { type: "failed"; result: FailedResult };
```

若走 CLI JSONL，stdout 每行只允许一个事件，stderr 只放诊断。未知事件类型可忽略，但每次操作必须恰好到达一个边界：`input_required`、`completed` 或 `failed`。

边界事件负责 Runtime 状态机；逐事件可视化另走 Connector-neutral 的 `WorkerActivity`。Driver 从上游事件机械投影后，通过 `ctx.onUpdate(text, { activity })` 外送：

```ts
interface WorkerActivity {
  source: string;                   // codex / puddingclaw / runtime / …
  sourceEvent: string;              // 上游原事件名，仅供诊断
  kind: "lifecycle" | "assistant" | "reasoning" | "tool" | "file" |
        "search" | "plan" | "approval" | "error";
  status: "started" | "running" | "updated" | "completed" |
          "failed" | "waiting" | "resolved";
  title: string;
  content?: string;
  itemId?: string;
  sourceSeq?: number;
  metadata?: Record<string, unknown>; // 小型、已脱敏的结构化事实
}
```

PuddingTeams 不依赖 provider 私有事件名渲染 UI，而只认 `kind/status`；同时保留 `sourceEvent`、`itemId` 和可选的上游 `sourceSeq` 供排障。Runtime 为每条活动再分配 delegation 内单调递增的 `seq`、`id`、`timestamp`，写入 `<PUDDINGTEAMS_HOME>/state/delegation-timelines/<delegationId>.jsonl`。该文件只追加不覆盖，先落盘再推送；REST 的 `afterSeq` 与 WebSocket 订阅使用同一本地序号，历史快照与后续订阅在同一 delegation 串行队列中衔接，避免“拉历史与开始监听之间丢一条”的竞态。

### 4.3 归一化结果

```ts
interface ResultBase {
  agentId: string;
  sessionHandle?: string;
  runHandle?: string;
  content?: string;
  artifacts?: ArtifactRef[];      // 交付物声明，见 §15
  usage?: {
    turns?: number;
    inputTokens?: number;
    outputTokens?: number;
    cost?: number;
  };
  meta?: Record<string, unknown>;
}

interface ArtifactRef {
  name: string;
  path: string;                   // workspace 内相对路径
  kind?: string;                  // report | data | diff | …，agent 自定
  size?: number;
  origin: "push" | "observe";     // agent 主动导出 / Driver 观察收集
}

interface CompletedResult extends ResultBase {
  status: "completed";
}

interface NeedsInputResult extends ResultBase {
  status: "needs_input";
  interaction: {
    id: string;                       // PuddingTeams 本地公开 id
    kind: "permission" | "question" | "confirmation";
    requests: InteractionRequest[];
    expiresAt?: string;
  };
}

interface InteractionRequest {
  requestId: string;
  prompt: string;
  permissionType?: string;
  toolName?: string;
  command?: string;
  path?: string;
  paths?: string[];
  risk?: string;
  reason?: string;
  options?: Array<"once" | "run" | "session" | "reject">;
}

interface FailedResult extends ResultBase {
  status: "failed" | "blocked" | "cancelled";
  errorCode: string;
  error: string;
  recoverable: boolean;
}
```

`interactionHandle` 不出现在 `NeedsInputResult`，也不进入 pi Session JSONL。浏览器只拿 PuddingTeams 生成的本地 `interaction.id`。

### 4.4 分发与回收：delegate 阻塞语义与边界事件结算（2026-08-17 补记）

manager 派活与结果回收的完整机制，之前散落在代码里，此处固化：

- **阻塞式分发**：manager 的 `agent_<id>__delegate` 工具在 `execute` 内 `await ScopedAgentInvoker.delegate`（`pi-bridge/agent-extensions.ts`），委派不结算，tool call 不返回。因此委派执行期间 manager 的 agent run 保持 active——pi SDK 只在 run 完全结束（无排队 turn、无重试）时发 `agent_settled`，"等 worker"期间会话 UI 仍处于 running 是真实状态，不是卡死。
- **事件驱动回收**：Runtime 以 `for await` 消费 driver 的 `AsyncIterable<AgentEvent>`（`agent-runtime/runtime.ts`），遇边界事件推进 delegation 状态机并 return，解开 manager 侧 await 的那把锁。completed/failed 是终态；`input_required`（needs_input）不是终态——delegation 挂起等 HITL respond（§6），审批闭环后 driver `respond` 继续驱动同一 run。
- **无边界兜底**：driver 事件流结束却没有到达任何边界（协议错误），按 `no_boundary_event` 记 failed 结算，delegate 工具不会无限悬挂。
- **失效会话透明重跑**：continue 撞上 session-not-found（`isStaleSessionFailure`）时，Runtime 丢弃失效 handle、以新会话重跑一次，不抛给 manager 连环试错；重跑仍失败才走正常 failed。
- **取消**：每个 run 注册 `AbortController`（按 delegationId），取消即中断 driver 流并按 cancelled 结算。
- **前端状态拆分**：等待文案据此区分——消息流中存在 running 态 delegate 工具调用（`isDelegateCall`）时，composer 显示「等待 <worker> 返回…」；否则才显示笼统的「agent 正在处理…」。数据全部来自既有 `tool_execution_start/end` 事件折叠出的工具卡状态，不新增通道。

## 5. PuddingClaw Driver 的精确映射

### 5.0 本机边界与调用方标记

PuddingClaw Driver 是双传输参考实现：`spawn` 启动已安装的本机 `puddingclaw`，`http` 直接调用 `<endpoint>/api/headless/*` 并增量解码 `application/x-ndjson`。两条路径把相同 `{event,data}` envelope 送进同一个 activity observer/终态 normalizer，因此房间只看到统一的 `WorkerActivity` 与 `NormalizedResult`。HTTP transport 的 probe 直接请求 `GET /api/headless/health`，以 `agent_id=puddingclaw`、`protocol_version=1`、`progress=jsonl` 以及 run/continue/respond/cancel 操作矩阵判断 API 契约兼容性；`server_version` 只作为 Backend 版本展示，不参与协议兼容判定，更不以 `cli_version` 代替 API 协议。PuddingClaw Backend 当前仍强制 `localhost`、`127.0.0.1` 或 `::1`；Driver 不注入调用凭据，metadata 固定附加 `caller_id=puddingteams`、`caller_name=PuddingTeams`，仅供调用日志筛选，不作为身份或权限依据。

### 5.1 Session 连续性：`continue`

```text
PWCP run(message)
  -> spawn: puddingclaw agent run --input-json - --jsonl
  -> http:  POST /api/headless/runs?stream=true
     body: {"message":"...","workspace_path":"...","request_id":"..."}

PWCP continue(sessionHandle, message)
  -> spawn: puddingclaw agent run --input-json - --jsonl
  -> http:  POST /api/headless/runs?stream=true
     body: {"message":"...","session_id":"worker-session-...","request_id":"..."}
```

也可映射为 `puddingclaw agent run "..." --session worker-session-... --json`。二者语义相同。

### 5.2 当前 Run 恢复：`respond`

PuddingClaw CLI 新增：

```text
puddingclaw agent respond <run_id> --input-json - --json
```

stdin：

```json
{
  "continuation_token": "opaque-token",
  "request_id": "puddingteams-response-uuid",
  "decisions": [
    {"request_id":"permission-request-id","decision":"approve","scope":"once"}
  ]
}
```

CLI 内部映射到现有：

```text
POST /api/headless/runs/{run_id}/resume
```

输出仍使用现有 Headless 结果：可能再次 `needs_input`，也可能进入最终 `completed/failed/blocked`。

为保证跨进程重试安全，PuddingClaw Backend 同步给 `HeadlessResumeRequest` 增加可选 `request_id`，并按 `run_id + request_id + request hash` 缓存本次 Resume 结果。当前 Resume schema 还没有这个字段；如果不补，PuddingTeams 在“上游已恢复、自己尚未来得及落盘”时重试，只能得到 409，无法判断上一次是否成功。

必须增加的 CLI 校验：

- `run_id`、token、完整 decisions 集合必填；
- `--input-json` 只接受 `-`；
- 非 TTY 不弹交互提示；
- stdout 保持 JSON-only；
- 410 映射为 `interaction_expired`；
- 409 映射为 `interaction_conflict`；
- continuation token 只允许出现在机器可读 JSON 协议字段中，不打印到 human output、stderr 或日志。

### 5.3 为什么不新增 `puddingclaw resume <session_id>`

因为它会把两类恢复再次混淆：

- Session 续聊已经由 `run --session` 完整表达；
- 同 Run HITL 必须依赖 `run_id + continuation_token + requestId 集合`，只有 session_id 不足以安全恢复；
- Codex 的 `codex exec resume <id>` 虽然命令名叫 resume，语义更接近这里的 `continue`，不是 PuddingClaw 权限 `respond`。

统一层应适配语义，不应为了命令外观一致而增加别名。

## 6. PuddingTeams 的 HITL 完整闭环

### 6.1 当前错误路径

```text
team_task -> PuddingClaw Run A -> needs_input
manager 把 needs_input 当文字告诉用户
用户回复 -> team_task 再调用 -> PuddingClaw Run B
Run A 仍 waiting_input -> 409 Session already has active Run or pending input
```

### 6.2 正确路径

```text
team_task / agent-specific tool
  -> Runtime.run 或 Runtime.continue
  -> Driver 返回 input_required
  -> DelegationStore 保存 pending Interaction
  -> tool result 返回“等待审批”结构，manager 本轮可正常结束
  -> WebSocket/历史消息显示审批卡
  -> 用户点击允许/拒绝
  -> POST /api/interactions/{localId}/responses
  -> Runtime.respond（不是 run/continue）
  -> 审批受理后 HTTP 立即返回 {status:"approved", details:{admitted:true}}，
     Delegation 原子地从 waiting_input 恢复为 running；同时向 manager 与
     worker 单聊立即追加 interaction_resolved(approved)，前端按 delegationId /
     interactionId 把原任务卡从“等待审批”对账为“执行中”，不等 worker 续跑落定
     （拒绝/冲突/幂等重放为快速路径，仍返回真实终态）
  -> PuddingClawDriver 调 `puddingclaw agent respond ...`（后台续跑）
  -> 若再次 needs_input：更新同一 Delegation revision，新审批卡投影到两边窗口
  -> 若 completed：写入 task_result，并触发 manager follow-up 汇总
  -> 四种结局（completed/rejected/failed/needs_input）都同时扇出到
     manager session 和 delegation 所属窗口的 active session（两边同步）
```

### 6.3 为什么采用“暂停并外送”，而不是让 tool call 一直阻塞

审批可能持续数分钟甚至跨页面。一直挂住 pi tool execution、WebSocket 和 HTTP 链路会造成：

- backend 重启后上下文不可恢复；
- manager Session 长时间保持 streaming，其他消息无法正常进入；
- 浏览器断开就容易误取消；
- timeout 含义变得混乱。

因此 Parent manager Run 可以在展示审批卡后结束；真正悬挂的是 Child Agent Run。审批完成后，通过 pi 已支持的：

```ts
session.sendCustomMessage(
  {
    customType: "pudding:task_result",
    content: workerResult,
    display: true,
    details: { delegationId, worker, status: "completed" }
  },
  { triggerTurn: true, deliverAs: "followUp" }
)
```

让 manager 在同一 pi Session 中继续汇总。`AgentSession.sendCustomMessage` 的 `triggerTurn` 已由当前依赖版本支持。

### 6.4 PuddingTeams API

```text
GET  /api/interactions?sessionId=...
GET  /api/interactions/{id}
POST /api/interactions/{id}/responses
POST /api/interactions/{id}/cancel
```

提交示例：

```json
{
  "revision": 1,
  "request_id": "ui-submit-uuid",
  "responses": [
    {"requestId":"perm-1","action":"approve","scope":"once"}
  ]
}
```

服务端必须校验：

- Interaction 属于当前窗口/manager Session；
- `revision` 未过期；
- responses 恰好覆盖当前 request 集合；
- 选定 scope 在该 request 的 options 内；
- 同一 `request_id` 重试返回相同结果；
- 非 pending 状态拒绝二次消费。

### 6.5 UI 与 Session 历史

历史中只存安全投影：

```json
{
  "customType": "pudding:interaction_required",
  "display": true,
  "details": {
    "interactionId": "int_local_x",
    "delegationId": "dlg_x",
    "worker": "puddingclaw",
    "status": "pending",
    "revision": 1,
    "requests": [{"requestId":"perm-1","command":"...","risk":"moderate"}]
  }
}
```

continuation token、Worker access token、原始 provider payload 不写进 pi JSONL、不发给 LLM、不下发浏览器。

历史卡状态由 `GET /api/interactions/{id}` 对账；pending/approved/rejected/expired/completed 都可重放。状态变化只追加事件，不修改旧 JSONL：`pudding:interaction_resolved(approved)` 在审批受理、Delegation 已恢复 `running` 时立即写入，前端按 `delegationId`（`interactionId` 兜底）同时折叠审批卡并校正原委派任务卡；最终边界稍后由 `pudding:task_result` 或下一轮 `pudding:interaction_required` 表达。

**两边同步（respond 扇出）**：审批提交后的恢复态与后续边界都会经 `managerSender` 同时写入 manager session 和 delegation 所属窗口的 active session（单聊镜像）；两者相同则只发一次，镜像目标解析失败不影响主流程。消息形态：

- approved/admitted：立即写 `interaction_resolved(approved)`，原委派卡进入执行中；
- completed：随后只写 `task_result(completed, 含 artifacts/usage)`；
- rejected：`interaction_resolved(rejected)` + `task_result(cancelled)`；
- failed：随后只写 `task_result(failed, 含 errorCode)`；
- needs_input（又一轮提问）：先有本轮 `interaction_resolved(approved)`，随后写 `interaction_required(pending, 同 interactionId, revision+1)`。

manager session 的 `task_result` 用 `triggerTurn: true, deliverAs: "followUp"` 唤醒 manager 汇总；单聊窗口全部 `triggerTurn: false`，仅展示。由此用户只待在 solo 窗口也能完成全部审批并看到所有 worker 结果。前端审批卡对多轮 needs_input 以对账后的 live revision 重新进入 pending，不会误显"已批准"。

**回写（2026-08-12 Direct 直派与派活即镜像）**：

- **Direct 直派**：direct 窗口不再经 pi manager relay。`POST /api/sessions/:id/messages` 命中 direct 窗口时由 `agent-runtime/direct-dispatch.ts` 消费——依次写入 `pudding:user_message`（用户气泡）与 `pudding:task_assign(status:"running")` 两张 custom message，后台直接 `AgentInvoker.delegate` 给窗口唯一成员（`managerSessionId` = 该窗口自己的 active session，`mode: "continue"`，stale handle 由 Runtime 透明回退新会话）；completed/failed/conflict 补 `pudding:task_result` 卡，needs_input 审批卡沿用 invoker 原有投影直接落回本窗口。窗口的 pi session 永不触发 manager 回合，仅作消息流容器（首条消息前经 `PiSessionStore.ensureSessionFile` 复制 SDK 首刷，避免延迟落盘丢历史）。
- **扇出不唤醒 direct**：respond 扇出时若 manager session 的属主窗口是 direct，`task_result` 降级为 `triggerTurn: false`（无 manager 可唤醒）。
- **派活即镜像**：solo 派活在 `scoped.delegate` 阻塞前先写 `pudding:task_assign(status:"running")` 到 worker direct 窗口（`announceToWindow`），`syncToWindow` 只在 outcome 后补结果/审批卡。前端把 manager 路由的 solo 镜像展示为「Manager 委派任务气泡 → worker 执行行 → worker 最终结果」；直接在 worker 单聊输入的 direct-dispatch 仍是普通用户气泡 → worker 执行行，不引入 manager 语义。同 `taskId` 的结果/审批卡到达后 running 行落定收起，任务气泡保留为对话上下文。结果卡继续携带 `delegationId`/`sessionHandle`/`processView:true`，因此委托完成后单聊仍可查看执行过程。
- **manager 运行态持久化（2026-08-21）**：group 不另画一张指派卡，solo manager 来源窗口也仍以原始 delegate 工具卡为唯一展示。Runtime 创建不可变 Delegation 后，通过 `PiSessionStore.appendCustomMessageProjection` 直接向正在执行中的 manager Session 追加 `display:false` 的 `pudding:task_assign(from:"group"|"solo")`，随后可再富化 `sessionHandle`。它不等待 manager 空闲、不进入模型队列；直写 SessionManager 后必须同时经 store 订阅通道广播同一隐藏 `message_start`，让已打开的 manager 页面立即折叠运行元数据；刷新/WS 重连时再由 JSONL 历史做同样恢复。前端按 `taskId` 把 `delegationId`/`sessionHandle`/`processView` 折回原工具卡，因此「执行过程」与「终止任务」入口在最终 toolResult 前不会消失；历史回放与实时 `message_update/message_end` 合并都必须保留已有工具运行元数据。委托参数 `session:"new"` 在 solo 与 group 都映射为 Runtime `run`，只有缺省/`"continue"` 才续接窗口内 worker binding。

## 7. PuddingTeams 数据模型

### 7.1 Window 保存每个 Worker 的最新 Session 绑定

```ts
interface WorkerBinding {
  sessionHandle?: string;
  /** 缺省表示未选择显式项目。 */
  workspaceId?: string;
  /** 产生该 handle 时冻结的运行目录。 */
  cwdSnapshot: string;
  /** 产生该 handle 时的 Agent/Connector 配置修订。 */
  agentRevision: number;
  updatedAt: string;
}

interface WindowConfig {
  // key 是不可变 agentId；value 是该窗口下此 Worker 的最新续接指针。
  workerBindings?: Record<string, WorkerBinding>;
  workspaceId?: string;
  cwdSnapshot: string;
}
```

实际落点是 `<PUDDINGTEAMS_HOME>/state/windows.json`。`workerBindings` 不是 Worker Session 内容，只是 PuddingTeams 保存的“这个窗口下次 `continue` 应把哪个不透明 handle 交回哪个 Worker”的最新指针；Worker 自己的 Session 历史仍由对应 Connector 后端负责（本地 pi 例外，落在平台 `sessions/workers/`）。

写入链路必须按当前实现理解：Driver 的边界事件先让 Runtime 更新 `DelegationRecord.sessionHandle`，Runtime 随 outcome 返回同一个已更新的 `DelegationRecord` 内存对象；`AgentInvoker` 再调用 `TeamsStore.rememberWorkerSession()` 更新 `windows.json`。这不是先写 `delegations.json`、然后把它当数据库重新读取并复制：

```text
Driver boundary event.sessionHandle
  → Runtime 更新 DelegationRecord.sessionHandle
     ├─> state/delegations.json：保留“这一次 Delegation 用了哪个 handle”
     └─> RuntimeOutcome.delegation（同一次结果的内存对象）
           → AgentInvoker.rememberSession()
           → TeamsStore.rememberWorkerSession()
           → state/windows.json.workerBindings[agentId]
              保存“这个窗口下次续接用哪个最新 handle”
```

因此同一 Worker 若先后产生 `D1 → S1`、`D2 → S2`：`delegations.json` 中 D1 仍保留 S1、D2 保留 S2，`windows.json.workerBindings[worker]` 则更新为最新 S2。下一次 `continue` 由 `AgentInvoker.sessionHandleFor()` 读取这个最新指针，而不是扫描 Delegation 历史。

旧 Run 落定得很晚时不能覆盖已经切换后的窗口绑定。`rememberWorkerSession()` 写入前必须重新读取权威窗口和 Agent 配置，并同时确认：

- Delegation 的 `workspaceId` 仍等于窗口当前 `workspaceId`；
- Delegation 的 `cwdSnapshot` 仍等于窗口当前实际 cwd；
- Delegation 的 `agentRevision` 仍等于当前 Agent/Connector 修订。

读取 `continue` handle 时重复执行同样三项校验；任一不匹配就把旧 handle 视为不可续接。pending Interaction 不放进 `windows.json`，因为它属于某一条尚未结束的 Run，而不是窗口的跨 Run Session 绑定。源码入口：`agent-runtime/invoker.ts` 的 `sessionHandleFor()/rememberSession()` 与 `store/teams.ts` 的 `rememberWorkerSession()`。

#### 7.2.1 Delegation 因果链的落盘与消费

`state/delegations.json` 是可变的 Delegation 索引/账本，不是 Session JSONL，也不是逐事件 timeline。文件外层固定为 `{version, delegations}`，`delegations` 以 `DelegationRecord.id` 为 key；新委托先以 `running/revision:0` 落盘，启动、审批与终态转移再更新同一条记录。`DelegationStore` 在进程内串行化变更，每次写入先生成临时文件再 `rename`，因此它是原子快照，不应按 append-only 日志解析。

`parentDelegationId` 是子记录指向上游记录的因果边：缺省 parent 的 `request` 是根任务，`followup` 沿 parent 继续追问，带 parent 的 `request` 表示上游结果触发了新的有返回义务的子任务。每条记录只有一个 parent，但一个 parent 可以被多条记录引用，所以所谓“链”实际可以是分叉的因果树/森林。写入前必须验证 parent 已存在且 `managerSessionId` 与子委托一致；读取时按 `managerSessionId` 取候选集，由子向父追溯上游，或建立 `parentId -> children[]` 反向索引展示分支。这只表示 `Worker A -> manager -> Worker B` 的因果，不允许 worker 绕过 manager 直连。可直接用于教程的完整 D1-D4 示例与三份事实源的关系见 `docs/2026-08-14-会话记录格式与Harness消费.md` §2.2。

#### 7.2.2 超长 worker 结果（已实现）

**实现边界**：Runtime 的 `DelegationRecord.result` 保留 Driver 产生的完整 `NormalizedResult`；pi worker 的原始回答另在 worker Session JSONL，而 spawn timeline 只是有界活动投影，不是全文备份。`LargeWorkerResultStore` 负责 completed worker 正文的无损外置与分页回读。此处的“完整”以 Driver 已归一化的 result 为边界；如果 Connector 自身已对上游内容做有界投影，PuddingTeams 无法凭空恢复上游原文。

**处理方式**：超过阈值时把 worker 原文按 delegation 落到 `<PUDDINGTEAMS_HOME>/state/large-worker-results/<delegationId>.txt`（平台受控、0600、原子写），manager toolResult 只投影 head/tail 预览、`originalChars/estimatedTokens`、`offloaded:true`、`delegationId` 与精确回读说明。平台核心工具 `read_delegation_result({delegationId, offset, limit})` 分页读取全文，并校验调用者当前 `managerSessionId` 拥有该 Delegation；不向模型暴露宿主真实路径，不把预览覆盖成唯一持久化结果。Artifact 仍是 worker 主动交付的用户产物，large-worker-result 只是 harness 的上下文外置层，两者不混用。

**设置归属**：像 PuddingClaw 一样放在全局“设置 -> Harness -> 上下文工程”下，子项名为“Worker 结果上下文”，落盘到 `config/product.json` 的 `harness.workerResults`。无损外置是始终生效的安全基线，不提供“改回静默硬截断”开关；可调参数为：

```json
{
  "harness": {
    "workerResults": {
      "offloadThresholdTokens": 20000,
      "previewHeadTokens": 6000,
      "previewTailTokens": 2000,
      "readChunkTokens": 8000
    }
  }
}
```

token 值为上下文保护预算，当前以 `ceil(chars/4)` 估算并记录原始字符数；`previewHeadTokens + previewTailTokens` 必须小于 `offloadThresholdTokens`，各值由服务端施加上下界，前端校验不是安全边界。

#### 7.2.3 WorkPlan/WorkItem 是 Harness 计划层，不是新 Driver 协议（已实现）

完整契约见 `docs/2026-08-21-Manager-WorkPlan与Delegation-Timeline融合方案.md`。solo/group 的 Session Goal 已增加结构化执行面 `GoalWorkPlan/WorkItem`，没有创建脱离 Goal 的独立计划对象：

- `WorkItem.dependsOn` 是 Manager 业务任务 DAG；`Delegation.parentDelegationId + handoffKind` 仍是执行因果。二者必须分开验证和展示；
- 一个 WorkItem 可以绑定多次 Delegation，`DelegationRecord` 仅新增可选 `workPlanId/workItemId/attempt` 引用，不把计划状态复制进 Driver SPI；
- `Delegation.completed` 生成 Submission 并把 WorkItem 推进到 `submitted`，Manager 通过 PuddingTeams core tool 明确 accept/revision/blocked；只有 accepted 解锁下游；
- 第三方 Worker 不需要适配 WorkPlan。Connector 仍只负责现有 `run/continue/respond/cancel`、`NormalizedResult` 和可选 `WorkerActivity`；提交验收、DAG、并发 revision 与 Goal 门禁都属于上层 Harness；
- WorkPlan 直接内聚到现有 `state/work-states.json` 的 Goal 聚合，与 recovery epoch、operation ledger 和 outbox 原子提交，不新增 `work-plans.json` 或 WorkItem timeline；选中一次执行后继续复用 pi Session 回放或 `state/delegation-timelines/<delegationId>.jsonl`。
- direct Session 也可有 Goal，但没有 Manager WorkPlan；统一抽屉从 `SessionWorkState` 读取 Goal/完成条件，再直接路由到该 Worker 的现有执行过程，Driver SPI 仍无新要求。

执行路径为：

```text
Manager update_work_plan
  → delegate(workItemId)
  → ScopedAgentInvoker → AgentInvoker → Runtime → Driver
  → Delegation/result 先落盘
  → GoalCommandGateway 幂等生成 Submission
  → Manager review_work_item
  → accepted 后解锁 dependsOn
```

这不会改变 §3.2.1 的边界：`AgentInvoker` 仍是委托门面，不等于 OS spawn；也不会把 WorkPlan 能力下放给 pi Extension 或 Connector 包。

### 7.3 重启语义必须诚实

第一版可做到：

- PuddingTeams 重启、PuddingClaw 未重启：从加密 InteractionStore 恢复并继续 `respond`；完成后通过 custom message 触发 manager 新 turn；
- PuddingClaw 重启：其 live `_HeadlessExecution` 丢失，PuddingTeams 将 Interaction 标记 `expired`，提示用户重新启动该任务；
- 不承诺恢复原来的 manager tool call；恢复的是业务 Delegation，随后在同一 manager Session 追加结果。

只有当 PuddingClaw 把 live execution/中断恢复做成持久化协议后，才能把第二种情况升级为真正跨进程恢复。

> 实现状态（2026-08-19，启动收割器）：PuddingTeams 进程重启后内存 Run 全灭，持久化的 running/waiting_input 委托即成孤儿。server 启动时 `AgentRuntime.reapOrphanedRuns()` 把这些孤儿统一转 `failed`（`errorCode: server_restart`），挂起审批转 `expired`、加密 provider state 清除，并补写 manager 会话：solo/群聊（真实工具调用）追加一条合成 toolResult（`isError`，含交接目录提示），direct 直派（managerToolCallId 实为 taskId、会话中无 toolCall）改补一张 `pudding:task_result` 失败卡。manager 下次运行能在上下文里看到失败原因并重新委派；前端历史重放把它折成「失败」而非「已中断」。这与上面「恢复 Delegation」的第一版设想不同：实际选择不恢复、诚实判死，把重新决策权交还 manager。

> 实现状态（2026-08-21，Goal v5 恢复）：启动收割后由 Goal 恢复协调逻辑按 `goalId` 对账 Goal 聚合、增加 recovery epoch，并通过持久 outbox 与接收端 `eventId` 去重唤醒同一 manager Session；进程运行期间 dispatcher 继续串行重试未确认事件。恢复开启新 Delegation 尝试，不把旧 D 改回 running；所有 Goal 写入口都携带 `expectedGoalId`，本地状态变更以 Goal 级 operationId 幂等，旧 Goal/旧 epoch 回调被 fence。Connector 可选接收 `idempotencyKey/operationId`，不支持时对外部副作用不承诺 exactly-once，结果不明时先人工对账。完整协议见 Goal/Timeline 融合方案 §10。

## 8. Spawn、JSONL、超时与取消

### 8.1 Spawn Runtime

把 `TeamsStore.spawnWorker()` 抽到 `agent-runtime/transport/spawn.ts`，保留现有正确行为：

- `shell: false`；
- stdout/stderr 分离；
- SIGTERM 后 5 秒 SIGKILL；
- AbortSignal 取消；
- stdin EPIPE 吞掉；
- stdout、stderr、单行长度分别限额；
- 子进程退出和协议终态分开判断。

增加：

- 逐行 JSONL decoder，保留尾部半行 buffer；
- 首个 `started/progress` 事件延迟指标；
- exactly-one-boundary 校验；
- 不把 stderr 原样送入模型，仅存 Trace 的有界诊断摘要。

### 8.2 PuddingClaw Headless JSONL（Backend 与 Driver 已接通）

单 JSON 仍是兼容边界；PuddingTeams 的正式运行链路应使用 `puddingclaw agent run --jsonl`，审批续跑使用 `puddingclaw agent respond ... --jsonl`。

真正的流式进度需要 PuddingClaw Backend 提供 SSE/JSONL streaming endpoint，CLI 只是把该流转发出来；只给 CLI 增加 `--jsonl` 而后端仍同步等待，不会产生真实进度。

**2026-08-20 PuddingClaw 0.1.19 源码落地**：Backend 已把 execution 创建与 response streaming 解耦，立即输出 `run_starting`，随后转发 allowlist 内的 lifecycle、工具、可见 content、HITL 和 final content；reasoning/内部 Trace 不外送。同一 execution 支持多观察者和按 `seq` 有界重放，PuddingClaw Web 可通过 Session SSE 与 CLI 同时观察。Resume API 与 CLI `respond --jsonl` 也保持流式；本机调用协议不包含 PuddingClaw Token。

**2026-08-20 PuddingTeams 接入完成**：PuddingClaw Driver 的 `run`、`continue`、`respond` 全部使用 `--jsonl`，`progress: "stream"`；公开的 17 类事件（run/preflight/outcome 生命周期、response/token/segment、tool、permission、final/done/error）都投影成 `WorkerActivity` 后写入 delegation 时间线。PuddingClaw 明确不公开 reasoning，因此 UI 不伪造思考事件。上游 CLI 当前不把 Backend `seq` 原样带到 PuddingTeams 也不影响连续性：平台始终使用自己的 delegation-local `seq`，未来拿到 `sourceSeq` 时只把它作为诊断字段保存。

同步边界仍可能出现“上游已经完成，但代理/网关先关闭连接”的情况。PuddingTeams Driver 对**运行超过 30 秒后**的 `connection_error/fetch failed` 不再立即结束委托：它使用原 `request_id` 重提同一请求，遇到 `An identical Worker Run is already in progress` 就短轮询，直到读到 PuddingClaw 的幂等终态或耗尽本 Run 的 active timeout。快速连接失败仍直接返回，避免把服务不可达误判成长任务恢复。该恢复只补“最终响应丢失”，不伪装成流式。

### 8.3 超时分三类

| 超时 | 含义 | 默认建议 |
| --- | --- | --- |
| 启动超时 | 进程未进入 started | 30 秒 |
| 活跃超时 | running 且长期无事件 | 120 秒，可按 Agent 配置 |
| Interaction TTL | 等用户审批 | 24 小时，受上游更短 TTL 限制 |

`waiting_input` 期间不计 active timeout；否则用户看审批卡几分钟就会被误杀。

## 9. Connector Extension 目录与接入边界

### 9.1 最小预置，其他接入依靠 Extension 二开

**定位（贯穿整个开发周期）**：Connector Extension 的本质是**给 pi 扩充连接其他 Agent 的能力**——每个 Connector 包都是可以发布到 pi 社区、`pi install` 可装的独立生态产物；但**完整的房间能力（manager-worker 编排、HITL 审批闭环、workspace 交接）只有 PuddingTeams 提供**。因此每个包采用"共享核心 + 双宿主入口"结构（§9.5），纯 pi 用户得到真实可用的轻量 delegation，PuddingTeams 用户得到完整 worker 接入，协议翻译核心只维护一份。

PuddingTeams 提供 Extension 安装入口、SDK、模板和编写指南，不维护一个不断膨胀的内置 Agent 列表。

**路由材料不预置（2026-08-17）**：Connector 包与内置种子（`DEFAULT_TEAMS`）都不携带给 Manager 的路由内容——Worker 的描述、capabilities 标签、责任边界一律由用户在前台按需填写（agents.json 是唯一事实源，概览页可改）。源码里烤死默认路由文案等于替用户做派活决策，且改默认值要动源码，违背"路由材料前台可改"的边界。

| 内容 | 默认发行 | 定位 |
| --- | --- | --- |
| PuddingClaw Connector Extension | 安装 | 第一方可运行基线，完成 run/continue/respond/cancel |
| Codex Connector Extension | 安装 | P1 主流样本：spawn + JSONL 流式，run/continue/cancel，无 HITL |
| Claude Code Connector Extension | 安装 | P1 主流样本：spawn + stream-json 流式，run/continue/cancel，无 HITL |
| 核心 delegation 投影 | 内置 Runtime | 为每个 Agent 生成基础 Pi 委托工具，不是 Capability 包 |
| Capability Extension | 预置一个未绑定的 `minimal-tool` 开发样例 | 用户按业务需要绑定；默认不进入任何 Agent 工具集 |
| Generic CLI Connector 模板 | 仅开发模板 | 演示声明式 Connector，不作为万能运行时兜底 |
| Pi/Hermes/OpenClaw/Grok Build | 文档案例 | 提供协议选型与样例片段，不承诺默认实现和持续跟版 |

例如，Grok Build 的本地源码可以作为代码型 Connector 编写指南的 ACP 案例：

- Headless 支持 `-p`、`--output-format streaming-json`、`--resume`、`--continue` 和 Session ID；
- `grok agent stdio` / `serve` 提供长连接 ACP；
- ACP 生命周期覆盖 `session/new`、`session/prompt`、流式 update、permission request 和取消；
- 因此用户编写 Grok Build Connector 时应首选 ACP。Headless 只作为无交互降级路径，不用正则解析终端文案来模拟 HITL。

Pi 可以调用另一个 Pi，但必须是新的 child `AgentSession`/独立 Session 目录，而不是让同一会话重入自身。PuddingTeams 对这类委托统一执行：

- 默认不向 child Pi 注册 PuddingTeams 的团队委托工具，避免无意递归；
- 显式允许递归时，传播 `delegationDepth`，默认最大深度为 2；
- 父 Run 取消必须向所有仍在运行的 child Pi 传播；
- 每个 child 都有独立的 `sessionHandle`、`runHandle` 和事件流。

**执行过程可视化（2026-08-23 更新）**：执行过程按来源分为两种只读视图。pi worker 继续从 child `AgentSession` 实时订阅并从 pi Session JSONL 回放完整 assistant/thinking/tool 历史；若 child Session 已建立但本次委托尚无 assistant/toolResult，抽屉明确显示「等待 Provider 首个模型事件」，而不是伪造 thinking 或把静止误判为 Driver 过滤。其他 Driver worker（spawn/http/rpc/acp）统一使用 delegation 活动时间线。Codex 仍走 `codex exec --json` / `codex exec resume --json`，不强制启动 `app-server`，并投影 `thread/turn/item/error` 以及 agent message、reasoning、command、file change、MCP/collab tool、web search、todo 等 item；多条 completed agent message 全部留在时间线，终态 `result.content` 只取最后一条。PuddingClaw 的 CLI JSONL 与 Headless HTTP NDJSON 把同一公开事件流送入同一个 observer，终态只采用明确的 `final_response`（旧 Backend `reply` 兜底），不拼接 token/segment。PuddingClaw Driver 在落盘前把连续 token 合并成一条 `token.batch`，保留合并文本、事件数和可用的上游 seq 范围；非 token 事件仍一对一追加。两者统一写入 `<PUDDINGTEAMS_HOME>/state/delegation-timelines/<delegationId>.jsonl`，按本地 `seq` 追加，聊天卡片只保存最新委派状态和最终交付，不承载高频事件。单委托读接口为 `GET /api/delegations/:id/process/timeline?afterSeq=` 与 `/api/delegations/:id/process/timeline/ws?afterSeq=`；房间侧栏通过 `GET /api/rooms/:id/delegation-processes?managerSessionId=` 获取当前会话的委托索引：服务端取 manager session 拥有的委托，并合并当前房间 Session 里以 `pudding:task_assign` 明确镜像的委托，按 delegationId 去重；不能对执行窗口与 managerSessionId 做 AND 过滤，因为 solo/群聊任务实际运行在 worker direct 窗口。这样 manager 房间和对应 worker 单聊都能在同一右侧 Inspector 中看到、切换并行 worker，又不会混入该 direct 窗口其他历史会话的任务。pi 与非 pi Driver 只在详情 Router 内分流。展示层可以隐藏 token batch 与 final、done 与 runtime terminal 等重复行并使用紧凑阶段行，但不得修改事实源或跨 Delegation 合并。执行过程视图保持只读，审批与终止走独立控制面。

**委托级终止（2026-08-20）**：执行过程视图仍只读，但所有 running 委托卡在 Runtime 创建不可变 Delegation 后立即获得 `delegationId`，并显示「终止任务」。`POST /api/delegations/:id/cancel` 只取消该 Run，不终止 manager Session；Runtime 先把 `cancelled` 结果与终态一起持久化，再 abort 本地 Driver 流，并在已取得 `runHandle` 时调用 Connector 的 `cancel`。取消不是静默操作：running 委托仍占用原 delegate tool call，abort 后以 `cancelled` toolResult 自然回到 manager；waiting_input 的 tool call 已在审批边界结束，因此额外投影 `pudding:interaction_resolved` + `pudding:task_result`，并用 follow-up 唤醒 manager 完成闭环。worker 单聊只同步展示，不启动 manager 回合。外部 CLI 尚未给出 `runHandle` 时只能先终止本地子进程；是否能同步取消上游取决于其协议是否及早流出 Run handle（PuddingClaw 0.1.17 尚不满足，见 §8.2）。

**pi 瞬时限流续跑（2026-08-21）**：child AgentSession 自带短退避仍无法跨过 RPM 窗口时，LocalPiDriver 不把本次工作立即结算为失败，也不要求 Manager 用完整任务创建新 Delegation。它保留同一 `delegationId`、`sessionHandle` 与累计 usage，进入可由 AbortSignal 终止的冷却等待，随后在同一会话中要求从已有进度继续；只有有限次冷却续跑耗尽才输出 failed 边界。

### 9.2 能力必须由 Driver 声明，不能由 UI 猜测

Driver 必须通过 `capabilities()` 暴露真实能力，并通过 `probe()` 返回安装、认证、版本和 Transport 健康状态。若 `respond` 不支持：

- Runtime 不生成“可以恢复原 Run”的虚假审批动作；
- 若上游在当前模式下会阻塞交互，启动前就返回 `interaction_unsupported`，或要求用户选择明确的自动审批策略；
- 不把用户审批转换成新的 `run`/`continue`；
- UI 显示“审批外送不支持”，而不是笼统的“不可用”。

ACP/RPC/HTTP Gateway 的价值是把长期连接、权限请求和取消变成原生协议。编写 Pi、Hermes、Grok Build 等 Connector 时应直接采用其结构化协议；只有确实没有结构化协议的 Agent 才使用 spawn 适配。这是 SDK 指导原则，不等于 PuddingTeams 默认维护这些 Connector。

### 9.3 目录、安装、绑定、启用是四个不同动作

默认策略：

1. 本地、团队或用户配置的 Connector 源可在“添加 Agent”目录中展示，但目录项不是已安装代码；
2. 用户选择目录项后先查看来源、权限、支持的上游版本和工具能力，再确认安装；
3. 安装完成后创建 Agent 实例并填写配置；只有显式启用后才进入 roster 和调度候选；
4. `probe()` 检测到本机 CLI 不代表自动启用，更不能自动读取或迁移第三方凭证；
5. 升级已有安装时，现有 PuddingClaw 配置直接重建为第一方 Connector binding，不做数据迁移（决策 20）；默认不新增其他 Agent；
6. 禁用后保留配置和历史绑定，但拒绝新委托；已经运行或等待审批的 Run 由用户选择“继续保留”或“取消”，不能静默杀死；
7. 同一个 Connector 可以创建多个 Agent 实例，例如两个 Codex 实例使用不同工作目录、模型策略或账号；
8. 卸载 Connector 前必须确认没有启用 Agent 和 active/waiting Run；历史保留，但对应 Agent 进入 `connector_missing`，不能静默回退到 Generic CLI。

### 9.4 Connector Extension 如何降低上游维护成本

维护成本不会凭空消失，但可以从核心仓库解耦并自动暴露风险：

- Connector manifest 声明 `supportedUpstreamVersions` 和 `versionProbe`；
- `probe()` 同时返回 Connector 版本和真实 CLI/服务版本；
- 上游版本超出已验证范围时状态变为 `untested` 或 `incompatible`，不静默假设兼容；
- 每个 Connector 独立版本、独立发布、可固定版本或选择自动更新；
- Connector 作者维护针对上游 CLI 的契约 fixture/集成测试，不阻塞 PuddingTeams 核心发布；
- 社区或用户可维护自己的 Connector，PuddingTeams 只保证 Driver SPI 的兼容周期。

版本策略建议：Driver SPI 使用独立 `apiVersion`，至少跨一个 PuddingTeams 大版本保持兼容。Connector manifest 同时声明：

```json
{
  "kind": "connector",
  "engines": { "puddingteams": ">=1.0 <2" },
  "connector": {
    "id": "grok-build",
    "apiVersion": "1",
    "supportedUpstreamVersions": ">=0.9 <1.1"
  }
}
```

### 9.5 双宿主包：一个包，pi 与 PuddingTeams 两种激活路径

Connector/Capability 包统一为 **pi 兼容的 npm/git 包**，发布到 pi 社区，`pi install <source>` 可装。包内是"共享核心 + 两个薄适配层"：

```text
pi-connector-openclaw/
├── package.json            # pi.extensions 声明 pi 入口；puddingteams 字段承载 §10 manifest
├── pi/
│   └── index.ts            # default export (pi: ExtensionAPI) => void：注册 delegate 工具，pi 当 manager 派活
├── driver/
│   └── index.ts            # createDriver 命名导出：接 Driver SPI（PWCP 事件、probe、HITL、多实例）
└── core/                   # 共享核心：spawn/ACP/JSONL 翻译、session 连续性、取消、错误归一化，不依赖任何宿主
```

两条激活路径互不相干，同一个 `pi install` 动作行为不同：

| | 纯 pi | PuddingTeams |
| --- | --- | --- |
| 加载器 | pi resource-loader（找 `pi.extensions` 入口） | ExtensionRegistry（读 manifest + `createDriver`） |
| 激活内容 | pi 内注册 delegate 工具，pi 自己当 manager | agent 进 roster，平台自动投影 `agent_<id>__delegate`，走房间体系 |
| HITL | 降级为 pi 自身权限提示或不支持 | 完整审批闭环（web 审批卡、409、拒绝也是合法响应） |
| 配置/密钥 | 包自管（如环境变量） | connector binding API + secretRefs |
| 生命周期 | 跟随 pi 会话 | server 托管：重启诚实、取消传播、多实例 |

#### 9.5.1 纯 pi 门面的具体样式与路径

双宿主包里的 `pi/index.ts` 与 §3.2.2 的 PuddingTeams manager inline Extension 都使用 `ExtensionAPI.registerTool()`，但不是同一条运行链。以当前 Codex Connector 为例，纯 pi 门面可以缩略为：

```ts
// extensions/connectors/codex/pi/index.ts
export default function codexConnector(pi: ExtensionAPI) {
  pi.registerTool({
    name: "codex_delegate",
    parameters: Type.Object({ task: Type.String(), cwd: Type.Optional(Type.String()) }),
    async execute(_toolCallId, params, signal, onUpdate, ctx) {
      const parser = new JsonlLineParser();
      const reducer = new CodexEventReducer();
      const result = await spawnWorker({
        command: "codex",
        args: ["exec", "--json", "-C", params.cwd ?? ctx.cwd, params.task],
        cwd: params.cwd ?? ctx.cwd,
        signal,
        onStdout: chunk => {
          for (const raw of parser.push(chunk)) {
            const progress = reducer.push(raw);
            if (progress) onUpdate?.({ content: [{ type: "text", text: progress }], details: undefined });
          }
        }
      });
      for (const raw of parser.flush()) reducer.push(raw);
      const boundary = reducer.boundary("codex");
      return {
        content: [{ type: "text", text: projectBoundary(boundary, result) }],
        details: { threadId: reducer.threadId, usage: reducer.usage, exitCode: result.exitCode }
      };
    }
  });
}
```

纯 pi 激活路径为：

```text
pi package loader 读取 package.json 的 pi.extensions
  → import pi/index.ts 的 default factory
  → factory 注册 codex_delegate
  → pi manager 产生 toolCall
  → pi 直接调用门面的 execute()
  → 门面经共享 spawn/归一化核心执行 Codex CLI
  → 返回 AgentToolResult
  → pi 包装并持久化 ToolResultMessage
```

这条纯 pi 路径**不会经过** PuddingTeams 的 roster、`ScopedAgentInvoker`、`AgentInvoker`、`AgentRuntime`、`state/delegations.json`、delegation timeline 或 Web HITL。相同包被 PuddingTeams 激活时则不加载 `pi/` 门面来承担房间委托：ExtensionRegistry 读取 `puddingteams.entry`，从 `driver/index.ts` 取得 Driver；manager 工具由平台的 §3.2.2 inline Extension 统一生成，再走 `ScopedAgentInvoker → AgentInvoker → Runtime → Driver`。这正是“pi 入口是轻量门面、Driver SPI 是 PuddingTeams Connector 本体”的含义。

工程约定：

- **下载安装复用 pi**：PuddingTeams 的安装渠道接受与 `pi install` 相同的 npm/git source，内部复用 pi SDK 的 `DefaultPackageManager`（固定目录、版本固定、update 检查现成），不重复造下载器；
- **manifest 折叠**：`pudding-extension.json` 的 §10 字段折叠进 `package.json` 的 `puddingteams` 字段，一个包一份元数据（过渡期两者都接受）；
- **加载器已兼容**：`ExtensionRegistry` 加载模块时同时识别 `mod.default`（pi 工厂）、`mod.createDriver`、`mod.driver`（extension-registry.ts），双导出包无需改加载逻辑；
- **目录管理**：仓库根 `extensions/` 是所有插件的唯一落点——`extensions/connectors/<agent>/` 放 Connector 包，`extensions/capabilities/<name>/` 放 Capability 包，`extensions/shared/` 放共享核心模板；`extensions/README.md` 维护全量索引（每个包的 kind、宿主入口、状态一目了然）；
- pi 入口是包的**门面**，Driver SPI 才是 Connector 的**本体**；不允许把 Driver 伪装成 pi extension（ExtensionAPI 没有 spawn、server 持久化和审批路由能力）；
- **Connector 的上游可以是另一个 pi**：本地 child `AgentSession`（独立 Session 目录，约束见 §9.1 的 Pi 调 Pi 铁律）或远程 pi（RPC transport）；**以本地 pi 为主**，作为 Phase 6 的第一个参考样例——协议双边可控，能跑满 Driver SPI 全语义（run/continue/cancel/stream 进度），给外部 Agent 的 Connector 当标杆；
- **pi 只是 worker 中的一种，产品上不特殊化**：pi connector 走与其他 Connector 完全相同的"目录 → 创建 Agent 实例 → 配置 → 启用"流程；"新增不同的 pi"即创建多个实例。Connector schema 只保留 `model`、`thinkingLevel`、`sessionDir` 等“怎样运行”的参数；Agent 追加运行指令、skills、prompt templates、Workspace context 开关统一属于 `AgentConfig.piResources`，pinned manager 与 Pi worker 共用同一模型和“提示词与资源”表单。`manager.prompt` 与 Pi Connector `config.systemPrompt` 已直接删除，不兼容双写。这里的运行指令只给当前 Agent 自己，不是 Manager 路由描述；cwd 由 Window/Delegation 快照传入；child session 不注册团队委托工具，递归默认关闭。Driver 能力诚实声明仍为 `operations: [run, continue, cancel]`、`interactionKinds: []`、`transport: "sdk"`。

> 实现状态（P2/P3-0，2026-08）：双宿主包已落地并真机验证。已落地：折叠 manifest（`readManifestFromDir`，pudding-extension.json 优先、package.json `puddingteams` 字段兜底，安装与 `extension validate` 同一入口）；共享核心 `extensions/shared/pwcp`（@puddingteams/pwcp：Driver SPI 类型 + spawnWorker + JsonlLineParser + observe 收集，server 侧 agent-runtime 对应文件均为 re-export）；两个真实包 `extensions/connectors/codex` 与 `claude-code`（pi/ 门面注册 codex_delegate/claude_delegate，driver/ 导 createDriver，core/ 事件归一），server 启动时 `installOrUpdateFromDir` 按仓库路径预置（不再是 builtin，改动即时生效）；`pi -e` 无头调用 codex_delegate/claude_delegate 成功，driver run/continue 会话记忆成功。P3-0 又增加宿主 `engines.puddingteams` semver 强制匹配、ESM cache busting 和事务式更新：候选模块先 import/校验，激活或落盘失败时恢复旧 runtime hooks 与持久化记录。仍 TODO：隔离 Extension Host（§10.3 第 2 级的进程隔离 + 权限 Broker）、npm/pi 社区发布渠道（发布前把 `workspace:*` 依赖改 semver）、puddingclaw/pi 两个内置 Connector 迁入 `extensions/connectors/`。作者指南：`docs/extensions/connector-extension.md`、`docs/extensions/connector-declarative-schema.md`。

>
> - `builtin`：内嵌 Connector（puddingclaw/pi），随 server 代码注册，无独立包目录；
> - `bundled`：第一方包（Codex/Claude Code 等），启动时按发行投影自愈 `sourcePath`，不把仓库绝对路径当跨版本事实源；
> - `user`：安装时复制到 `extensions/packages/<id>/<version>/`，走 staging → 校验 → 原子切换，Registry 保存 sha256 digest 清单，更新失败保留旧版本；
> - `local-link`：开发者模式专属，只记规范化绝对路径 + digest，不复制源码；关闭开发者模式立即停用，路径漂移标记 `drifted`，不静默回退到同名包。
>

## 10. Agent 配置与 Extension

### 10.0 控制面信息架构（2026-08-15）

前端将两个概念拆成独立一级入口：`/agents` 管理 Manager/Worker 角色与运行状态，`/extensions` 管理 Skills、MCP 与插件。Agent 配置页只保留该 Agent 自身的概览、模型与运行、提示词和模板；Skills 不再作为隐藏在 Manager/Worker 编辑页中的二级入口。当前服务端 Extension SPI 的真实目录仍是 Connector/Capability，故“插件”页展示两者；MCP 在没有可执行协议实现前只展示边界说明，不制造不可用的连接按钮。

```ts
interface ConnectorContribution {
  id: string;
  displayName: string;
  apiVersion: "1";
  defaultTransport: "spawn" | "http" | "rpc" | "acp" | "sdk";
  supportedTransports: Array<"spawn" | "http" | "rpc" | "acp" | "sdk">;
  configSchema?: Record<string, unknown>;
  secretSchema?: Array<{ key: string; label: string; required: boolean }>;
  supportedUpstreamVersions?: string;
  versionProbe?: Record<string, unknown>;
}

interface AgentConfig {
  id: string;
  name: string;
  /**
   * 通用展示说明；同时提供给 pi manager 做 roster 展示、搜索与委托路由。
   * 不是 Worker 自己的运行提示词，不替代 responsibility，也不证明能力或权限。
   */
  description: string;
  capabilities?: string[];
  connector: AgentConnectorBinding;
  capabilityExtensions: AgentCapabilityBinding[];
  enabled?: boolean;
  avatar?: string;
}

interface AgentConnectorBinding {
  extensionId: string;             // 安装的扩展包 id
  connectorId: string;             // ConnectorContribution.id
  transport: "spawn" | "http" | "rpc" | "acp" | "sdk"; // 该 Agent 实例的实际选择
  config: Record<string, unknown>;
  secretRefs?: Record<string, string>;
  versionPin?: string;
}

interface AgentCapabilityBinding {
  id: string;                      // binding 实例 id
  extensionId: string;             // 安装的扩展包 id
  capabilityId: string;            // CapabilityContribution.id
  enabled: boolean;
  config: Record<string, unknown>;
  secretRefs?: Record<string, string>;
  activation?: "always" | "searchable";
  versionPin?: string;
}

interface ExtensionManifestBase {
  id: string;
  publisher: string;
  displayName: string;
  version: string;
  source: "builtin" | "trusted" | "external";
  engines: { puddingteams: string };
  permissions?: ExtensionPermission[];
}

interface ConnectorExtensionManifest extends ExtensionManifestBase {
  kind: "connector";
  connector: ConnectorContribution;
}

interface CapabilityExtensionManifest extends ExtensionManifestBase {
  kind: "capability";
  capability: CapabilityContribution;
}

type PuddingTeamsExtensionManifest = ConnectorExtensionManifest | CapabilityExtensionManifest;
```

### 10.0 Agent 元数据、运行指令与提示词可见性

PuddingTeams 的核心提示词管理事实源是 `docs/2026-08-11-PuddingTeams核心提示词管理方案.md`。本节固定通用 Agent/Extension 边界：

- `description` 保留通用字段名，不改成 `routingSummary`；它既用于普通 UI 展示，也作为 manager 的简短路由摘要；
- `responsibility` 是给 manager 的结构化责任、停止与升级边界；`description + responsibility + capabilities + delegate tool` 共同构成 Manager 路由卡。平台在每个 manager 回合开始前，按 Window 候选集合把最新路由卡投影进 pi manager system prompt：Solo=全部启用 Worker，Group=全部已启用成员（2026-08-12 起 Direct 无 manager 回合，用户消息直派唯一 Worker，不再注入 roster/relay，见 §6 回写）；
- Pi Agent 的 `piResources.systemPrompt` 是**当前 Agent 自己读取的追加运行指令**，不是给 manager 选择该 Worker 的描述。产品文案称“Agent/Worker 运行指令”，不再称含糊的“Agent Profile”；
- Worker 运行指令不得进入 manager roster；Manager 路由卡也不作为 Worker 的 system prompt 重复注入；
- Window collaboration 只给窗口 manager。Solo 无协作段；Direct 无 manager 回合、无协作段（2026-08-12 起直派 worker）；Group 才允许用户编辑群聊协作提示词；
- `~/.pi/agent/AGENTS.md` 是 pi global context，显式 Workspace 的 `AGENTS.md` / `CLAUDE.md` 是项目 context。两者正文都不由 Agent 配置页编辑；Workspace 开关只控制后者；
- PuddingTeams 不覆盖 pi 内嵌默认 system prompt。Agent 运行指令与 Group collaboration 必须经 append 槽注入并保留 pi 原生 `APPEND_SYSTEM.md`，不得用 `systemPromptOverride` 把它们变成替代内嵌 base 的 `customPrompt`。

这是两条控制面，不因产品以 pi manager 为中心就合并：Pi manager 路由控制面回答“选谁、如何协作”，Pi Agent 运行控制面回答“被选中后如何执行”。本提示词装配建立在 Pi ResourceLoader 上；非 Pi Worker 由各自 Connector/Driver 管理私有运行提示，平台不得把 Pi 资源模型自动套给它们。

Connector Extension 和 Capability Extension 是两种独立包，禁止一个 manifest 同时贡献两类能力：

- Connector 的发布、升级和兼容性围绕上游 CLI/服务协议；
- Capability 的发布、升级和兼容性围绕 Pi 工具 Schema 与业务工作流；
- 二者混包会迫使“上游 CLI 参数变更”和“业务工具改版”同步升级，重新制造耦合；
- 若同一作者同时提供两类扩展，应发布两个独立 package，并用文档声明推荐组合。

它们的执行位置也不同：

- Connector Extension 安装到服务端 Connector Extension Host，向动态 DriverRegistry 注册 Driver；它不进入 Pi ResourceLoader，也不直接向模型注册工具；
- Capability Extension 通过具名 `extensionFactories` 装配到 Pi manager Session，向模型注册工具；它不注册 Driver，也不直接操作 CLI/HTTP/ACP；
- 二者的唯一业务连接点是 Runtime 创建的 `ScopedAgentInvoker`。

不要在通用配置中写 `runArgs`、`resumeArgs` 并让用户手工拼模板。命令映射是 Driver 代码的一部分；用户只配 executable、transport 和安全设置。

`probe()` 的结构化结果至少包含：

```ts
interface ProbeResult {
  extensionInstalled: boolean;
  extensionVersion?: string;
  detected: boolean;
  configured: boolean;
  authenticated: boolean | "unknown";
  enabled: boolean;
  compatibility: "supported" | "untested" | "incompatible" | "unknown";
  upstreamVersion?: string;
  version?: string;
  transport?: "spawn" | "http" | "rpc" | "acp" | "sdk";
  capabilities: DriverCapabilities;
  issues: Array<{ code: string; message: string; fixAction?: string }>;
}
```

智能体管理按产品角色分层展示：pinned `manager` 独立成组；Worker 再按所绑定 Connector 的目录来源标签分为「内置」与「第三方」。目录 `origin: "builtin"` 的 Connector（如 PuddingClaw、本地 pi）产生的所有 Worker 实例都属于内置 Worker；`bundled` / `user` / `local-link` Connector（包括随发行预置的 Codex、Claude Code），以及没有 Connector 标签的 legacy 命令接入，归入第三方 Worker。因此同一个 pi Connector 衍生出的多个 pi Worker 都稳定落在内置分组，新安装 Connector 的默认 `user` 来源也自然进入第三方。

前端“Agent 接入”页面按 Connector 目录项展示 `扩展未安装 / CLI 未检测 / 待认证 / 已配置但未启用 / 已启用 / 版本未经验证 / 不兼容`，并展示真实支持的四项操作。安装扩展、安装上游 CLI、登录、创建 Agent 和启用是不同动作，不合并成一个含糊按钮。

### 10.1 Agent 管理页

每个 Agent 的管理抽屉/详情页固定分为三项：

1. **基础接入**：当前 Connector Extension、Transport、服务/CLI 状态、认证、工作目录、权限策略、四操作能力和 probe 状态；
2. **Extensions**：只管理 Capability Extensions（零到多个），展示版本、来源、工具、激活方式和配置，并提供“添加 Extension”；
3. **运行状态**：Session/Run、待审批 Interaction、最近错误和审计事件。

Connector 只在“基础接入”中安装、选择或更换；“Extensions”页签中的“添加 Extension”只展示与当前 `connectorId` 兼容的 Capability。前端根据 manifest Schema 生成普通配置表单，根据 secret schema 单独写入 CredentialsStore 并只保存 `secretRefs`。保存前展示来源、权限、版本范围和将注册的工具。

Agent 总开关优先级高于所有 Capability Extension 开关：Agent 禁用时全部不可调用，但保留配置；Agent 再启用时恢复之前的选择。Capability 单独禁用只撤销该绑定提供的工具，不影响 Connector 和其他 Capability。Connector 不提供普通开关；更换或卸载属于基础接入变更，必须先处理 Session/Run 兼容性。

建议 API：

```text
GET    /api/extensions/catalog
POST   /api/extensions/install
POST   /api/extensions/:extensionId/update
DELETE /api/extensions/:extensionId
GET    /api/agents/:agentId/connector
PUT    /api/agents/:agentId/connector
GET    /api/agents/:agentId/extensions
POST   /api/agents/:agentId/extensions
PATCH  /api/agents/:agentId/extensions/:bindingId
DELETE /api/agents/:agentId/extensions/:bindingId
POST   /api/agents/:agentId/extensions/:bindingId/probe
```

Connector/Capability 写操作增加 Agent 的 `extensionRevision`。响应返回受影响的 manager Session 数量和 `active_now / reload_pending`，让界面如实显示“已撤权，运行时将在当前回合结束后刷新”。

`GET /api/extensions/catalog` 必须支持 `kind=connector|capability`，前端不得把两类结果混在同一个选择器中。

### 10.2 基础 Extension 与专属 Extension

每个已绑定 Connector 的 Agent 由平台生成基础 `agent-delegation` Pi Extension，只注册稳定委托能力，并从 Connector 暴露的 Driver capabilities 决定允许哪些操作。它是运行时投影，不是第二份安装包；用户通过 Agent 总开关整体禁用。

专属 Extension 才承载业务语义。例如：

- PuddingClaw 可绑定“智能问数”“产品配置分析”“知识库编译”；
- 代码类 Agent 可由用户绑定自建的“代码审查”“CI 修复”“发布流程”；
- Hermes/Pi 可绑定各自擅长的研究或自动化工具。

这些 Capability Extension 可以定义不同参数和提示规则，但执行远端/子 Agent 时必须调用 `ScopedAgentInvoker`。这样更新 Connector、Transport、CLI 版本或恢复机制时，不需要重写业务 Capability；同一个 Capability 也可以复用于多个兼容 Connector。

### 10.3 两级 Connector 实现模型

为了让用户自己接入简单 CLI，又不要求所有人编写高权限 Node 扩展，提供两级模型：

1. **声明式 Connector**：manifest 声明 executable 探测、四操作的参数构造、stdin framing、JSON/JSONL 解码和能力矩阵；实际 spawn、超时、取消、网络及 secret 注入全部由核心 Transport Broker 执行。适合常见一次性/Session CLI；
2. **代码型 Connector**：用于 ACP、RPC、WebSocket、复杂 HITL 和自定义恢复协议。代码运行在隔离 Connector Extension Host，通过受限 RPC 使用 Transport Broker，不直接进入 PuddingTeams server 进程。

> 实现状态（P2-c，2026-08）：第 1 级已落地——manifest 的 `connector.declarative` 声明由核心 `DeclarativeDriver`（`apps/server/src/agent-runtime/declarative-driver.ts`）直接执行（Transport Broker 的独立形态仍是 Phase 6）；`connector.declarative` 与顶层 `entry` 互斥，并且当前校验为唯一 `transport:"spawn"`，不能仅靠 manifest 虚标 HTTP。HTTP/RPC 等传输必须使用代码型 Driver。样例包：`extensions/connectors/echo`（纯 manifest，无 entry、无 pi 门面）。

用户接入流程：

```text
puddingteams extension init --type connector|capability
  -> 生成 manifest、声明式模板或代码 Host 模板、契约 fixture
puddingteams extension validate <path>
  -> 校验 schema、权限、版本探测和 PWCP 事件
puddingteams extension install <path|package>
  -> 展示权限并安装到本地扩展目录
Agent 管理页 -> 选择该 Connector -> 配置 -> probe -> 启用
```

> 实现状态（P2-d，2026-08）：`extension init` / `extension validate` 已落地（`apps/server/bin/puddingteams.mjs` 引导 tsx 跑 `src/cli/extension-cli.ts`）。init 支持 `--type connector [--declarative]` 与 `--type capability`，模板在 `extensions/shared/templates/`（connector 代码型双宿主骨架 / connector-declarative 纯 manifest 骨架 / capability 工具骨架）；validate 与安装流程共用 `readManifestFromDir`（`extensions.ts`）做 manifest 全量校验，再查 entry 存在性、代码型包导出和声明式包的 `{packageDir}` 引用文件。`extension install` 子命令留待后续。

Connector Extension Host 只能获得 manifest 声明并获用户批准的能力，例如特定 executable 的 spawn、特定域名网络访问、工作区访问和命名 secret reference。核心仍持有 CredentialsStore；能由 Transport Broker 代填的 secret 不把明文交给 Connector Host。

### 10.4 Extension 作者指南与模板

默认发行不靠大量预置扩展制造“开箱即用”的假象，而是把二开体验做成产品能力。至少交付以下文档和模板：

```text
docs/extensions/
├─ README.md                         # 两类 Extension 的选择与生命周期
├─ connector-extension.md            # Driver SPI、PWCP、Session/HITL/cancel
├─ connector-declarative-schema.md   # 简单 CLI 声明式接入
├─ connector-code-host.md            # ACP/RPC/HTTP 代码型接入与权限
├─ capability-extension.md           # Pi registerTool、参数、guidelines、结果投影
├─ security-and-permissions.md        # Extension Host、secretRefs、供应链风险
├─ compatibility-and-testing.md      # engine/upstream 版本、fixture、validate
└─ migration.md                      # API version 升级规则

extensions/examples/
├─ connector-declarative-echo/
├─ connector-acp-reference/
└─ capability-minimal-tool/
```

两套 `init` 模板必须生成不同入口和测试：

- Connector 模板生成 manifest、probe、capabilities、run/continue/respond/cancel mapper 和 PWCP fixture；
- Capability 模板生成 Pi Extension factory、`registerTool()`、配置 Schema、ScopedAgentInvoker mock 和工具快照测试；
- `validate` 必须拒绝 Connector manifest 中出现 Pi tool contribution，也拒绝 Capability manifest 请求 Driver/Transport contribution。

第一版预装数量固定为：四个第一方 Connector（PuddingClaw、本地 pi、Codex、Claude Code）与一个未绑定的 `minimal-tool` Capability 开发样例。样例进入 catalog 但不自动绑定，因此默认不进入任何 Agent 工具列表；它用于验证 package → catalog → binding → namespace tool 的真实闭环。

Pi Extension 的 TUI `renderCall/renderResult` 不会自动成为 PuddingTeams Web UI。第一版 Web 端继续渲染统一 Tool/Interaction 事件；若以后支持 Extension 自定义 Web 卡片，必须通过受控的 renderer registry 和声明式 payload，不能让 Extension 向浏览器注入任意组件代码。

运行时有两层门控：Extension 只把已启用且属于当前 Window 的 Agent 暴露给 manager；`AgentInvoker.delegate()` 再次检查启用状态和成员关系，防止旧 Session 的陈旧 tool schema 越权调用。

PuddingClaw 的 agent-specific tool 不应暴露 `model`：当前 CLI 明确拒绝 `model/analytics_model_id`，由 Backend 根据 question 自动路由。`team_task.model` 随 `team_task` 一并移除；任何 Driver 收到 `model` 字段都应拒绝并给出明确提示。

**configSchema 的前端渲染约定**（JSON Schema 子集 + 平台注解）：`type: string/number/boolean` 映射为输入框/数字框/勾选；`enum`（string 数组）渲染为下拉，非必填项带「不设置」清除项（回写时删 key）；`format: "model"` 是平台模型目录注解——渲染为可用模型下拉（数据源 `/api/models`，含自定义 provider 的模型），pi connector 的 `model` 字段使用此方式。字段可用 `"x-puddingteams-transports": ["spawn"]` 或 `["http"]` 声明仅对哪些 transport 显示，值必须是该 Connector `supportedTransports` 的子集；transport 本身不放进 provider config，而由 `AgentConnectorBinding.transport` 独立保存。若选项只能由上游 Agent 按当前账号/版本动态给出，Connector 可声明 `"x-puddingteams-options": "driver"`，并实现可选的 `AgentDriver.listConfigOptions(field, ctx)`；Web 经 `GET /api/agents/:name/connector/config-options/:field` 获取选项，宿主只负责注入该 binding 的 cwd/env/secrets 和转发结果，不猜测 provider 模型。

多 transport 的代码型 Connector 必须提供 `createDriver(config, transport)` 工厂；静态 `driver` 只允许单 transport。宿主在 probe、能力查询和委托入口核对实例 `DriverCapabilities.transport` 与 Worker binding，防止声明 HTTP 却静默落到 spawn。

Codex connector 的 `model` 使用 Driver 动态选项：每次打开已有 Agent 的配置页时，短暂启动 `codex app-server --stdio`，初始化后分页调用 `model/list`（`includeHidden: false`），读取当前 Codex 账号实际可选模型与默认标记，完成后立即关闭进程。这里只借用 app-server 做控制面发现；任务数据面仍是 `codex exec --json` / `codex exec resume --json` 的 spawn + JSONL，不切换为常驻 app-server。发现失败时前端降级为可手输文本框，避免配置页因 CLI 版本、登录状态或网络问题不可用；留空表示继续使用 Codex 默认模型。

Claude Code connector 同样声明 Driver 动态选项，但不能照搬 Codex 协议：Claude Code 只有交互式 `/model` picker 与 `--model <alias|name>`，没有稳定的无头 model-list 命令。Driver 因此读取用户配置目录（`CLAUDE_CONFIG_DIR` 或 `~/.claude/settings.json`）与当前 workspace 的 `.claude/settings.json` / `.claude/settings.local.json`，按 Claude Code 的合并语义收集 `availableModels`、`modelOverrides`、`model` 和 `env` 中的 `ANTHROPIC_MODEL` / `ANTHROPIC_DEFAULT_*_MODEL` / `ANTHROPIC_CUSTOM_MODEL_OPTION`；未声明 allowlist 时补充官方稳定别名 `best`、`sonnet`、`opus`、`haiku`、`sonnet[1m]`、`opus[1m]`、`opusplan`。若显式 allowlist 为空，下拉只保留“不设置”，从而继续使用账号层默认模型。最终账号套餐、企业策略和 provider 可用性仍由真正执行的 Claude Code 校验，PuddingTeams 不伪造账号级目录，也不直接读取 Claude OAuth 凭证。

### 10.6 模型与 Provider 控制面（借鉴 PuddingClaw，映射到 pi 原生分层）

平台的模型层就是 pi 的 `ModelRuntime`（builtin 目录 + `models.json` 自定义层 + `auth.json` 凭证层），不自建 registry。借鉴 PuddingClaw `ProviderRegistry` 的交互模式，落点：**模型目录层用 pi 原生文件（与 pi CLI 共享），凭证层用平台自有文件（与 pi CLI 解耦）**——provider key 只写入 `<PUDDINGTEAMS_HOME>/secrets/auth.json`（`configureSharedModelRuntime({ authPath })`，`pi-bridge/model-runtime.ts`），不读写 pi 全局 `~/.pi/agent/auth.json`；所有 `createAgentSession` 调用显式传入共享 `modelRuntime`，会话不再各自回退到 agentDir 的 auth.json。这样平台与独立使用的 pi 各管各的 key，互不出现。

- **自定义 Provider**：任意 OpenAI-compatible 端点（vLLM/Ollama/网关）经 `PUT/DELETE /api/providers/custom/:id` 写入 `<agentDir>/models.json`（原子写 + 0600），条目含 `name/baseUrl/api/models[]`；凭证不进 models.json，走平台凭证存储（`setProviderKey`/`removeProviderKey` 同一通道）。写操作后重建进程级共享 `ModelRuntime`（`pi-bridge/model-runtime.ts`），新会话即刻可见；
- **连通性测试与模型发现是两个显式动作**：`POST /api/providers/test`（带鉴权 `GET {baseUrl}/models` 探针，响应体丢弃，401/403 单独映射，返回 latency）与 `POST /api/providers/discover`（拉模型 id 清单，用户挑选后随 provider 登记）；两者都支持测未保存的新 key；
- **binding（按用途分派）**：manager 默认模型（§10.5）、会话级模型（composer 切换）、worker 实例模型（connector config `model`，`format: "model"` 下拉）三层各自独立，解析优先级：worker 实例 config > pi 默认；pi worker 改配置模型后对**驻留/恢复中的旧会话**也生效——`LocalPiDriver.reconcileModel` 在每次开会话（内存驻留命中或 JSONL 恢复）后对比 `session.model` 与配置解析结果，不一致即 `setModel` 纠偏（2026-08-19）；
- 明确不抄的部分：明文 credentials.json（用 pi 的 AuthStorage 机制但落平台路径）、遗留迁移/backfill（未上线无包袱）、硬编码 preset 清单（builtin 目录由 pi SDK 维护，自定义层开放增删）。

### 10.5 Pi Manager 作为可编辑的内置 Agent

manager 目前硬编码在 `PiSessionStore`（`apps/server/src/pi-bridge/session-store.ts`）：模型走运行时默认、solo 没有 prompt 入口、工具策略写死。目标是让它以 pinned 内置条目出现在智能体管理界面，与 worker 共用一套编辑 UI。

**可编辑项（按 pi SDK 能力映射）**：

| 配置 | SDK 支撑 | 生效时机 |
| --- | --- | --- |
| 默认模型 | `createAgentSession({ model })` | 新建会话 |
| Agent 运行指令与资源（append prompt / skills / templates / context） | `AgentConfig.piResources` + `DefaultResourceLoader` | manager/Pi worker 分别读取自己的配置；新建或重开会话生效，Group collaboration 独立组合 |
| 内置工具开关 | `tools` / `noTools` | 新建/重开会话 |
| 资源加载开关（skills/prompt templates/context files/extensions） | loader 的 `noSkills`/`noPromptTemplates`/`noContextFiles`/`noExtensions` | 新建/重开会话 |
| 库技能/模板选用名单 | `skillsOverride`/`promptsOverride` 按名单过滤（2026-08-10 落地） | 新建/重开会话 |
| thinking level | `session.setThinkingLevel()` | 运行时即改 |
| 压缩策略 | `session.compact(customInstructions)` / compaction settings | 运行时 |
| 名称、头像、描述 | 平台自存，复用 avatar 接口 | 即改 |

**实现要点**：

- `teams.json` 放一条 pinned 保留条目（`name: "manager"`，`invoke: { type: "pi" }`），`upsertAgent` 目前只收 `command`（`teams.ts:258`），需放开 `pi` 类型且只允许这一个保留名；不可删除、不可禁用；
- Direct 不接受用户可编辑的 Window Prompt（2026-08-12 起 direct 窗口无 manager 回合，固定 relay 已废弃）；Group 的 `window.prompt` 是仅给该群聊 manager 的协作提示词；Solo 不注入 Window collaboration；
- `PiSessionStore.create()/open()` 读该配置装配会话，改动只对新建/重开的会话生效（运行中会话用 `setModel`/`setThinkingLevel` 即时项除外）；
- 与 worker 的差异在 UI 上体现为表单分区：manager 没有 invoke command/probe/secrets，替换为上述 SDK 配置区。

**实现回写（2026-08-10 资源库与统一配置页，2026-08-15 UI 信息架构调整）**：技能/模板资源库直接使用 pi 全局目录（`<agentDir>/skills`、`/prompts`，与 pi CLI 共享），存储层 `pi-bridge/resource-library.ts` + 路由 `/api/resources/skills|templates`（含 `import`）；Agent 级选用是白名单语义——`PiResourceConfig.enabledSkills/enabledPrompts`（缺省不启用，取代已删除的 `loadGlobalSkills/loadGlobalPrompts`），装配经 `piResourceLoaderOptions()` 返回的 `skillsOverride/promptsOverride` 按 filePath 前缀过滤全局目录条目，Workspace 与额外挂载资源不受管；manager 与 worker 编辑入口合并为 `PUT /api/agents/:name/config` 一条合并更新接口（旧 `PATCH /manager`、`PUT /connector`、`PUT /pi-resources` 保留给非 pi 管理抽屉）。当前前端独立配置页 `/agents/config?name=` 保留概览/模型与运行/提示词/模板四分区，Skills 从 Agent 配置导航移出，统一在 `/extensions` 作为一级能力入口；插件页展示 Connector 与 Capability，MCP 在协议未落地前只展示边界说明。

**Goal 独立复核的宿主边界（2026-08-10）**：独立 reviewer 复用 Pi SDK 作为一次性推理宿主，但不是 Connector、Capability Extension、房间成员或 Delegation。PuddingTeams 在 manager 提交完成申请后创建全新的 `SessionManager.inMemory()` Session，关闭全部工具、Extension、Skill、模板与 context file，只注入冻结 Goal/完成条件和平台投影的只读证据；可选择与 manager 相同或不同 provider/model。Reviewer 只返回结构化 `CompletionReview`，无权调用 Driver SPI、委托 worker、修改 workspace 或写 `SessionWorkState`。它也不生成验收标准：`completionBoundary` 的每个非空行由用户在当前创建流程中冻结，Reviewer 返回的 criterion 必须逐行、原序、原文覆盖，只能补充 `status/explanation/evidenceRefs`；主观或授权条件证据不足时返回 `needs_human`。复核 verdict、revision 对账、活动委托/待决策门禁与最终 resolved 提交全部属于 PuddingTeams 控制面，因此不改变“pi 入口只用 ExtensionAPI、Connector 本体只用 Driver SPI、完整房间编排只属于 PuddingTeams”的边界。

Goal 与当前工作是会变化的控制面状态，manager 必须在每次 Pi 模型请求的 `context` 阶段读取并注入最新 revision，形成仅对本次请求可见的隐藏上下文消息；不能把它作为 `before_agent_start` 的粘性 system prompt 覆盖。后者不会覆盖由 custom message 触发的 DecisionRequest 回答和续接路径，会造成状态陈旧。房间 roster 等 Session 启动级上下文仍可留在 `before_agent_start`。

## 12. 验收标准

### 12.1 协议与状态机

- 新任务使用 `run`，续聊使用 `continue`，待授权只使用 `respond`；
- 同一 Session 同时最多一个 active/waiting Run；
- `respond` 后 `runHandle` 不变；
- 一次返回多个 request 时必须一次完整处理；
- 重复 response request_id 不重复执行授权；
- Interaction 过期明确显示，不自动创建新 Run。

### 12.2 PuddingClaw

- TTY `run` 仍可原地交互审批；
- 非 TTY/`--json` 返回结构化 `needs_input`；
- 新 `respond` 可从另一个 CLI 进程恢复同一 Run；
- continuation token 只出现在 `--json`/stdin 机器协议中，不进入 human output、stderr、普通日志和 Session 历史；
- `continue` 仍使用现有 `run --session`，历史 Session 不回归。

### 12.3 PuddingTeams

- `needs_input` 不再指导 manager 重跑 `team_task`；
- 页面刷新后审批卡仍能从存储恢复状态；
- 用户批准后不发送新的 child task，而是调用 Driver.respond；
- 完成结果写入原 direct/group manager Session，并自动触发后续汇总；
- 非当前窗口不能审批该 Interaction；
- Extension 无法读取凭证明文和 provider continuation token；
- 配置的 Extension 源中的 Connector 可被发现，但只有已安装、已配置且启用的 Agent 实例进入 roster；
- 禁用 Agent 后，旧 Session 即使仍持有旧 tool schema，也无法发起新委托；
- Driver 能力、安装、认证与启用状态在 API 和 UI 中一致；
- 每个 Agent 管理页可独立绑定多个 Capability Extension，并显示实际注册工具与信任来源；
- Agent/Capability 禁用后立即阻断新调用，空闲重建后不再出现在 manager 的 active tools；
- Extension 只能调用绑定 Agent 的 `ScopedAgentInvoker`，不能越权指定其他 Agent；
- Extension 配置变化不复制或重写 Pi Session JSONL 历史。

### 12.4 Connector Extension SDK

- PuddingClaw 第一方 Connector 完成完整回归；
- 声明式 Connector 样例可由用户复制后二开，并通过 validate/fixture 测试；
- ACP 代码型样例证明 stream/respond/cancel 可经 Extension Host 归一化；
- 未声明或未验证 `respond` 的 Connector 不展示可恢复审批能力；
- 任一 Connector 未安装、未认证、服务不可达时，`probe()` 返回可操作原因而不是运行时模糊失败；
- Connector 版本和真实上游版本可见，超出已验证范围时显示 `untested/incompatible`；
- 用户可用声明式 Connector 接入简单 CLI，并通过 validate 契约测试；
- 代码型 Connector 在隔离 Extension Host 中运行，未经授权不能 spawn、联网、读取工作区或使用 secret；
- 更新单个 Connector 不要求升级 PuddingTeams 核心，固定旧版本仍可回滚。

### 12.5 故障场景

- PuddingClaw Backend 重启：卡片转 expired，允许用户显式“重新执行”，不静默重跑；
- PuddingTeams Backend 重启：加密 provider state 可恢复；
- 浏览器断开：Child Run 仍 waiting_input；
- 用户拒绝：Run 收到 reject 并给出终态；
- worker stdout 非 JSON、重复终态、超大行、进程忽略 SIGTERM 都有测试。

## 15. 工作区与产物交接（Workspace & Handoff）

> 2026-08-06 补充。回答两个问题：agent 间共享文件怎么做（对比 AgentTeams 的 MinIO）；中间产物与交付物如何分界。

### 15.1 两个概念必须分开

| 概念 | 含义 | 归属 |
| --- | --- | --- |
| **workspace** | 房间可选绑定的本地项目，agent"对什么干活"（用户项目/数据本身） | 用户在房间指定；未选择时保持平台原有默认 cwd |
| **handoff 产物** | Run 结束时的交付物，需要在 agent 之间、agent 与用户之间交接 | 平台登记管理 |

中间过程产物（scratch、临时文件、agent 私有 workspace 内部状态）**各 agent 自理，平台不介入**。AgentTeams 用 MinIO 是因为多节点容器必须走网络存储；PuddingTeams 单机形态下等价物就是本地目录约定，第一阶段不引入对象存储。

### 15.2 workspace 绑定

> 实现状态（P3-1，2026-08-10）：Workspace/Session 正确性已按平台实体收口，不再把路径直接挂在 Window 上。

- Workspace 是可选增强，不是聊天前置条件。未选择时 `WindowConfig.workspaceId` 缺省，并把创建时的平台默认 cwd 持久化为 `WindowConfig.cwdSnapshot`；manager 与 worker 都使用该快照，保持原有聊天入口且不创建伪 Workspace；
- `WorkspaceRecord` 保存 `rootPath + canonicalPath + gitRoot?`，按 `realpath` 后的 canonical path 去重；只有仍解析为同一可读目录时才标记可用。路径失效不阻断服务启动，只阻断对应 Window 执行，绝不回退到默认 cwd；
- 本地产品可通过 server-side native picker 取得真实服务端目录：macOS 调系统 `choose folder`，Windows 调 `FolderBrowserDialog`，取消不改变 UI；Web 内嵌目录浏览与未来 Electron 主进程选择器复用同一“返回 canonical 服务端路径”协议；
- `WindowConfig.workspaceId?` 只引用显式项目身份；direct Window 去重键为 `(worker, workspaceId ?? cwdSnapshot)`，无项目单聊在默认 cwd 变化后也不会复用旧目录的 Session；
- `DelegationRecord.workspaceId? + cwdSnapshot` 在委托创建时冻结。即使没有 Workspace，也必须冻结默认 cwd；run/continue/respond/cancel/artifact 全部读取快照，不重读 Window 当前值；
- 委托创建、respond/cancel admission 与原地切换共享 Window 生命周期门；Run 记录落盘后才释放 admission，切换可枚举并取消所有已接纳任务（包括 solo 路由到 direct 的任务）；
- manager 的 `SessionManager`、`ResourceLoader`、内置工具与 worker Driver 使用同一 workspace cwd；
- manager Session 可以共享同一个 `sessionDir`，但目录枚举与重启恢复必须使用不带 cwd 过滤的全量发现，再由 Window 保存的 Session ID 与 `cwdSnapshot` 确定归属；不能用某个 Workspace cwd 过滤共享目录。Session 存活判断还必须包含当前进程内已打开但尚未首次持久化的实例，避免 fresh solo Session 被误建替换；
- worker binding 同时记录 `workspaceId? + cwdSnapshot + agentRevision + sessionHandle`，项目/cwd 或 Agent 配置修订变化后不得续接旧 Session；
- Runtime 自持每个 active Run 的 AbortController；取消先封存 `cancelled` 终态、触发真实子进程终止并等待有界 settle，迟到 completed 不得复活状态或登记 artifact；
- 上下文切换支持显式 Workspace 与“不绑定项目”双向切换；默认创建成员相同的新 Window，显式原地切换先取消 active/waiting Delegation，再清空 worker binding 并以新 cwd 重建 manager Session；
- workspace 是项目上下文和默认操作范围，不是平台承诺的通用文件权限沙箱。Codex sandbox、Claude permission mode、Agent 自身权限与 OS 隔离才负责强制执行；
- artifact 登记和下载以 Delegation `cwdSnapshot` 做 realpath containment，项目外绝对路径与越界 symlink 在登记时拒绝；下载使用 `O_NOFOLLOW` 文件描述符并以 dev/ino 复核，校验后不再按可变路径重开文件。

> 实现状态（2026-08-11，Workspace 信任门）：`WorkspaceRecord` 增加 `WorkspaceTrust{state: pending|trusted|denied, decidedAt, policyVersion: 1, canonicalPathAtDecision, approvedResources?}`（`approvedResources` 缺省为 context/skills/prompts 三类全批准）。managed Workspace 默认 trusted，外部项目初始 pending，`realpath` 与决定时记录不一致自动退回 pending；信任决定经 `PUT /api/workspaces/:id/trust` 保存，`GET /api/workspaces/:id` 只返回资源类型与数量摘要、未批准前不返回正文。Workspace context/skills/prompts 进入装配候选的判定收敛为单点——`显式 workspaceId && trust = trusted && approvedResources 含对应 kind`，再与 Agent 自身资源开关相与；Preview、会话创建/重开与 Delegation 统一消费该判定。撤销信任将相关活跃 Session 标记 `runtimeDirty`。无 `workspaceId` 时 cwd 快照固定为 `PUDDINGTEAMS_HOME/workspaces/unscoped` 并强制关闭全部 Workspace 资源发现。详见 `docs/2026-08-11-用户数据目录与Workspace上下文迁移方案.md` §6.3/§7。

### 15.3 目录布局

```text
<workspace>/
├─ …（用户项目本身，agent 直接读写）
└─ .pudding/
   └─ handoff/<delegationId>/     # 本次 Run 的交付物
```

### 15.4 handoff 的两种来源，一个登记接口

"怎么知道交付物是什么"是 Driver/Connector 的事；"交付物的登记与交接"是 Runtime 的事。两种来源对 Runtime 无差别：

| 模式 | 适用 | 机制 |
| --- | --- | --- |
| **push** | PuddingClaw（自家 CLI） | `puddingclaw agent run --export <dir>`：执行完把交付物导出到指定目录，result 中声明清单 |
| **observe** | Codex / Claude / Pi（改不了的第三方） | Driver 从事件流机械收集（`apply_patch` / `Write` / `Edit` 事件触碰的文件集），git 仓库用 diff、非 git 用目录快照 diff 兜底 |

关键原则：**不依赖模型自觉声明，也不扫描目录猜测**。observe 模式下模型在最终回复里的清单只作为命名/kind 元数据补充，事实源是事件流和文件系统。coding agent 的交付物往往就是 workspace 里的改动本身，git diff 天然表达；`.pudding/handoff/` 只装报告、导出物这类"工作区之外的产物"。

### 15.4.1 为什么 PuddingClaw 不向 observe 对齐

push/observe 的分工不是"自家 CLI 没改"，而是两类 agent 的本质差异：

| | 修改型（Codex/Claude/Pi） | 生成型（PuddingClaw） |
| --- | --- | --- |
| 输入 | workspace 里的项目文件 | 数据库/数据源 API，不读文件系统 |
| 输出 | 对 workspace 的就地修改（有 before/after） | 报告、导出数据（生成物，无 before） |
| 文件产生地 | 平台可见的 cwd | backend 管理的 workspace（可能远程） |

git/fs diff 观察对 PuddingClaw 不成立：房间目录里没有它要写的东西；文件在 backend 侧（远程时另一台机器），CLI 侧不可见；生成物没有 diff 语义，untracked 文件堆分不清交付物与内部 scratch。即使把 `PUDDINGCLAW_PROJECTS_ROOT` 指向房间目录，落入 diff 视野的也是 session 状态等内部文件，恰恰制造"扫描目录猜测"。

统一发生在**语义层**（四操作、PWCP 事件、artifacts 清单），机制层保留差异正是 Driver 存在的意义。流式落地（Phase 7）后，事件流观察对 PuddingClaw 同样成立，进度体验与 coding agent 一致；只有 fs diff 这条轨迹不适用它。

### 15.5 软引导入口（提升质量，不作事实源）

1. **`AGENTS.md` / `CLAUDE.md`**：平台在绑定 workspace 时写入 handoff 约定（报告类交付物写入 `.pudding/handoff/`，最终回复列出清单）——Codex、Claude、Pi 都自动读取；
2. **任务 prompt 包装**：Capability Extension 派活时在任务文本中附带交付约定；
3. **Pi 子 agent**：`createAgentSession` 时进 system prompt 片段。

### 15.6 产物数据流

```text
Run 结束
  → Driver 汇总 artifacts 清单（push / observe）
  → CompletedResult.artifacts（§4.3）
  → Runtime artifacts store 登记（名称/路径/kind/大小/产出者/delegationId）
  → artifact.created 事件 → UI 产物面板（下载/预览）
  → 接力派活：manager 在任务文本中引用路径（传路径不传内容）
```

超限额的大结果沿用旧方案结论：转 artifact 引用，不进 tool result 正文。产物面板列为后续阶段（原平台设计文档阶段四备忘），第一阶段只要求登记和 API 可查。

### 15.7 PuddingClaw CLI 改造补充

在 §11 Phase 2 清单之外增加：`run`/`respond` 支持 `--export <dir>`，执行终态时把交付物（报告、导出数据）复制到该目录并在 result JSON 中声明 `artifacts`。CLI 不知道平台目录结构，导出路径由 Driver 按 §15.3 约定生成并传入。

---

这套方案的最小正确闭环是：**PuddingTeams 先能区分 Session 续聊和 Run 恢复，PuddingClaw CLI 再补公开 `respond`，最后由 InteractionBroker 把浏览器审批准确送回原 Run。** Extension、JSONL 和更多 Agent 都建立在这个闭环之上，而不是反过来。
