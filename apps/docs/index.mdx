---
title: PuddingTeams 是什么
description: 一个以持续会话为中心、可连接不同 Agent 的本地协作 Harness。
---

<Status tone="preview">PREVIEW</Status>

PuddingTeams 解决的不是“同时启动几个 Agent”，而是一个更基础的问题：**当工作跨越多个执行者、多个回合和人的判断时，怎样让上下文、责任、进度和交付仍然连续。**

它以 pi 作为 Manager Harness，通过 Connector 接入 Pi、PuddingClaw、Codex、Claude Code 等 Agent，并把协作状态保存在本机。Agent 可以更换，知识与项目仍归用户；执行可以中断，Goal、证据和交付不会因此消失。

<Principle title="第一性原理：协作必须有可恢复的共同状态">
一次模型调用只能生成一次响应。工程协作还需要持续身份、工作目录、会话续接、等待输入、验收边界和可追溯交付。PuddingTeams 把这些状态放在 Agent 之外，才可能让不同 Agent 在同一工作上可靠接力。
</Principle>

## 六个核心对象

| 对象 | 解决的问题 | 事实来源 |
| --- | --- | --- |
| Window | 谁在同一个对话关系里 | solo、单聊或群聊配置 |
| Session | 哪一段对话需要连续 | pi Session JSONL 与 Worker handle |
| Delegation | 谁执行了哪一次委托 | 归一化委托记录与执行时间线 |
| Goal | 什么结果才算完成 | Session Goal、完成边界与复核记录 |
| Workspace | 工作在哪个目录发生 | 显式绑定、路径快照与信任状态 |
| Artifact | 哪个产物可以被引用和验收 | 登记记录、哈希与冻结快照 |

## 产品边界

PuddingTeams 自己负责：

- solo、单聊与群聊的关系和消息流；
- Manager 路由、WorkPlan、Decision 与完成复核；
- Session 续接、委托幂等、恢复和取消；
- Workspace 信任、附件、Artifact 与本地数据边界；
- Extension Registry、权限声明和 Connector 生命周期。

具体 Agent 的私有协议由 Connector 负责：

- 如何启动、续接、回答交互与取消；
- 如何把上游事件归一化为进度、结果和 Artifact；
- 使用 spawn、SDK 或未来的 HTTP 等 Transport；
- 上游 CLI、账号、模型与鉴权要求。
