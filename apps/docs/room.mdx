<Status>1.0 STABLE</Status>

PuddingTeams 把侧栏里的持续关系称为 Window。协作模式不由界面风格决定，而由一个更基本的问题决定：**用户的这条消息应该由谁先理解，是否需要路由，以及结果应回到哪段持续会话。**

| 模式 | 成员 | 首个接收者 | 适合 |
| --- | --- | --- | --- |
| solo | 用户 + pi Manager | Manager | 自由讨论、跨 Agent 路由、自动组队 |
| 单聊 direct | 用户 + 1 个 Worker | 唯一 Worker | 与同一 Agent 持续工作，不需要二次路由 |
| 群聊 group | 用户 + Manager + 2 个以上 Worker | Manager | 多角色拆分、并行、接力和统一验收 |

## Solo

Solo 是全局置顶单例，不可删除。Manager 每轮看到全部已启用 Worker 的最新路由卡，包括描述、责任边界、能力事实和真实可用的委托工具。

当任务适合一个 Worker 时，Manager 发起 Delegation，并把派活和结果镜像到该 Worker 的单聊窗口。没有对应单聊时平台自动创建；这让后台委托仍然拥有一个可继续对话的归属窗口。

当任务需要两个以上 Worker，或存在明显的跨 Worker 接力时，Manager 可以创建群聊并把整体任务交给群聊继续执行，而不是在 solo 里充当人工复制粘贴中间结果的中转站。

Solo 适合“我知道目标，但不想先决定用谁”。如果你已经知道只需要某个 Worker，直接打开单聊更短。

## 单聊

单聊是**纯 Worker 通道**。用户消息由服务端直接派给窗口唯一 Worker，不经过 Manager relay，也不再做 Agent 选择。

这带来几条明确边界：

- 同一个 Worker 在同一 Workspace 只有一个单聊 Window；重复发起会打开该项目已有窗口；
- Worker 的 `sessionHandle` 由 Window binding 保存，用于后续 `continue`；
- 单聊不提供群聊协作提示词；Worker 行为由自己的运行指令或上游配置决定；
- HITL 交互、结果和执行过程直接回到当前单聊；
- 单聊也可以设置 Session Goal，但没有 Manager WorkPlan，不伪造一层不存在的 Manager Todo。

Workspace 是单聊 Window 身份的一部分。切换项目会打开该 Worker 在目标项目的已有窗口或创建新窗口，不会覆盖当前窗口。Workspace、cwd 快照或 Agent 修订不一致时，Runtime 拒绝直接续接旧 binding。

## 群聊

群聊包含 Manager 和两个以上 Worker。用户仍对一个对话窗口发言，由 Manager 在当前成员集合内拆分、并行、接力、裁决和汇总。

群聊可以配置一段只给 Manager 的“群聊协作提示词”，用于说明分工方式、交接规则或汇总格式。它不会传给 Worker，也不能替代每个 Worker 自己的运行指令。

Manager 可以在执行中邀请新的已启用 Worker。删除成员、删除房间等会影响运行中任务的动作仍由用户显式操作。

## Window 与 Session 不是同一个对象

```text
Window：一段长期关系
  ├─ 成员与类型
  ├─ 当前 Workspace 与协作配置
  ├─ Solo 离开项目的 parked contexts
  ├─ Worker bindings
  └─ 多个 Session

Session：Window 中的一段连贯对话
  ├─ 消息历史
  ├─ 可选的活动 Goal
  └─ 相关 Delegation / Decision / Artifact
```

切换 Session 不会创建新的侧栏关系；删除 Session 也不等于删除 Window。每个激活的 Window context 至少保留一个 Session，且有一个 active Session。Solo 切项目只切换激活 context：离开的项目历史被停放，切回时恢复；Direct/Group 则打开项目对应 Window。

## 一次委托怎样流动

```text
用户消息
  → solo/group Manager 或 direct Worker
  → Agent Runtime 创建 Delegation
  → Driver run / continue
  → progress / input_required / completed / failed
  → 当前 Window 消息流 + 执行 Inspector
```

对 solo 委托，执行归属和展示归属可以不同：任务在 Worker 的 direct Window 绑定下续接，但 solo Session 仍保留委托卡和跳转入口。平台用明确的 Delegation ID 连接两边，不按“窗口看起来像谁”猜测执行事实。

## 怎样选择

- 任务对象未知或可能需要多 Agent：用 solo。
- 已经明确某个 Agent，想保持连续上下文：用单聊。
- 需要多个专业角色共享目标、依赖和验收：用群聊。
- 只是临时并发几个无关联请求：分别使用单聊，不必人为制造群聊。
